## §1 crate 落位决策（2026-09-21，✅ 完成）

**结论：workspace member，crate 名 `ash_renderer`，位于仓库根 `F:\okzkx\bevy\ash_renderer\`。**

### 决策依据（对照"独立仓库 + path 依赖"方案）

| 维度 | workspace member（选定） | 独立仓库 + path 依赖 |
|---|---|---|
| path 依赖 | `bevy = { path = ".." }`，同 bevy_city 模式，零成本 | 同样可行，但要维护两层 Cargo.toml |
| 锁文件/target | 共享根 Cargo.lock 与 target 目录，增量编译直接复用 bevy 缓存 | 独立 lock，首次全量编译 |
| profile | 自动继承根 [profile] 调优（members 可覆写 profile 属 workspace 根权限，子 crate 反而拿不到） | 无继承 |
| 上游合并成本 | 根 Cargo.toml members +2 行（1 行注释 + 1 行路径），跟随 release tag 升级时若冲突手工保住即可 | 零冲突 |
| 撤退成本 | 删目录 + 删 members 行，回到纯上游 | 天然隔离 |

workspace member 的"动上游文件"代价是一行级、可预期的，换取增量编译复用与单一锁文件——学习仓库场景下收益明显更大，选定。**crate 名可随时改**（改 `Cargo.toml` name + members 行 + 目录名三处）。

### 连带禁项实测：PbrPlugin 不可保留（0.19.1 审计"最后未验证点"验证结果）

运行即 panic（`bevy_asset/src/server/info.rs:865`）：`Cannot allocate an Asset Handle of type 'bevy_shader::shader::Shader' because the asset type has not been initialized`。

- **根源链**：`PbrPlugin::build` 无条件 `load_shader_library!`（`bevy_pbr/src/lib.rs:183-192`，0.20 起为 WESL）→ 分配 `Handle<Shader>` 要求 `Assets<Shader>` 已注册 → 而注册在 `RenderPlugin::build`（`bevy_render/src/lib.rs:385`）→ RenderPlugin 已禁 → 无人注册 → 炸；
- **为何不能预注册绕过**：`init_asset` 第一步就 `world().resource::<AssetServer>()`（`bevy_asset/src/lib.rs:658-662`），AssetServer 由组内 AssetPlugin 创建——自有插件插不进 DefaultPlugins 组内顺序，此路不通；
- **代价与 step3 备选**：PbrPlugin 同时是 `Assets<StandardMaterial>` 容器与 `GltfExtensionHandlerPbr`（glTF 材质接入缝）的注册者——禁掉后 step3 取材质需**手动接线**：`init_asset::<StandardMaterial>()` + 自行注册材质扩展 handler（或放弃 StandardMaterial 容器自研材质容器，待 step3 实测定）；
- **caller 清单佐证**：全仓 `load_shader_library!` 调用者 = core_pipeline/pbr/post_process/render/solari/sprite_render/ui_render 七 crate——其中只有 PbrPlugin 不在禁用名单，其余全被 8 件名单连带覆盖，无需再禁。

### 0.20-dev 链路复核（侦察篇结论全部仍然成立）

- `RawHandleWrapper` 仍是 Component + `unsafe impl Send/Sync`（bevy_window/src/raw_handle.rs），**`get_window_handle()` 是安全方法**（:87），返回 `RawWindowHandle::Win32{hwnd: NonZeroIsize, hinstance: Option<NonZeroIsize>}`；

- rwh 0.6 未被 bevy 再出口 → ash_renderer 需直依（Cargo.toml 已加，带注释）。

### ash 0.38.0 关键事实（Cargo registry 源码逐条核实）

- **模块已重构**：loader 类型在 `ash::khr::{surface, win32_surface, swapchain}` 与 `ash::ext::debug_utils`（如 `khr::surface::Instance`），`ash::extensions/` 下只是扩展方法 impl；**`NAME` 常量在模块级**（`ash::khr::surface::NAME`），不在 loader 结构上；
- **全套无 `impl Drop`**（extensions_generated.rs 零命中）——销毁全部手动，`Drop for VulkanContext` 按 `device_wait_idle → Swapchain ← Surface ← Messenger ← Device ← Instance` 反序；
- 默认 feature `loaded`（libloading）→ `unsafe { Entry::load() }`；**Entry 字段必须持在结构体里**：fn 指针在 new 时已拷走，但字段掉了会把 vulkan-1.dll 卸载（`#[expect(dead_code)]` 标注）；
- Win32 建面字段名是 `.hwnd()`（非 `.hwindow`）；
- Win32SurfaceCreateInfo 的 hinstance 用 `GetModuleHandleW(None)` 兜底（手写 `unsafe extern "system"` 声明，零额外依赖）；
- edition 2024：extern 块与 extern fn 必须 `unsafe extern`；safe fn 里的 unsafe 调用要显式 unsafe 块（编译器逐个拦）。

### 实现形态

- `ash_renderer/src/vulkan.rs`（lib）：`VulkanContext::new(&RawHandleWrapper)` 一条龙——Entry → Instance（API 1.3 + 验证层按可用性 + debug messenger WARNING/ERROR）→ Win32 Surface → PhysicalDevice（graphics+present 同族、离散卡优先）→ Device（单通用队列 + VK_KHR_swapchain，features 空）→ Swapchain（FIFO、BGRA8_UNORM 优先、min+1 张、COLOR_ATTACHMENT）；
- main.rs：Startup 系统 `init_vulkan`——`Query<&RawHandleWrapper, With<PrimaryWindow>>` + `NonSendMarker` 钉主线程 + `commands.insert_resource`；时序假设（首窗先于 Startup）被打破时 panic 显式失败；
- 队列族：graphics 与 present 同族（桌面 GPU 普适，异族需求出现时再拆）。

## §4 帧循环：acquire → 清屏 → present + resize 重建 + 退出拆除（2026-09-21，✅ 完成）

### 退出顺序设计（README 待决问题④，0.20.0-dev 源码定案）

侦察篇 §5 的风险备忘"bevy runner `exiting` 回调清场前 Vulkan 对象必须先死"，0.20 实情比预想的更险：

- **`exiting` 回调先杀窗后清场**（state.rs:521-527）：`WINIT_WINDOWS.windows.clear()`（hwnd 毁）在前，`world.clear_all()`（drop 全部 Resource）在后——若等清场才 Drop `Context`，surface 是在宿主 hwnd 死后销毁的，顺序违法；
- 更早在**最终一帧的 Last 调度内**就有退出链：`exit_on_primary_closed`（`ExitSystems` set，bevy_window，写 `AppExit`）→ `OnAppExitSystems` set（bevy_app："AppExit 已发、退出前的系统"）→ `despawn_windows`（bevy_winit，`.after(ExitSystems).after(OnAppExitSystems)`，把 winit 窗口挪进系统 Local 并销毁）；
- **官方钩子先例**：bevy_time 的 `silence_delayed_command_queues_on_exit` = `Last → in_set(OnAppExitSystems).run_if(AppExit 非空)`——照抄该形态。

**选定方案**：`teardown_vulkan`（exclusive 系统，`&mut World`）挂 `Last → in_set(OnAppExitSystems).run_if(!messages.is_empty())`，同步按创建的相反顺序 `remove_resource`：FramePool（帧级）→ Swapchain（resize 级）→ Context（进程级，销毁 Surface/Device/Instance）。**不能依赖 `world.clear_all()` 兜底**：清场顺序对 Resource 是任意的，跨资源反序（swapchain 必须死于 Device 之前）只有手动保证。

### 生命周期拆分（施工③评审时定下的演进，本次落地）

原 `VulkanContext`（施工④更名 `vulkan::Context`，见《Context与Swapchain分家：按生命周期拆分.md》）按生命周期四层拆成四模块，各自 `Drop` 独立、互不纠缠：

| 模块 | 生命周期 | 内容 |
|---|---|---|
| `vulkan.rs` `Context` | 进程级 | Entry/Instance/验证层 messenger/Surface/PhysicalDevice/Device/Queue |
| `swapchain.rs` `Swapchain` | resize 级 | swapchain + images + **views** + format/extent；`rebuild()` 整体重建 |
| `frames.rs` `FramePool` | 帧级 | 命令池 + 2 组（命令缓冲/双信号量/fence），跨重建轮转复用 |
| `error.rs` `VulkanError` | — | 类型化错误：`SwapchainOutOfDate` / `Vk(vk::Result)` / `Init(String)` |

拆分红利：resize 重建只动 `Swapchain`，同步对象原地不动；`OUT_OF_DATE` 能 `match` 分流（"重建重试"与真失败语义分开）；`Context::new` 的错误也从 `String` 升级为 `VulkanError`。

### 帧循环实现要点

- **清屏走 Vulkan 1.3 动态渲染**（`vkCmdBeginRendering`）：无 RenderPass/Framebuffer/管线，`loadOp=CLEAR` 即清屏；设备创建时须 `push_next` `PhysicalDeviceVulkan13Features.dynamic_rendering(true)`（1.3 feature，不默认开）。选它而非 `vkCmdClearColorImage`（省 feature 链但要求 TRANSFER_DST usage + GENERAL 布局绕路）：image view 本来就是 step3 管线路径的必经件，一步到位；
- **一 update = 一帧**：winit `about_to_wait → app.update()` 就是帧心跳（侦察篇 §4），Update 系统 `draw_frame` = 等帧槽位 fence → acquire → 录制提交 → present，错误按 `VulkanError` 分流；
- **resize 桥**：`MessageReader<WindowResized>`（winit 回调暂存 → PreUpdate 入队）→ `Swapchain::rebuild`；rebuild 幂等（尺寸没变不重建）、最小化（extent=0）跳过——建 0 尺寸 swapchain 非法；acquire/present 的 SUBOPTIMAL 折叠成 `Ok(次优标记)`，OUT_OF_DATE 折叠成 `Err(SwapchainOutOfDate)`，present 后任一标记置位即重建；
- **两帧在飞**：`MAX_FRAMES_IN_FLIGHT=2`，每组 = 命令缓冲 + image_available（acquire 侧）+ render_finished（present 侧）+ in_flight fence（CPU 闸门）；同组两次使用至少隔 2 帧且 fence 保证上一轮已完成，这是与"每 image 一份同步对象"不同且更省的合法简化；
- 清屏颜色随 `Time` 缓慢呼吸（深蓝↔青蓝），肉眼可证帧在动，替代施工②的帧心跳日志（`frame_heartbeat` 已删）。

### 坑与解法

1. **`ERROR_NATIVE_WINDOW_IN_USE_KHR`（首个真 Vulkan bug，实测抓到）**：`rebuild` 初版写 `*self = Self::new(ctx)?`——RHS 先求值 = **先建新 swapchain 后拆旧**，而 Win32 WSI 限制同一 hwnd 同时只能挂一个 swapchain，创建即报 `ERROR_NATIVE_WINDOW_IN_USE_KHR` 并无限重试刷屏。解法：显式 `self.destroy()`（views + swapchain 反序销毁、句柄清 null 幂等）后 `*self = Self::new(ctx)?`；顺带补上"建好 swapchain 后取 images 失败也要就地销毁"的洞（否则坏 swapchain 一直占着 hwnd）；
2. ash 0.38 结构名再踩一坑：`vkCmdBeginRendering` 的 info 结构叫 `vk::RenderingInfo`（直觉猜的 `CommandBufferRenderingInfo` 不存在）；`Time::elapsed_seconds_f64` 在 0.20 改名 `elapsed_secs_f64`；
3. `Frame` 字段最初私有导致 main.rs 编不过——同步对象的使用权就在编排系统手上，直接 pub。
