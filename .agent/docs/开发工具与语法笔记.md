## 2. `#[repr(C, align(8))]`——内存布局钉子

> 2026-09-14。在 `Entity` 源码上遇到（`crates/bevy_ecs/src/entity/mod.rs:423`，注释："Alignment repr necessary to allow LLVM to better output optimized codegen for `to_bits`, `PartialEq` and `Ord`"）。

**先纠正直觉：C 布局不"更好"，是"可预测"。** Rust 默认布局（`repr(Rust)`）故意什么都不承诺，把自由让给编译器：

1. **字段重排省 padding**：`struct S { a: u8, b: u32, c: u8 }`——C 布局按声明序 = 12 字节（`a,填3,b,c,填3`）；Rust 默认可重排成 `b,a,c` = 8 字节。ECS 海量小组件，这笔乘以百万实体就是缓存钱；
2. **Niche 优化**：`Option<&T>` 和裸指针一样大（null 当 None）、`Option<NonZeroU32>` 仍 4 字节；
3. **布局随编译器版本自由演进**：标准库敢持续改内部布局而不破坏生态，因为没人被允许依赖它。

**`repr(C)` 是一份合同**：字段严格按声明序 + 平台 C 对齐/填充规则，偏移跨编译器稳定、可与 C 互操作。付的代价 = 可能变大 + 放弃重排/niche 优化。什么时候买：FFI、**按位重解释**（`transmute`/`to_bits`/`bytemuck`）、memcpy 到 GPU/文件、外部工具按固定偏移读。

**Entity 案例复盘**（宏的两半各有用途）：

- `repr(C)`：字段顺序钉死为 `index` 在前 → little-endian 下 index 落 u64 **低 32 位** → `to_bits()` 只写 `index | (generation << 32)`（`entity/mod.rs:566`），结构体与 u64 位等价，`PartialEq` 直接走单条 64 位比较（源码注释"cmp uses to_bits"是为 LLVM codegen）。"Do not reorder the fields here"就是合同条款；
- `align(8)`：两个 u32 自然对齐是 4，不抬到 8 则数组里相邻 Entity 可能**跨 8 字节边界**——单条 64 位 load/cmp 做不了，原子操作（`AtomicU64`）更直接要求 8 字节对齐。对 Entity 这份合同**免费**（u32+u32 本就无 padding）——不是所有 struct 都这么幸运。

**图形程序员类比**：`repr(Rust)` ≈ 引擎内部布局（怎么省怎么排）；`repr(C)` ≈ 顶点属性/std430 布局——memcpy 给 GPU 前必须钉死的"格式"。

**repr 家族速查**：`repr(C)`（C 排序）/ `repr(transparent)`（单字段新类型零封装）/ `repr(packed)`（去 padding，取引用 UB）/ `repr(align(n))`（抬对齐，对应 C11 `alignas`）/ `repr(u8)`（枚举判别值定宽）。

**语言设计通则**：默认给性能自由，保证按需 opt-in——与 `unsafe`、`Send/Sync` 是同一个哲学：保证的代价落在需要它的人头上。

## 3. 从 Bevy `add_systems` 学：泛型接受任意函数的七件套

> 2026-09-16。在 `IntoScheduleConfigs` 源码上遇到（`crates/bevy_ecs/src/schedule/config.rs:314`）。Bevy 侧完整链路（ScheduleLabel/System/DSL/建图）在《1-熟悉Bevy结构/System与调度DSL.md》，本文只记**可迁移的语言套路**。

"一个参数能传任何函数、还能从函数**参数列表**里榨出类型信息"——没有宏魔法之外的黑科技，是七个普通特性叠加：

1. **函数是匿名 ZST 类型**：每个 `fn` 定义都有独一无二的类型，传给泛型形参（`impl Trait` = 泛型语法糖）时**逐函数单态化**——每处调用点各得一份专用代码，零运行时开销。别拿 `&dyn Fn` 顶替，那是虚表分发；
2. **关联类型榨签名**：`trait SystemParamFunction<Marker> { type Param: SystemParam; ... }`，宏实现里用高阶约束 `for<'a> &'a mut F: FnMut(A, B) -> Out` 匹配调用形态，编译器唯一确定 `type Param = (A, B)`——**参数列表本身变成一个类型**，后续泛型代码随便引用。同款：axum handler 的 `FromRequestParts` 参数自动提取；
3. **Marker 幻影参数解 overlapping impls**：给"所有函数"和"所有元组"两族写同一 trait 的 impl，rustc 会认定可能重叠（即使实际不可能）——每个 impl 家族带不同幻影标记（Bevy 的 `IsFunctionSystem`、`ScheduleConfigTupleMarker`），既是分辨器也是报错定位锚。自己写宽泛 trait 遇到 conflicting implementations，先想 marker；
4. **变长参数 = `all_tuples!` 宏生成 1~N 元 tuple impls**：Rust 没有变长泛型，宏枚举元数是社区标准解（Bevy 到 20 元，函数参数 impl 到 16 元）；
5. **参数即能力声明 → 编译期推导调度**：签名 `Res`=读 / `ResMut`=写 / `Commands`=延迟，框架汇总成访问集自动排并行、插同步点。**对 bindless 渲染器直接可迁移**：`Read<Texture>`/`Write<Texture>` 参数类型收集 pass 读写集，自动推导 pipeline barrier（写后读=布局转换）——正是手写 Vulkan barrier 最易漏同步的根治手段；
6. **`#[diagnostic::on_unimplemented]`**：给宽泛 trait 定制用户可读的编译错误（"X 不是合法系统，检查参数是否都实现 SystemParam"），写库必带；
7. **组合优于集中配置**：`(a, (b, c).after(a))` 约束长在代码结构里，每个配置方法返回树自身供链式生长——对照 Unity Script Execution Order 的集中数值表。

**代价**：逐点单态化吃编译时间（Bevy 编译慢的主要来源之一）；元数有宏天花板（超限得到误导性报错）；报错依赖 on_unimplemented 兜底。

**通则**：这套"函数当数据 + 签名当接口 + 编译期榨取"是 Rust 生态构建 DSL 的通用配方——Bevy 系统、axum 路由、serde 派生全是同一思路的不同投影。
