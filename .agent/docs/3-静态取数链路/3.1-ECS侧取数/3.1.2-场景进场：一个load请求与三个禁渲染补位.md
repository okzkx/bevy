## §1 进场链路（机制）

```text
Startup:  asset_server.load("…FlightHelmet.gltf#Scene0")   ← 占位 Handle 立即返回
          commands.spawn(WorldAssetRoot(handle))            ← 组件 Add hook 挂靠（bevy_world_serialization/src/lib.rs:96）
   │
   ├─ 异步：GltfLoader 解析 JSON/bin → 逐 primitive 产 Mesh 子资产 → 逐材质产 GltfMaterial
   │        → 三钩子（我们的 AshMaterialHook）转 StandardMaterial、给 primitive 实体插 MeshMaterial3d
   │        → 临时 World 整树序列化成 WorldAsset（"…#Scene0" 子资产）
   │
   └─ 依赖就绪后：WorldAssetRoot 的实例化系统把整树展开进主 World
          → primitive 实体 = Mesh3d + MeshMaterial3d + Transform/GlobalTransform + …
```

load 是异步的，"到货"不能在 Startup 里等——所以配一个 Update 轮询系统 [`report_scene_arrival`]：primitive 实体数 > 0 即到货，报一次统计后自歇（`Local<ArrivalState>` 的 done 位）；10s 未见实体按 Tier① warn 一次（加载失败不可在本系统修，根因看资产侧错误日志），帧循环照常。

**资产根路径是第一坑**：`asset_server.load("models/…")` 相对谁？`get_base_path`（bevy_asset/src/io/file/mod.rs:25）三段式——`BEVY_ASSET_ROOT` 环境变量 → `CARGO_MANIFEST_DIR` → **exe 所在目录**。cargo run 时 manifest 目录是 `ash_renderer/`，直跑 exe 时是 `target/debug/`——**两种跑法都到不了仓库根的 `assets/`**（首跑日志 `Path not found: F:\okzkx\bevy\target\debug\assets\models/…`）。修复：main 装配 `AssetPlugin.file_path` 编译期指到仓库根（`env!("CARGO_MANIFEST_DIR")` 拼 `../assets`）——装配级参数，属 main 统筹地盘。小坑：0.20 的 `file_path` 是 `String` 不是 `PathBuf`（E0308）。

## §2 三个禁渲染补位（本次的肉）

### 2.1 ImageLoader 停在 Pending——贴图永远 Loading（最深的一个）

**症状**：glTF、Mesh、材质全部到货，唯独 15 张贴图 handle 永远 `state=Loading`、`Assets<Image>` 停在内置 2 张，无任何错误日志。

**机制**：loader 注册分两步——`preregister_asset_loader` 只占位（`MaybeAssetLoader::Pending`，内含 broadcast channel）；真正 `register_asset_loader` 把 Pending 换成 Ready。贴图加载任务取 loader 时走 `MaybeAssetLoader::get`（bevy_asset/src/server/loaders.rs:283）：Pending 状态下 `receiver.recv().await` **永远等待，除非有人广播**。

**为什么 glTF/mesh 没事**：GltfLoader 由 GltfPlugin::finish 注册（渲染无关）；Mesh 资产在 GltfLoader 任务**内部**构造（不经 AssetServer 二次加载）。只有贴图走"独立路径 + ImageLoader"。

**谁该注册**：`TexturePlugin::finish`（bevy_render/src/texture/mod.rs:46-60）——读 `CompressedImageFormatSupport`（wgpu device features 生成）后 `register_asset_loader(ImageLoader::new(formats))`。**渲染族禁用 = TexturePlugin 不存在 = 无人广播 = 永久 Pending**。ImagePlugin 只做 preregister（bevy_image/src/image.rs:258），DefaultPlugins 里它独立挂载、不在禁用名单——所以容器和扩展名都活着，唯独真 loader 缺位。

**判别过程**（一句话方法论：Loading 卡死先分"全部卡"还是"嵌套卡"）：Startup 顶级直载同一张 png，同样卡 Loading → 排除"嵌套加载特异"，锁定 ImageLoader 本身没注册 → 顺着"谁注册 ImageLoader"找到 TexturePlugin::finish。

**修复**（host.rs，宿主桥的"禁渲染补位"职责）：`register_asset_loader(ImageLoader::new(CompressedImageFormats::NONE))`，与已有的 `CompressedImageFormatSupport(NONE)` 自报配对——NONE 只表示不解压缩纹理（basis/ktx2），png/jpeg 照常；3.3 接 ash 后按实际查询的 VkFormat 改写。

### 2.2 MeshMaterial3d 反射注册——展开实体树 panic

**症状**：资产就绪后 `world_asset_spawner.rs:635` panic：`world contains the unregistered type …`（类型名要开 bevy_utils/debug feature 才显示，本次临时开过取到名字）。

**机制**：WorldAsset 展开走反射逐组件写入，组件类型必须已注册。`MeshMaterial3d<StandardMaterial>` 的注册点在 `MaterialPlugin::<M>::build`（bevy_pbr/src/material.rs:448 `register_type::<MeshMaterial3d<M>>()`）——被我们连带禁用的 PbrPlugin 之内。

**修复**（scene.rs，材质缝插件的接线职责）：`register_asset_reflect::<StandardMaterial>()`（PbrPlugin 原有，Handle 反射需要）+ `register_type::<MeshMaterial3d<StandardMaterial>>()`。

## §4 机制注记：兜底材质为什么不驻留

到货统计 StandardMaterial = 6 而非 7：on_root 确实跑了（loader/mod.rs:266 无条件调用，把 `DefaultMaterial/std` 标注入库），但**无引用的标注子资产不驻留容器**——加载完成时 `process_asset_load`（bevy_asset/src/server/info.rs:445）先递归处理全部标注子资产，再过 `infos.contains_key` 守卫；基础 Gltf 资产无人持有（我们只持 "#Scene0" 子资产句柄），其句柄在加载任务结束时丢弃，无引用子资产的信息条目随之清退，入库被跳过。6 份正式材质因 primitive 实体的 MeshMaterial3d 持柄而存活。

含义：on_root 兜底材质只在"有 primitive 无材质"时经 `get_label_handle` 被引用、随实体驻留——FlightHelmet 6 个 primitive 全有材质，兜底不出现是健康态。
