# 3.2.2.1 内存契约:memory type、usage、绑定与对齐

对应[施工 3.2](README.md)任务 3.2.2.1。代码落位 `ash_renderer/src/vulkan/resources.rs`(契约本体:`MemoryContract` / `BufferRole` / `GpuBuffer` / `align_up`),探针 `ash_renderer/examples/memory_probe.rs`。本任务只冻结**内存契约**——池与缓存(3.2.2.2)、容量与销毁(3.2.2.3)、transfer 提交与票据(3.2.4)不在本任务内。

**状态:已实现并验收(2026-09-24)。**验证层 + 同步验证下组 A(合同正路)零 VUID、拷贝闭环逐字节一致;组 B(绑定负例)被对齐条款精准收账。`main.rs`/`host.rs` 零改动(资源件全在 `vulkan/` 内,本任务尚不接宿主壳)。

## §1 定案(契约本体)

### 角色表:usage 与 memory 属性一处定案,创建入口只引用

| 角色 | usage | 必需属性(不满足即报错,不降级) | 优先属性(同分取小索引) |
|---|---|---|---|
| `DevicePool` | VERTEX_BUFFER + INDEX_BUFFER + TRANSFER_DST + TRANSFER_SRC | DEVICE_LOCAL | — |
| `Staging` | TRANSFER_SRC | HOST_VISIBLE | HOST_COHERENT |
| `Readback` | TRANSFER_DST | HOST_VISIBLE | HOST_CACHED + HOST_COHERENT |

- **staging 的 HOST_VISIBLE 是硬契约**:选型函数([`MemoryContract::find_type`])在 `VkMemoryRequirements::memoryTypeBits` 允许的集合里二次筛选,必需属性不满足就带全部证据(需要什么/优先什么/设备给过什么)报 `Init` 冒泡——"契约被设备打破"是初始化失败,不是静默换路。集成显卡的 DEVICE_LOCAL 本就允许宿主可见,属设备事实,不做"可见性降级"。
- **DevicePool 带 TRANSFER_SRC 的缘由**:3.2.2.3 的迁移/扩容与 3.2 的内容抽查都要把池内容拷出去,池是天然拷贝源。这是探针实抓后补定的(见 §3:首跑验证层收了 VUID-00118,pool 缺 TRANSFER_SRC 不可作拷贝源)。
- **persistent map 定案**:host-visible 分配创建时 map 一次(整段 `VK_WHOLE_SIZE`),Drop 时 unmap。map/unmap 次数与 buffer 寿命一致,3.2.4 的 staging 复用不逐批重映射。
- **coherent 分支**:
  - 类型带 `HOST_COHERENT`:免 flush/invalidate。规范明言此时两个命令"非必需且有性能代价"(memory.adoc §Host Access 之 Note)。
  - 不带:`GpuBuffer::write` 写后自动 flush、`GpuBuffer::read` 读前自动 invalidate,范围按 `nonCoherentAtomSize` 舍入(§2.4)。纪律收在读写 API 里,调用方没有"忘记 flush"的入口——unmap 不隐式 flush,忘了就是永不可见(memory.adoc §memory-device-unmap-does-not-flush)。

## §2 机制

### 2.1 类型选择为什么是"必需 + 优先"两级

`memoryTypeBits` 是设备对**这个 buffer**的允许集合(随 requirements 查出);必需属性是合法性判定(缺 = 报错),优先属性是选择偏好(命中数多者优先,纯排序不否决)。同分取小索引保证决策确定可复现。这与"逐个查属性位再挑"的直觉写法差别在:必需项不足时**必须失败**,静默换成"差不多"的类型会把 host-visible 池悄悄变成可 mapping 陷阱,验证层救不了语义错误。

### 2.2 绑定四条款与"offset 0 单分配"的天然满足

`vkGetBufferMemoryRequirements` 返回三元组 (size, alignment, memoryTypeBits),绑定条款(resources.adoc,commonvalidity/bind_buffer_common):

| 条款 | 内容 | 本实现 |
|---|---|---|
| VUID-{refpage}-memoryOffset-01031 | memoryOffset < memory 大小 | offset 恒 0,分配恰为 requirements.size |
| VUID-{refpage}-memory-01035 | memory 类型在 memoryTypeBits 内 | find_type 只在集合内选 |
| VUID-{refpage}-memoryOffset-01036 | memoryOffset 是 alignment 整数倍 | offset 0 平凡满足;**子分配时才真正活跃**(3.2.2.2 bump 必须按 alignment 取整,`align_up` 已备) |
| VUID-{refpage}-size-01037 | requirements.size ≤ memory 大小 − offset | 恰按 requirements.size 分配、offset 0 |

另:`vkAllocateMemory` 受 `maxMemoryAllocationCount` 约束(超限未定义行为,VUID-vkAllocateMemory-maxMemoryAllocationCount-04101)——这是"一把大池多次子分配"而不是"每 mesh 一次分配"的规范动机,记账归 3.2.2.2。

### 2.3 map 与竞争防护的边界

`vkMapMemory` **不检查在用**即返回指针(memory.adoc §memory-device-hostaccess-hazards):host 写与 GPU 读的 hazard 防护是提交侧的内存依赖/票据纪律(3.2.4),不是读写 API 的职责。本任务的 `write`/`read` 只担保范围合法(checked_add 越界前置)与 coherent 分支正确;调用方必须先用完成票据证明"GPU 不在读这段",才能写/读。这条边界在 `GpuBuffer` 文档与 Drop 注释双处声明。

### 2.4 非 coherent 路径:atom 舍入的三个细则

1. **舍入规则**:无 HOST_COHERENT 时,host/device hazard 保证必须覆盖舍入后的范围——起点向最近 atom 倍数**向下取整**,终点**向上取整**(memory.adoc L3572-3583)。flush/invalidate 的范围结构另有硬条款:`offset-00687` 要求 offset 恒为 atom 倍数(无条件,空范围也约束);显式 size 须为 atom 倍数,或延伸到 memory 末尾(`size-01390`)。实现:`atom_range` 先把终点压回分配整体再向上取整,终点触底时自然落入 01390 的"到 memory 末尾"分支;len 为 0 直接跳过(空范围连 00687 都约束,不送 API)。
2. **"未写的 atom 不得 flush"条款为何天然满足**:条款要求只有宿主写过的 atom 集才可 flush。连续写区向两端舍入只波及**含写入字节的两个边界 atom**,中间不存在未写的洞——整段盲 flush 才会踩这条。
3. **粒度事实**:`nonCoherentAtomSize` 规范要求 2 的幂(limits.adoc L841-844)、要求上限 256(L5447);`minMemoryMapAlignment` 下限 64(L5402)。本机 RTX 2060 实测 atom = 64B。

## §3 探针与证据

`cargo run -p ash_renderer --example memory_probe`(仓库根)。与 timeline_probe v2 同纪律:组 A 是合法用法观察组,组 B 是负例诊断组,探针 PASS 不作规范裁决,验证层消息才是执法证据。同步验证照主工程常开(`VkValidationFeaturesEXT`);本探针用旧 SubmitInfo + 旧 pipeline barrier,不启用 synchronization2(接口定案归 3.2.4);探针 device 不链 12/13 feature(内存路径不涉及这些位,与主工程差异在此,不冒充同配置)。

**实跑记录(2026-09-24,RTX 2060,API v1.3.289,验证层 SDK 1.4.357.0):**

- 设备内存事实:6 类型/3 堆;非 coherent atom = 64B;类型 3/4/5 均 HOST_VISIBLE+HOST_COHERENT(4 另带 HOST_CACHED,5 兼 DEVICE_LOCAL)。
- 组 A 全绿:
  - 选型:staging → 类型 3(HOST_VISIBLE|HOST_COHERENT,免 flush 分支);pool → 类型 1(DEVICE_LOCAL);readback → 类型 4(+HOST_CACHED,优先位打分生效)。
  - 绑定:恰按 requirements.size 分配、offset 0 绑定,请求/分配字节一致。
  - 读写:两段区域([0, 65536) 整段 + [70000, 70016) 非 atom 对齐起点)写→读回逐字节一致。
  - 闭环:staging → DEVICE_LOCAL 池 → readback 最小 copyBuffer(transfer 写→transfer 读、transfer 写→HOST 读两条屏障),fence 等待后读回逐字节一致;**组 A 验证层消息零条**。
- 组 B(负例诊断):memoryOffset = 3、alignment = 4 的绑定,驱动返回成功(违反 VUID 未必被驱动拒绝的活证据),验证层按 `VUID-vkBindBufferMemory-None-10739` 收账——SDK 1.4 层报新修订条款(QCOM tile 例外措辞),同一执法点在 v1.3.289 对应 `memoryOffset-01036`;探针判据按 VUID-vkBindBufferMemory 前缀收账,不绑定修订号。
- 验收插曲(保留):首跑组 A 被收一条 ERROR——pool 未带 TRANSFER_SRC 却作拷贝源(VUID-vkCmdCopyBuffer-srcBuffer-00118)。契约修正(usage 表补 TRANSFER_SRC)后复跑零 VUID。验证层在验收中抓到契约缺口,正是前置闸门"执法轮"的预期工作方式。
- 编译/lint:`cargo build` + `cargo clippy`(lib + examples)全净。

**未实测边界(README 验证 4 纪律)**:本机全部可见类型皆 coherent,flush/invalidate 分支在实现里存在但**本机未实测**——非 coherent HOST_VISIBLE 类型出现时(或换机)须补跑探针确认 atom 舍入实测;本轮不以代码存在替代实测。

## §4 边界(本任务不是什么)

- **不是池**:单 buffer 单分配、offset 0;子分配 bump、按资产去重缓存、按收齐需求定容量是 3.2.2.2。
- **不管理容量与销毁**:不足扩容、迁移等待、维护停顿记账是 3.2.2.3;`GpuBuffer::drop` **不等 GPU 在飞**,"等待最后使用完成再销毁"由 3.2.2.3 的账本与 3.2.4.4 的退出排空承担。
- **不提交**:usage 冻结了 TRANSFER_DST/SRC,但提交、票据、跨族 release/acquire 归 3.2.4;host/GPU 竞争防护在提交侧(§2.3)。
- **不设 host hazard 防护**:读写 API 无在飞检查,3.2 的"正常上传零逐批 idle"承诺建立在其票据纪律上,与读写 API 无关。
