## §1 D1：timelineSemaphore 未显式启用

### 已实现的形状

[context.rs](../../../../ash_renderer/src/vulkan/context.rs) 的设备创建区（243～265 行）只链 `PhysicalDeviceVulkan13Features.dynamic_rendering(true)`，删除了原 `Vulkan12Features.timeline_semaphore(true)`。285 行却继续打印固定文本 `timelineSemaphore=on`。

版本归属明确：`e0acf1989` 初版有显式启用，`ebc2f9304` 为坚持 1.3 基线而删除；1.3 基线检查本身保留正确，错误是把它当成免声明 feature 的依据。

### 为什么是缺陷

**设备必须支持，不代表逻辑设备默认启用。**`Vulkan12Features` 是较早晋升特性的聚合结构，1.3 应用仍要用它或等价 feature 结构声明所用能力。Vulkan13Features 不重复列 timeline，不是取消 timeline 的启用位。

规范 v1.3.289：

- `features.adoc` 105～106 行要求逻辑设备用到的细粒度 feature 在设备创建时启用。
- `VUID-VkSemaphoreTypeCreateInfo-timelineSemaphore-03252` 要求未启用 timelineSemaphore 时不得创建 TIMELINE semaphore。
- 普通 Vulkan 1.2 已要求支持 timeline；“1.2 可选、1.3 无条件自动开启”的历史叙事也不准确。

当前生产循环没有创建 timeline，所以清屏成功不会触发这个待用能力的违规。新探针的 PASS 也不能关闭本问题，原因见 D5。

### 修复边界与验收

保留 Vulkan 1.3 设备门槛，显式启用 timeline；不能借修复引入不需要的低版本兼容分支。若后续使用 `vkQueueSubmit2`，另显式启用 synchronization2。

- [x] 代码中能区分 supported、requested/enabled，日志不再硬称未请求能力为 on。
- [ ] 在验证层开启下，正确启用组创建 timeline、signal、wait、查值均通过且无相关 VUID。
- [ ] 负例只作为独立验证测试，记录“未启用”的诊断，不期待驱动必返回 ERROR_FEATURE_NOT_PRESENT。
- [x] 生产初始化失败仍走两 Tier 的优雅退出，队列选择与 1.3 门槛不回退。

## §2 D2：提前重置 fence，使跳帧失去下一次唤醒者

### 已实现的形状

- [frames.rs](../../../../ash_renderer/src/vulkan/frames.rs) `FramePool::wait_and_reset`（103～115 行）先等 fence，再立即 reset fence 和 command buffer。
- [host.rs](../../../../ash_renderer/src/host.rs) 212 行调用它，之后才 acquire。
- acquire 的 `SwapchainOutOfDate` 分支在 223～227 行重建后直接 return，没有 queue submit；帧槽也没有 advance。

### 触发条件与后果

只要本帧已经 reset fence，但 acquire、后续录制或提交前的路径提前退出，就可能没有任何提交负责再次 signal 该 fence。下一帧仍等同一帧槽的 unsignaled fence，当前 `u64::MAX` 等待可能永久阻塞主线程和消息泵。

这不是上一轮最小化 stale acquire 的同一个问题。MAILBOX、最小化闸门、帧首重建能改变触发概率，却不能保证所有 acquire 永远成功，不能代替 fence 状态机。

### 修复边界与验收

把“等待旧帧完成 / 重置可重录资源”和“重置待提交 fence”分开。只有确实准备提交时才 reset fence；如果 reset 之后 submit 失败，不得直接返回后继续等这个 fence，应明确恢复同步状态或转 Tier② 退出。

同样检查 acquire 已成功但后续失败的分支：image_available 和所持图像也有待消费状态，不能只修一个 fence 调用位置就宣称整条失败路径安全。

- [x] 故障注入一次 acquire OUT_OF_DATE，本帧返回后仍能处理窗口消息并渲染后续帧。
- [x] 覆盖录制失败/提交失败的退出策略，不出现等待无人 signal 的 fence。
- [ ] SUBOPTIMAL 正常消费 acquire 信号并完成本帧，按需标记重建。
- [x] 连续最小化、还原、resize、关闭回归，不只看启动第一帧。

参考：[Khronos 教程“Fixing a deadlock”](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Tutorial/main/en/03_Drawing_a_triangle/04_Swap_chain_recreation.adoc)。

## §3 D3：present 信号量的复用依据不足

### 已实现的形状

[frames.rs](../../../../ash_renderer/src/vulkan/frames.rs) 的 `Frame`（25～30 行）每个在飞帧槽持有 `render_finished`；FramePool 有两槽，按帧 fence 和槽位轮转复用。`host.rs` 248 行把当前槽的 render_finished 交给 `queue_present`。

### 为什么帧 fence 不够

帧提交 fence 证明相关 rendering submit 已完成，不证明 presentation engine 已结束对 render_finished 的 wait/使用。CPU 返回、queue_present 返回和画面已呈现也不是同一事件。

因此，两帧轮转加 graphics fence 不是该 present-wait semaphore 可再次 signal 的完整证明。若前一次 present 仍引用它，就有错误复用的可能；并不要求每次本机都重现才构成设计缺口。

### 修复边界与验收

本项目优先采用官方推荐的**按 swapchain image 分配 render_finished**：根据 acquire 返回的 image index 选择，而不是根据 frame index 选择。重新 acquire 同一 image 并正确等待其获取依赖，为前次 present wait 的完成提供依据。

image_available、command buffer、graphics fence 仍可按帧槽管理，不能把“有一个按 image 管的信号量”误解成所有同步对象都要搬进 Swapchain。

- [x] 明确区分 frame index 与 image index，记录实际关联，证明不是按帧槽假装按 image 管理。
- [ ] 在 swapchain image 数与在飞帧数不同的情况下持续运行，同步验证不报 pending semaphore 复用。
- [x] 覆盖 resize 更换图像集合时信号量的保留/回收；最后一批 present 的销毁另按 D4 处理。
- [x] 不把 MAILBOX 模式或“隔两帧”当作完成保证。

参考：[Khronos Vulkan Guide：Swapchain Semaphore Reuse](https://raw.githubusercontent.com/KhronosGroup/Vulkan-Guide/main/chapters/swapchain_semaphore_reuse.adoc)。

## §4 D4：退出等待发生在相关资源销毁之后

### 已实现的形状

[host.rs](../../../../ash_renderer/src/host.rs) 的 `teardown_vulkan`（268～277 行）依次移除 FramePool、Swapchain、Context。

- FramePool::drop（frames.rs 223～234 行）立即销毁信号量、fence、command pool。
- Swapchain::drop 立即销毁 views 和 swapchain。
- 直到 Context::drop（context.rs 308～321 行）才 `device_wait_idle`。

调用顺序是源码事实。本轮没有证明 GPU 在每次退出时都恰好未完成；历史 WM_CLOSE 退出码 0 也不能证明销毁在规范上始终安全。

### 为什么反序拆除还不够

**反序解决对象依赖，等待解决异步使用；两者都要满足。**当前 draw_frame 排在退出拆除之前，退出帧仍可能刚提交 GPU 工作，不能在其完成前销毁相关对象。

`VUID-vkDestroyFence-fence-01120` 要求引用 fence 的队列提交已执行完；`VUID-vkDestroyCommandPool-commandPool-00041` 要求池内 command buffer 不在 pending。Context 最后的等待无法追溯保护已被拆掉的资源。

### 修复边界与验收

在第一项 GPU 资源被销毁前完成所需排空，然后继续按依赖反序拆除；设备丢失等等待失败要有明确退出清理策略。

**WSI 另有一层边界**：graphics submit 完成和 present 资源可销毁不能混为一谈。单纯把 `device_wait_idle` 前移能解决队列工作仍使用 command pool/fence 等问题，但最终 present-wait semaphore 和旧 swapchain 的回收仍需符合 presentation 完成规则。按设备能力选择 present fence/maintenance 扩展或官方无扩展的延迟回收方案，不能只靠习惯断言 idle 已覆盖一切。

- [x] GPU 仍有工作时请求关闭，等待发生在销毁 FramePool、image view 等之前。
- [ ] 明确最终 present 与旧 swapchain 资源回收依据；启用相应验证时无 pending 使用告警。
- [x] 关闭、初始化中途失败、resize 中关闭均保持窗口句柄晚于 Surface 相关清理销毁。
- [x] 正常退出码和两 Tier 分流不回退；退出日志记录完成阶段，不只打印“反序完成”。

## §5 D5：timeline 探针不能裁决“feature 无需启用”

### 已存在的探针与历史观察

[timeline_probe.rs](../../../../ash_renderer/examples/timeline_probe.rs) 由其他会话在 `68fdafa88` 加入。记录报告 RTX 2060 上 A（无 feature）和 B（仅 timeline=true）两组创建、查值、submit2 signal、host wait 都 PASS。本轮保留这份观察，未运行该探针，也不改它。

### 源码确认的三个问题

1. **有效用法缺少共同前提。**`create_device`（87～106 行）两组都没有开启 synchronization2；`run_timeline_round` 130 行却调用 queue_submit2。两组都违反 `VUID-vkQueueSubmit2-synchronization2-03866`，B 不是干净对照。
2. **没有建立合规诊断。**29～35 行创建 Instance 不请求验证层，无 debug messenger 或测试诊断收集。不能据没有收到错误或 PASS 文案认定验证层通过。
3. **判据错误。**10、109 行等注释假定违规必得 ERROR_FEATURE_NOT_PRESENT，83 行把 A PASS 直接打印成“无需启用”。应用违反 valid usage 时，驱动不承担以指定返回码拒绝每种误用的保证；成功返回不是规范许可。

此外，探针把 features 无法链到 Properties2 称为 ash 漏标（53～55 行），实为混淆查询结构：feature 使用 Features2 链，properties/limits 使用 Properties2 链。类型系统阻止错误组合不是 bug。

### 修复与验收

- [x] 合法组启用 timeline 和所选提交 API 所需的 synchronization2；或两组统一使用合法的旧 submit 路径，以隔离 timeline 变量。
- [x] 请求验证层并收集 VUID；负例只验证预期诊断，不继续当正常路径无限运行。
- [x] 报告同时包含设备、查询支持值、创建时启用集合、验证层状态和运行结果。
- [x] 删除“PASS 即合法 / 必须返回固定错误 / 13 结构没有字段即无需启用 / ash 漏标”的错误判据与注释。
- [x] 提交和信号量销毁的完成条件可证明；不能因为 host 看到了某个中间信号值，就不加分析地推断所有提交对象都已可销毁。

原始探针和运行记录作为历史证据保留；当前文档已经撤回其超出证据范围的闭案结论，源码输出仍待修。

### D6：进场屏障与 acquire 的竞争（首轮执法实抓，修复前所有回归不可见）

**已实现的形状（修复前）**：frames.rs 清屏录制的进场屏障 `old=UNDEFINED → new=COLOR_ATTACHMENT_OPTIMAL` 以 `srcStage=TOP_OF_PIPE` 提交，且不带 access 掩码。

**为什么是缺陷**（同步验证实抓 WRITE_AFTER_READ ×9 + WRITE_AFTER_WRITE ×9 + 重复上限提示，共 20 条）：

- **WRITE_AFTER_READ**：提交在 `COLOR_ATTACHMENT_OUTPUT` 阶段等 image_available（wait_dst_stage_mask），布局迁移写却从 `TOP_OF_PIPE` 起就可能执行——不在信号量等待的 dst 作用域内，与 acquire 对 image 的访问无序。
- **WRITE_AFTER_WRITE**：纯执行依赖不排序两次**写**——迁移写与后续 `loadOp=CLEAR` 的清屏写之间缺内存依赖（同一命令缓冲内命令顺序不构成同步）。

**修复**（官方 vulkan-tutorial 同款）：进场屏障 `srcStage` 提到 `COLOR_ATTACHMENT_OUTPUT`（落入信号量等待作用域）+ `dst_access_mask=COLOR_ATTACHMENT_WRITE`（迁移写 → 清屏写的内存依赖收口）。

- [x] 修复后全套回归零 VUID（见下）。
