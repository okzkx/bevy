# 3.2.1 Context 扩展：transfer 队列族与 timeline 信号量开关

对应 [施工 3.2 README](README.md) 任务 ①、[施工计划 §3](../施工计划：Bindless起步五段拆解.md)。本任务是 3.2 的地基扩容：只动 `vulkan/context.rs` 一处，不建任何 buffer、不碰帧循环——目标是让 Context 在 3.2.2~3.2.4 开工前就备好两个前提：**拷贝提交有自己的队列**、**timeline 信号量这个设备能力已开启**。

**状态：✅ 完成（2026-09-23）**。本机 RTX 2060 命中专用 transfer 族（族 1，无 GRAPHICS），未走退回分支；退回路径已实现并记取舍于 §2。**定案修订（同日，用户拍板"学习工程钉 1.3 基线，不考虑老设备兼容"）：`Vulkan12Features` 链删除，1.3 基线改为物理设备选择处硬校验，见 §3。**

## §1 改了什么

全部改动在 `ash_renderer/src/vulkan/context.rs`，四处：

1. **transfer 族查找**（物理设备选定后、设备创建前）：在选中设备的队列族表里找第一个"有 `TRANSFER` 且无 `GRAPHICS`"的族；找到 → 记为 transfer 族；找不到 → 直接取 graphics 族号（合批退回）。设备选择逻辑零改动——不为凑专用族换卡。
2. **1.3 基线硬校验**（定案修订新增）：物理设备枚举循环开头查 properties，`api_version < 1.3` 的设备记日志出局；全部出局 = `Init` 报错冒泡（Tier②）。
3. **设备创建**：`queue_create_infos` 从单个 graphics 族变为"graphics 族 + 独立 transfer 族"（同族时仍只提交一份，避免重复声明同族）；features 链零新增——timeline 信号量在 1.3 是无条件核心，无需 features 位（初版曾按施工计划原文链 `Vulkan12Features.timeline_semaphore`，定案修订后删除，经过见 §3）。
4. **Context 新字段**：`transfer_queue_family_index` + `transfer_queue`。退回时与 `queue_family_index`/`queue` 同值——下游比对族号即可分辨，不另设 bool。
5. **就绪日志**：报出图形族号、transfer 族号与"专用 / 同族合批"标注、`timelineSemaphore=on`。

帧循环、swapchain、frames 模块零触碰；`Drop` 无需新清理（`device_wait_idle` 本就覆盖全部队列）。

## §2 transfer 队列族：要它什么、不要它什么

**为什么单开拷贝队列**：上传大池是把几百 KB 顶点/索引从 host 内存拷进 device 内存。拷贝命令排在与图形同一条队列时，flush 必须插进帧提交的前后文，渲染命令被复制串行挡路；独立 transfer 队列让拷贝与图形提交并行在飞（3.2.4 的 timeline 信号量负责在"顶点真被顶点着色器读到"之前收口）。这是路线图"合批上传 + 拷贝队列起步"的队列侧半边。

**查找条件为什么是 `TRANSFER 且无 GRAPHICS`，而不要求 present/compute**：
- 拷贝队列只做拷贝，不碰 present（那是 graphics+present 队列的事）、不需要 compute；
- 条件里排除 `GRAPHICS` 是关键——含 GRAPHICS 的族不是"专用"拷贝引擎，选它等于没分流。

**退回分支的取舍（本机未走，但按计划必须实现并记录）**：桌面 GPU 常态是 transfer 能力就长在 graphics 族上（尤其多数核显只有一族），独立 DMA 族是独显的额外馈赠。找不到时**退回 graphics 合批**而不是另想办法（比如从 compute 族凑）——因为合批上传本身已经是本段的主收益（一次 flush 一个 staging buffer 一次提交），队列分流只是独显上的加成；跨队列提交流（需要跨队列信号量传递所有权）复杂度显著高于同队列，不为独显以外的人群付这个价。落点：`transfer_queue_family_index == queue_family_index` 时一切按同队列合批走，3.2.4 无需分叉。

**本机实测**：`NVIDIA GeForce RTX 2060 (DISCRETE_GPU)`，图形族 0，transfer 族 1（NVIDIA 典型 copy engine 布局：族 1 为 `TRANSFER(+SPARSE_BINDING)` 独立引擎）。日志：

```text
Vulkan 进程级上下文就绪: API v1.3.289  设备 NVIDIA GeForce RTX 2060 (DISCRETE_GPU)
  图形队列族 0  transfer: 族 1（专用 transfer 族（无 GRAPHICS））  timelineSemaphore=on
```

## §3 timeline 信号量：它是什么，以及 1.3 基线定案

### 它是什么——从 binary 讲到 timeline

二值（binary）信号量是 Vulkan 队列上的单次握手原语：signal 一次、wait 一次、用完重置，只有"响了/没响"两个状态。现有帧循环的双信号量（image_available/render_finished）各桥接一次单向握手，天然匹配。

timeline 信号量 = 带单调递增 64 位 payload 的信号量，一次创建反复使用、无需 reset：提交时可指定"signal 到值 N"或"等到值 V 才开始执行"（`SubmitInfo2` + wait/signal semaphore value）；CPU 侧可 `vkGetSemaphoreCounterValue` 随时查当前进度、`vkWaitSemaphores` 带超时等到某个值。**D3D12 的 `ID3D12Fence` 就是它**——`Signal(value)`/`SetEventOnCompletion(value)`/GPU 端 `WaitFence(value)` 全套语义；Unity 图形侧的 fence 语义同源。反过来说：Vulkan 1.0~1.1 时代只有二值信号量（≈D3D11 的门），D3D12 天生具备的 fence 进度语义，Vulkan 直到 1.2 收编 `VK_KHR_timeline_semaphore` 才补齐，1.3 进无条件核心。

**为什么 3.2 上传链需要 timeline 而不是 binary**：上传是流水化的——第 1 批拷贝 signal 10、第 2 批 signal 20、第 3 批 signal 30（每批 = 一次 flush 的累计值），渲染提交"等到 20"即拿到前两批数据直接用，不必知道批的内部构成。binary 信号量表达不了"等到第 N 个进度"：它 signal 两次未 wait 是未定义行为，fence 则要为每批配一个对象再逐个等。CPU 侧还能 `vkWaitSemaphores` 等旧值回收 staging 内存——fence 之外又多一条可选的回收闸门（3.2.4 定用哪条）。

### 1.3 基线定案（2026-09-23 用户拍板修订）

施工计划原文写"设备创建开 `Vulkan12Features.timelineSemaphore`"，初版照做。用户随即修正方向：**学习工程，认定设备必须支持 Vulkan 1.3，不做老设备兼容路径**。落法两处：

1. **删 `Vulkan12Features` 链**。timeline 信号量的能力演进：1.1 是扩展 → 1.2 进核心但仍是可选 feature bit → **1.3 无条件核心**（`Vulkan13Features` 无此字段，1.3 设备上 `Vulkan12Features.timelineSemaphore` 恒报 true）。对 1.3 设备链 12 位是空操作，删。
2. **"认定 1.3"落成显式校验**而非隐式假设：物理设备选择循环里 `api_version < 1.3` 直接出局（记日志），全部出局 = `Init` 报错优雅退出。不然"认定"只是愿望——链着 1.3 feature 结构喂给 1.2 设备是 VUID 违规，验证层报错或驱动带病创建，崩得没头没尾；闸门前移后，不达标设备的失败形态 = 启动期一条清晰错误。

区分两类 1.3 内容：**timeline 信号量是 1.3 无条件核心**（无 features 位，闸门过即得）；**dynamicRendering 是 1.3 的可选 feature**（`Vulkan13Features` 里仍有位，必须显式开）。所以 features 链里真正要声明的只有后者。

### 对校验意见的复核（2026-09-23，探针实证闭案）

校验意见质疑："1.3 基线不代表 timeline 自动启用——需区分'设备支持'与'逻辑设备创建时启用'，`Vulkan12Features` 的名字表示特性归入 1.2、不等于兼容老设备；1.3 基线仍需显式声明启用；且当前清屏循环没创建过 timeline 信号量，运行通过没验证到这个问题。"

复核结论：**"必须启用"不成立，"路径未覆盖"成立并已补**。三条证据：

1. **结构性证据**：ash 0.38+1.3.281 头的 `PhysicalDeviceVulkan13Features` 全部 14 个字段里没有 timelineSemaphore——1.3 的 feature 启用位以 13 结构为家，没有位即没有"启用"这个动作可做。
2. **查询实测**（Features2 链查 RTX 2060 / v1.3.289）：`Vulkan12Features.timelineSemaphore = true`——"1.3 设备上该位必须报 true"的 mandatory 约束实测成立；同链的 dynamicRendering/synchronization2/descriptorIndexing 均报 true。
3. **运行时 A/B 裁决**（`ash_renderer/examples/timeline_probe.rs`，本机可复跑 `cargo run --example timeline_probe`）：组 A 设备创建**完全不链任何 features**，timeline 信号量创建 → 查初值 0 → `queue_submit2` signal 到 5（空命令提交）→ `vkWaitSemaphores` 等到 5 → 复查，全链 PASS；组 B 链 `Vulkan12Features.timeline_semaphore(true)` 同样 PASS。若"必须启用"成立，组 A 应在创建或提交处拿到 `ERROR_FEATURE_NOT_PRESENT`——没有发生。

"支持 vs 启用"的二分法本身没错，错在适用范围：**1.2 时代** timelineSemaphore 是可选 feature，二分法成立、启用确有必要；1.3 把它移出可启用集合（mandatory core），二分法失去了对象。校验意见把 1.2 的启用约束套到了 1.3 上。它真正站得住的一点是：定案当时清屏循环确实没执行过任何 timeline API，"跑通"覆盖不到这条路径——探针正是为补这个覆盖而写，结论因此从"规范记忆"升级为"实测"。

**顺手坑记录**：ash 0.38 的 extends 矩阵漏标了 12/13 features → `PhysicalDeviceProperties2` 的 pNext 合法性（`ExtendsPhysicalDeviceFeatures2` 有、对应 properties2 没有）；手接裸指针 pNext 链实测驱动不填充（原因未深究）。查询 feature 支持一律走 `PhysicalDeviceFeatures2` + `push_next` 类型安全链。

## §5 下游衔接

- 3.2.2 `resources.rs`：transfer 命令池建在 `ctx.transfer_queue_family_index` 上；内存类型 helper、顶点/索引池、staging 池都在新模块，不进 context.rs。
- 3.2.4 `flush_uploads`：拷贝提交发往 `ctx.transfer_queue`，timeline 信号量在拷贝命令后置位；渲染提交（graphics 队列）以 `waitSemaphoreValue` 等待该值，dst stage = `VERTEX_INPUT`。若退回同族，则两条提交天然同队列顺序化，等待仍有语义（渲染提交仍需等拷贝完成）但无跨队列所有权传递问题。
