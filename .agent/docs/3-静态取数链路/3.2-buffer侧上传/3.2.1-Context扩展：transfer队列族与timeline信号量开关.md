# 3.2.1 Context 扩展：transfer 队列族与 timeline 信号量开关

对应 [施工 3.2 README](README.md) 任务 ①、[施工计划 §3](../施工计划：Bindless起步五段拆解.md)。本任务是 3.2 的地基扩容：只动 `vulkan/context.rs` 一处，不建任何 buffer、不碰帧循环——目标是让 Context 在 3.2.2~3.2.4 开工前就备好两个前提：**拷贝提交有自己的队列**、**timeline 信号量这个设备能力已开启**。

**状态：✅ 完成（2026-09-23）**。本机 RTX 2060 命中专用 transfer 族（族 1，无 GRAPHICS），未走退回分支；退回路径已实现并记取舍于 §2。

## §1 改了什么

全部改动在 `ash_renderer/src/vulkan/context.rs`，四处：

1. **transfer 族查找**（物理设备选定后、设备创建前）：在选中设备的队列族表里找第一个"有 `TRANSFER` 且无 `GRAPHICS`"的族；找到 → 记为 transfer 族；找不到 → 直接取 graphics 族号（合批退回）。设备选择逻辑零改动——不为凑专用族换卡。
2. **设备创建**：`queue_create_infos` 从单个 graphics 族变为"graphics 族 + 独立 transfer 族"（同族时仍只提交一份，避免重复声明同族）；features 链在 `Vulkan13Features.dynamic_rendering` 之外加挂 `Vulkan12Features.timeline_semaphore(true)`。
3. **Context 新字段**：`transfer_queue_family_index` + `transfer_queue`。退回时与 `queue_family_index`/`queue` 同值——下游比对族号即可分辨，不另设 bool。
4. **就绪日志**：报出图形族号、transfer 族号与"专用 / 同族合批"标注、`timelineSemaphore=on`。

帧循环、swapchain、frames 模块零触碰；`Drop` 无需新清理（`device_wait_idle` 本就覆盖全部队列）。

## §2 transfer 队列族：要它什么、不要它什么

**为什么单开拷贝队列**：上传大池是把几百 KB 顶点/索引从 host 内存拷进 device 内存。拷贝命令排在与图形同一条队列时，flush 必须插进帧提交的前后文，渲染命令被复制串行挡路；独立 transfer 队列让拷贝与图形提交并行在飞（3.2.4 的 timeline 信号量负责在"顶点真被顶点着色器读到"之前收口）。这是路线图"合批上传 + 拷贝队列起步"的队列侧半边。

**查找条件为什么是 `TRANSFER 且无 GRAPHICS`，而不要求 present/compute**：
- 拷贝队列只做拷贝，不碰 present（那是 graphics+present 队列的事）、不需要 compute；
- 条件里排除 `GRAPHICS` 是关键——含 GRAPHICS 的族不是"专用"拷贝引擎，选它等于没分流。

**退回分支的取舍（本机未走，但按计划必须实现并记录）**：桌面 GPU 常态是 transfer 能力就长在 graphics 族上（尤其多数核显只有一族），独立 DMA 族是独显的额外馈赠。找不到时**退回 graphics 合批**而不是另想办法（比如从 compute 族凑）——因为合批上传本身已经是本段的主收益（一次 flush 一个 staging buffer 一次提交），队列分流只是独显上的加成；跨队列提交流（需要跨队列信号量传递所有权）复杂度显著高于同队列，不为独显以外的人群付这个价。落点：`transfer_queue_family_index == queue_family_index` 时一切按同队列合批走，3.2.4 无需分叉。

**本机实测**：`NVIDIA GeForce RTX 2060 (DISCRETE_GPU)`，图形族 0，transfer 族 1（NVIDIA 典型 copy engine 布局：族 1 为 `TRANSFER(+SPARSE_BINDING)` 独立引擎）。日志：

```text
Vulkan 进程级上下文就绪: API v1.3.289  设备 NVIDIA GeForce RTX 2060 (DISCRETE_GPU)
  图形队列族 0  transfer: 族 1（专用 transfer 族（无 GRAPHICS））  timelineSemaphore=on
```

## §3 timelineSemaphore：1.3 时代为什么还链 Vulkan12Features

timeline 信号量的能力演进：1.1 是扩展（`VK_KHR_timeline_semaphore`）→ **1.2 进核心但仍是可开启的 feature bit** → **1.3 无条件核心**（`Vulkan13Features` 里已没有这个字段，查询必为 true）。本项目 API 声明 1.3，理论上什么都不链也能用。

仍按施工计划显式开 `Vulkan12Features::timeline_semaphore(true)`，理由有二：

1. **依赖可见**：3.2.4 的整条上传链（拷贝完成置位 → 渲染提交等待）押在 timeline 信号量上，这是本渲染器第一个"超出清屏基线"的同步原语。设备创建处显式声明，读代码的人不用去查"1.3 核心包不包含它"才知道依赖从哪来——学习项目里，声明处就是文档。
2. **兼容 1.2-only 设备**：若换到只报 1.2 的设备/驱动，这个 bit 仍是必须显式开启的开关，链上即正确；1.3 设备上该 bit 必报支持，开着零成本。

代价是 features 链多一个结构（`push_next` 顺序：12 与 13 都挂在 DeviceCreateInfo 的 pNext 链上，先后无语义）。

**timeline 与 binary 的分工预告**（正式使用在 3.2.4，此处只开能力）：现有帧循环的双 binary 信号量（image_available/render_finished）各桥接一次单向握手，用完即重置，天然匹配；而"一批拷贝全部完成"是一个**进度值**（可能多批在飞、渲染侧要等其中第 N 批），binary 信号量表达不了"等到某个值"，timeline 的 64 位 payload 就是为此生的。

## §5 下游衔接

- 3.2.2 `resources.rs`：transfer 命令池建在 `ctx.transfer_queue_family_index` 上；内存类型 helper、顶点/索引池、staging 池都在新模块，不进 context.rs。
- 3.2.4 `flush_uploads`：拷贝提交发往 `ctx.transfer_queue`，timeline 信号量在拷贝命令后置位；渲染提交（graphics 队列）以 `waitSemaphoreValue` 等待该值，dst stage = `VERTEX_INPUT`。若退回同族，则两条提交天然同队列顺序化，等待仍有语义（渲染提交仍需等拷贝完成）但无跨队列所有权传递问题。
