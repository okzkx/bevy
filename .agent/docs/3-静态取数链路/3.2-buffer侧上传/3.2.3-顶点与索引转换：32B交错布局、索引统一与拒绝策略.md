# 3.2.3 顶点与索引转换:32B 交错布局、索引统一与拒绝策略

对应[施工 3.2](README.md)任务 3.2.3。代码落位 `ash_renderer/src/vulkan/mesh_convert.rs`(`convert_mesh` / `ConvertedMesh` / `MeshConvertError` / `VERTEX_STRIDE`)——纯 CPU 字节整形,零 Vulkan 调用;Vulkan 侧只消费产出的字节。任务口径:POSITION/NORMAL/UV_0 → 交错 32B vertex-input 布局;正确处理 U16/U32、字节偏移、对齐和 draw 的 firstIndex/vertexOffset;验证缺字段/不支持拓扑策略。

**状态:已实现并验收(2026-09-24)。**探针组 A 逐字节验证布局(offset 0/12/24、小端、U16→U32 保序、缺字段 0 填充)与三种拒绝的错误类型精确匹配;App 实跑 FlightHelmet 6 资产 55392 顶点全部转换成功,字节数与 Assets 统计吻合。

## §1 定案

### 布局:交错 32B,字段 offset 0/12/24

| 字段 | offset | 尺寸 | 来源 | 缺失策略 |
|---|---|---|---|---|
| POSITION | 0 | 12B `[f32;3]` | `Mesh::ATTRIBUTE_POSITION` | **拒收**(没有位置的网格无法构成绘制) |
| NORMAL | 12 | 12B `[f32;3]` | `Mesh::ATTRIBUTE_NORMAL` | 全 0 填充 |
| UV_0 | 24 | 8B `[f32;2]` | `Mesh::ATTRIBUTE_UV_0` | 全 0 填充 |

- 这是**我们的布局选择**(施工计划 §2:不是 Vulkan 禁止 SoA),与 3.4 的 vertex-input 状态是同一份契约,本模块是唯一生产点。
- "交错 32B 不得未经验证复用为 WGSL storage struct"——M2 顶点数据只走 vertex-input 路径,不进描述符;Bindless 表(set0)只装贴图/采样器,顶点/索引不占槽(与 [GpuBuffer 对照篇](GpuBuffer：契约、用法与frenderer三分法对照.md) §3 的边界一致)。
- 字节序:`to_le_bytes` 逐分量展开——布局不依赖平台内建序的巧合(x86/主流 GPU 均小端,但显式写出让契约可读)。

### 索引:输入 U16/U32 均收,输出统一 U32

放弃"U16 输入保 U16 输出"的省内存分支:一字节序、firstIndex 步长、绑定对齐三处只留一条路,验收面减半。代价:FlightHelmet 284166 索引按 U32 = 1.1MiB(池容量余量覆盖,实跑索引池 2MiB 无压力)。无索引网格输出顺序索引 0..n(显式策略,不跳过)。`first_index`/`vertex_base` 的除法基准(4 / 32)由输出格式唯一确定,账本行登记时算好(见 [3.2.2.2 §1](3.2.2.2-池与缓存：DEVICE_LOCAL大池、bump分配与资产身份去重.md))。

### 拒绝策略:拒收是 `MeshConvertError`,编排层按 Tier① warn 一次后跳过

| 拒绝 | 条件 | 理由 |
|---|---|---|
| `UnsupportedTopology` | 非 TriangleList | M2 管线只配 TriangleList;strip/line 的绕向与索引语义另议,不静默当 TriangleList 画 |
| `EmptyMesh` | 0 顶点 | 没有可上传的内容 |
| `MissingPosition` | POSITION 缺失或非 Float32x3 | 无位置的网格无法绘制 |

NORMAL/UV_0 **缺失是 0 填充继续,不是拒收**(3.4 调试着色允许无光/无贴图;格式不是 Float32x3 时 warn 后同样 0 填充,信息缺口日志化)。资产到货与否由编排层分流(未到货跳过重试),不进转换错误。

## §2 机制

### 2.1 bevy 侧取数的防 panic 面

`Mesh::attribute` 在数据被提取到 RenderWorld 后会 panic(MESH_EXTRACTED_ERROR);本工程禁渲染无提取,但取数一律走 `try_attribute`——按 Result 处理,把"资产侧意外"变成错误值而不是进程崩溃(非必要不 panic)。

### 2.2 顶点数的单一事实源

`count_vertices()` 是行数权威;POSITION 切片长度与它不符属资产侧矛盾(debug_assert 拦截)。NORMAL/UV 切片按同一索引 i 取值——bevy 保证各属性行数一致,转换不自行兜底错位数据。

## §3 证据

**探针组 A**(`upload_probe`,纯 CPU,2026-09-24):
- 布局:顶点 1 @offset 32 的 pos.x/y、normal.x/z、uv.u/v 逐字段断言(小端字节级),顶点 2 pos = (2,4,6);
- 索引:U16 `[0,1,2,2,1,3]` → U32 加宽保序(重复索引保序,firstIndex 语义可考);
- 缺字段:NORMAL/UV 区全 0 断言;无索引网格 → 顺序索引 0..n;
- 拒绝三连:LineList → `UnsupportedTopology`、空网格 → `EmptyMesh`、缺 POSITION → `MissingPosition`,错误类型精确匹配(不是"随便报错")。

**App 实跑**(2026-09-24):FlightHelmet 6 资产转换成功,顶点 1772544B = 55392×32、索引 1136664B = 284166×4,与采集统计逐字节吻合(README 验证 1 的字节数对账);内容逐字节校验由探针组 B 的池读回承担(不只对总字节数)。

## §4 边界

- **不做顶点缓存优化/三角带化**:索引重排、顶点重排、strip 化都是步骤 4 之后的资产侧工程。
- **不碰坐标变换**:bevy 的右手系/朝向原样上传;Y 翻转、绕向修正是 3.4 管线侧(viewport/front face)的定案点,不在转换里偷改数据。
- **TBN/切线不搬**:M2 判定线不含法线贴图;TANGENT/JOINT/WEIGHT 等属性被有意丢弃,后续任务用到再加字段。
