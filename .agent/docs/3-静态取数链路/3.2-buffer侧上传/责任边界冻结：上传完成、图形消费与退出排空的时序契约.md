# 责任边界冻结:上传完成、图形消费与退出排空的时序契约

对应[施工 3.2](README.md)前置闸门第三项:"冻结上传完成、图形最后使用完成、staging/命令缓冲复用与退出排空的责任边界"。本篇是**契约篇**——把四个等待/回收面各自归谁、凭什么证明、何时生效一次说清;各机制的实现细节看对应施工记录。

**状态:已冻结(2026-09-24)。**四条边界在 3.2 全部有代码落点与证据;图形消费面(第②条)在 M2 尚无实际消费者,按"冻结 + 预演"收账,3.4 接线时不得另立规则。

## ① 上传完成 = timeline 票据(归 Uploader)

- **定义**:上传批次完成 ⇔ `ticket_semaphore` 计数 ≥ 该批票据值。signal 发生在 transfer 提交完成时,由 GPU 写——"完成"是设备事实,不是 CPU 猜测。
- **signal 方**:Uploader(3.2.4.1);**等待方**:槽位复用/池维护(3.2.4.3/3.2.2.3)与 3.4 的图形提交(挂 wait 列表)。
- **失败不发布**:submit_batch 早退发生在发票据之前(3.2.4.4),不存在指向未上传数据的票据。
- 证据:探针组 B/C 的票据单调序列与完成判定;App 批次 #1。

## ② 图形最后使用完成 = 帧槽 fence + 票据等待(归 3.4,现已冻结形状)

- **谁拥有**:图形消费的"最后一次使用完成"由**帧槽 in_flight fence** 表达(现有 FramePool 纪律:第 N 帧槽重录前等上一轮提交完成);跨族消费前另有**票据等待 + acquire**(探针组 D 预演的形状)。
- **回收含义**:池区间/旧池/描述符槽的销毁与覆盖,必须证明"上传完成(票据)∧ 图形最后使用完成(帧槽 fence 或退出排空)"两个条件同时满足。M2 无 draw,条件第二半空真——3.4 接线时按此冻结不得只凭"归 Swapchain"或"反正空闲"跳过(施工计划 3.4 §3 的明文警告)。
- **同族分支**:transfer 与 graphics 同族时无 ownership 转移,但票据等待 + TRANSFER→消费屏障仍是内存依赖的最低配置(组 D 的同族说明 + memory_probe 同族闭环)。

## ③ staging/命令缓冲复用 = 槽位票据闸门(归 Uploader)

- 2 槽轮转,每槽"最后提交票据"完成才可重录/重写(3.2.4.3);staging 扩容同样只在槽票据完成后整槽重建。
- 池区间正常路径只增不覆盖;覆盖场景(维护迁移)由 3.2.2.3 的等待纪律承担。
- 命令缓冲与 staging 同槽绑定:同槽必是同票据,不出现"staging 已复用而命令缓冲还在飞"的错位。

## ④ 退出排空 = teardown 单点(归 host::teardown_vulkan)

- 顺序:AppExit 写入 → `device_wait_idle`(队列无在飞)→ 反序 Drop(FramePool → Swapchain → Uploader → MeshPool → Context)。D4 定案:等待先于一切 GPU 资源销毁,验证层对销毁条款(VUID-vkDestroyFence-fence-01120 等)的执法以此为前提。
- Uploader/MeshPool/GpuBuffer 的 Drop **都不等 GPU**——等待职责收在排空单点,对象销毁不各自为政。
- 探针的清场是同款纪律的缩样:等票到 + 宿主读完再拆(可证明无在途引用)。

## 分账表:谁的等待记谁的账

| 等待 | 归属 | 记账 |
|---|---|---|
| 槽位复用等待 | Uploader | 复用日志,逐次可查(3.2.4.3) |
| 维护等待(在飞 + 迁移票据) | MeshPool | `MaintenanceLedger`,与正常上传分账(3.2.2.3) |
| 帧槽 fence 等待 | FramePool | 帧循环重录闸门(既有机制) |
| 图形消费等待(票据 + acquire) | 3.4 record_frame | 未接线,形状已由探针组 D 冻结 |
| 退出排空 | teardown_vulkan | D4,退出日志 |

正常上传路径(逐批)上没有任何 CPU 等待——README 验证 3 的承诺由本表结构担保:等待都长在"复用/维护/退出/消费"这些**合法调用点**上,不长在上传路径上。
