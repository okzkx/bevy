# 验证层：CPU 侧的规范执法者——它查什么、怎么查、保证到哪

> 2026-09-23 建档。缘起：V1 前置闸门装 SDK 开验证层，首轮执法实抓 D6（进场屏障竞争，见[《已实现缺陷与修复验收》§10](已实现缺陷与修复验收.md)）——趁机制还热，把两轮问答（验证层有什么用/怎么工作 + "debug layer 理解对不对"的复述校验）落成机制篇。实证与缺陷编号都在缺陷文档，本文只管机制。

## §0 一句话定位（先立判定线）

**验证层 = 规范合同的模拟执行者，不是 GPU 的监工。**它管"你签的条款有没有违约"，不管"这次履约现场有没有出事故"。它说错 = 你确实违约（GPU 暂时没追究）；它说对 = 合同层面无懈可击（现场事故另有肇事者）。它的"无告警"是**证明性证据**——凡 VUID 可推导的违规不存在——不是"跑了几次没炸"的统计性观察。

## §1 为什么没有它就是裸奔：驱动按契约假设你合法

Vulkan 与 GL/D3D11 最大的分野：**合法性是应用方的义务**。规范里每条 valid usage（VUID）写的都是"应用**必须**保证 X"，驱动拿到调用默认你保证过了——因为逐次调用核对对象生命周期、队列归属、跨提交读写时序的成本极高，而 Vulkan 的卖点恰是把这类检查从热路径删掉。驱动的姿态是：假设合法、不保证拒绝非法用法、甚至不保证会炸。

本项目 2026-09-23 实测两例：探针组 B **不启用 timeline feature** 直接创建 TIMELINE 信号量，RTX 2060 驱动照样返回成功（非法用法被微笑接受）；D2 的死锁面里，驱动从不检查"这个 fence 有没有人会 signal 它"。而观察式回归的盲区在 D6 显形：进场屏障竞争的时间窗口在清屏轻负载下趋近于零——截图回归跑一万次也撞不到。不是没 bug，是 bug 显形依赖时序与负载。

类比：这就是 D3D12 的 **debug layer**——同一思想的微软版，RELEASE 设备零检查，开 debug 设备才全量校验。Unity 的 device lost 恢复、UE 的 RHI removed 则说明了另一件事：真出事时的恢复单位是**设备级重建**，从来不是"这一帧重来"。

## §2 工作机制：layer 链 + 三个开关

验证层不是"加了驱动就变聪明"，而是**插在应用和驱动之间的参考实现**。Vulkan 的 loader 是分层架构：创建 Instance 时声明 `VK_LAYER_KHRONOS_validation`，loader 把每个 `vk*` 调用先路由进验证层——拦截、记账、检查，再把调用原样转发给驱动的真实现。违规在调用点当场报，经应用注册的 debug callback 输出（本项目用 `[VK-ERROR]/[VK-warn]` 前缀打 stderr，与 bevy 应用日志天然可分流）。

它知道的比"检查"多：旁路记录每次提交、每个对象生命周期、每次 signal/wait 配对——驱动内部也记但**不查**（省性能），验证层专门为查而活。

抓到 D6 需要**三个开关全开**，缺一不可：

1. **层在盘上**——装 SDK（`VK_LAYER_khronos_validation.json` 注册进注册表）；
2. **请求挂载**——instance 的 `enabled_layer_names` 声明它；
3. **同步验证显式打开**——默认关！须 `VkValidationFeaturesEXT.SYNCHRONIZATION_VALIDATION`。

这就是核心检查多年不报、同步验证一来就抓到 D6 的原因：核心检查管不到跨提交的同步时序。

## §3 查什么：四类执法面 + 一个 GPU 侧反例

1. **用法合法性（core validation）**：句柄有效、枚举合法、结构体链正确，以及"启用"约束——用某能力前 feature 必须在设备创建时声明。活例是 VUID-03252 的报错原文："semaphoreType is VK_SEMAPHORE_TYPE_TIMELINE, but timelineSemaphore feature was not enabled"。"支持/启用/使用"三件事里"启用"的执法者（见[Timeline 信号量机制篇](Timeline信号量：用法、与阻塞的区别、现代引擎的做法.md)）。
2. **同步验证（sync validation）——V1 轮的主角**：给每次提交建读写访问账本（每个访问记下对象、stage、队列），按规范的同步规则推导任意两笔访问之间有无 happens-before；没有且同类相撞（写后写/写后读/读后写）就报 hazard。本质是**把人肉推不动的全组合时序分析交给工具**：D6 里"acquire 的读 vs 进场屏障的写"，人肉推演漏了内存依赖半边（纯执行依赖不排序两次写），工具不漏——它不采样、不撞运气，逐访问对推导。
3. **生命周期**：销毁时是否仍有在飞引用——VUID-00629（本项目探针的 messenger 泄漏被它抓出）、fence 在飞时销毁、命令缓冲 pending 时销毁池。D4 那类退出时序问题全在这个执法面。
4. **状态与布局**：image layout 错误使用、描述符指向无效资源、pipeline 兼容性。
5. **GPU-AV（"只在 CPU 侧"的反例脚注）**：bindless 场景下描述符指向哪块内存只有 GPU 执行时才知道，GPU-assisted validation 往 shader 注入检查代码，把验证**搬到 GPU 上跑**。3.3 接 bindless 时启用这个档位。

## §4 保证的边界：四条不说满

1. **合法≠正确**。清屏颜色算错、相机看反、矩阵传错、剔除剔多——全部合法、全部错。渲染正确性的裁判是判定线（数值核验）+ 抓帧工具（RenderDoc），不是验证层。
2. **性能不管，且自身是负担**。核心检查有调用开销，同步验证要维护跨提交访问图，重场景帧时间可观。工业界默认只在 debug 开；本项目学习期常开（"误用当场可见"哲学），3.4 真实绘制嫌慢时把 `VkValidationFeaturesEXT` 的 enables 换成空数组即降回核心检查，一行。
3. **覆盖有版本差**。验证层跟规范同步演进，旧层对新 VUID 有盲区；它自己也有已知怪癖——本项目撞到 `duplicate_message_limit`：同一 VUID 报 10 次就静默，收账计数可能被截断。
4. **不改变合法性本身**。验证层安静 ≠ 不挂验证层时也合法。契约始终是应用签的，层只是帮你发现自己违约了没有。

## §5 一个复述的校准（2026-09-23 问答）

用户复述："debug layer 在 CPU 侧 hook 图形 API 调用，构建 vk 对象依赖链，依赖前置不满足就报警告报错。但它察觉不到实际资源在 GPU 侧的流转——也许它认为是对的但 GPU 侧有问题（概率很小），或者它认为错的但 GPU 侧运气好没出现问题。"

三处校准：

- **构建的不是"对象依赖链"，是规范模型的推演账本**（§3.2）。立场性修正：它模拟"这串调用按规范合同是否保证安全"，不模拟"这块 GPU 实际在干什么"。合同的作用恰是把执行顺序的不确定性抽象掉——同步写对了，GPU 内部怎么并行都无所谓，所以它**不需要**察觉 GPU 侧流转。
- **"认为错但 GPU 没事"不是对称的运气，是定义问题**。报 hazard = 按规范这段程序是未定义行为，判决是终审的，程序确实错了。GPU 眼下容忍不是侥幸，是 UB 的常态：硬件高度并行、有自己的内部同步、驱动可能残留 GL 时代的隐式习惯、小竞争窗口本来就窄。但合同已作废——换驱动、升驱动、加负载，随时开始炸。组 B 的"驱动接受≠合法"是同一件事的另一面。
- **"认为对但 GPU 有问题"存在但概率极小，责任几乎都在层外**：驱动 bug、硬件 bug、规范留白（如 WSI 的 MAILBOX 替换时机——完全合规的程序画面行为也不确定）、验证层自身覆盖缺口或版本滞后。区分清楚：GPU 的问题是真的，但不是验证层漏判了它职责内的东西——它的"无告警"承诺的是规范合规，不给具体硅片作保。

## §6 本项目口径

- V1 四态记录（缺陷文档 §10）里"已验证无告警"的含金量 = 执法者确认无此类违规；**裸奔的运行一律记"不构成证据"**。
- 同步验证在 Context 与探针内常开（`context.rs`/`timeline_probe.rs` 的 `VkValidationFeaturesEXT`），3.4 帧时间受限时一行降级。
- 3.3 bindless 起启用 GPU-AV 档位。
