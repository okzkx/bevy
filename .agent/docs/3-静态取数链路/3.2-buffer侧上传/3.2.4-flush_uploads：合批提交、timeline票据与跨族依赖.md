# 3.2.4 flush_uploads:合批提交、timeline 票据与跨族依赖

对应[施工 3.2](README.md)任务 3.2.4(含 3.2.4.1~3.2.4.4)。代码落位:`ash_renderer/src/vulkan/uploader.rs`(`Uploader` / `UploadBatch` / `Ticket` / `StagingCopy` / `CopyRegion` / `Release`)为机制本体,`ash_renderer/src/upload.rs`(`AshUploadPlugin` + `flush_uploads` 系统)为 bevy 编排。任务口径:一次合批一个 staging 范围 + 一次 transfer 提交;票据、依赖、复用、失败与退出四个子项分别收账。

**状态:已实现并验收(2026-09-24)。**探针四组 + App 实跑全程验证层 + 同步验证零 VUID;跨族 release/acquire 在本机专用 transfer 族上全链实跑。

## §1 定案(对应四个子项)

### 3.2.4.1 提交与票据

- transfer 命令池归 `Context::transfer_queue_family_index`([3.2.1](3.2.1-Context扩展：transfer队列族与timeline信号量开关.md) 定案的族);本机 RTX 2060 = 专用 transfer 族(族 1,无 GRAPHICS),同族回退机型与图形提交同队列(合批退回)。
- **票据语义**:提交成功后 signal timeline 信号量的新值 `next_ticket`(从 1 起单调 +1,满足 VUID-VkSubmitInfo-pSignalSemaphores-03242"signal 值须大于当前值");timeline 进提交按 VUID-VkSubmitInfo-pNext-03239 挂 `TimelineSemaphoreSubmitInfo`(VUID-03241:signalSemaphoreValueCount == signalSemaphoreCount)。
- **空批次不提交**:无 staging 写、无拷贝 → `Ok(None)`,不留无人 signal 的票据。
- **失败不发布虚假票据**:reset/录制/提交的任何失败都在改写 `next_ticket` 之前 `?` 早退——票据号不发、槽位不占、驻留不登记(编排层只在 `Ok(Some(ticket))` 分支 commit)。
- 提交不挂 fence:完成只由 timeline 表达,等待只发生在消费点(见下)。

### 3.2.4.2 依赖

- **接口定案**(面板口径):保留旧 SubmitInfo + `TimelineSemaphoreSubmitInfo`,不启用 synchronization2,全程不混用 submit2/barrier2(设备创建也从未开它)。
- **同提交内写后读**:uploads 与 device_copies(迁移/回读)之间按池逐 buffer 挂 `TRANSFER_WRITE → TRANSFER_READ` 屏障(barrier 必须挂具体 buffer,null 非法)。
- **跨族所有权(EXCLUSIVE,旧式)**:本机有专用 transfer 族,拷贝在 transfer 队列、图形消费在 graphics 队列——上传批末尾对"图形要读的池"记录 **release**(src=transfer 族,dst=graphics 族;规范明言 release 的 dstStageMask/dstAccessMask 被忽略,填 BOTTOM_OF_PIPE/空只满足旧式屏障掩码非零前提,sync.adoc §Queue Family Ownership Transfer)。配对 **acquire** 记在图形族提交:src 阶段用 ALL_COMMANDS(规范:acquire 第一作用域为空,happens-before 由 ALL_COMMANDS 引入)、srcAccessMask 置空(同被忽略)、dst 是真实访问(TRANSFER 读)。
- **M2 现状的诚实边界**:3.2 帧循环只清屏,图形尚不消费池数据——正常路径 `releases` 为空、App 无 acquire;release/acquire 成对机制由探针组 D 全链实证,3.4 接 draw 时按同一形状接线。同族回退(无专用 transfer 族设备)无 ownership 转移,但"等票据 + TRANSFER→消费屏障"的内存依赖仍在,同族形状由 memory_probe 组 A 闭环覆盖(零 VUID);同族机上的 release/acquire 路径本机无硬件载体,注明未实测。
- **等待点语义**:等待发生在 GPU 执行依赖处——图形提交把票据信号量挂进 wait 列表(ALL_COMMANDS 阶段),CPU 不阻塞等上传完成再提交(施工计划 §2)。

### 3.2.4.3 复用

- staging 与 transfer 命令缓冲按 **2 槽轮转复用**,不逐批新建对象;每槽记住最后提交的票据,复用前查 timeline 计数,未完成则 CPU 等待——"按完成票据复用资源所需的 fence/timeline 等待是正常同步"(判定线 6),每次等待有日志。
- 槽位 staging 按需扩容(整槽销毁重建):重建只发生在"该槽上批票据已完成"之后,旧数据无在飞引用。
- 池区间的覆盖/回收由[容量维护](3.2.2.3-容量与销毁：显式维护迁移与停顿分账.md)的等待纪律承担(bump 模式正常路径不覆盖任何旧区间)。

### 3.2.4.4 失败和退出

- **失败路径的结构保证**:submit_batch 里任何 `?` 早退都发生在 `next_ticket += 1` 与 `slot.in_flight = Some(ticket)` 之前——不发布票据、不占槽、不登记驻留;"等无人 signal 的 fence/timeline"死锁面从结构上不存在(App 层 Vulkan 失败按 Tier② 冒泡退出,与帧循环 D2 同款纪律)。
- **退出排空**:不在本模块等——`teardown_vulkan` 的 `device_wait_idle` 先于一切资源 Drop(D4 定案,验证层对销毁条款的执法面);Uploader/MeshPool 的 Drop 只拆对象,与 `GpuBuffer::drop` 同边界。

## §2 机制

### 2.1 一次合批的形状

`UploadBatch = staging(整批字节) + uploads(staging→池分段) [+ device_copies(迁移)] [+ releases(异族挂点)]`。App 的 `flush_uploads` 每帧把"未驻留且已到货"的资产转换结果连续排进一个 staging 范围,每资产两段拷贝(顶点/索引);**一次 queue_submit** 对应全部资产——不逐资产/逐批新建 staging、不碎提交。FlightHelmet 6 资产实跑就是单批 #1 完成。

### 2.2 CPU 等待只在三处,且各有账

| 等待点 | 触发条件 | 账 |
|---|---|---|
| 槽位复用 | 该槽上批票据未完成 | 复用安全(3.2.4.3),每次有日志 |
| 池维护 | 迁移前等全部在飞 + 迁移后等迁移票据 | 维护停顿(3.2.2.3 分账) |
| 探针/验证 | 读回校验前等票据 | 证据采集,不属运行路径 |

逐批上传路径上没有 CPU 等待(README 验证 3);GPU 侧等待(3.4 图形提交 wait 票据)是执行依赖,不是 CPU 阻塞。

## §3 探针与证据

`cargo run -p ash_renderer --example upload_probe`(2026-09-24,RTX 2060,API v1.3.289,验证层 SDK 1.4.357.0 + 同步验证,**全程消息零条**):

- **组 B(上传闭环)**:两资产分两批,票据 #1/#2;四段(顶点/索引 × 2)pool→readback 读回逐字节一致;重复快照零提交、票据停在 #2;账本行引脚 vertex_base/first_index 就位。
- **组 C(维护)**:见 [3.2.2.3 §3](3.2.2.3-容量与销毁：显式维护迁移与停顿分账.md)——迁移批耗 #2、资产批拿 #3,单调序列共用。
- **组 D(跨族,3.4 预演)**:上传批 #1 末尾 release 顶点池给 graphics 族 → graphics 提交(wait timeline #1 @ALL_COMMANDS + acquire + pool→readback 真实读 + fence)→ fence 完成后宿主读回逐字节一致。EXCLUSIVE 成对 release/acquire 在同步验证执法下全链跑通,CPU 未阻塞等上传(等待在 GPU 依赖处)。
- **App 实跑**:`上传批次 #1:资产 6 个,顶点 1772544B / 索引 1136664B 进池`(与采集统计逐字节吻合)→ `静态资产全部驻留` → 后续帧零批次;验证层 WARNING/ERROR 零条;退出(SIGTERM)无残留告警。

**施工插曲(保留)**:首跑读回全零——`submit_batch` 录制了拷贝却从未把批内容写入 staging(漏一行 write)。修复:staging 落盘收在 submit_batch 内、录制之前,调用方没有"忘记写入"的入口(与 3.2.2.1 把 flush 收进 write 同一思想)。探针在读回校验上抓出交付代码缺口,是验收工具在工作的证据。

**未实测边界**:① 槽位复用的**实际阻塞**分支(GPU 快于 CPU 时计数已达标,wait 未阻塞)——代码路径存在,等待语义由 completed/wait_until 的完成判定覆盖,阻塞时长依赖设备速度,不以零等待冒充"无等待";② 同族机的 release/acquire 回退路径(见 3.2.4.2);③ 非 coherent staging 的 flush 分支(承 3.2.2.1 未实测边界)。

## §4 边界

- **不做图形提交**:图形消费等待点(挂票据进 wait 列表)在 3.4 的 `record_frame` 里接线,本任务只留 `ticket_semaphore()` 出口与探针预演。
- **不做贴图**:image 拷贝、布局迁移、描述符是 3.3 的上传路径,可与本票据共用但不机械复用屏障(施工计划 3.3 §2)。
- **性能不做承诺**:专用 transfer 队列的并行收益需实测(README 待决问题),本段只保证正确性与合批形态,不宣称复制已与图形硬件并行。
