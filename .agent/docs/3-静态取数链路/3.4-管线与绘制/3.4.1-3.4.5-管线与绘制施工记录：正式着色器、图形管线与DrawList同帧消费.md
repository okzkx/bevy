## §0 总回应：面板要什么，交付了什么

面板把 3.4 定义为"第一次在正式帧循环画出完整 FlightHelmet"，五个任务（着色器与布局 / 图形管线 / 深度附件 / record_frame / DrawList）加三项前置闸门。交付状态：五任务全部完成，三项闸门全部核过；宿主实跑六 primitive 受光画出，全程零 VUID/WARN；非均匀缩放+旋转、resize、最小化、退出码 0 全部回归通过；主计划"目的"句（第一次画出完整调试模型）兑现。

有两个任务在施工中**反转了我开工时的预设**——任务 3.4.2 的"明确 Vulkan viewport Y"查出正高度直出才是对的（教科书直觉的反例），任务 3.4.5 的跨族接线从"补 release/acquire"改判为"拆掉让渡改 CONCURRENT"。这两处是本篇反思的重心（§3、§6）。

## §1 前置闸门：三项核验的回应

**①"既有帧同步缺陷已关闭，不继承旧承诺"**——核验方式：D1~D6 的修复在 3.2 已落库并有回归证据；本段用"是否还认得旧约束"来检验承诺是否真的放下：`record_clear_and_submit` 整个函数被重写为 `record_frame`（面板 3.4.4 明令），fence 重置仍在提交前一刻（D2）、颜色进场屏障仍罩住 acquire 读（D6）——**保留下来的不是"旧结构"，而是被论证过的同步语义**；被丢弃的是"清屏专用函数"这个形状本身。

**②"3.3 的 WGSL/binding/layout 已用小例子验证"**——核验方式：正式 shader `debug_draw.wgsl` 的 set/binding/push 接口与 3.3 前置闸门冻结表逐字段对照（§2），没有一行接口是 3.4 新发明的。这正是闸门存在的意义：3.4 施工当天没有再发生任何"接口层"纠纷。

**③"reverse-Z 成套"**——核验方式：投影来源（`get_clip_from_view`，bevy 无限反向透视）、深度清值（0.0）、比较算子（GREATER）三处同源落码，管线状态里找得到成套的三个值；不混 LESS 的检查在写管线状态时就近完成（§4.1）。

## §2 任务 3.4.1：正式着色器与数据布局

### 面板要求

vertex 做坐标变换，fragment 按索引采样并做简化光照，编译失败走 Tier②；Rust 偏移 / 矩阵乘序 / shader offset / push range 有统一表，不按 84B 估计上传；法线用正确的逆转置并验证非均匀缩放；贴图 sRGB 解码、线性光照、输出编码恰一次。

### 实现原理

**接口为什么原样沿用 3.3 的冻结表**：set0 b0/b1 runtime binding_array、set1 b0 每帧 UBO、`var<immediate>` push——这些不是本段的选择题，而是 3.3 用探针花了四道验收点买下来的已知合法形状。本段的义务是"逐字段沿用并核对"，不是"重新设计一遍再验证一遍"。这决定了 shader 的自由度只剩着色内容本身。

**push 96B 为什么必须三方互证**：主计划点过两个反例——旧估计 84B 是错的（自然布局 0/64/68/80、span 96B），`repr(C)` 和"低于 128B"都不能独立证明 CPU/shader 对齐。所以执法形态选了编译期：`pipeline.rs::PushLayout` 镜像 struct + `offset_of!`/`size_of` 静态断言（0/64/68/80、size 96），WGSL 侧字段顺序与之逐字对齐，pipeline layout 的 push range 声明 0..96——**任何一侧改动，断言先于画面报警**。运行时字节由 `pack_push` 按偏移常量手工排（与 mesh_convert 的 to_le_bytes 纪律同款），不赌平台内建序。

**法线为什么用 cofactor 矩阵**：需求是"逆转置且扛非均匀缩放"。第一反应是找 `inverse()`——WGSL 没有这个内建。退一步问数学目的：着色端需要的是 normalize(IT·n)，而 (M⁻¹)ᵀ 与 cofactor 矩阵只差行列式倒数这一个标量，normalize 后消失。于是不需要除法、不需要 inverse，每顶点 9 次乘 6 次减就得到正确法线，det=0（退化缩放）不在资产假设内。验证交给任务面板的"非均匀缩放"条款（§7.2 的临时缩放实验）。

**颜色空间链为什么这样排**：glTF loader 已按用途把 base color 落在 SRGB 格式（采样端 TMU 解码），着色器因此全程拿线性值做光照；编码的那一次放在输出端（见 §5.2 的 SRGB view 别名）——在中间任何一处手工 pow 都是重复编码。着色器里看不到任何 gamma 代码，正是"恰一次"的正面证据。

### 过程

- **编译坑**：第一版把 Rust 习惯（块尾裸表达式）带进 WGSL，naga 报"expected `;`"但裸 message 没有位置。先给 build.rs 的 WGSL 解析错误接上 `emit_to_string` 源码定位（这项改进留在管线里），重跑后 10 秒定位到缺 `return`。
- **build.rs 盲区**：补丁器对每个 wgsl 逐文件声明 `rerun-if-changed`，**新增** `debug_draw.wgsl` 不触发重编译（cargo 对"新增文件"无感知），`include_bytes!` 找不到产物直接构建失败。补目录级声明，两种触发并存。
- 非均匀缩放验证见 §7.2（临时系统，验证后已删）。

### 反思

1. "工具链的诊断质量是管线的一部分"——第一次正式着色器就把 build.rs 报错做厚，比第 N 次踩坑后再做便宜。
2. "数学需求先于 API 检索"——inverse() 没有时先问目的（normalize 消标量），解法比 API 更简单；反例是当初若硬上 CPU 侧传逆转置矩阵，push 冻结布局就要为 48B 的 normal matrix 重开一张表。

## §3 任务 3.4.2：图形管线

### 面板要求

dynamic rendering、颜色/深度附件、动态 viewport/scissor、正确 vertex input；reverse-Z 成套（clear 0 + GREATER）；**明确 Vulkan viewport Y、front face 和顶点绕向**；先关背面剔除，验证后再开变体。

### 实现原理（状态选型的依据）

- **reverse-Z 成套**：投影是 bevy 的无限反向透视（近平面 → depth 1），所以比较必须 GREATER、清值必须 0，三者是一个语义包；混入 LESS 的结果不是"测试不太对"而是近远景全反。
- **动态 viewport/scissor**：尺寸随 swapchain 逐帧给，重建不动管线——这是"重建成本转移到每帧两个 cmd"的取舍，买的是 resize 零管线重建。
- **剔除关闭**：M2 场景里 HoseMat 是双面、镜片按不透明覆盖，且（后见之明证实）绕向在本机未被 viewport 镜像——cull NONE 是三者齐备前的诚实默认，不是遗漏。

### 过程：朝向风波（本段最大的一次反转）

**现象**：首跑画面上下颠倒（底座在上、盔体悬垂）。

**当时的预设**："Vulkan NDC 的 Y 向下、要翻转"——来自教科书和 wgpu-hal 源码注释（`height: -rect.h // flip Y`）。既然"该翻转而没翻"，我加了负高度。**更糟了**：负高度渲染同样上下颠倒（与正高度互为翻转），说明颠倒根本不是"缺一次翻转"，而是**翻转这件事本身不该发生**。

**逐环节取证**（每步只排除一个变量）：
1. E4 应用侧取证：真实 `view_proj` 把世界上方映到 NDC +1.25——矩阵是 Y-up（与 glam 源码 directx 变体的文档一致，`bevy_math` 重出口就是这个模块）；
2. **E5 光栅级实验**：顶点着色器直出已知 clip 坐标（`vec4(position.xy * 0.8, 0.5, 1.0)`，绕过全部矩阵）——正高度 viewport 下模型 +y 落屏上方。矩阵变量被排除，结论落到光栅化环节本身；
3. **官方对照**：官方 `color_grading` 示例（同 FlightHelmet、同取景）wgpu 渲染同法截图，与我们正高度渲染**同向**；
4. 反例：负高度在 E5 下同样翻转。

**定案**：正高度 viewport 直出，不做翻转；"教科书直觉"在本机不成立，以实测为准。证据链五张截图入档。

**一个没解释通的东西，如实记录**：wgpu-hal 30.0.1 对 Vulkan 用负高度且注释写明 "flip Y"，与本机实测相反——wgpu 栈内必有别处补偿（或其 NDC 约定有变），没有深挖。施工记录不装作解释通了这件事；将来任何镜像/颠倒类症状先回这一节。

### 反思

1. **"预设错在哪"比"哪改对了"值钱**：我开工时写进管线注释的第一版就是"负高度翻转"（自信来自教程和 wgpu-hal），首跑被画面打脸。四条独立证据（规范公式转述、glam 源码、E5、官方对照）里，**最硬的是 E5**——它把矩阵、UBO、shader 全部排除，只剩光栅语义。教训：跨栈的坐标约定之争，用"直出已知值"的实验裁决，不靠引用（包括引用规范转述）。
2. **规范的引用要分级**：排查中我引的"Vulkan NDC -1 映顶"其实是模型转述的规范公式，与实测矛盾；当时正确的一步是承认矛盾而不是找理由调和。依据要么逐字核实，要么标注"未核实"——半信半疑的依据不能进定案。
3. 前置闸门第③条"朝向成套"的真正风险不是"忘写 GREATER"（这种错验证层和画面都会抓），而是**直觉性翻转这类"看起来就是常识"的预设**——闸门挡不住它，只有画面能。所以面板把"明确 viewport Y"写成任务而不是闸门，是对的。

## §4 任务 3.4.3：深度附件

### 面板要求（待决两条原文）

"按帧槽还是图像索引分配：本段按实际提交访问确定，**必须有同步证据**"；"数量按在飞访问设计，或显式同步复用，不把'生命周期归 Swapchain'当成无读写冲突证明"。

### 实现原理与论证（为什么是帧槽）

两个候选的冲突模型完全不同：

- **图像索引**（每张 swapchain image 配一张深度）：安全性依赖一条外部推理链——"重新 acquire 到 image N ⇒ present engine 已消费完 present(N) ⇒ 渲染(N) 已完成 ⇒ 深度图无并发引用"。成立，但它是**动态时序推理**，且依据在 WSI 内部（present engine 行为），不在我们能引用的同步原语里。
- **帧槽**（每帧槽一张）：在飞两帧各用各的深度（并发写结构性不可能）；同槽重用之间隔着 `wait_for_slot` 对帧 fence 的等待（signaled = 全部命令完成）——**证据是代码内可见的同步原语**，且复核发生在录制之前，CPU 侧可断言。

面板警告"不把归 Swapchain 当无冲突证明"——帧槽方案恰好把证明材料从"生命周期归属"换成了"fence + 槽位隔离"。选帧槽。

**布局纪律的语义**：每帧 UNDEFINED→DEPTH_ATTACHMENT_OPTIMAL——UNDEFINED 作 oldLayout 是"旧内容不要了"的声明，与 loadOp CLEAR 配套；storeOp DON'T CARE，深度从不读回，出场屏障不存在。D32_SFLOAT 支持先查后用（1.3 mandatory 仍不省查询，证据落日志）。重建：`rebuild_depth` 幂等（extent 不变空手而归），销毁前自带 device_wait_idle——在飞帧可能还引用旧深度，与 swapchain 重建同纪律。

### 过程

resize 回归实测了重建链：SetWindowPos 到 900×620 → swapchain 重建日志 + 深度附件 ×2 重建 + "随 swapchain 重建"日志 → 新尺寸下照常画出（截图入档）。

### 反思

同步设计的证据有强弱之分：**"结构上不可能"（槽位隔离）强于"时序上必然已完成"（acquire 链推理）**——前者是静态事实，后者是一条跨 present engine 的推理链。写代码时选前者，不是因为后者错，而是因为后者的每一步都要靠"相信规范/驱动的某句话"成立。这个分级以后适用于所有"要不要加一层隔离"的决策。

## §5 任务 3.4.4：record_frame（清屏生长为绘制帧）

### 面板要求

接上传票据、必要的屏障、清屏、直接 draw 与提交；**错误返回前保持 fence/信号量/资源状态可恢复，否则优雅退出**；"不能为了保留旧函数结构而保留错误顺序"。

### 实现原理

**录制序的每一段都有归属**：颜色进场屏障（D6 形状：srcStage=COLOR_ATTACHMENT_OUTPUT 罩住 acquire 的读）→ 深度进场屏障（§4）→ dynamic rendering（loadOp CLEAR 清屏 + 逐 draw）→ 颜色出场屏障 → 提交。

**跨队列等待点**：提交的等待列表是 `image_available @ COLOR_ATTACHMENT_OUTPUT` + 上传票据 timeline @ ALL_COMMANDS。设计意图是施工计划 §2 的原话——"等待发生在 GPU 执行依赖处，不要求 CPU 先阻塞等上传完成再提交"：图形命令缓冲在 CPU 侧立即录完、立即提交，GPU 在 ALL_COMMANDS 处等 timeline 值到位；这一条内存依赖同时收口 transfer 写对池/贴图的可见性（CONCURRENT 下没有所有权屏障，全部指望它——§6）。票据值为 0（从未上传过）的形状分支保留但不可达（fallback 批在 init 提交），是"0 值不可等待"条款的显式化。

**错误可恢复性的边界**：帧首等待/重置失败 → Tier②；acquire OUT_OF_DATE → 重建重试（fence 未动，状态可恢复）；acquire 成功之后的任何失败 → Tier② 优雅退出（D2 定案：那时同步状态无法原样恢复，warn-继续是死锁面）。record_frame 内部不新增提前返回——fence 重置到 submit 之间保持零返回点。

### 过程与反思

面板点名的"不能为保留旧结构而保留错误顺序"在本段的对应动作是**直接替换函数**而非包装扩展：`record_clear_and_submit` 删除，`record_frame` 承接其全部同步纪律。反思：3.2 冻结的"责任边界"（上传完成/图形消费/退出排空的时序契约）在本段全部兑现且无一处需要破坏——前置闸门③当时说的"先关前置同步缺陷，不能为了保留旧函数结构而保留错误顺序"，实际施工中一次也没有被迫违反。

## §6 任务 3.4.5：DrawList 同帧消费（含本段最大的排障）

### 面板要求

PostUpdate 传播+采集，Last 准备并提交；拓扑快照不跨 CPU 帧；M2 可逐 draw push constants；**六 primitive 用明确的不透明调试策略并记录材质覆盖，不丢弃镜片**。

### 实现原理

**组装管道**：快照行（entity + 双柄 + 终值矩阵）× 三本账——MeshPool 驻留引脚（vertex_base/first_index/index_count）、`Assets<StandardMaterial>` 的 base_color（**to_linear 后直进 push**，与采样端解码互补）、ImageCache 槽位（缺 base color 贴图走 fallback 槽 0——面板给的选项是"有效 fallback 或暂缓"，贴图缺不拦几何；mesh/材质未驻留才整行暂缓，Tier① 下帧重试）。逐 draw `cmd_push_constants`（96B）+ `cmd_draw_indexed`（池整绑一次，引脚走 vertexOffset/firstIndex）。

**相机进 UBO**（3.5 任务 1 的"相机"半件提前）：`get_clip_from_view() × view`，写本帧槽 UBO 的时机在 wait_for_slot 之后——在飞安全由帧 fence 担保，3.5 的"复用前等对应帧使用完成"对相机部分已生效。

### 过程：Draw-09600 三轮 bisect

**现象**：首跑 14 条 VK-ERROR，全部是 VUID-vkCmdDraw-None-09600（draw 的描述符布局断言：描述符声明 SHADER_READ_ONLY，验证层账本停在 TRANSFER_DST）。三个反常：acquire 屏障自身零点名（说明 release/acquire 配对被接受）；错误数逐跑波动（9/10/12+2，与批次到达时序相关）；错误集合 ≈ "已发布贴图 − 被采样的 base color"（约 15−6）。

**受控实验**（每轮只动一个变量）：

| 轮 | 假设 | 改动 | 结果 |
|---|---|---|---|
| E1 | binary 信号量在等待列表 index 0 抢占票据链接 | 票据挪第 0 位 | 依旧报 |
| E2 | 混合等待列表破坏跨队列链接 | 等待列表只留 timeline | 依旧报（还引出 WRITE_AFTER_PRESENT 族，反向确认 acquire 等待不能省） |
| E3 | 在飞 release 的时序账本问题 | 录制前 CPU 等全部票据完成 | 依旧报——**账本根本不认 release** |

**定性**：验证层对 UAB 数组"已写入但未被访问"的元素做保守 09600 断言，而其布局账本在 EXCLUSIVE 让渡形态下不更新。**修复的取舍**：关同步验证 = 烧掉裁判，不做；改 CONCURRENT 双族共享 = 结构上消掉所有权让渡，release/待办账本整套删除，图像屏障族号一律 IGNORED（CONCURRENT 上显式族号本身又被 VUID 拒，首跑实抓）。可见性改由票据信号量收口，跨队列故事与 buffer 池统一。EXCLUSIVE 成对语义的机制实证保留在 image_probe 组 C 不删。

**同轮另收**：swapchain 少挂 `MUTABLE_FORMAT` 旗标（§5.2 的三件套由此补齐）。

### 材质覆盖的回应

调试覆盖报一次即歇：六 primitive 全部不透明——blend 关、unlit 标志忽略、统一调试 Lambert、镜片照画不丢弃。**一个如实记录的观察**：面板预设"镜片是半透明的"，实测 6 行 base_color.alpha 均 =1——glTF BLEND 的半透明经 bevy_gltf 转换后并不落在 alpha 上。不硬凑"覆盖了 BLEND"的故事，把实测写进记录；生产材质差异的完整对照本来就是 3.5 的受控条件。

### 反思

1. **探针的"全绿"只对它测过的形状负责**。image_probe 组 C 验证了"release → 等票据 → acquire → **拷贝读回**"，全绿；生产是"acquire 后**经描述符采样**"——形状差一环，这一环在生产首跑才暴露。正确姿势是把探针升级到与生产同构（补一个采样读回组），而不是让宿主首跑当探针。"探针先于生产"的纪律不止于"跑过探针"，而是"探针覆盖了生产的消费形态"。
2. **验证层报错的两条出路里，永远选改结构的那条**：绕过或调弱验证，等于下次出错时没有证人。
3. 错误数波动本身就是线索——稳定复现的错误通常指向确定性 bug，波动指向时序/批次——我到第三轮才把这个波动当主线索，前两轮在"链接形状"上空转。下次排障先问"什么在跑与跑之间变化"。

## §8 反思总账（跨任务的沉淀）

1. **探针形状要覆盖生产消费形态**（§6 反思 1）——"探针全绿"与"生产合法"之间隔着消费方式这道墙。
2. **实证对预设的裁决权**（§3）：四个独立证据一致时，书本知识（含规范转述）必须让位；反过来，定案里解释不通的部分要如实挂账，不能顺手圆上。
3. **同步证据分强弱**（§4）：结构隔离 > 时序推理。
4. **验证层是裁判不是绊脚石**（§6）：09600 的弯路恰恰花在"想绕过账本"而不是"读懂账本为什么不记"。
5. **结构性事实要编译期执法**（§2）：offset 断言、usage↔format-feature 查询，都是"改错先报错"的形态。
