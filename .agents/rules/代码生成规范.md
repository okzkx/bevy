# AI 代码生成规范

> 本规范是本仓库 AI 生成和修改代码时的默认约束。模块分组条款适用于 `ash_renderer` 的新增与整理代码；修改 Bevy 上游代码时，遵循对应 crate 和模块的既有约定，不机械套用项目结构。

## 1. 通用文档规则

### 1.1 先说机制与判定线

- 先说明代码实际做什么、由谁调用、数据或控制流经过哪里，再使用比喻或概括。
- 将核心不变量、决策依据或验收标准放在前面；细节用于支撑结论，不让读者从零散材料中自行归纳关键规则。
- 围绕读者理解和执行所需的问题组织内容，不按作者的写作过程堆叠材料。

### 1.2 明确事实状态与证据

- 区分**当前代码事实**、**已定设计**、**建议方案**和**待验证事项**。计划、假设、驱动器行为或单次运行结果不能表述成已验证结论。
- 涉及实现时给出准确的源码路径、类型或函数；涉及测试时说明实际执行的命令及结果。没有执行或无法复现的检查要明确说明，不得暗示通过。
- Vulkan 合规性、同步和资源生命周期等结论，以代码路径、规范约束和验证证据支撑；“能运行”本身不等于行为正确或符合规范。

### 1.3 精简但不丢信息

- 同一事实只完整说明一次；删重复表述，不删理解机制或正确操作所必需的条件、边界、失败分支和证据。
- 术语与代码对应，命名和路径保持可核验；新术语先解释再使用。
- 文档只覆盖本次主题，不复制路线图、施工历史或已有权威规则全文；需要上下文时引用其入口。

## 2. 模块分组规则

### 2.1 按抽象层次与变化边界分组

- 根据项目自身的抽象层次划分模块组，使同一组内的代码在概念上内聚，并围绕可说明的边界协作。
- 以依赖关系、生命周期、变化原因或数据所有权作为分组依据；不按文件数量、行数或表面整齐机械切分。
- 上层可以组合下层能力；底层不反向依赖上层，也不直接读取上层内部状态。整体依赖保持单向、无环。
- 跨组交互通过窄接口或明确的数据契约完成。对外能力由模块边界统一组织，避免调用方耦合到无关的内部文件。
- 共享基础设施只放确实跨组复用、且不承载特定业务流程的能力；不得以“可能复用”为由提前抽象。
- `mod.rs` 用于组织模块边界、说明必要的依赖关系并暴露所需接口；新增子模块应对应真实边界，而非拆分本身。

### 2.2 公开主体类型与文件归属

- 新增具有独立职责的 `pub struct` 时，以该类型为主体单独建立一个 `.rs` 文件；文件名使用与主体对应的 `snake_case`。
- 只服务于该主体类型的 private `struct`、辅助函数和实现放在主体文件中，不为私有辅助项单独拆文件。
- 只有当辅助类型被多个模块共享，或形成独立维护边界时，才考虑提取；拆分应体现真实的职责、依赖或生命周期边界。
- 纯函数、系统函数或职责模块若没有合适的公开主体类型，按职责组织即可；不得为了套用“一类型一文件”而虚构 `pub struct`。
- 该规则约束新生成和新整理的代码，不意味着现有一个文件含多个公开类型的代码已违反要求，也不构成全量拆分旧文件的授权。对既有结构做迁移应限于用户要求的范围。

### 2.3 核心代码精简：重复模板下沉公共层

- **核心代码（业务流程本体）尽可能精简是硬要求**：重复出现的模板代码（判空冒泡、一次性收账、日志去重、参数束等）下沉到 `common` 工具层成标准件，核心现场一行调用——这是代码分层的思想：标准件住工具层，业务现场只表达"发生了什么"，不复制"怎么做"。
- 模板方法尽可多写；同一模板在核心代码出现第二次即考虑下沉。用户已两次定稿此原则（2026-10-10 错误处理一行化 + OnceLog 收账下沉）。
- 下沉时机仍守 §2.1 的"确实重复才抽象"：已重复的模板必须下沉，但不得以"可能复用"为由提前造标准件。
- 判据：评审核心代码时，凡是"机械重复、与业务含义无关"的行（样板），都应能指到一个公共标准件；指不出来的就是待下沉候选。

## 3. 代码注释规则

> 适用范围与模块分组条款相同：约束 `ash_renderer` 的新增与整理代码；对既有注释的批量校验按本节作为验收口径（2026-09-29 host 拆分提交 10ebaea2f 为首次批量应用）。

### 3.1 两纪律：写内容与坑点，不写历史与原理

- 注释写给"下一个修改这段代码的人"，只放两类信息：
  - **内容**：代码当前做什么——职责边界、执行顺序、调度住址、失败后会怎样（一句话，如"任一步失败直接报错退出"）、不明显决策的一行理由（幂等、去重、"多设无害"等）。
  - **坑点**：踩过的坑必须留住——症状在哪、为什么坏、对策是什么（如最小化死锁、present 次优、fallback 槽 0）。坑点不随结构整理删除。
- 不放三类信息：
  - **时间标识**：日期、"暂时/目前"类 tracer。
  - **历史叙事**：排障编号（D 编号）、施工步骤号（"3.4.5 起""3.6.1 拆分自"）、出处引用（"抄自 frenderer/bevy_time"）。来历归提交信息。
  - **复杂原理**：深度机制讲解归 `.agents/docs/` 知识库文档，注释不重写原理；可留现行文档指针，失效链接要清。

### 3.2 注释必须与代码同真

- 注释是代码现状的镜像：改动注释所描述的行为或事实时，注释在同一提交内同步更新。
- 失真或过时的注释按最高优先级订正——错误注释是"错知识"，优先于结构整理（实例见 3.6 盘点 P0 批次：负高度旧说、UBO 64B 旧值、teardown 归属过时）。
- Vulkan 同步证据必须在代码内可见：屏障注释写明"谁罩谁、内存依赖在哪收口"，不采信跨 present engine 的时序推理（细则以渲染器实现规则正本 §4/§6 为准）。

### 3.3 写法：短、白话、只讲一次

§3.1 管写什么，本节管怎么写。判据：注释要能帮读者看懂或改对代码，做不到的就删。

- **名字已说明的不写**：类型名、函数名已经说明"它是什么"的，不再复述；代码一眼看得出的步骤不复述。
- **说大白话，少用术语**：项目内部代号（Tier②、看门、闸门③、统一通道等）一律换成直白说法；Vulkan 专有名词只在坑点确实需要时出现（如 VUID 编号，便于搜索）。
- **一条一到两行**：重要信息压成一两行。坑点写成"会出什么事 + 怎么避"，以"坑："开头，方便检索。
- **同一件事只讲一次**：放在最该被看到的位置（函数文档注释或依赖发生处）；文件头不复述函数注释，相邻注释不互相重复。
- **逐项理由收成总规则**：一组同类理由（如拆除顺序逐项解释）收成一条规则，放在表头或段首。
- **隐式顺序依赖在依赖点标出**：编译器管不住的顺序约束，在相关的那一步写一句（如"会提交上传"），让调整顺序的人能看到。
- **裸数字标含义**：魔数参数在行尾注明含义和单位。
- **日志和错误消息不算注释**：运行时输出的字符串不受本节约束，要改另行处理。
- **精简不删坑点**：删掉的说明若是坑点，要么在别处已有完整记录并留一行指针，要么压成一行保留。

范例：`ash_renderer/src/driver/host/init.rs`（注释从约 130 行精简到约 35 行，代码零改动）。

## 4. 已有专属规范

- 错误处理遵循项目的两 Tier 原则与统一错误通道：非必要不 panic；可丢弃且不影响运行的错误就地 log 继续，影响运行的错误按签名 `Result<(), BevyError>` 冒泡（判定线与糖家族见 `.agents/rules/System错误处理规范.md`）。
- `ash_renderer` 的 Vulkan 接口布局、同步、资源生命周期、验证层与施工验收等细则，以项目渲染器实现规则正本及 `.agents/docs/` 中对应专题文档为准；本规范不重写这些领域规则。
- Rust 格式和静态检查遵循仓库根目录 `rustfmt.toml`、`Cargo.toml` 与 `docs/linters.md`。
