# /plan-execute：按施工计划开工（临时分支 → 实施计划 → 写文档 → 提交 → 测试 → 修复）

把一份已立案的施工计划变成临时分支上的成套改动：代码 + 施工记录 + 状态同步 + 判定线验证。计划是唯一施工依据。本 Skill 不立案（立案走 $doc-plan-register）、不并回主干（并回由用户拍板，流程见 merge-chain）。

## 输入与边界

- 输入：施工计划文档路径，或段号（按号在 `.agents/docs/` 下定位 `N-步骤/N.M-段/施工计划：*.md`）；定位不到就停下向用户要，不擅自代立计划。
- 铁律：调用 /plan-execute 即视为授权在临时分支上按任务粒度分组提交；**推送、并回 develop、删分支不在授权内，收尾后留待用户拍板**。
- 纪律引用（不重复正文）：编号与落位见路线图"编号约定"与入口篇 §九（N.M.K 只增不复用）；提交纪律见 $auto-commit；新文件 UTF-8、CRLF、无 BOM，rust 源码 LF；文件名冒号全角。

## 阶段一：临时分支

1. `git status`：有未提交改动先列出并停下确认归属，不擅自 stash/丢弃。
2. 从当前分支 HEAD（通常为 develop，应已含该计划立案提交）建并切换：`git switch -c goal/<段号>`（如 `goal/4.1`；无段号用计划标题短横线化），报告起点 SHA。
3. 同名分支已存在则 `git switch` 接续（跨会话续工），不重建、不复位。

## 阶段二：实施计划

1. **重读计划全文**与计划边界里"开工前先读"的底座文档——用户会话外改文档属常态，禁止凭记忆施工。
2. 开工动作：按计划"任务拆解"建/转段 README 任务面板（计划已注明"开工时转段 README 任务面板"）。
3. 按计划给定顺序逐任务写代码：保持编译通过，随做随做轻量自验；发现计划未覆盖的结构问题，在被后续段依赖之前先向用户提出，动不动由用户拍板。

## 阶段三：写文档

1. 每任务一篇施工记录 `N.M.K-标题.md` 入段目录，写"实际做了什么"与待决项钉明结果；计划文档只流转状态，不回写实现细节。
2. 状态流转：计划头部、段 README、路线图三处同步（⬜ 已立案 → 施工中 → ✅ 收官；标记用词先看路线图现行写法再落笔）。

## 阶段四：提交

- 按 $auto-commit 纪律分组提交到临时分支：docs（施工记录/README/路线图）与 feat（代码）分开；只提交本任务产物，不推送。

## 阶段五：测试

1. 按计划"测试方案"节逐项执行；计划未写测试方案的，按判定线逐条设计最小验证。
2. 手段按《测试规范与方式》三级递进：BRP Remote 首选（`tools/brp.py`，需要新写操作优先扩自定义方法族）→ 打 Log 重编译 → 鼠标注入仅限用户声明无人模式。
3. 画面类判定线按《画面功能视觉验证》执行（PrintWindow 截图 + 当前会话模型读图）；取证截图进根目录 `.temp/`，不入 docs。
4. 代码验证线 = 按目标 crate clippy 全净；整仓 `cargo fmt` 禁止（手工排版仓库）。
5. 回归：计划判定线 + 既有判定线零回退（计划有回归矩阵的照单全测）。

## 阶段六：修复

1. 测试暴露的问题在本阶段收口：修复 → 复测 → 补提交（同阶段四纪律），循环到判定线全过或如实报"未过"。
2. 修复牵出的结构取舍仍先提出后动手；修不动的列遗留项，不硬凑"已过"。

## 收尾报告

- 分支与提交：分支名、起点/终点 SHA、提交标题清单。
- 判定线对照：逐条 ✅/❌/未测 + 一句话证据；没测的明说没测，不把"应该能过"写成"已过"。
- 钉明与遗留：待决问题的落定、未决与顺延项。
- 临时分支留存待评审；并回/推送/删除由用户拍板；项目记忆 next 指针受影响则同步。

## 自查清单

- [ ] 全部施工与提交都在临时分支上，未碰 develop、未推送
- [ ] 每任务一篇施工记录（`N.M.K-` 前缀、冒号全角、CRLF），计划文档只流转状态未回写实现
- [ ] 提交 docs/feat 分组清晰，只含本任务产物
- [ ] 状态三处（计划头部/段 README/路线图）口径一致
- [ ] 判定线逐条有结论有证据，修复已复测，无"未测写成已过"
- [ ] 收尾报告完整，并回与推送留待用户拍板
