- **来源**：2026-10-10 用户增补（[3.13 Remote 虚拟鼠标](3-静态取数链路/3.13-Remote虚拟鼠标/README.md)收官之后）。3.13 交付了注入与自验闭环但画面上无虚拟光标——AI 在操作什么、点到哪里，人只能靠数值读回间接判断；登记为外置拓展，不回改已收官段。
- **内容**：在自研渲染器画面上叠加显示虚拟鼠标光标（2D overlay），实时反映 Remote 注入的光标位，让 AI 的虚拟操作对人可见、可录像。数据源现成：注入经官方通路自管光标位，`Window::cursor_position()` 直接可见（3.13 段 README 钉）。

### 3. 旋转拖拽松手后的欧拉显示连续性（2026-10-14 登记）

- **来源**：2026-10-14 用户实测反馈（[4.6 实测缺陷修复段](4-可靠增量链路/4.6-实测缺陷修复/README.md)收官之后）：拖"Y 轴"旋转松手时 X/Z 两框数值会突跳（±180°）。已核实**不是缺陷**——真实旋转（四元数、画面）恒等，松手瞬间面板从拖拽缓存（按下帧表示分支）切回 `to_euler(YXZ)` 规范分解（中间轴 X 被 asin 钉在 [-90°,90°]，越界由 X/Z 各 ±180° 等价吸收），与 Unity Inspector 同款行为；性质与处置建议已记录在[4.6 施工记录 §3 遗留](4-可靠增量链路/4.6-实测缺陷修复/4.6.1-4.6.2-实测缺陷修复施工记录：注释清扫与拖拽旋转闪烁.md)。用户要求消除"松手显示跳变"，当日拍板接受现状、外置登记。
- **内容**：让属性面板旋转三框在松手后继续显示拖拽期缓存的三元组（显示连续性），直到选中实体变化、外部途径改值或用户再次编辑，才回落规范分解读数；可选另一形态 = 松手时把缓存规范化回写显示。只动 egui 读数策略，不碰 `apply_transform_edit` 写路径与四元数本体。
- **恢复条件**：显示跳变实际干扰编辑体验（如用户在松手后要基于显示值继续微调、或读数对比教学场景需要连续读数）时捡起。
- **边界**：挂起期间姿态恒等是既有事实（4.6 判定线已验），本条只关"显示读数"不关"旋转正确性"；若实施，需钉明"缓存显示与 World 分解值不一致期间，面板读数不再逐字镜像快照"的新账面口径，并防外部改值（BRP/热重载）时的陈旧显示。

### 4. 场景内 Transform gizmo：点选、边缘高亮与中心坐标轴拖拽（2026-10-14 登记）

- **来源**：2026-10-14 用户增补（[4.6 实测缺陷修复段](4-可靠增量链路/4.6-实测缺陷修复/README.md)收官之后）。当前对物体的空间操作走属性面板数值框与 4.6 拖拽链，画面内没有直观的空间操作手段；登记为外置拓展，不回改已收官段。
- **内容**：三件套——①**点选**：鼠标点击拾取画面中的游戏物体（射线拾取）；②**边缘高亮**：选中物体以描边/轮廓方式高亮，让"选中了谁"在画面上可见；③**中心坐标轴 gizmo**：以选中物体中心出现三色坐标轴手柄，支持平移、旋转、缩放三种拖拽操作，拖拽结果写回实体 Transform（与属性面板读数联动）。
- **恢复条件**：需要 Unity 式场景内直观操作物体（点选即中、所见即所改），或属性面板数值拖拽不足以支撑演示与教学场景时捡起；挂起期间不阻塞任何段。
- **边界**：不承既有段判定线责任。开工时须钉明的点：拾取路线（CPU 侧射线求交 vs GPU 侧 id buffer 读回）、边缘高亮实现形态（pass 外描边 vs 后处理轮廓）、与 egui 指针仲裁的归属规则（gizmo 拖拽 vs UI 命中，沿用 `layer_id_at` 定案）；旋转拖拽须吸取 4.6 F24 教训（欧拉表示分支混写），拖拽态与面板读数的表示一致性另见条目 3。注意与"右上角坐标轴"需求（4.7 候选、屏幕空间姿态指示）是两件事：本条是场景内、随物体走的可拖 gizmo。

### 5. 着色管线模式升级：forward+ 光源扩展与 vis-buffer（deferred material）（2026-10-15 登记）

- **来源**：2026-10-15 问答沉淀（5.2 开工前，"GPU-driven 用什么管线模式 / vis-buffer 是什么 / G-buffer 与 vis-buffer 什么关系"三轮），知识正本=[笔记《渲染管线模式与 VisBuffer：GDR 的着色层搭档》](笔记/引擎/渲染管线模式与 VisBuffer：GDR 的着色层搭档.md)；登记为外置拓展，不进步骤 5 编号体系。
- **内容**：自研渲染器着色架构的两级升级路径——①**forward+**：加 clustered light 列表（光源按空间网格分桶，shader 现场索引），堆光源不动 GDR 基建；②**vis-buffer / deferred material**：几何 pass 只写三角形 ID+重心坐标，全屏 resolve 回表（bindless）现场算材质属性再光照——GDR 最深引擎（UE5 Nanite / id Tech / Frostbite）的共同形状。
- **恢复条件**：①光源数上量级（单方向光不够、需要多光源实时）时捡起 forward+；②出现海量微几何（cluster 光栅化）或高分辨率带宽压力、或决意走 vis-buffer 学习路线时捡起 deferred material。知识背景见正本笔记（管线模式与 GDR 正交、两种格式的存在前提与判据）。
- **边界**：挂起期间不进编号体系、不承判定线责任；步骤 5 的 compute 剔除/indirect 闭环**不依赖**本条（它们换提交方式不换着色层），当前单 pass forward（3.5）在 5.1~5.5 全程够用。实施 forward+ 须钉明与 set1 UBO 128B 冻结边界的关系（灯光数进表=解冻一次，照 5.1.1 解冻清单先例）；实施 vis-buffer 须先过 5.3 indirect 闭环，且按知识篇 §6 信号判据（"三角形 ID 表 + 全屏 resolve 消费"出现才算踩线）。

### 6. 虚拟纹理（VT）：页表 + feedback 驱动的页级流送（2026-10-19 登记）

- **来源**：2026-10-19 问答沉淀（"粗粒度/细粒度流送是什么"讲解后的追问——"虚拟纹理是不是也是流送"），知识正本=[笔记《虚拟纹理调研：页表、feedback 与流送》](笔记/渲染/虚拟纹理调研：页表、feedback 与流送.md)，该调研同日已定调"当前不立项"；登记为外置拓展，不进步骤 6 编号体系。
- **内容**：把 6.4 mip 级流送的驻留单位从"单资产的某级 mip"下沉到"全场景统一虚拟地址空间的 128×128 页"——所有贴图拼进一张巨大虚拟纹理，GPU 侧只留小容量物理页缓存 + 页表，采样走页表间接（miss 给低清回退），渲染后 feedback pass 实测上报实际采样命中的页、缺页下帧流进。与 6.3/6.4 的关系：6.3 是 chunk 级进出、6.4 是每张贴图自己管 mip 驻留，VT 是全局一本页表按页记账，收益前提=贴图总量远超显存且单帧可见页极稀疏。
- **恢复条件**：世界贴图总量大到 mip 级流送（6.4）扛不住、或步骤 7 正式场景出现单帧稀疏采样高分辨率贴图集的实际压力时捡起；届时 VT 替代的是 6.4 而非 6.3（chunk 级进出仍归 6.3）。知识背景见正本笔记（页表/feedback 机制与收益判据）。
- **边界**：挂起期间不进编号体系、不承判定线责任；步骤 6 的 6.3/6.4 流送段**不依赖**本条（mip 链 + blit 续批在 5.4 已就位，6.4 按整级 mip 流送即够用）。实施须钉明：feedback 读回通路（类似 6.1 Hi-Z 读回的边界问题）、页表与 5.1 常驻描述符布局的关系、页搬运走 6.3 的上传账面还是自建通道。
- **状态追记（2026-10-19 同日）**：6.4 细粒度流送已由用户拍板**转正立案**（[施工计划：细粒度流送拆解](6-高级剔除LOD与流送/6.4-细粒度流送/施工计划：细粒度流送拆解.md)——驻留单位下沉到**整级 mip 与 mesh LOD 档**，非 VT 路线）；VT 本体（页表+feedback）仍挂起本条目，恢复条件不变——6.4 整级粒度被压测证伪、或步骤 7 出现稀疏采样高分辨率贴图集压力时，VT 才按"替代 6.4"转正。

### 7. Virtual Shadow Maps：page 级虚拟阴影图（2026-10-20 登记）

- **来源**：2026-10-20 问答沉淀（步骤 8 管线形状定案 deferred + Clustered Forward 透明层当日，"shadow map 要不要上更 GPU-driven 的技术"讨论）。用户同日拍板：8.3 保持 CSM+PCSS 选型，shadow map 的 GPU-driven 性由"标记链 + build_indirect 逐 cascade"兑现（见[路线图步骤 8 节](学习目标实现步骤.md)），VSM 本体外置登记；与条目 6（VT）同族——都是"把驻留管理器在另一空间再写一遍"的缓存管理功法。
- **内容**：UE5 式 page 级虚拟阴影图——shadow atlas 按 page 缓存、GPU 侧判脏（page invalidation）只重画脏页、按需分配（sparse-ish），高分辨率 shadow map 不再随级联全量重画。与 8.3 的关系：替换的是"级联 shadow depth pass 的组织方式"，PCSS 滤波质量正交保留。
- **恢复条件**：步骤 7 正式场景出现阴影精度不足或"阴影重画风暴"（级联全量重画成本主导）、或决意练习"GPU 判脏页 + 页缓存"这套缓存管理模式时捡起；收益前提=场景有 Nanite 级密集几何或超高分 shadow map 需求（当前负载形态兑现不了 VSM 主要卖点）。
- **边界**：挂起期间不进编号体系、不承判定线责任；8.3 CSM+PCSS **不依赖**本条。实施须钉明：page 表与 6.1 深度资源的关系（复用金字塔底座还是独立 atlas）、判脏信号来源（几何变更账 vs 光源/相机移动）、page 分配与 4.4 回收账面的关系。
