# GPU 模拟计算：哪些纯数值模拟能整体搬上 GPU

一个 CPU 粒子池的一帧 update 通常长这样：位置、速度、寿命三个数组；job system（把循环切成任务块交给线程池并行执行）把下标范围分给几个 worker，每个 worker 遍历自己那段，读位置和速度，算 `v += a·dt`、`p += v·dt`、`life -= dt`，写回；最后再走一遍存活列表，把寿命耗尽的粒子删掉，或者打标记后压缩。线程池让这段循环用上了多核，但每颗粒子仍然要由 CPU 读一次、算一次、写一次，任务块之间要同步，压缩存活列表还要处理并发写。

同一批粒子放到 GPU 上，形状变了：位置、速度、寿命数组常驻显存；一次 compute dispatch（让 GPU 启动一批线程执行同一个 compute shader，即在 GPU 上运行的通用计算程序）里，一个线程只处理一颗粒子，读自己那一格，算完写回；存活列表的压缩换成一次前缀和扫描（先算出每个元素前面有多少个存活标记），再按新下标散射。CPU 这一帧只写发射率、风、全局时间这些参数，不再逐粒子读改写。

省掉的不是积分公式，也不是粒子数量，而是 CPU 逐个处理与跨线程管理的形状。公式一模一样，粒子数也一样多；变的是这些工作的位置：每帧 N 次逐粒子处理、任务切分、块间同步、池分配与回收，全部从 CPU 主线程消失。

> **判据不是"算法适不适合 GPU"，而是"游戏逻辑这一帧要不要读结果"：不读，整个模拟闭环可以留在显存；要读（命中、拾取、AI 感知），闭环就断在把结果拷回 CPU 这一步。**

还有一条前提：数据要能常驻显存。模拟每帧变化的状态只在显存内部流转，跨总线的是发射率、风速、时钟这些参数，或者少量增量；如果每帧都要把整份粒子数组从内存重传，上传成本会抵消 GPU 算得快的那部分收益。这条和本仓库常驻表的前提是同一条：对象表一次写入，模型环只传改动行。

这里的“环”指按帧槽轮转的缓冲：同一份逻辑数据按在飞帧槽各存一份，随帧槽轮换。后文几个环各管一件事（bN 指实例表 set2 的 binding N）：模型环 b1 存每个实例槽的模型矩阵（64 B/槽）；在场环 b4 存本帧允许绘制的实例槽号；命令环 b5 存每个在场槽一条 20 B 的 indirect 命令；档位环 b8 存每个槽的 LOD 档位。

## 每颗粒子只管自己：粒子、毛发、草、群集

粒子是这一类里最简单的：每颗粒子的下一帧只取决于它自己的位置、速度、寿命，最多再读一个全局风场。数据布局通常是位置、速度各一条数组，按粒子下标一一对应；寿命和存活标记另放一条更小的数组。每帧的 kernel（在 GPU 上执行的那段逐单元程序）只做三件事：读自己那一格，积分，写回。碰撞可以加，但只读静态平面或高度图，不读别的粒子。Unity 的 VFX Graph、UE 的 Niagara GPU 粒子属于这一类：模拟在 GPU 上，结果只给渲染（行业调研口径，未在本仓核实）。

原地更新还是双缓冲？如果每个线程只读写自己那一格，原地更新就够；只有当下一步要读邻居的旧值（SPH、布料）时，才需要两份缓冲轮换。本仓库的帧槽轮转（`MAX_FRAMES_IN_FLIGHT = 2`）解决的是另一个问题：CPU 写的环不能覆盖 GPU 还在读的那一份。它不能替代模拟内部的双缓冲——那是模拟相邻两趟 dispatch 之间的读写顺序（同一帧或跨帧）。

CPU 那边原来由谁做的管理，现在落到哪：

- 粒子池的分配/回收：GPU 侧变成空闲槽号表或原子计数器（用原子操作取号，多个线程同时取也不冲突），新粒子从表里取号；CPU 只写"这一帧发射多少、初速度范围"。
- 存活列表压缩：变成一次前缀和 + 散射；死亡粒子要么被压掉，要么留标记让命令组装跳过。
- 按材质/贴图排序：粒子通常共用一种材质，这一步本来就不存在；如果有多材质，才需要额外的桶排序。

这些工作没有消失，只是从 CPU 主线程变成 GPU 上的扫描/散射几趟 dispatch，CPU 不再随粒子数增长而逐颗处理，这是搬过去的主要收益。

毛发和草更简单：CPU 侧原来按 strand 或簇拆 job 并行；如果摆动只是"静止姿势 + 风场随位置和时间变化"的纯函数，连状态都不需要，直接在顶点着色器里算，compute 都不用；如果每根 strand（一根毛发或草叶）有持久状态（阻尼、碰撞、上一帧位置），就用和粒子一样的逐单元 compute，一根 strand 一个线程。它们的共同点是：结果只给渲染，CPU 不需要知道第几根草弯了多少。

群集不是逐单元独立：每只 boid（靠分离、对齐、聚集三条局部规则成群的对象）要看邻居。CPU 路线是空间分格后按格子拆 job 并行；GPU 把分格本身做成一次计数排序——把空间切成格子，按格子原子累加数量、前缀和、把 boid 索引散射进格子数组；然后每只 boid 只读自己格和相邻 26 格（三维），做分离、对齐、聚集三条规则的力合成，再积分。整条链没有一步需要 CPU 读中间结果；boid 的最终位置照旧写进实例矩阵，作为后面剔除与绘制的输入。

## 邻居耦合但规则：欧拉网格流体与 SPH

欧拉网格流体把速度、密度、压力存在三维网格的格点上。一帧的步骤是固定的几趟：平流（每个格点按速度回溯到上一帧的位置，落在格点之间时做线性插值）、算散度、解压力（Jacobi 迭代若干趟，每一轮只用上一轮的值算修正、再统一更新）、减压力梯度；压力迭代的每一步要读上下左右前后六个邻居。早期游戏在 CPU 上算小规模流体，就是把网格切片分给 job system 并行；GPU 路线把每一趟变成一次 compute dispatch，一个线程算一个格点。为了让邻居数据在片上复用，每个工作组（GPU 上一起调度的一组线程）先把一块瓦片连同边界装进共享内存（同一工作组内可见的片上内存），组内同步一次，再算瓦片内部。邻域是固定的六格，不随场景变化，所以这种模板计算（每个格点只读邻居一圈的固定模式）很适合 GPU。

SPH（用一堆带质量的粒子近似连续流体，靠邻居加权求和算密度和压力）把流体当成粒子：密度是邻居核函数的加权和，压力由状态方程给出，力是压力梯度加粘性。邻居查询同样用均匀网格；每个粒子要读邻居上一帧的位置和速度，所以位置/速度要双缓冲：这一趟读 A 写 B，下一趟反过来。双缓冲不是可选项，是邻居耦合的直接后果。

这两类能搬，是因为耦合是局部的、规则的，中间结果不需要 CPU 读。它们也可能不该搬：如果玩法要读"水位""烟浓度"——船的浮力、角色在烟里的窒息判定——回读就会让 CPU 等 GPU。常见做法是 CPU 保留一个低维近似（水位高度图、几个探针），GPU 算视觉场，两边允许轻微不同步；这和"整个模拟闭环留 GPU"是两种不同的取舍，不要混为一谈。

## 全局变换：海面 FFT 整条链留在显存

海面用频谱法：给定风速和风向，生成一张 Phillips 频谱（按风速给不同波长的波分配能量）；每帧按深水色散关系（决定不同波长的波跑多快）推进相位；做二维逆 FFT（快速傅里叶变换：把频域频谱一次变换成空间域波形），得到波高和水平位移场；顶点着色器按世界坐标采样这张位移纹理，法线从同一张纹理的斜率算。

CPU 路线通常是多线程 FFT 库逐帧算这张场，再把波高/位移传成顶点数据或纹理。GPU 路线把整条链留在显存：二维逆 FFT 拆成行、列两趟，每行做一维 FFT，转置，再做列；每一趟的蝶形运算（FFT 里成对合并频点的一步）在共享内存里完成，一次 dispatch 处理一批行或列。频谱纹理、相位、中间复数场、最终位移纹理都不落 CPU；CPU 每帧只写时间、风速、风向。没有逐对象决策，也没有需要 CPU 知道的中间量。

如果玩法要读某点的波高——船的浮力、浮标的位置——就得把那一小块纹理读回，或者 CPU 再算一套 Gerstner 波（用一组正弦波叠加近似波面）近似。前者要等 GPU，后者是两套波形的轻微不同步。这就是"要读结果"的代价的具体样子，和刚体物理是同一条判据的不同表现。

## 约束迭代：布料与破坏残骸，冲突要另付代价

布料和软体常用 Verlet 或 PBD。Verlet 用上一帧位置差代替显式速度；PBD（基于位置的动力学：先按预测位置移动，再迭代修正约束）把布料表示成一堆距离约束，每条约束连接两个粒子、记一个静止长度；一次迭代就是遍历所有约束，把两端沿连线拉回目标长度。

CPU 多线程的做法是把互相共享粒子的约束分成 island（必须一起求解的一组粒子）：不同 island 可以并行，因为岛之间不共享粒子；岛内串行，或者按冲突分组。PhysX 的布料求解长期留在 CPU，用多线程按约束批次并行（行业调研口径，未在本仓核实）。GPU 的做法是一次 dispatch 一个迭代，所有约束同时算。问题在于两条约束可能写同一个粒子，产生写冲突。两种处理：

- 雅可比式：所有约束读上一轮位置、各自算修正，再对每个粒子求平均或求和后统一更新；多一趟归约，收敛慢一些。
- 图着色：把约束按"是否写同一个粒子"分组，组内无冲突，一组一趟 dispatch；组数取决于网格连接度。

island 划分作为"CPU 并行的前提"消失了，但代价是迭代次数变多或收敛变慢；消失的是 CPU 侧为并行而做的划分，不是约束求解这件事本身。

破坏残骸走的是另一条路：CPU 路线是大量小刚体在物理引擎里按 island 并行；GPU 路线把真刚体语义（摩擦、堆叠、休眠、接触流形——接触点的几何描述）不要了，改成"位置 + 速度 + 简单平面/球碰撞"的粒子式解算；碎片之间不互相堆叠，只保证大致飞散和落地。视觉上够用，玩法上不能当掩体。战地系列的碎片粒子化是行业里的同类路线（调研口径，未在本仓核实）。

如果玩法要问"这块残骸挡不挡路"，碎片就不能只做视觉解算：要么 CPU 留一份简化碰撞体，要么接受回读延迟。

## 动画求值：CPU 只留一个时钟，但玩法可能还要骨架

旧路线：每个角色每帧从动画曲线采样每根骨骼的变换，乘出骨骼矩阵，再把矩阵数组上传到 GPU；CPU 成本是角色数 × 骨骼数，job system 按角色或骨骼并行。新路线：把骨骼矩阵按时间烘焙成一张矩阵贴图（把每根骨骼每个时刻的矩阵存成一张浮点纹理），顶点着色器按当前时间和骨骼索引采样，直接算蒙皮（用骨骼矩阵把顶点从绑定姿势变换到当前姿势）；CPU 每帧只更新一个全局时钟，角色数不再进入 CPU 成本。另一种变体是 compute 先算矩阵、顶点着色器再读，区别只是采样发生在哪个阶段。

它算模拟，是因为逐帧求值一套变换状态，和粒子积分同属"纯数值、结果只给渲染"；它特殊，是因为动画往往同时驱动命中盒、脚步声、根运动（角色整体位移），玩法要读。行业里常见的折中是 CPU 保留一份简化骨架或事件轨道，GPU 只负责视觉蒙皮。本仓库路线图的边界里蒙皮不在主线，这里只说明它在负载形状上的位置：它是"逐单元独立 + 结果只给渲染"的又一种，不是刚体物理。

## 刚体物理留在 CPU：消费方在游戏逻辑

刚体物理的结果每一帧都要被玩法读取：角色位置、命中判定、拾取、AI 感知、网络同步。这些消费方在 CPU 上，而且每帧都要读当前帧的位置。把模拟放 GPU，读回要等 fence（CPU 用来确认 GPU 已执行完某次提交的同步对象）。本仓库最多允许 2 帧在飞（`MAX_FRAMES_IN_FLIGHT = 2`）：CPU 提交第 N 帧后，不等 GPU，接着准备第 N+1 帧；第 N 帧的 fence 信号到达时，CPU 刚要开始准备第 N+2 帧。如果要在第 N+1 帧使用第 N 帧的模拟结果，CPU 只能停下来等第 N 帧执行完，两帧并行的流水线退化成串行。

寻路、AI 决策这类同样每帧被玩法读取的负载，通常也留在 CPU；它们受同一条判据约束。

行业现状是这条判据的旁证：Havok、Jolt、PhysX 的主流用法仍在 CPU 多线程；Unity 的 VFX Graph 是 GPU 模拟、纯视觉，DOTS 粒子是 CPU 模拟、逻辑可读，两条产品线并存。这些是行业调研口径，不是本仓库的实测，也不引具体数字。

如果一定要把刚体放到 GPU，只有三条路：留 CPU；CPU 算逻辑近似、GPU 算视觉精确版，两套轻不同步；容忍异步读回延迟，几乎不用于逐帧玩法。这不是"GPU 算不动"——约束迭代在 GPU 上能跑得很快；限制它的是结果给谁用。

## 接得上：模拟的输出端就是现有的剔除与绘制链

本仓库的剔除（5.2）、遮挡（6.1）、LOD（6.2）这些决策类负载，搬的是 CPU 的逐对象决定循环；模拟类搬的是 CPU 的逐单元数值更新。两者的接入点相同：都写显存里的实例表与环，后面由 5.3 的 indirect 命令闭环消费；流送（6.3）管资产驻留，不在这条逐帧 compute 链上。现在 compute 前置段（② 段）的顺序是（`ash_renderer/src/render/frame/record.rs`）：

1. 视锥剔除（`cull`，判断物体在不在相机视野内）：读 set2（实例表的描述符集，bN 指它的 binding N）的对象表 b0、模型环 b1，对槽位上界内的每个实例槽判可见性，写剔除标记 b3。
2. 遮挡测试（`occlusion`，用深度图判断物体有没有被挡住）：读 b3 和本帧槽的 Hi-Z 金字塔（把深度图逐级降采样成小图，用来快速判断遮挡；内容是两帧前的深度），写合并后的 b3 和只进诊断的遮挡标记 b6。
3. LOD 选档（`lod`；LOD 指同一物体按距离换用不同精度的网格）：按包围盒投屏尺寸选档，读档位环 b8 里两帧前的值做迟滞，写回本帧档位。
4. 组装命令（`build_indirect`）：读在场环 b4、b3、对象表 b0、材质环 b2、LOD 变体表 b7、档位 b8，为每个在场槽写一条 20 B 的 `VkDrawIndexedIndirectCommand` 到命令环 b5；不可见行和透明行的 `instanceCount` 写 0，选中档未驻留的缺口位写进 b9。
5. 图形阶段：G-buffer pass（不透明几何写颜色、法线、材质参数的那一趟）里只发一次 `cmd_draw_indexed_indirect`（绘制参数写在显存里的 draw 调用），读 b5 的命令数组；顶点着色器按 `@builtin(instance_index)`（等于 `firstInstance`）读对象表 b0、模型环 b1。

5.5 分档压测（当时还没有遮挡剔除和 LOD）给过这条链的 CPU 侧读数：1 万/5 万/10 万档（实际实例 10006/50006/100006，GPU 标记可见 9648/47261/93536），主视图不透明绘制的绘制调用数（draw_calls）恒 1、逐对象 push 常量（随单次绘制提交的小块参数）恒 0、录制提交 0.43/0.45/0.46 ms；零变化形态的 GPU 全帧 p50（中位数）是 35.80/137.36/254.00 ms，compute（剔除 + 命令组装）p95（95 分位）全档 ≤1.6 ms。模拟 compute 加进来会增加 GPU 的成本（模拟本身，以及粒子带来的绘制量），但不会把 CPU 的逐对象循环加回来——前提是模拟输出直接写进同一套表，而不是每帧读回 CPU 再上传。

现成的设施：`MAX_FRAMES_IN_FLIGHT = 2` 的帧槽轮转与 fence 纪律、对象表 131072 槽、在场环、命令环、LOD 变体表/档位环、缺口标记环，以及 cull/occlusion/lod 三组诊断读数。缺的是模拟 kernel 本身，和一处接线：让模拟的每个单元占一个实例槽。对象表一行 48 B（`first_index`/`index_count`/`vertex_base`/`material_index`/局部包围盒），粒子共用同一段网格时这些字段可以相同；每颗粒子的差异先落在模型矩阵（b1，64 B/槽）。模拟 compute 直接写这些槽的矩阵，前面的剔除/LOD/命令组装不用改。CPU 只需要在初始化或增删时登记槽位，并让在场环包含这段连续槽位；如果粒子会动态增删，再决定存活/死亡怎么让命令组装跳过——固定上限加标记，或另建粒子表并让 build_indirect 读它。

对象表容量 131072 槽，十万粒子会占掉约四分之三，和场景对象共用前要先算预算。CPU 侧的 `InstanceLedger`（实例账本）现在按实体登记槽位；粒子系统起步做法可以只登记一个实体，让它持有一段连续槽位（账本侧加一条范围登记），模拟写这段槽位的矩阵。粒子数再大，就要另建粒子表或扩容量。粒子的起步成本最低：一个积分 kernel、一个占位网格（小四边形或低模），加上现成的 indirect 链，就能跑通"模拟 → 剔除 → 一次绘制"的闭环。布料/流体的起步成本更高，要加邻域结构和多趟 dispatch，但消费端不变。

调试手段跟着变：数据在显存里，CPU 只能异步回读。本仓库已有的纪律是读回只进诊断——`cull_stats`、遮挡、LOD 的读数都在 fence 之后读本帧槽（也就是两帧前的输出），只显示在 egui 面板和 BRP（Bevy Remote Protocol，从外部查询运行中程序的接口）里，不参与"画什么"；缺口标记 b9 在帧起读本帧槽（两帧前的输出），只交给驻留管理器和 BRP 统计，不参与本帧绘制。模拟的读数（存活数、最大速度、越界计数）照同一纪律走：可以回读给人看，不能在同一帧拿它决定发射、绘制或玩法。

当前路线图的九个步骤里没有模拟族：步骤 7 是大型正式场景，8 是延迟渲染管线，9 是全局光照。要立项，按 `.agents/docs/开发步骤/外置拓展需求/外置拓展需求.md` 的条目格式新增一条（来源、内容、恢复条件、边界）；它不占 N/N.M 编号、不进施工顺序表、不承验收责任。本篇不主张新增施工，只说明负载形状与现有接口。
