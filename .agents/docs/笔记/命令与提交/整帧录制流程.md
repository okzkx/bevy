# 整帧录制：九段的顺序、边界与提交

一帧要画的东西，最后都要落进一块 command buffer（命令缓冲：CPU 把要 GPU 执行的动作逐条写进去的一块命令内存）。本仓库里，本帧的渲染命令只在一个地方录：`FramePool::record_frame` 包一层错误升级（把下层错误统一包成致命错误再往上抛）后调用 `record_frame_steps`（`ash_renderer/src/render/frame/record.rs`）。它把本槽（帧槽：在飞各帧轮流使用的一整套资源，本帧独占其中一槽）的 command buffer 以 ONE_TIME_SUBMIT 方式重录一遍（提交一次就丢弃，驱动可以按这个前提省掉复用检查），按固定顺序录完九段，末尾一次 `queue_submit` 交给图形队列。帧的输入不在这里找：`draw_frame` 先把它们组装成两个参数——`RenderFeatures` 装本帧各功能模块的绘制/计算输入与开关，`SceneResources` 装跨段共用的场景资源与规格——录制体（`record_frame_steps` 这个函数）只读这两个参数，不查 World、不碰资源管理器。

**段的边界 = image layout 迁移点 + 计时打点；段与段之间没有隐式状态，衔接只靠屏障。**

image layout 是图像在显存里的用途状态：颜色附件、深度附件、可采样、可呈现各是一种；换用途要做一次布局迁移，迁移本身是一次写。barrier 是写进 command buffer 的同步指令，声明前一批读写完成后后一批才能开始，布局迁移也由它完成。段的切点选在“上一段的产物要换用途给下一段”的位置，GPU 计时打点挂在同一批位置，帧耗时按段分桶。不是每条边界都有一条迁移——② 段就没有图像布局迁移——但每条跨段读写都有屏障收口。

## 九段总览

| 段 | 计时点 | 录什么 | 主要输入 |
|---|---|---|---|
| ① 进场 | T0（`reset_and_start`，在进场屏障之前） | 开 command buffer、重置计时、录三组进场屏障、预填透明排序键 | `target.image`、`frame.depth`、`res.gbuffer` 的四张图、`feature.transparent.t_keys` |
| ② compute 前置 | T1 `Compute` | 视锥剔除 → 遮挡 → LOD 选档 → indirect 组装 → shadow 组装 → 光源分簇 → 透明三连 | `feature.frustum_cull`/`hiz`/`lod`/`indirect`/`shadow`/`cluster`/`transparent`，`res.instance_set` |
| ③ shadow depth | T2 `Shadow` | 四张级联图的进出屏障（恒录）+ 每级一次动态渲染、不透明与 MASK 各一条 indirect | `feature.shadow.passes.write`、`feature.shadow.images`、`feature.shadow.set` |
| ④ G-buffer | T3 `GBuffer` | 三色 + 深度 CLEAR，一条 indirect 消费整个命令环 | `res.pipeline`、`res.gbuffer` 的视图、本槽深度视图、`res.bindless_set`/`frame_set`/`instance_set`、顶点/索引池、`res.indirect_buffer`/`indirect_count` |
| ⑤ 合成 + 透明前向 | T4 `Lighting` | G-buffer 转可采样 → 合成写 HDR → 透明混合 → HDR 转可采样 | `res.composite`、`res.gbuffer`、本槽深度、`feature.cluster.set`、`feature.shadow.set`、`feature.transparent` |
| ⑥ Hi-Z | T5 `HiZ` | 透明用过深度则转回只读；金字塔逐级归约 | `feature.hiz.pyramid`、本槽深度、`feature.transparent`（判断深度是否被透明层用过） |
| ⑦ Bloom | 无独立点（归 T6） | prefilter → 逐级 down → 逐级 up | `feature.post.bloom` |
| ⑧ tonemap / SMAA / UI | T6 `PostUi` | tonemap（恒录）→ SMAA edge/blend → neighborhood（终点）→ UI 逐 clip | `feature.post`、`feature.ui`、`res.frame_set`、`res.gbuffer.sampled_set`、`res.bindless_set`、`target.view` |
| ⑨ 出场 + 提交 | T7 `FrameEnd` | PRESENT_SRC 出场屏障 → 结束 command buffer → 重置 fence → 组等待列表 → 提交一次 | `target`、`frame`、`feature.upload_wait` |

表里的段号与 `record.rs` 注释里的 ①…⑨ 一致；计时点是 `TimestampPoint` 的七个段界打点。T0 由 `reset_and_start` 写在进场屏障之前，T1…T6 是六个段的收尾，T7 在出场屏障之后、`end_command_buffer` 之前。帧样本取前六个区间（T0→T1 … T5→T6）做 `gpu_compute_ms` … `gpu_present_ms`；T6→T7 的尾段单独算、不入账，T0→T7 作为全帧口径。⑦ 没有独立打点，Bloom 的耗时并入 T6。

几个 Vulkan 词先说明：swapchain image 是呈现引擎轮转给本帧的那张图，acquire 就是向它要下一张可写的图；set0/1/2 是场景管线的三个描述符集（一组资源绑定的打包），依次是 bindless 表、每帧 UBO、实例表；UBO 是 uniform buffer，着色器只读的小块常量缓冲；HDR/LDR 分别是高/低动态范围的颜色缓冲。

几个渲染词：indirect 指间接绘制——绘制参数写在显存缓冲里，GPU 执行到那条命令时才读，CPU 只发一条消费命令，不再逐对象调 draw；compute shader 是在 GPU 上运行的通用计算程序；G-buffer 是 albedo/normal/matparam 三张几何中间图加深度；Hi-Z 是层级深度金字塔，把深度逐级降采样，遮挡测试用粗层快速判断；Bloom 是泛光，把亮部模糊后叠回画面；tonemap 是色调映射，把 HDR 亮度压到显示范围；SMAA 是一种后处理抗锯齿。① 里的 `t_keys` 是透明层的排序键缓冲。

## 段界为什么这样切

九段不是按代码文件切的，是按“上一段的产物交给谁、要不要换用途”切的。① 把本帧要写的图迁成附件；② 的 compute 不换图像布局；③ 写四张 shadow 图，写完转可采样，⑤ 的合成才能采样；④ 写 G-buffer，⑤ 把它转成可采样后合成；⑤ 的透明层（有的话）要把深度转回附件；⑥ 再把深度交回只读做 Hi-Z（没有透明层时深度一直是只读，不用迁）；⑦⑧ 的每个中间目标都走“附件 → 可采样”一轮；⑨ 把 swapchain image 交给呈现引擎。这样切，段的产物就是下一段的输入，段内不用假设上一段留下了什么布局或可见性。

### 屏障只有三个产地

- 各 pass（一趟绘制或计算）自己的 `record` 函数内：compute dispatch 之间（`Handoff::ComputeRead`/`ComputeReadWrite`）、indirect 命令的写→读（`Handoff::IndirectCommandRead`）、Hi-Z 级间、shadow 命令组装与消费之间。谁写谁负责收口，屏障跟着数据走。
- 段界的布局迁移：进场、shadow 图 → 可采样、G-buffer → 可采样、深度在只读与附件之间往返、HDR/LDR → 可采样、出场。这些迁移发生在段与段之间，由外层（`record_frame_steps` 或该段的 `record`）在段界录，单个子 pass 不假设上一段留下的布局。
- 提交参数里的等待：`image_available`（等呈现引擎把图交出来）和上传票据（等上传队列的 transfer 写完）。这两项不在 command buffer 里，是 `queue_submit` 的等待项，GPU 在提交时等，CPU 不阻塞。

### Option 为 None 是这个模块不录

Option 是 Rust 的可空包装；`None` 表示这个模块本帧不录。`RenderFeatures` 里有两层可空：

- 顶层字段为 `None` 时，这个模块整个不录：`frustum_cull`、`lod`、`indirect`、`transparent`、`ui`。它们是 ②、⑤、⑥、⑧ 里的子步骤或子段，不是九个编号段之一；`timer` 也是 Option，但它只控制 timestamp 写不写，不影响绘制。
- 嵌套字段为 `None` 时只跳子 pass：`hiz.occlusion`、`shadow.passes`、`cluster.build`、`post.bloom`、`post.smaa_edge_blend`。外层的 `HizFrameDraw`、`ShadowFrameDraw`、`ClusterFrameDraw`、`PostChainDraw` 本身仍然传进来，因为它们的恒录部分还要用。
- `res.indirect_count == 0` 是另一道门：它不是 Option，但 ④ 的场景绘制看它决定发不发 draw。

反过来，不随开关消失的部分要单独记住：shadow 的四张级联图每帧都要录进出屏障（合成 pass 的 shadow 描述符总是绑定，布局必须始终是 SHADER_READ_ONLY）；tonemap 与 neighborhood 恒录（前者是 HDR 到 LDR 的唯一出口，后者是 LDR 到 swapchain 的唯一出口）；① 的进场屏障、⑨ 的出场屏障、fence 重置与提交本身就是帧的边界。原因在各自的段落里展开。

`transparent` 是跨段字段：② 里 collect/sort/gather，⑤ 里前向绘制，⑥ 里判断深度要不要转回只读。三处看同一个 Option，所以它作为一个整体字段传；拆成三个字段就会有三份 None/Some 要同步。

### ①⑨ 留在录制体里，因为它们是帧槽自己的首尾

① 和 ⑨ 是帧槽自己的首尾：开/关 command buffer、重置 fence、组等待列表、提交，这些动作只在这里发生。它们要碰的 command buffer、fence、`image_available` 属于 `FramePool` 的 `Frame`，不属于任何业务模块；`target` 作为本次 acquire 的产物直接从参数传入，中间段只借用它的 extent/view，不负责提交。中间的段会用到本槽深度（④ 作深度附件、⑤⑥ 迁它的布局）和 G-buffer，但不需要自己开/关 command buffer 或组提交。把这些集中到 `record_frame_steps`，每个 pass 拿到的都是已经按帧槽定位好的资源，不用自己查 `FramePool` 或本次 acquire 的图。

## ① 进场：三个屏障对象，三种身份

① 段只做四件事：开 command buffer、重置计时、录进场屏障、预填透明排序键。

三个进场屏障对象各自身份不同：

- `target.image`（swapchain image）：跨帧，上一次停在 PRESENT_SRC 或已被呈现引擎交回。用 `discard_to_color` 从 UNDEFINED 进 COLOR_ATTACHMENT_OPTIMAL，srcStage 取 COLOR_ATTACHMENT_OUTPUT——提交在这一阶段等 `image_available`，屏障排在这个等待之后；dstAccess 含 COLOR_ATTACHMENT_WRITE，衔接后面的 `loadOp=CLEAR`。
- `frame.depth.image`（本槽深度）：同槽上一轮的提交已被 `wait_for_slot` 的 fence 等完（fence 是 CPU 用来确认 GPU 已执行完某次提交的同步对象），录制时没有并发引用，所以 srcAccess 可以为空。srcStage 取 EARLY|LATE_FRAGMENT_TESTS，dst 是深度附件写。
- `res.gbuffer` 的四张（albedo/normal/matparam/HDR）：同上，都是本槽私有、上一轮已 fence 等完；一次循环各录一条 UNDEFINED → COLOR_ATTACHMENT_OPTIMAL。G-buffer 的进场迁移放在这里，④ 段开头因此没有布局屏障，可以直接开渲染。

贴图不录进场屏障：图像是 CONCURRENT（多个队列族同时共享同一布局）双族共享，不做所有权转移；上传时的 TRANSFER_DST → SHADER_READ_ONLY 在上传队列的提交内完成；跨队列可见性由 ⑨ 的票据等待兜底。只有 EXCLUSIVE（同一时刻只归一个队列族）共享才需要逐图所有权转移。

透明排序键 `t_keys` 预填 `-inf`：bitonic（固定容量的并行排序网络）全容量升序排序把真实条目推到尾部，gather 从尾部反向取，空位的键必须是最小值。`cmd_fill_buffer` 是 transfer 写，后面的 sort/collect 是 compute 读写，所以填完立刻录一条 `TRANSFER_WRITE → COMPUTE_SHADER(SHADER_READ|SHADER_WRITE)` 的内存屏障。填充必须在所有 compute dispatch 之前。

T0 在进场屏障之前写，所以帧总时长包含进场开销。

## ② compute 前置：顺序就是依赖

② 段按固定顺序调用：

1. 视锥剔除（`frustum_cull`）：主视图标记与四级阴影标记一次产出；
2. 遮挡测试（`hiz.occlusion`）：读本槽两帧前的金字塔；
3. LOD 选档（`lod`）；
4. indirect 命令组装（`indirect`）；
5. shadow 命令组装（`shadow.passes.build`）；
6. 光源分簇（`cluster.build`）；
7. 透明三连（`transparent` 的 collect → sort → gather）。

每一步的写都是下一步的读，屏障在各 pass 的 `record` 里，录制体只管顺序调用。六个固定模块的 dispatch 都由 host 按开关与空场决定录不录：关闭或空场时为 `None`。视锥剔除有一个例外——shadow 开启时，即使主视图剔除关闭，也要 dispatch 产出阴影标记。LOD 关闭时 host 把档位环填 0（最细档），indirect 组装读到的档位仍然合法，画面回退到最细网格，不是不画。

遮挡测试读的是本槽上一轮归约出的金字塔，也就是两帧前；相机跳变、金字塔未就绪这类跳过条件在 host 判定，录制体只看到 `None`。

透明层字段里 collect/gather 是 Option，sort 在 `transparent` 为 Some 时恒录：固定容量数组每个非空帧都要重排，否则本帧新增的透明行会以未排序状态进 gather。排序后 `-inf` 填充在前缀，gather 从尾部取真实条目。

T1 在透明三连之后，整段 compute 都计入这个桶。

## ③ shadow depth：布局屏障恒录，pass 可以跳

`feature.shadow.record_depth` 每帧都录四张级联图的进出屏障，pass 开关只决定中间要不要画：

- 进场：四张图各一条 UNDEFINED → DEPTH_ATTACHMENT，srcStage 取 FRAGMENT_SHADER——四张图跨帧共享、不分帧槽，这条屏障在等上一帧合成采样读完（WAR，写后读：新写要等旧读完成）；srcAccess 为空，旧内容不要。
- 出场：四张图各一条 DEPTH_ATTACHMENT → SHADER_READ_ONLY，供 ⑤ 的合成采样。
- 为什么不能省：合成 pass 的 shadow 描述符总是绑定，四张图的布局必须始终是 SHADER_READ_ONLY。pass 本体可以跳，布局不能省。UNDEFINED 作 oldLayout 从任何状态都合法，因为每帧 `loadOp=CLEAR` 重写全图。

pass 开着时，每个 cascade（级联：把相机视锥按距离切成几段，每段一张阴影图）一次动态渲染（Vulkan 1.3 的 `cmd_begin_rendering`，不需要 RenderPass/Framebuffer）：先绑不透明管线画 `commands[c]`，再绑 MASK 管线画 `mask_commands[c]`，两条都是 `cmd_draw_indexed_indirect`，各推一次 4B cascade 索引。四张图是 2048² D32（32 位浮点深度），深度清 0（reverse-Z：近处深度值大、远处小，1 是近平面、0 是远平面），比较操作用 GREATER；不透明行走无片元着色的 depth-only 管线（early-Z 有效），MASK 材质（用 alpha 裁切的材质）走片元裁切管线，采样 bindless 贴图。

shadow 命令是在 ② 的 build dispatch 里按“每个在场行 × 每个 cascade”写好的，读 shadow 标记与 LOD 档位环，不参与遮挡，LOD 比主视图再粗一档。build 同时写两套命令环：不透明行走 b6..9，MASK 行走 b10..13；同一行只命中一套，另一套写 0 实例。`command_count` 是在场行数，两套环共用同一个条数上界；透明行在两边都是 0。

## ④ G-buffer：一条 indirect 消费整个命令环

④ 段开渲染，三张颜色附件加深度，全部 `loadOp=CLEAR`；颜色附件数必须与管线声明一致（VUID-06179：`colorAttachmentCount` 要相等）。深度清 0（reverse-Z 远平面），storeOp 用 STORE——⑤ 的合成和 ⑥ 的 Hi-Z 还要采样它。

场景绘制只有一条 `cmd_draw_indexed_indirect`：读 `res.indirect_buffer` 里 `res.indirect_count` 条命令，draw 调用数不随对象数增长。每条命令自带 vertexOffset/firstIndex，顶点/索引池整池绑一次；实例槽号放在 `firstInstance`，VS 用 `@builtin(instance_index)` 按槽号读 set2（实例表描述符集）。不可见行的 instanceCount=0，命令还在，只是不画。

`res.indirect_count == 0` 时只开渲染、清附件，不发 indirect draw；它和“有场但全不可见”不是一回事：后者有命令，只是每条 instanceCount=0。

顶点/索引池缺席，而在场行非空，是上传链与绘制链的状态矛盾：`pool_buffers()` 返回 `VulkanError::Contract`，`record_frame` 外层按致命错误冒泡，不会静默跳过整个场景。

viewport 高度用正值：Y 已经在 shader 里翻过，负高度会二次翻转。

## ⑤ 合成 + 透明前向：深度一趟三态

⑤ 段先迁布局：三张 G-buffer 颜色 → SHADER_READ_ONLY，深度 → DEPTH_READ_ONLY；dstStage 含 COMPUTE_SHADER，因为 ⑥ 的 Hi-Z 归约也读深度。

合成是一个全屏 pass，无深度附件：读 frame UBO、G-buffer 采样集、光源分簇集、shadow 集，写 HDR 目标并 CLEAR。clear 色按线性域给值——HDR 目标的 SRGB view 在写出颜色时才编码，别拿 sRGB 十六进制直接换算。depth==0（reverse-Z 远平面）的像素当背景。

透明前向紧接在同一个 HDR 目标上：LOAD + alpha 混合，深度 LOAD、只测不写（GREATER）。它绑 bindless、frame、instance、cluster 四集，一次 indirect 消费透明命令环：绘制条数按在场行数上界，但只有前 `t_count[0]` 条是排好序的透明行；多出来的下标由 gather 写成零命令，避免重放上一轮同帧槽的旧命令。

两次动态渲染之间没有光栅序保证：合成写 HDR → 透明混合读写，必须显式 memory barrier。这条内存屏障和“深度从只读转回附件”合成同一次 `vkCmdPipelineBarrier`。

深度在本帧走三态：只读（合成采样）→ 附件（透明测深不写）→ 只读（⑥ Hi-Z 归约读）。没有透明层时，中间态不发生，深度从 ⑤ 到 ⑥ 一直是只读。

深度转回附件的屏障 srcAccess 含 DEPTH_STENCIL_ATTACHMENT_WRITE：布局迁移本身是一次写，必须排在 ④ G-buffer pass 的深度 store 之后（同步验证层的 WRITE_AFTER_WRITE，写后写）。

段尾 HDR → SHADER_READ_ONLY，供 Bloom prefilter 与 tonemap 采样。

## ⑥ Hi-Z：归约恒录，warmup 走账

透明层画过，深度现在是附件；先转回 DEPTH_READ_ONLY：srcAccess 取 DEPTH_STENCIL_ATTACHMENT_READ | DEPTH_STENCIL_ATTACHMENT_WRITE（透明 pass 读过，G-buffer pass 写过），dstStage 只等 COMPUTE_SHADER。没有透明层时，深度从 ⑤ 起一直是只读，这条不录。

归约链本身恒录，不属于 Option：`feature.hiz.pyramid.record_reduction` 每帧把本槽金字塔从 level 1 逐级降到最小级。level 0 不派发——2×2 MIN 写进全尺寸 level 0 只会写左上四分之一，其余未定义，整条链读垃圾；遮挡侧的 mip 选择因此下限 1。级与级之间录一条 compute 读写屏障，末级的写→下一轮遮挡读由下一轮 cull 的全局内存屏障罩住。

warmup（预热计数：金字塔内容还没就绪的帧数）在金字塔刚建或重建后初始化为 `MAX_FRAMES_IN_FLIGHT`（2），每录完一帧归约 `note_reduced` 减一，减到 0 才 `ready()`，遮挡测试才允许 dispatch。录制与走账一一对应，不能只录不减或只减不录。

归约进场首用是 UNDEFINED → GENERAL，之后恒 GENERAL；从 GENERAL 进时 srcAccess 只等 SHADER_READ，确保本帧更早的遮挡读已完成。

T5 在归约之后，所以 Hi-Z 桶只含归约，不含 ② 的遮挡测试。

## ⑦ Bloom：目标跨帧共享

`feature.post.bloom` 是 Option；关闭时整个 Bloom 链不录，tonemap 仍绑 bloom 参数集，但 shader 内不采样。

链路：prefilter 从 G-buffer 采样集里读 HDR，按亮度阈值提取亮部写 `down[0]`；再逐级 down（1..4），再逐级 up（3..0），`up[0]` 是半分辨率 bloom 纹理，供 tonemap 叠加。共 9 个全屏 pass：prefilter + 4 次 down + 4 次 up，级数 `BLOOM_LEVELS = 5`。

Bloom 目标不分帧槽：跨帧共享。每个目标进场时 `discard_to_color` 的 srcStage 取 FRAGMENT_SHADER，等上一帧的片元采样读完再覆写（WAR）；出场转 SHADER_READ_ONLY。每轮都写满全图，旧布局用 UNDEFINED 合法。

## ⑧ tonemap / SMAA / UI：恒录的进场与自己的管线

tonemap 恒录，不随 Bloom/SMAA 开关消失：LDR 是每帧槽一张的 8 位 UNORM（0..1 归一化整数）线性目标，上一轮停在 SHADER_READ_ONLY；进场必须从 UNDEFINED 迁回 COLOR_ATTACHMENT_OPTIMAL，否则 `cmd_begin_rendering` 时布局不符，触发 VUID-09592。写完转 SHADER_READ_ONLY 供 SMAA 采样。

tonemap 读 frame UBO、G-buffer 采样集里的 HDR、bloom 参数集，写 LDR；全屏三角形只有 3 个顶点，没有顶点 buffer。sRGB 编码只在最后写 swapchain 的 SRGB view 时做一次，LDR 本身是线性存储。

SMAA edge/blend 是 Option，关闭时 neighborhood 在 shader 里直通；neighborhood 混合（SMAA 的最后一步，把边缘权重混回颜色）恒录，是 LDR 到 swapchain 的唯一出口，并且开渲染不关——UI 接着在同一次渲染里按光栅序画在场景上。

UI 是 Option；有 UI 时切 overlay 管线。overlay 有自己的 pipeline layout（管线布局：描述符集与 push 参数的排布），只声明 set0（bindless 表），切过去后 set0 要按它的 layout 重绑（同一个集对象，不同 layout）。场景分支不一定跑过 viewport，UI 自己设。

每个 clip 设一次 scissor（裁剪矩形），push（push constant：随一次绘制提交的小块参数）16B：`screen_size` 整帧同值、单位是 points（与顶点坐标同域的逻辑像素），纹理/采样器槽位逐 clip 变。overlay 不声明深度格式，因为这个渲染实例只挂颜色附件；声明 DEPTH_FORMAT 而深度附件为 NULL 会触发 VUID-08913。`record_frame_steps` 在 UI 之后才 `cmd_end_rendering`，所以 UI 的绘制还在 T6 之前。

## ⑨ 出场与提交：fence 重置在最后一刻

⑨ 段先把 `target.image` 从 COLOR_ATTACHMENT_OPTIMAL 迁到 PRESENT_SRC_KHR：srcStage/access 是 COLOR_ATTACHMENT_OUTPUT/COLOR_ATTACHMENT_WRITE，dstStage 是 BOTTOM_OF_PIPE、dstAccess 空。T7 在这之后、`end_command_buffer` 之前写，所以全帧口径包含出场屏障，不包含提交。

`reset_fences` 在 `queue_submit` 前一刻才做：这里到提交之间不能有提前 return。若提前 return 时 fence 已重置，没人 signal 它，下一帧 `wait_for_slot` 会在 `wait_for_fences(u64::MAX)` 上永久卡死主线程和消息泵。当前写法下，reset 失败时 fence 仍是 signaled 状态，下帧照常通过；submit 失败则没人 signal，帧循环按致命错误退出，不会回来死等。

等待列表有两项：

- `image_available`：binary 信号量（只有 signaled/unsignaled 两态），`value` 填 0 占位，dstStage 是 COLOR_ATTACHMENT_OUTPUT；所以 ① 之前的命令（开 command buffer、重置计时）可以与 acquire 重叠。
- 上传票据：`UploadWait` 在 `draw_frame` 备料后取快照，票 0 表示启动后从未上传，这时不追加等待——不能等 timeline 信号量（带递增值，等某个值等于等它之前的所有提交）的 0 值（VUID-03242）；票非 0 时在 ALL_COMMANDS 等这个 timeline 值。这个等待同时兜底 transfer 写池/贴图的跨队列可见性：池和贴图是 CONCURRENT 共享，没有所有权屏障，全靠提交参数里的这条依赖。

`queue_submit` 只发一次，提交在 GPU 侧等，CPU 不阻塞；完成时 signal `target.render_finished`（按 swapchain image 分配，给 present 用；present 是把画好的图交给屏幕显示）与本槽 `frame.in_flight` fence（给下一轮 `wait_for_slot` 用）。present 不在这里，是 `draw_frame` 在 `record_frame` 返回后调用的下一步。

## 字段为什么这样分组

`RenderFeatures` 与 `SceneResources` 的字段不是按文件切的，是按“谁和谁必须一起决策、谁被几段消费”切的。

`SceneResources` 放场景链的句柄与规格，跨段共用的优先放这里：`pipeline`、`bindless_set`（set0）、`frame_set`（set1）、`instance_set`（set2）、`vertex_buffer`/`index_buffer`、`gbuffer`、`composite`。`bindless_set` 在 ④⑤⑧ 用，③ 的 shadow 写管线另带同一个集（`ShadowWriteDraw.bindless_set`）；`frame_set` 在 ④⑤⑧ 用；`instance_set` 在 ②③④⑤ 用；顶点/索引池在 ③④⑤ 用；`gbuffer` 在 ①④⑤⑦⑧ 用。`pipeline` 只在 ④ 用，`composite` 只在 ⑤ 用；它们和三个集、顶点池、G-buffer 是同一套场景绘制规格，拆开只会让 ④ 或 ⑤ 多借一个参数。

`indirect_count`/`indirect_buffer` 虽在 `SceneResources` 顶层，但只被 ④ 消费；它们和命令环同属实例表账本，且 `indirect_count` 同时是 `draw_frame` 组装透明层与 shadow 录制输入的规模读数，所以按归属留在顶层，不按“跨段共享”计。

`RenderFeatures` 一个字段装一个功能模块，字段顺序就是九段的消费顺序。跨多段的模块不拆：`hiz` 管 ②⑥，`shadow` 管 ②③⑤，`cluster` 管 ②⑤，`transparent` 管 ②⑤⑥，`post` 管 ⑦⑧。拆开会让同一个 Option、同一份句柄出现多次，None 的判定也会分散。

相反，② 的六个 compute 模块不合成一个结构：它们的 Option 条件、输入集和管线各不相同，合并会让一个字段带六套状态；字段顺序已经表达了依赖序。

`post` 内部把 tonemap、bloom、smaa、neighborhood 收在一起，因为 `PostChainDraw::record` 一次录完，中间没有打点；这四者的输出是串行的一条链，拆成四个字段只会让 ⑧ 的调用点更长。`ui` 单独一个 Option，因为它是 ⑧ 里可整段缺席的 UI 子段；`UiDraw` 里装 overlay 管线、绘制产物和本帧槽的顶点/索引环 buffer。

①⑨ 的帧槽私有物不进这两个结构：command buffer、fence、`image_available`、本槽深度在 `FramePool` 的 `Frame` 里；`render_finished` 在 `Swapchain` 的 `PresentTarget` 里；`target` 作为 `record_frame` 的参数传入。唯一进 `RenderFeatures` 的同步物是 `UploadWait`——它不是槽私有物，而是本帧对上传队列的等待快照（票据值 + 上传队列的 timeline 信号量），`draw_frame` 在备料后取，录制体只把它转成提交参数。
