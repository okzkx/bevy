# GPU-Driven 本质：谁在什么时候决定画什么

假设场景有一万个物体。CPU 驱动渲染时，CPU 每帧要循环一万次：判断每个物体可不可见、准备它的矩阵和材质、发一条 draw 调用。这个循环就是 GPU 驱动渲染（GPU-driven rendering，下称 GDR）要搬走的东西。

GDR 把逐对象的决定推迟到执行时：CPU 只写相机参数、可画行列表和一条 indirect 调用（绘制参数写在显存里的 draw 调用）；GPU 的 compute shader（在 GPU 上运行的通用计算程序）读常驻表，算出可见性和 LOD 档位（同一物体的多档精度网格），把结果写成命令，图形阶段再消费。

**这个移动不减少 GPU 要画的东西。** 它省掉的是 CPU 每帧逐对象做决定、再把决定翻译成 draw 调用的循环；决定本身仍然要做，只是换到 GPU 上做。

| | CPU 驱动 | GPU 驱动 |
|---|---|---|
| 决定时刻 | CPU 录制命令时 | GPU 执行命令时 |
| 决定输入 | 系统内存里的副本，或读回的旧结果 | 显存里的常驻表 |
| 决定输出 | N 条 draw 调用 | 1 条 indirect 调用 + 命令缓冲 |
| CPU 是否知道逐个物体的可见性 | 知道 | 不需要知道，只知道哪些行允许被画 |

## 一、一个决定需要什么，为什么读回会打断流水线

“画这个物体”需要四类输入：

- 它在不在视锥里：相机矩阵和物体包围盒；
- 它有没有被挡住：本帧或近几帧的深度；
- 它该用哪一档 LOD：屏幕覆盖尺寸、阈值、本帧槽上一次的档位（两帧前）；
- 它画成什么样：网格引脚、模型矩阵、材质参数、贴图槽。

CPU 驱动时，这些输入要么在系统内存里另算一份，要么从 GPU 读回旧结果；决定输出是一串 draw 调用。GPU 驱动时，输入和决定都在显存里：compute shader 读同一批常驻表，把结论写成另一种显存数据——indirect 命令。

为什么不把 GPU 算出的可见性读回 CPU，让 CPU 继续做决定？**因为读回（把显存里的数据拷回 CPU 可读的内存）要让 CPU 等 GPU，而等待会拆掉多帧并行。**

本仓库最多允许 2 帧在飞：CPU 提交第 N 帧后不等 GPU，接着准备第 N+1 帧。第 N 帧的 fence（CPU 用来确认 GPU 已执行完某次提交的同步对象）发出信号时，CPU 刚要开始准备第 N+2 帧。如果 CPU 要在第 N+1 帧使用第 N 帧的可见性，它只能停下来等第 N 帧执行完；两帧并行退化成串行，逐对象决策的循环又回到 CPU 手里，只是多绕了一次显存往返。

这条约束筛掉了所有“可见之后 CPU 还要做事”的对象：更新骨骼的角色、CPU 模拟的粒子、每帧在 CPU 上生成顶点的动态网格、可见性会触发流送或玩法逻辑的对象。它们不能把可见性完全交给 GPU。可见性只供绘制时，这段决策链可以留在显存；一旦它还要驱动 CPU 侧的角色、粒子、流送或玩法，就只能留在传统路径。展开与走查见 [为什么没有全上 GPU 驱动](为什么没有全上%20GPU%20驱动.md)。

## 二、走一遍本仓库的链

假设场景里有一万个物体，CPU 已经把可画行的槽号写进在场环（一份列出本帧允许被画的实例槽号的缓冲）。以下 bN 指实例表（set2）的 binding N；实例槽是对象表里的一行，一个物体占一个槽。以下是 GPU 侧一帧的顺序。

1. **视锥剔除**（`cull`）。读 set2 的对象表 b0、模型环 b1，按相机六平面判每个在场槽，结果写剔除标记 b3；同一次 dispatch 还为四级阴影生成可见标记（shadow marks）。
2. **遮挡测试**（`occlusion`）。读 b3 和本帧槽的 Hi-Z 金字塔，把 b3 从“视锥可见”改成“视锥可见且未被遮挡”；另写一份独立的遮挡标记 b6，只进诊断读数。金字塔是这个帧槽上一次被使用时的深度，也就是两帧前。相机与两帧前相比位移超过 0.5 世界单位或旋转超过 15° 时，这一步跳过，b3 保持视锥结果，b6 填全可见。
3. **LOD 选档**（`lod`）。按包围盒投屏尺寸和阈值选档，读档位环 b8 里两帧前的值做迟滞，写回本帧档位。新档位本帧就被下一步消费；两帧前的值只作为“上次选到哪一档”的参考。
4. **组装命令**（`build_indirect`）。读在场环 b4、b3 标记、对象表 b0（引脚回退）、材质环 b2（透明判定）、LOD 变体表 b7、档位 b8，为每个在场槽写一条 20 B 的 `VkDrawIndexedIndirectCommand`：`instanceCount` 由可见性决定，`firstInstance` 写实例槽号；透明行和不可见行的 `instanceCount` 写 0。命令写进 b5，选中档未驻留的缺口位写进 b9。
5. **消费命令**。图形阶段只发一次 `cmd_draw_indexed_indirect`，读 b5 的命令数组。顶点着色器用 `@builtin(instance_index)`（等于 `firstInstance`）读对象表 b0、模型环 b1，把材质索引传给片元；片元按材质索引读材质环 b2 和 bindless 表（按槽号索引贴图和采样器的描述符表）。场景绘制的图形管线没有逐对象 push 常量（随单次绘制提交的小块参数），命令参数全在 20 B 记录里。
6. **归约金字塔**。透明层画完，Hi-Z 归约把本帧槽深度逐级降采样，写回金字塔。下一次轮到这个帧槽（两帧后），第 2 步的遮挡测试读的就是它。

在场景绘制这条链上，CPU 每帧只做几件与对象数无关的事：写帧 UBO、写在场环、写模型/材质/LOD 环（模型与 LOD 增量，材质全量）、提交一次命令缓冲，等等。逐对象的“画不画、用哪档、画几份”全部发生在第 2~4 步的 compute 里。

这带来一个设计约束：**GPU 的结论允许旧，不允许等。**

- 遮挡用两帧前的深度；相机跳变时直接跳过遮挡，按视锥结果画。
- LOD 用两帧前的档位做迟滞；档位对应的网格还没驻留时，`build_indirect` 向更细的常驻档回退。
- 缺口标记要等 fence 后才被 CPU 读到，读到的是两帧前的输出；它不参与本帧画什么，只触发后续的资产请求。
- base color 贴图缺席时指向 fallback 白图（建表时占好槽位的白色兜底贴图），其余贴图缺槽时直接跳过采样。

宁可多画一点，也不让 CPU 停下来等 GPU。这是所有“旧结论”共同的兜底方向。

## 三、换来了什么

**1. CPU 提交侧变成常数。** 本仓库 5.5 分档压测（当时还没有遮挡剔除和 LOD）的读数：1 万 / 5 万 / 10 万可见实例三档，主视图不透明绘制的 draw_calls 恒为 1、逐对象 push 为 0、CPU 录制提交约 0.43 ms，且不随实例数增长。CPU 不再逐对象装配参数、切换状态、发 draw 调用；这个循环被一条 indirect 调用替代。

**2. 决策在显存内部闭合。** 可见性不再是“渲染的副产品，CPU 要用就得读回”，而是下一轮决策的输入：本帧的深度归约成金字塔，两帧后喂给遮挡测试；本帧的 LOD 档位写进环，同帧喂给命令组装。Hi-Z 与 GPU LOD 的收益不是“算得更快”，是“不用把结果搬回 CPU 再搬回来”。

**3. CPU 和 GPU 的分工变清楚。** CPU 保留流程编排（pass 结构、屏障、dispatch 形状、提交顺序）和策略层（资产加载/淘汰、显存预算、场景变更发现）；GPU 拿走逐对象的提交决策。CPU 的工作粒度从“每帧每对象”变成“每帧一次编排 + 按事件供数”。

**它不是“GPU 更快”。** 剔除、遮挡、选档都是真实的 compute 成本，进 GPU 账；“免费”只指没有同步等待，不是零成本。

## 四、不换来什么

- **不降低 GPU 负载。** 5.5 的同一组读数里，GPU 全帧是 36 / 137 / 254 ms（p50），逐档线性增长，三档都超过 16.7 ms；瓶颈在图形段的顶点/片元负载，不在提交侧，也不在 compute 剔除。决定时刻搬家把提交循环压成常数，但“画多少东西”没变，GPU 负载就不变。降负载要靠遮挡剔除、LOD、流送这些真正减少绘制量的手段。
- **不解决半透明排序。** 排序精度取决于按什么粒度排，不取决于谁来排；两块相交的玻璃，CPU 排和 GPU 排会得到同样错的结果。要逐像素正确，得靠 OIT（顺序无关透明：按像素记录多层颜色再统一合成）或另一条透明通道。
- **不接管逐对象定制。** 选中高亮、单对象材质覆盖、渲染回调这类需求，GDR 路径要么加字段/分支，要么把对象退回传统路径。实际引擎普遍选后者，所以传统路径会长期存在。
- **不适合小场景。** 几百个对象时，CPU 剔除加按状态合批更便宜；GDR 的四样常驻设施（变更发现、固定槽位、延迟回收、多帧轮转）是固定开销。本仓库默认 Sponza 只有 103 个 primitive，按规模是负优化，照做是为了练整套设施。

这四条合起来是一条边界：GDR 换掉的是提交循环，不减少 GPU 负载、不解决透明排序、不接管逐对象定制，小场景按规模仍是负优化。展开、角色/粒子/半透明与行业实现的走查见 [为什么没有全上 GPU 驱动](为什么没有全上%20GPU%20驱动.md)。

## 五、怎么判断真的换到了

四个检查，缺一个都说明只换了写法：

1. **draw 调用数**是否与实例数解耦（本仓库主视图不透明绘制恒为 1）；
2. **CPU 提交耗时**是否随实例数增长（本仓库约 0.43 ms 平坦）；
3. **渲染决策路径**里是否还有读回（诊断读数不算，只要它不参与“画什么”）；
4. **决定所需的数据**是否常驻显存，增量更新是否只传改动。

反过来的检查同样有用：如果 GPU 帧时间仍随实例数线性增长，而剔除/LOD/流送没有减少实际绘制量，那么你只是把 CPU 的循环搬到了 GPU，没有换到“决策在显存内闭合”的收益。
