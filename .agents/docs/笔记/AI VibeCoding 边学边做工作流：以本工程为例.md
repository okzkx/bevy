# AI VibeCoding 边学边做工作流：以本工程为例

**一句话说明**：本文记录本工程实际在用的"边学边做"协作工作流——用户定目标、AI 调研拆解、小段立案、切分支施工、四件产出、用户验证问答、灯笼并回——每一步指到仓库内的正本文件与 Skill；本文是总览与委托表，**不复制任何正本正文**。

**定位**：跨主题通用方法论，与《写文档纪律》并列留根。适合回答"下一段该怎么开工""产物齐不齐""哪些事必须等用户拍板"；各环节的执行细则以所引正本为准。

## §0 核心原则（先于一切步骤）

- **一次只施工一小段**：步骤（N）拆成段（N.M），段内任务（N.M.K）只增不复用；依赖链顺序不可倒置，验证与讲解消化后再进下一段。
- **计划是唯一施工依据**：无立案不施工；施工中重读计划全文，禁止凭记忆。
- **判定线先于代码**：每段立案时先写"怎么算过"（判定线/测试方案），施工后逐条对账，不允许事后补口径。
- **如实报告**：测试未过就是未过，修不动列遗留项，不硬凑"已过"；失败信息如实进文档。
- **正本唯一**：同一工作流不维护两套等价正文，本文只做指针。
- **拍板点不可代行**：见 §八 分工边界。

## §一 六步循环总览

| # | 步骤 | 本工程落点 | 正本/工具 |
|---|---|---|---|
| 1 | 用户设定项目目标，AI 调研、拆解成大小步骤 | 项目目标与学习路线 → 步骤/段拆解 → 调研笔记 | `项目目标与Bevy使用指南.md`、`学习目标实现步骤.md`（路线图）、`笔记/` |
| 2 | 每小步先出设计文档 + 施工计划 | 段目录 + 段施工计划 + 段 README + 三处状态流转 | `$doc-plan-register` |
| 3 | AI 切分支执行 + 回归测试 | `goal/<段号>` 临时分支施工；判定线 + 三级测试 + 压测脚本 + 截图读图 | `$plan-execute`、`测试规范与方式`、`画面功能视觉验证`、`tools/*.py` |
| 4 | 施工记录、施工总结、原理文档、变更文档 | 施工记录 + 流程导读（含代码改动解析）+ 原理专题篇 + 状态流转 | `plan-execute` 阶段三定例 |
| 5 | 用户验证 + 原理问答 + 代码校验优化 | 判定线逐条对账、复述校准回写文档、验收归档、遗留挂账 | 段 README 验收状态、`待修复清单.md`、`外置拓展需求.md` |
| 6 | 灯笼合并回 main | 源分支先变基到目标再同链合并 → 推送 → 删临时分支 → 分批记账 | `merge-chain`、`$auto-commit` |

## §二 第 1 步：目标、调研与拆解

1. **用户设定项目目标**：写进 `.agents/docs/项目目标与Bevy使用指南.md`（做什么、Bevy 使用边界）与 `学习目标实现步骤.md`（学习路线总览）。
2. **AI 调研**：方向性调研落成笔记进 `.agents/docs/笔记/` 对应主题域（如 `渲染/` 的 SCGI/PBR/GI 调研四篇），共享体例为"对 ash_renderer 的启示"收尾；调研结论反过来修订路线图。
3. **拆解成大小步骤**：路线图把目标拆成步骤（M1~M8），每步骤再拆成段（如步骤 6 = 6.1 Hi-Z 遮挡 → 6.2 GPU LOD → 6.3 粗粒度流送 → 6.4 细粒度流送）；同一条依赖链的段顺序固定，独立段标明"不阻塞主线收官"。
4. 拆解粒度判据：一段 = 一次会话能"立案→施工→收官"的量（本工程多段为当日立案当日施工收官）。

## §三 第 2 步：每小步先立案（设计文档 + 施工计划）

"只写文档不改代码"的立案走 `$doc-plan-register`，产出四件：

1. **段目录** `N.M-段名/`（`.agents/docs/N-步骤/` 下）。
2. **施工计划** `施工计划：<段名>拆解.md`，固定栏目：定位与现状核实（先查现有代码/依赖到底什么样）、任务拆解 N.M.K、**判定线草案**（怎么算过，逐条可验证）、**待决项**（列明不擅自拍板，施工中或验收时落定）、测试方案、底座指向（上游参照实现/既有段复用）。计划开头与每个 N.M.K 都要有一句话说明（做什么/铺路/不主张什么）。
3. **段 README**：段索引与材料清单，开工时转任务面板。
4. **三处状态流转**：计划头部、段 README、路线图同步（⬜ 已立案 → 施工中 → ✅ 收官）。

立案即冻结范围：施工中发现计划未覆盖的结构问题，在被后续段依赖之前先提出，动不动由用户拍板。

## §四 第 3 步：切分支施工与回归测试

按 `$plan-execute` 执行（阶段一~六），要点：

- **分支**：`git switch -c goal/<段号>`，同名分支跨会话接续；调用即授权按任务粒度**分组提交**（docs 与 feat 分开），推送/并回/删分支不在授权内。
- **测试手段三级递进**（按侵入程度选，见 `测试规范与方式`）：BRP Remote 首选（`tools/brp.py`，新操作优先扩自定义方法族，可复用）→ 打 Log 重编译 → 鼠标注入仅限用户声明无人模式。
- **压测/回归脚本化**：压测入口进 `tools/`（如 `scene_hiz.py`/`scene_lod.py`/`scene_stream.py`/`scene_fine.py` 配方族），判定线逐条自动核对，收官后整段可一键重跑回归。
- **画面类验证**：按 `画面功能视觉验证`——PrintWindow 截图 + 当前会话模型直接读图；取证截图进根目录 `.temp/`，不入 docs。
- **代码验证线**：clippy 全净（整仓 `cargo fmt` 禁止，手工排版仓库）、零 VUID、宿主 exit 0、库测试全过。
- **修复循环**：测试暴露的问题修复→复测→补提交，循环到判定线全过或如实报"未过"；压测实抓的钉子（首钉）记进施工记录。

## §五 第 4 步：四件产出

| 产出 | 落点 | 要点 |
|---|---|---|
| 施工记录 | `N.M.K-<段名>施工记录：….md` 入段目录 | 写"实际做了什么"，待决项钉明结果；计划文档只流转状态，不回写实现细节 |
| 施工总结 | `<段名>流程：<从…到…的各级账面>.md`（流程导读） | 新机制/新数据流段的收官定例：账面全景、新文件分工表、逐时刻走读、失败与稳态路径；**文末附代码改动简要解析**（按文件列要点与取舍，`git show --stat` 实数）——即变更文档 |
| 原理文档 | 段内讲解篇/机制深潜，或专题笔记（如 `Hi-Z 原理篇`、`GPU-Driven 本质`） | 机制先于比喻，对着读者下一个问题写；用户复述校准的结论回写 |
| 状态流转 | 计划头部 + 段 README + 路线图三处 | 状态标记先看路线图现行写法再落笔 |

## §六 第 5 步：用户验证、问答与优化

1. **验证**：用户按段 README 验收状态与判定线逐条对账；步骤级再做验收归档（逐条复核 + 归档轮 lint 收敛，参照步骤 4 验收归档先例）。
2. **原理问答**：用户复述理解求校验，AI 从原理与取舍讲起（Unity/UE 类比）；**校准出的偏差要回写文档**——讲错的地方和被纠偏的理解都是知识（如 Hi-Z 原理篇六轮校准）。
3. **代码校验优化**：归档轮重跑 clippy/lint 收敛新告警；结构缺陷主动提出不等用户问（时机 = 被后续段依赖之前）。
4. **遗留挂账**：没做/不做的去处分流——缺陷进 `待修复清单.md`，编号体系外的拓展需求进 `外置拓展需求.md`（条目 = 来源/内容/恢复条件/边界）。

## §七 第 6 步：灯笼合并回 main

只在用户拍板后执行，走 `merge-chain`：

1. 源分支（`goal/<段号>`）先变基到目标分支，再同链合并（避免分叉时丢上下文）。
2. 合并指令即含**推送授权**（仅限目标分支）；本地 `main` 直追 `okzkx/main`。
3. 删临时分支收尾；按批次记账（批 N 合入哪些段），分批推进、报告须标注 SHA 下批会改写。

## §八 分工边界

| 用户拍板 | AI 自主（如实报告） |
|---|---|
| 项目目标与路线取舍 | 调研、拆解草案 |
| 计划批准、待决项裁决 | 立案文档撰写与三处状态同步 |
| 结构缺陷取舍、是否返工 | 分支上按计划施工与分组提交 |
| 无人模式授权（仅此时允许真实鼠标注入） | 三级测试、判定线核对、修复复测 |
| 验收结论、遗留项定性 | 施工记录/流程导读/原理篇撰写 |
| 并回、推送、删分支 | 灯笼合并的技术执行（拍板后） |

## §九 样例走读：6.3 粗粒度流送的一天

2026-10-19 该段走完了整个六步循环，可作对照样本：

1. **目标与拆解**：路线图步骤 6（M5）拆出 6.3 段，与 6.1/6.2 构成依赖链"遮挡省下的量 → LOD 换来的粗细 → 超预算世界靠流送"。
2. **立案**：`6.3-粗粒度流送/施工计划：粗粒度流送拆解.md`——现状核实（4.3 readiness 与 4.4 停尸房为账面地基）、任务拆解 6.3.1~6.3.6、判定线六条、待决六项。
3. **分支施工**：`goal/6.2` 分支（6.2/6.3/6.4 同日连续施工）上实现驻留管理器（mesh bytes 预算/请求=脏标重传/淘汰=回收账/冷却窗），`tools/scene_stream.py` 超预算游历压测 7/7。
4. **产出**：施工记录《6.3.1-6.3.6-…》、流程导读《粗粒度流送流程：从预算账到请求与淘汰动作的各级账面》、段 README 状态流转。
5. **验证与钉子**：首钉实抓——"关闭沿不重驻留致 B 面回不到基线"，压测④实抓即修（激活态下降沿全行置脏），钉子与修复记入施工记录与提交信息。
6. **并回**：`goal/6.2` 七笔 feat/docs 留待用户拍板并回（未并回状态本身也是如实报告的一部分）。

——以上六步任何一步的细则疑问，以 §一 表中所引正本为准。
