# 桌面 GPU 硬件单元：四块专用电路与 Vulkan 逻辑阶段的对应

Vulkan 的管线阶段（`VERTEX_SHADER`、`FRAGMENT_SHADER`、`COMPUTE_SHADER`、`TRANSFER`……）是同步用的**逻辑划分**，规范不规定任何命令必须走哪个硬件单元。桌面 GPU 普遍有光栅器、纹理单元（TMU）、ROP、DMA 拷贝引擎四块专用电路，这是各家为效率做出的设计共识，不是规范要求。本篇硬件细节以 NVIDIA Turing（本机 RTX 2060）为主、注 AMD 对应名；厂商未完全公开的部分写的是公开资料的通行说法。

## 0. 判定线

- **逻辑阶段 ≠ 硬件单元。** 可编程阶段（顶点/片元/compute/曲面细分/几何/mesh）在统一架构上共用同一池着色器核心（SM），哪个线程组落哪个 SM 由运行时硬件调度器动态决定；固定功能阶段（顶点装配、光栅化、深度测试、混合）落专用电路，映射由硬件设计固定；`TRANSFER`（拷贝/清屏/blit）落哪里由驱动决定。
- **统一的是结果约束，不是走哪个单元。** 规范保证的是：命令只能进具备对应能力的队列族、格式能力要先查、同步范围按提交顺序划定、同一 draw 内数据按逻辑阶段流动、同一采样点的测试/混合/写入按图元顺序、显式同步与内存模型的语义。CPU 软件实现（SwiftShader、lavapipe）没有任何专用单元也通过一致性测试，就是反证。
- **正确性只按逻辑阶段推理；硬件单元是性能分析的坐标系。** 应用能控制的只有：提交到哪条队列、屏障/信号量的阶段掩码（约束）、工作怎么切分。阶段掩码越准，驱动可重叠的余地越大；`ALL_COMMANDS` 等于让后面的工作等前面全部做完。

## 1. 一块桌面 GPU 的数据流

```
            ┌────────────── PCIe ──────────────┐
 系统内存 ⇄ │ DMA 拷贝引擎（copy engine）       │ ⇄ 显存
            └──────────────────────────────────┘
命令缓冲 → 命令前端 ─┬→ 几何前端：取顶点、图元装配、裁剪/剔除、曲面细分
                     │        ↓
                     │   光栅器 + 粗粒度深度剔除（Hi-Z / ZCULL）
                     │        ↓  生成片元，打包成线程组
                     └→ SM 着色器核心池（顶点/片元/compute 共用）⇄ 纹理单元 TMU
                              ↓  片元颜色和深度
                         ROP：深度/模板测试、混合、MSAA、压缩
                              ↓
                         L2 缓存 → 显存控制器 → 显存
 显存 → 显示引擎（扫描输出到显示器）    其他：视频编解码、RT core、Tensor core
```

能编程的只有中间的 SM，其余框都是专用电路。

## 2. 光栅器（含图元装配和粗粒度深度剔除）

- **做什么**：把三角形的三个顶点变成它覆盖的采样点（片元）——覆盖测试 + 沿三角形插值属性（UV、法线等）。前面一般还有图元装配、裁剪、背面剔除；后面紧跟一层粗粒度深度剔除（NVIDIA 叫 ZCULL）：先查一块屏幕区域已写下的深度，整块被挡住就直接丢掉，不派给 SM。
- **为什么做成专用电路**：每帧几十亿次覆盖判断，运算极规整又在最热路径上，专用电路的吞吐和功耗比着色器实现好一个数量级。
- **规模**：Turing 每个 GPC（一组 SM 的集合）配一个光栅引擎，按屏幕分块分工；AMD 是每个 Shader Engine 一个 Rasterizer。
- **Vulkan 对应**：光栅化本身不是可单独写进屏障的阶段，夹在 vertex/geometry 与 `EARLY_FRAGMENT_TESTS` 之间；粗粒度深度剔除属于 early fragment tests。
- **本工程**：④ G 缓冲先写深度或大体近→远画时，ZCULL 能整块丢弃被挡片元；shader 里 `discard` 或改写深度会让早期深度测试失效或降级。硬件早期剔除是像素级的，与本工程的 Hi-Z 遮挡剔除（compute 里按物体剔除、draw 之前整个删掉）是两回事。

## 3. 纹理单元（TMU / Texture Unit）

- **做什么**：shader 采样一次纹理，TMU 完成整串工作——
  - 算地址：UV、wrap/clamp 寻址、选 mip 级；
  - 从缓存取像素；
  - 解压块压缩格式（BC1~7 / ASTC）；
  - sRGB 转线性；
  - 过滤：双线性 4 像素、三线性跨两级 mip、各向异性最多 16× 方向采样，结果交还 shader。
- **为什么做成专用电路**：一次三线性采样要读 8 个像素、几十次乘加再加格式解码，全放进 shader 会吃掉大量算力和寄存器。
- **规模**：Turing 每个 SM 4 个 TMU；RTX 2060 是 30 个 SM、120 个 TMU。
- **Vulkan 对应**：format feature `SAMPLED_IMAGE_FILTER_LINEAR` 本质是问“TMU 对这个格式支不支持线性过滤”；`maxSamplerAnisotropy` 是它的各向异性上限；blit 的 `vk::Filter::LINEAR` 在图形队列上常见实现也是借 TMU 过滤。
- **本工程**：bindless 采样全走 TMU。mip 的意义不只是不闪，还在缓存命中——远处物体采低级 mip，取的像素少且内存上挨得近；这也是 mip 续批必须生成完才放行的原因之一。storage image / storage buffer 读取不经过过滤，走普通加载路径。

## 4. ROP（Render Output Unit；AMD 叫 RB / Render Backend）

- **做什么**：片元着色完成后写进附件的最后一段——
  - 晚期深度/模板测试；
  - 颜色混合（`blendOp`）；
  - MSAA 采样合并；
  - 颜色/深度无损压缩（如 NVIDIA delta color compression）；
  - 写回 L2 和显存。
- **为什么做成专用电路**：混合是对同一像素“读 → 改 → 写”，且必须按图元提交顺序。让成千上万片元线程自己抢锁效率极差；ROP 在电路上保证同一像素写入按序，应用无须介入。
- **规模**：ROP 与显存控制器按分区绑在一起。RTX 2060 是 192 位总线、48 个 ROP，即每 32 位控制器 8 个 ROP——砍显存位宽，ROP 跟着变少，填充率和带宽一起下降。
- **Vulkan 对应**：`LATE_FRAGMENT_TESTS` 与 `COLOR_ATTACHMENT_OUTPUT`。后者正是 image_available 的等待阶段、④ G 缓冲写颜色开始的地方——“第一次写颜色就被拦”，拦的就是 ROP 往附件写之前这一段。
- **本工程**：
  - 合成、Bloom 4 降 + 4 升、tonemap、SMAA 三遍都是全屏 pass：片元着色器轻，每像素却都要经 ROP 写一次附件，往往受 ROP 填充率与显存带宽限制，不是 SM 算力；
  - G 缓冲一次写 3 张颜色附件 + 1 张深度，写入带宽是延迟渲染的主要成本；
  - 透明前向混合依赖 ROP 的按序保证，所以 draw 之间不用加屏障。

## 5. DMA 拷贝引擎（Copy Engine；AMD 叫 SDMA）

- **做什么**：在 PCIe 两端（系统内存 ↔ 显存）或显存内部搬运数据，独立于 SM 运行、不占着色算力。
- **为什么做成专用电路**：搬数据只需地址生成和突发读写，用不着几千个着色线程；独立引擎让上传和渲染同时进行——这就是 transfer 专用队列族存在的意义。
- **能力边界**：只做逐字节拷贝与 buffer ↔ image 布局重排，不做格式转换和过滤——blit 不能交给它、mip 续批必须回图形队列的硬件原因；有对齐要求，Vulkan 用队列族属性 `minImageTransferGranularity` 暴露，专用 transfer 族在部分硬件上比图形族更粗。
- **Vulkan 对应**：“族 1：只有 TRANSFER”就是驱动把拷贝引擎暴露给应用。图形队列上提交的 copy，驱动可能交给拷贝引擎，也可能用 SM 跑拷贝 shader，选择不公开。
- **本工程**：Q1 上传批把 staging（落在 CPU 可写的系统内存）经 PCIe 搬进只有 GPU 访问的显存。RTX 2060 是 PCIe 3.0 x16，理论单向约 16 GB/s，实际更低。[设备队列在飞快照](../Vulkan/_assets/queue-inflight-moments.svg) 时刻 ③ 的“大批没拷完、整条图形队列冻结”，瓶颈在 PCIe 通道和拷贝引擎，与 SM 忙不忙无关。

## 6. 另外两个与帧循环直接相关的单元

- **显示引擎（display engine）**：按刷新率从显存读出帧图、扫描输出到显示器。swapchain 的“演示引擎”= 显示引擎 + 操作系统合成器（Windows 窗口模式下是 DWM），所以 image_available 何时置位取决于它们何时用完那张图。
- **命令前端**：每条硬件队列一个，按顺序取命令。“同一队列的提交按序被取出”是这块电路的行为；取出后各阶段流水执行，相邻 draw、相邻 cmb 的首尾可以重叠，直到遇到屏障。

## 7. 规范为什么不强制这些单元

1. **CPU 软件实现**：SwiftShader、lavapipe 没有任何固定功能单元，光栅、过滤、混合全用 CPU 代码模拟，照样合规。
2. **移动端分块延迟渲染（TBDR：Mali / Adreno / PowerVR / Apple）**：先跑完整帧顶点、按屏幕分块，再逐块跑片元；混合与深度测试在片上块内存完成，ROP“写回显存”这步基本消失；Apple 与 PowerVR 还支持 shader 直接读写当前像素做可编程混合。
3. **同一功能放在不同地方**：AMD RDNA 的 NGG 把顶点与几何阶段合成 primitive shader 在 SM 上跑；几何着色器、曲面细分在部分硬件上完全由着色器模拟；mesh shader 绕过传统取顶点与图元装配前端。
4. **差异的暴露方式**：规范只描述可观察结果，硬件差异通过 feature / format feature / limits / 队列族能力暴露。不能问“有没有 TMU”，只能问“这个格式能否线性过滤”；不能问“有没有拷贝引擎”，只能问“有没有只带 TRANSFER 的队列族”。

## 8. 用单元模型判断瓶颈

| 瓶颈类型 | 典型症状 | 本工程可能出现处 |
|---|---|---|
| SM 算力（ALU） | 着色器运算重；降分辨率收益不成比例 | 合成光照、分簇光照循环 |
| 纹理（TMU / L1TEX） | 采样多、跨度大、mip 用不上 | G 缓冲材质采样、SMAA 查表 |
| ROP / 显存带宽 | 全屏 pass 多、附件格式宽 | G 缓冲写入、Bloom 链、后处理链 |
| 光栅 / 几何前端 | 三角形多而小（每个只盖几个像素） | 大场景远处高模（所以有 LOD） |
| 拷贝 / PCIe | 上传批大、图形队列在等票据 | 大批资产首次上传 |

Nsight Graphics 的 GPU Trace 按单元列出吞吐占比（SM、L1TEX、ROP 类、几何前端类、L2、显存、PCIe 等，名称以工具显示为准），哪项接近 100%，瓶颈就在哪个单元。方法论见 [渲染性能归因方法](../开发方法/渲染性能归因方法.md)。
