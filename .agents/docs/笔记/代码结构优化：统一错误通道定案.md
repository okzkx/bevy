# 代码结构优化：统一错误通道定案

> 2026-10-10 定案,**未施工**。起因:4.1 对象增量施工中(`upload.rs` 容量保证段)发现 Tier② 收尾样板(`if let Err { error + exit.write + return }` 与判空 let-else 同款)在一个文件里重复九处,用户提出"错误即冒泡、上层统一收尾"。三轮讨论后定案:**用官方 API(`set_error_handler` + `Severity` + 看门 system)统一裁决,壳+body 模式整体退役**。本文是设计定案与落地清单;两 Tier 思想本身不变,见宪法篇《[错误处理体系:两Tier思想与优雅退出](错误处理体系：两Tier思想与优雅退出.md)》。

## 0. 判定线

**冒泡与否只看一件事:本次失败是否要求提前 return。**

- **不 return 的,就地 log,不进错误通道**——覆盖两类:强时序性过程记录(第几次重试、本帧让路几张贴图,离开现场时间线就没有意义)与**循环内逐项降级**(转换拒绝、材质未到货,log 后 continue)。第二类"影响不大"但**不能冒泡**:冒泡的物理语义是放弃整批剩余项,逐项跳过永远就地。
- **要 return 的才冒泡**,消息用 `.context(...)` 进错误值,**错误点不再打 log,handler 统一打**(ErrorContext 白送出错的 system 名)——单点日志,零重复。
- **return 之后的走向由 Severity 裁决**:`Severity::Warning` = 影响不大、下帧自愈;非 Warning = 状态不可信,优雅退出。
- **日志落点跟着 return 走**:不 return 的就地打,要 return 的搬进 handler。

## 1. 问题:九处同款样板

`ash_renderer/src/driver/upload.rs` 的上传 system(返回 `()`)内部,Tier② 收尾样板重复九处(行 221/226/231/255/306/311/343/359/398-402),每处五行:错误点 `error!` + `exit.write(AppExit::error())` + `return`。用户期望的形状是 `?` 一行冒泡,上层统一 log / 优雅退出。

现役答案 `frame_body` 壳模式(`host/frame.rs:128-183`:system 壳返回 `()`,主体拆 `frame_body(...) -> Result<(), TierError>`,`?` 冒泡到壳,壳 match `Warn => {}` / `Fatal => exit.write(...)`)虽可行,但用户批评:**凭空多一层嵌套,收尾逻辑还是每个 system 各写一遍壳**,没有真正"统一"。

## 2. 机制事实(Bevy 0.20.0-dev 源码核实,2026-10-08 与 2026-10-10 两轮)

- system 返回 `Result<T, 自定义E>` 时整个 Result 被当普通值,Err **静默吞**(编译照过)——`SystemParamFunction` 的错误路由靠 `IntoResult`(`function_system.rs:253`),只有 `Result<T, BevyError>` 转 `RunSystemError::Failed` 上交执行器。
- 执行器每帧取 `world.fallback_error_handler()`(`schedule.rs:604`),`Failed(err)` 就地交 handler;单线程执行器调用点 `single_threaded.rs:138-141`,**多线程执行器在 worker 线程就地调**(`multi_threaded.rs:815-831`)。
- `ErrorHandler = fn(BevyError, ErrorContext)`(`error/handler.rs:105`)是裸函数指针,无 world 访问权——写不了 `AppExit`,这是 Tier② 裁决进不了 Bevy 通道的旧结论。
- 默认 handler `match_severity` 按 `Severity` 元数据路由,无标注默认 `Severity::Panic` → panic;`BevyError` 自带 `with_severity()` / `context()`(anyhow 承载),`App::set_error_handler`(`bevy_app/app.rs:1493`)可换 handler。

## 3. 被否决路线:改 bevy_ecs 让 handler 拿 World

最直觉的改法是 `ErrorHandler` 签名加 `&mut World`。被否决,三条理由:

1. **架构堵死**:多线程执行器(非 WASM 默认)在 worker 线程就地调 handler,worker 没有 `&mut World`——要改就得把错误收集挪到主线程统一调,动两个执行器骨架;
2. **分层禁止**:`bevy_ecs` 不依赖 `bevy_app`,执行器不能引用 `AppExit`,要在执行器里写退出消息还得加一层 trait 注册机制;
3. **维护代价**:改动面 5~8 个文件、破坏公共 API,且 `src/error/` + `src/schedule/executor/` 是官方 error handling 活跃演进区——本仓库持续分批吃上游,这批文件每批 merge 都是冲突热点。

## 4. 定案:官方统一通道(零 fork 改动)

一次性基建三件,全局生效:

```rust
static FATAL: AtomicBool = AtomicBool::new(false);

fn tier_handler(err: BevyError, ctx: ErrorContext) {
    match err.severity() {
        Severity::Warning => warn!("{ctx}: {err}"),           // Tier①
        // panic 岗保留:有 payload 的 Panic 原样 resume_unwind,保住 backtrace 取证
        Severity::Panic if payload_exists(err) => resume_unwind(...),
        _ => { error!("{ctx}: {err}"); FATAL.store(true, Ordering::Release); }, // Tier②
    }
}

// 看门 system(Update 早位):置位 → 优雅退出
fn fatal_gate(mut exit: MessageWriter<AppExit>) {
    if FATAL.swap(false, Ordering::AcqRel) { exit.write(AppExit::error()); }
}
// app.set_error_handler(tier_handler); + 注册 fatal_gate
```

业务 system 之后的形状——无壳、无 body、无 exit 参数:

```rust
fn upload_system(...) -> Result<(), BevyError> {
    pool.ensure_capacity(...).or_fatal("池容量保证失败,上传链无法继续,优雅退出")?;
    let vertex_buffer = pool.vertex_buffer().ok_or_else(|| fatal("容量保证后顶点池仍缺席,状态矛盾"))?;
    // ...
}
```

顺带收益:observer/command 的错误也走 fallback handler,一套裁决全场景生效;忘标 severity 的错误按 Tier② 优雅退出而非 panic,"非必要不 panic"进一步坐实。

## 5. 日志分流(用户定案,2026-10-10)

**强时序性的繁琐 verbose log 就地直接打,不进通道;有特定禀报、影响不大、或一句话能完整说明问题的,冒泡统一处理。** 对应关系:

| 日志性质 | 出口 | Severity |
|---|---|---|
| 时序性过程记录(重试计数、让路数量) | 就地 log,正常控制流 | — |
| 循环内逐项降级(缺材质、转换拒绝) | 就地 log + continue | — |
| 整批/整帧让路,下帧可自愈 | 冒泡 | `Warning` |
| 状态不可信,一句话说清(判空矛盾、创建失败) | 冒泡 | 非 `Warning` |

**旧定案翻案**:壳模式下"日志在错误点打完,错误值无负载"(`TierError` 无负载的依据)——统一 handler 后改为**错误值带 context 负载,日志落点挪到 handler**。`or_warn`/`or_fatal` 糖随之改写:从"就地 log + 返回 `TierError`"改为"log(如需)+ `with_severity` + 返回 `BevyError`"。

## 7. 坑钉

- **全局静态是进程级的**:多 App 并存会串扰——本项目单进程单 App,写进代码注释钉死前提;
- **置位到退出有半帧延迟**:FATAL 置位后本帧剩余 system 照跑,runner 帧末查 `AppExit` 才停——与壳模式等价(壳 return 也只跳过本 system,不拦其他 system),且本帧正常收尾更平滑;
- **handler 里必须保留 panic 的 `resume_unwind` 分支**:panic 会被 `handle_unwind` 捕获转回 handler(`handler.rs:149-159` 先例),自定义 handler 若吞掉 payload,丢 backtrace 取证能力——panic 不设岗,但岗位要还给 panic;
- **`Skipped`(参数校验失败)静默跳过,不算错**,不进通道,勿混淆。
