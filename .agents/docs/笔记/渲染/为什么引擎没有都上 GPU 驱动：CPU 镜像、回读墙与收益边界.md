# 为什么引擎没有都上 GPU 驱动：CPU 镜像、回读墙与收益边界

> 2026-10-15 建档。出处：5.2 视锥剔除开工前"为什么现代引擎不都采用 GPU Driven 模式"之问——当时全库只有[入口篇](../项目目标与Bevy使用指南.md)一句免责声明（"不宣称所有现代引擎都无需 CPU 镜像"），没有正面论证，本文补这篇。与上游知识库《GPU-Driven Rendering》（`C:\Users\zengkaixiang\.agents\docs\游戏制作\游戏引擎\渲染\渲染管线\GPU-Driven Rendering.md`，绝对路径引用）分工：那篇 §8 讲 API/硬件门槛与调试工具成本，本文讲**架构层理由**，门槛部分引用不重复。GDR 本体机制见[GPU 驱动第一课](../5-GPU驱动与常驻大场景/5.1-常驻绘制数据/GPU驱动第一课：从逐draw推参数到实例索引读表——新旧两套写法对照.md)，本文默认你已读过它的 §1。

## 0. 结论先行

**GPU-driven 不是"更先进的默认形态"，是特定规模与内容形态下的专项优化。** 它只买走一样东西：CPU 逐对象的"发现—剔除—装配—提交"循环。留下三类它管不了的事：

1. **CPU 镜像消不掉**——游戏逻辑、物理、动画、AI 都要在 CPU 读同一份场景状态，GPU 常驻表只是渲染侧的投影；
2. **回读墙**——GPU 算出的可见性结论，CPU 逻辑要么等不起（GPU 时间线延迟），要么读过时的（对 Gameplay 是错误答案），要么自己在 CPU 再算一份（GPU 剔除对逻辑贡献为零）；
3. **收益边界**——对象数没到量级时，GDR 的常驻表纪律（环、fence、槽位、停尸房）是纯负优化。

§1~§6 逐条展开，§7 收"行业实际形态"，§8 自测。

## 1. 先钉准 GDR 到底买走了什么

先排除一个误解（上游参考篇 §1 的钉子，这里收紧一次）：GDR 改变的不是"资源放哪"——顶点/纹理从 VBO 时代就常驻显存了。它买走的是**决策权**：画哪些（剔除）、按什么顺序画（排序合批）、每笔的参数从哪来（逐 draw push → 实例索引读表）。[第一课](../5-GPU驱动与常驻大场景/5.1-常驻绘制数据/GPU驱动第一课：从逐draw推参数到实例索引读表——新旧两套写法对照.md)的新旧代码对照：旧写法 CPU 逐对象装配 DrawList、每物体每帧 96B push constants；新写法 CPU 只递 4B 实例槽号，参数本体住在 GPU 里。

**本文剩下全部内容就是这个"决策权搬运"的边界**：搬走的前提是"决策结果只服务绘制"。凡是结论还要被 CPU 消费的（AI、音频、网络、Gameplay），这条搬运路线就断——§2/§3；凡是决策本身的复杂度超过收益的（小场景、透明排序、特例需求），就不该搬——§4/§5/§6。

## 2. 理由一：CPU 镜像消不掉，权威数据不能进 GPU

游戏引擎的权威场景状态必须住在 CPU 侧（ECS World / GameObject 层级 / Actor 树），因为每帧有一整套**非渲染系统**要随机读写它：物理步进写 Transform、动画写骨骼、AI 做射线查询、网络序列化快照、Gameplay 按语义增删对象。这些访问的形状是**细粒度、随机、写密集**——CPU 内存模型（缓存行、原子、锁）就是为这个形状造的。

GPU 显存是相反的形状：并发线程成千上万，但没有细粒度同步原语（锁、原子链表做不了或极慢），随机写和分支都贵。把权威场景状态搬进 GPU = 让物理/AI/网络全上 compute = 用一个只擅长大规模规则并行的处理器去跑一个以随机读写为主的数据库，两头错位。

所以行业的实际形状是**单向投影**：权威状态住 CPU，渲染侧把"画"需要的字段子集投影成 GPU 常驻表。本仓库正是这个形状——4.1 的 InstanceLedger 以 ECS World 为权威、flush 脏行增量写入对象表；对象表只记"物体是什么"（范围、材质槽、包围体），状态（model 矩阵）单独走模型环。**投影是只读镜像，不是搬家**——CPU 那份才是本体。这就是入口篇"不宣称所有现代引擎都无需 CPU 镜像"的机制内容。

Unity 对照：DOTS/ECS 把数据搬进 chunk 是为了让 JobSystem 并行，**仍然在 CPU**；GPU Resident Drawer 的 GPU instance data 同样只是渲染投影，权威还在 ECS World。UE 的 FPrimitiveSceneProxy 是 CPU 场景 primitive 的渲染侧镜像，每帧 upload——UE 干脆没做"写一次常驻"，因为它的场景更新形状（大量动态 primitive）下增量换槽不值。

**这一条为什么挡住"全 GPU 化"**：只要权威数据在 CPU，每帧就有一条"CPU 状态 → GPU 表"的同步通道要养。本仓库 4.1~4.4 四段修的全是这条通道（变更发现、资产失效、异步就绪、回收热重载）。GDR 并没有把这四段的成本变成零，只是把它们从"每帧全量"压成"增量"。**引擎要上 GDR，先得有这套增量底座——这是比 API 门槛更贵的工程量门槛。**

## 3. 理由二：回读墙——CPU 逻辑等不起 GPU 的答案

剔除、遮挡、LOD 决策搬上 GPU 后，结论住在显存里。CPU 侧任何想消费它的系统面前隔一堵墙：

- **延迟**：结果本帧算完，CPU 最早帧尾（通常隔 1~2 帧）才能读。同步 fence 等待把 CPU 拖进 GPU 时间线（本仓库帧首 fence 等待=背压，见环机制篇）；异步读回则结论天然过时。**晚一帧画出来无所谓，晚一帧告诉 AI"你看得见玩家"就是事故**——AI 视线、音频遮挡、网络兴趣管理、相机遮挡淡出，要的都是"现在"的答案。
- **重复计算**：这一条对 CPU 管线的对比不是"读回比 CPU 算慢"的量级问题，是性质问题——CPU 管线里可见性是剔除循环的免费副产品（同 tick、同内存，逻辑顺手拿）；结论上了 GPU，逻辑只能三选一：等、读过时的、**自己在 CPU 再算一份**。第三条意味着 GPU 剔除对逻辑贡献为零、CPU 剔除照跑——GDR 只省了绘制半边，逻辑半边的账一分没少。
- **节拍耦合**：回读把逻辑系统的执行时机挂上渲染帧时间。GPU 负载一高回读点推迟，逻辑跟着抖——引擎架构上不会允许。
- **本仓库红线的机制内容**：主计划 §2"CPU 不回读可见集、不逐对象重建 draw list"防的就是这条路——CPU 一旦为"决定画什么"回读，决策权就流回 CPU，indirect 闭环断裂、提交墙回来。诊断性计数回读（2026-10-15 放行）只进计量不进决策，原则是**读数不投票**。

所以可见性的天然分工：**给绘制用的可见性 → GPU 算；给逻辑用的可见性 → CPU 算便宜的那部分**（粗粒度射线、距离判定），或另设独立异步链路。没有引擎会为省一次 CPU frustum 求交去动这堵墙。

## 4. 理由三：透明与排序——GDR 不买走排序难题

混合（blend）数学上不可交换，"从后往前按某种粒度排序"是半透明的**正确性要求**——这一点与管线形态无关：Deferred 同样处理不了半透明，不透明走 G-buffer 延迟光照、半透明单独 forward pass 借不透明留下的深度；GPU-driven 引擎同构，不透明走 indirect 主通道、半透明独立 forward。真正值得看的是两点：

- **排序粒度才是天花板，且与谁算无关**：per-object back-to-front 对相交、大物体本来就是近似——CPU 算和 GPU 算一样粗。instance 粒度的深度排序可以在 compute 里做（GPU 排序 → 按序生成 indirect），省的是 CPU 排序时间，但精度一步没涨；精确到像素是 OIT（逐像素链表、近似合成）的活，与管线无关。**所以这条的理由不是"GPU 排序做不了"，是"GDR 不买走排序难题，只把同样的近似换个地方算"**——多一层结构，少一分好处。
- **Nanite 只吃不透明的深层原因也不止排序**：vis-buffer/微三角形"先写后算"的形态，与 blend"逐像素读改写目标色"的语义根本冲突。UE5 最极致的 GDR 落地把半透明、发丝、植被 alpha blend 全留在传统路径，官方文档明说。
- 换句话说：能写深度的几何才有资格进 GDR 主通道。这天然把"画什么"分成两个世界，**GDR 是其中一个世界的优化，不是渲染的替代品**。

## 5. 理由四：收益边界——对象数不到量级是纯负优化

CPU 视锥剔除是 O(n) 平面求交，一万个对象亚毫秒级（本仓库 5.2 的 CPU 参照用的就是同一套数学：`conservative_world_aabb` + 平面求交）。CPU 真正的痛在**提交循环**——每对象 API 调用、参数装配、状态切换，几千 draw call 起才开始疼。

GDR 的固定成本清单（本仓库 5.1 一样不缺，全是真实代码）：

| 固定成本 | 本仓库落点 | 没到规模时 |
|---|---|---|
| 常驻表纪律（写一次+换槽+停尸房多活一帧） | 对象表/材质表槽位生命周期 | 纯管理负担 |
| 环 ×N 轮转 + fence 时机纪律 | 模型环/材质环/帧槽环 | 小场景整块重写更便宜 |
| 增量账本（发现/稳定槽/脏行 flush） | 4.1 InstanceLedger | 全量快照更简单 |
| 剔除结果不可 printf，要专门回读计量 | 5.2.4 诊断性回读 | CPU 剔除打 log 就行 |

**判据一句话：GDR 每一刀省的是"每对象 × 每帧"的 CPU 成本，还回的是"一次性建、永久在册"的常驻纪律。对象数小时分子小分母大，负优化。** 本仓库拿十几个实例的头盔场景练全套纪律，是学费不是产品选择——真实产品在这个规模会直接 CPU 剔除 + 状态合批（Unity 标准路径就是 SRP Batcher），够用。

## 6. 理由五：特例成本与工具链引力

（API/硬件/内存门槛见上游参考篇 §8，不重复。）架构层还有两股引力：

- **特例成本**：Gameplay 驱动的绘制需求——选中高亮、debug draw、HUD 遮罩、逐对象材质变体——在 CPU 提交路径上是"多 push 一个对象"；在 indirect 路径上每条都要在 GPU 数据结构里开特例口子。引擎不可能只留快路不留慢路，结果是**两套路径长期并存、双份维护**，GDR 只覆盖其中一套。
- **工具链惯性**：profiler、抓帧、单对象单画、draw 诊断全围绕 CPU 提交接口建。indirect 化之后这些都挪进 RenderDoc/PIX 的 GPU 时间线，上游 §8 说的"调试难度"，在引擎团队视角是**全组工具链与工作流的更新成本**。

## 7. 行业实际形态：分层混合，不是二选一

| 层 | 谁在管 | 实例 |
|---|---|---|
| 权威场景状态 | CPU，永远 | 所有引擎 |
| 给逻辑用的粗可见性 | CPU | AI 视线、兴趣管理、遮挡淡出 |
| 大重复内容的细可见性与提交 | GPU-driven | 植被/岩石/群集：Unity 6 GPU Resident Drawer（opt-in）、UE Nanite（仅不透明）、Frostbite |
| 其余对象的提交 | CPU + 状态合批 | SRP Batcher、UE proxy 路径 |
| 半透明 | 独立路径（OIT 等） | 所有引擎 |

**头部引擎的答案从来不是"全上"，是"给数据形状合适的层开 GDR 通道，其他层照旧"。** 这也是本项目的路线形状：步骤 5 把"画哪些实例"的决策交给 GPU，但 CPU 参照永远在（5.2 判定线 1）、权威永远在 World——练的是那个"数据形状合适的层"的完整通道，不是把整个引擎搬进 GPU。
