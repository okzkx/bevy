# 显存纹理压缩：BCn 是显存格式，不是打包技巧

贴图压缩有两族，分界线是"数据以什么形态被 GPU 采样"。存储压缩（PNG、ZIP、Crunch 的盒子层）必须在进显存前解压成原始像素；块压缩（BCn/ASTC/ETC2 这些带数字后缀的格式家族）则让显存里驻留的、采样器读到的，**始终是压缩态**——解压单元做在采样硬件里，按块在采样瞬间现解。全篇围绕这条分界展开：显存占用由第二族决定，下载体积由两族叠加决定。

> 核心不变式：**资产的出生地决定格式，运行时只搬运不解压。** mip、块数据、sRGB 语义都在离线期定型；加载路径做的是把既成字节放进显存。

## 为什么 GPU 能直接采样压缩数据

RGBA8 用 4 字节存一个像素。BCn 把 4×4 像素打成一块，整块压缩成 8 或 16 字节——存的是块的端点色和每像素 2~4 bit 的调色板索引，采样时硬件按块展开。代价是块内有损（视觉上接近无损的档位也留了编码余地），收益是显存占用除以 4~8。

| 格式 | 每像素字节数 | 块内结构 | 典型用途 |
|---|---|---|---|
| BC1 | 0.5 | RGB 调色板 + 2 bit 索引 | 不透明颜色 |
| BC3 | 1 | BC1 颜色 + 插值 alpha | 带平滑 alpha 的颜色 |
| BC4 | 0.5 | 单通道 8 级插值 | 高度图、单通道掩码 |
| BC5 | 1 | 两个独立 BC4 通道 | 法线图（存 XY 重建 Z） |
| BC6H | 1 | HDR RGB（FP16 域） | 环境贴图、HDR 光照图 |
| BC7 | 1 | RGBA 多模式 | 高质量颜色 |

采样是逐块解压，成本几乎为零；线性过滤、各向异性过滤全部照常工作。shader 拿到的就是采样结果，和采未压缩格式没有语法区别。

## 按数据角色选格式，不按"质量好坏"选

每一家格式都是为特定数据形态设计的，选型是查表不是权衡：

| 贴图角色 | 选型 | 理由 |
|---|---|---|
| baseColor（不透明） | BC1_SRGB | 量大管饱，8× 压缩 |
| baseColor（平滑渐变/主角材质） | BC7_SRGB | BC1 的 2 bit 调色板会在渐变上出条带 |
| baseColor（混合/镂空材质） | BC3_SRGB 或 BC7_SRGB | 需要平滑 alpha 通道 |
| 法线图 | BC5_UNORM | 法线是数据不是颜色 |
| 单通道掩码 | BC4 | 0.5B/px |
| HDR 环境光 | BC6H | 唯一支持 HDR 域的家族成员 |
| UI 图集 | 不动 | 小图，压缩收益为零 |

两条铁律：

- **法线不进 BC1/BC3**。BC 的三个颜色通道共享调色板，通道间互相渗色，法线会糊；BC5 每通道独立插值，是行业标准做法。
- **数据图不用 sRGB**。roughness/metallic/掩码是线性数据，BC4/BC5 干脆不提供 sRGB 变体——这是特性不是缺失。

sRGB 的处理方式与 ash_renderer 输出链一致：颜色类贴图选 `_SRGB` 后缀格式，采样瞬间硬件完成 sRGB→线性，shader 里不手工 pow。

emerald 场景 225 张贴图全按 RGBA8 驻留，实测 4.6GB（RTX 2060 的 6GB 显存占 90%）。按上表主力 BC1/BC5、配角 BC7 分账后约 0.7~1.0GB——格式选型这一个决定，占掉显存问题的大头。

## 引擎怎么做：格式在导入/cook 期定型

Unity 与 UE 架构相同，差别只在离线层叠了什么：

- **Unity**：导入期按平台烘焙 BCn（PC = BC1/BC5/BC7，Android = ASTC），mip 链在压缩之前用 CPU 滤波生成，一起烘进资产。运行时加载 = 块数据直接上传。可选 Crunch 在包体上叠一层存储压缩，加载时解码回 BCn——解出来仍是块数据，不是原始像素。Texture Streaming 按显存预算流送 mip 档位。
- **UE**：cook 期烘焙 BCn + 烘焙 mip，烘完的块数据再过 Oodle Texture RDO——它重新编码块本身，让每个块仍然合法（显存里解出后还是标准 BCn），但对熵编码更友好，磁盘再省三到五成。加载时 Oodle 解码 → 得到 BCn → 上传。

这也回答了"为什么导入设置换格式、打包产物跟着变"：**包里装的就是将来进显存的那份字节**。选 ASTC 6×6，包内是 0.25B/px 的块数据；选 RGBA32，包内是 4B/px 原始像素。LZ4/LZMA 只是外层，解开后必须还原成块数据原样，因为 GPU 只认这些块。切换格式触发全量重导入，是因为每张贴图都在重新烘焙。包体大小和显存占用在量级上相等，因为它们是同一份数据的两个观察点。

## Vulkan 接入面：换格式，不换流程

BCn 在 Vulkan 里没有独立 API，是同一套 image/copy/采样流程下的格式替换。改动集中在四处：

**特性位**。BC1~BC7 的采样支持挂在物理设备特性 `textureCompressionBC` 上。桌面独显恒真，但纪律不变：支持（查询）→ 启用（无额外开关，特性位即授权）→ 使用（VUID 由验证层执法）。实测 RTX 2060：`textureCompressionBC = true`，`textureCompressionETC2 = false`，`textureCompressionASTC_LDR/HDR = false`。

**创建**。usage 只有三个合法值：

```text
usage: TRANSFER_DST | TRANSFER_SRC | SAMPLED
```

压缩格式不允许 `COLOR_ATTACHMENT` 与 `STORAGE_IMAGE`，`vkGetPhysicalDeviceImageFormatProperties` 直接拒绝。0 级 mip 的宽高必须是 4 的倍数（离线编码器自动做边缘 padding，资产侧保证）。mip 级数公式不变，末尾的 2×2、1×1 级合法。sRGB 变体就是格式本身，不需要 view 别名那套机制。

**上传**。`vkCmdCopyBufferToImage` 的算术从像素换成块：

```text
block_bytes = BC1/BC4 → 8，其余 → 16
level_bytes = ceil(w/4) × ceil(h/4) × block_bytes
```

`bufferOffset` 必须是 `block_bytes` 的倍数；`bufferRowLength`/`bufferHeight` 写 0 表示紧排。宽高小于 4 的末两级 mip 有部分块的例外条款与额外 VUID，实现时把最小尺寸用例喂给验证层跑通再定稿。

**mip 的出生地搬家——这是最大的改造点**。`vkCmdBlitImage` 不支持压缩格式（源和目标都不行），"GPU 逐级 blit 生成 mip"这条路径对 BC 纹理直接断链。替代是资产侧预烘焙：toktx `--genmipmap` 或编码器自带，所有级别在 staging 里排好，一次逐级 copy。ash_renderer 上传器现在的"续批 blit"（日志可查）对 BC 纹理整条跳过。

采样与描述符零改动：还是 `sampler2D`，bindless 双表的槽位机制、`DescriptorWriter`、管线布局全部不动。唯一动 shader 的是 BC5 法线——glTF 法线是 XYZ 三通道，BC5 只剩 RG，shader 里补一行 `z = sqrt(saturate(1 - dot(xy, xy)))` 重建，不补则光照全错。

## 格式家族与平台：桌面只剩 BC，移动双雄选型

Vulkan 的压缩贴图三族——BC（桌面）、ETC2/EAC（移动）、ASTC（移动）——各自挂独立特性位，硬件解压单元按家族制造，不支持就不支持，没有软件兜底。桌面 NVIDIA 不带 ETC2/ASTC；移动 GPU 全带 ETC2（GLES 3.0 基线强制），2016 年后的 Mali/Adreno 带 ASTC。

移动端选型（Unity 打 Android 的实例）：

- **ETC2 的唯一存在理由是保底**：覆盖 2013~2015 年的 GLES 3.0 设备。码率固定两档（RGB 0.5B/px、RGBA 1B/px），画质弱于 ASTC。
- **ASTC 是质量曲线赢家**：块尺寸 4×4 到 12×12 连续可调，码率 0.125~1B/px。ASTC 6×6（0.25B/px）比 ETC2 RGB（0.5B/px）体积减半、画质更好。HDR 模式和 3D 变体（光照探针）只有 ASTC 有。
- **块尺寸按贴图角色分**：baseColor 6×6 够，法线必须 4×4（法线是数据不是颜色，ASTC 大块会糊），UI/文字 4×4~5×5。
- 近五年机型为主的项目：ASTC 全量，不养 ETC2 双份资产。

跨平台时 BC 与 ASTC 是两个不相交的家族，要么离线各出一份资产（UE cook 模式），要么存 Basis/KTX2 中间格式、装机时一次转码（KTX2 是容器不是格式，显存收益取决于最终落进 `vkCreateImage` 的格式）。

## 压缩之外的正交杠杆

显存减量不止格式一轴。按投入产出排序：

1. **BCn 化**：一次改造，全局 4~8× 收益，见上面的接入面。
2. **mip 流送**：不动格式，只改驻留多少。贴图体积的大头永远在最上面两级 mip，远处的物只传 0~3 级，靠近再补。ash_renderer 步骤 6 的驻留管理器（档位账 + 缺口请求环）是现成骨架，缺"贴图按 mip 级分档"这一个粒度。机制见《[GPU LOD与流送](GPU%20LOD与流送.md)》。
3. **稀疏驻留**：把 image 拆成 64KB 页只绑定实际被采样的页，Vulkan 级虚拟纹理原语。RTX 2060 实测 `sparseResidencyImage2D = true`。工程量是流送的数倍，留给大世界阶段评估，机制见《[虚拟纹理调研](虚拟纹理调研.md)》。
4. **低带宽未压缩格式**：R8/R8G8/R5G6B5 捡漏，适合小图与杂项数据图，不值得单独立项。

UE/Unity 的公共形态就是"BCn + 流送"两条腿：格式把单张贴图的成本降下来，流送决定驻留哪部分。压缩与流送相乘，才是大世界显存预算的完整解。
