# 体素渲染调研：VXGI 的大场景证伪与光源分簇的可行条件

> 2026-10-20 沉淀（步骤 8 管线形状定案"deferred 主体 + Clustered Forward 透明层、开工即 3D cluster"当日的追问链：tile vs cluster → VXGI 适合大场景吗 → 体素光源剔除可行吗）。
>
> **一句话说明**：本篇把"体素/分块记账"家族的成败判别钉成一条成本公式——**记账内容 × 记账空间 × 账本寿命**，并给两个推论：VXGI（记辐亮度数据、铺世界体积、永久账本）在大型场景被行业证伪；3D 光源分簇（记 u32 索引、只铺视锥、一帧寿命）站在成本公式的最便宜档所以可行。本篇是[全局光照谱系调研](全局光照谱系调研：烘焙、探针、屏幕空间与世界空间缓存.md)里 VCT 一档的成败复盘，不改变步骤 9 SCGI 定案，也不主张引入体素 GI。

## 0. 判定线

- **分块记账的成本公式：成本 ≈ 记账内容 × 记账空间 × 账本寿命。** 同一种"把空间切成格、逐格记账"的结构，三个变量任一换档，成本档位就换天——这是本篇全部结论的母公式。
- **判别式：记"索引/决策"便宜且稳，记"数据/辐亮度"大场景喂不动。** 索引/决策类（光源列表、可见性标记）：载荷轻（u32 级）、寿命短（一帧内消费）、错也错得无害（保守列表只多着色几个像素，永不产生画面伪影）；数据/辐亮度类（体素 GI）：载荷重（RGBA16F+mip 链）、寿命永久（跨帧保鲜）、错误直接上屏。**决策类结构的容错率和数据类结构差一个量级。**
- **行业对"数据类"的修正路线是同一句话：只记表面，不记体积。** 真实大场景的几何贴在二维流形上，体积网格里的空气体素全是白记的；Lumen（距离场+表面卡片）与 SCGI（表面 patch）都把记账空间从 O(体积) 压回 O(表面积)——步骤 9 SCGI 定案已兑现这条修正。
- **决策类错得无害的前提是保守**：列表宁多勿漏（false positive = 性能损失，false negative = 剔错光源 = 画面 bug）。这与视锥/遮挡剔除的保守性纪律（5.2/6.1）同一条。

## 1. VXGI 为什么败给大场景（四条死因）

1. **内存是体积函数，不是表面函数。** 体素网格记的是整个三维体积，场景一放大体素数按立方涨，显存与体素化带宽先崩——这是与"大"的第一冲突。
2. **级联带来的"远处变糊"。** 世界空间网格跟相机走 clipmap 级联后，离相机越远体素越粗；大型场景的大部分画面恰好是"远处"，锥追踪采出来的就是糊掉的间接光。小场景（全动态、贴脸）藏得住，大场景藏不住。
3. **动态更新税。** 体素化要每帧把动态几何灌进 3D 纹理；静态部分可缓存，动态一多体素化本身成为主导成本。税根在"永久账本要做增量保鲜"。
4. **质量病根。** 光渗（薄墙漏光）与锥追踪走样是 VCT 的结构性缺陷，滤波只能缓解不能根除。

**行业图景**：2014~2017 热闹过一阵（NVIDIA VXGI、UE4 VCT 插件、《Rise of the Tomb Raider》PC 档 VXGI 选项），之后大型项目集体离场——大体量开放世界清一色走烘焙+探针、硬件光追（《赛博朋克》RT:Overdrive、《Metro Exodus Enhanced》）或表面缓存类（UE5 Lumen 明确不用体素做主缓存）；体素 GI 至今的活口是**小而全动态**生态位（《Teardown》整世界体素+路径追踪 GI，玩法天然需要体素，GI 搭车）。

## 2. 3D 光源分簇为什么可行（同一结构、另一档成本）

| 变量 | 3D Cluster 光源剔除 | 体素 GI（对照） |
|---|---|---|
| 记账内容 | 每体素一个光源索引（u32 级） | 每体素 radiance（RGBA16F + mip 链） |
| 记账空间 | 只覆盖视锥（屏幕 tile × 深度片） | 整个世界体积（clipmap 级联） |
| 账本寿命 | 一帧——用完即弃，下帧重建 | 永久驻留——跨帧保鲜 |

逐死因免疫：

1. **内存跟分辨率走、不跟场景大小走**。1080p、16×16 tile、32 深度片 ≈ 26 万体素，平均每体素挂 8 个光源时列表+计数仅几 MB，比一张 G-buffer 附件还小——VXGI 崩掉的"体积 × 立方"乘数在这里不存在。
2. **每帧从光源位置现算，零更新税**。没有历史要维护、没有跨帧一致性要保证、动态光移动零成本——"一帧寿命"直接取消了体素化的保鲜税。
3. **存的是决策结果不是被采样数据**，无光渗、无锥追踪糊；列表偏保守只是性能损失，画面零伪影。

## 3. 家族地图：可复用的四件 pattern（不是结构本体）

体素家族里能跨场景复用的是**模式与 kernel 原语**，不是某个数据结构本体：

1. **"逐 cell 求交 → 计数 → 前缀和 → 填列表"compute 流水线**——cluster 构建、粒子密度网格、SPH 邻居查询、OIT 片段排序、GI 探针分配全是同一套骨架，只换求交对象与 cell 形状。**这是引入体素概念最大的复用红利。**
2. **indirect 驱动的构建链**——"先数后填"两段 dispatch + indirect，即 build_indirect 思想在 compute 侧再用一次。
3. **mip 链归约**——VCT 的锥追踪沿体素 mip 采样（粗锥走粗 mip），与 Hi-Z 金字塔同构（深度换 radiance、MIN 换加权平均）；6.1 已把"沿 mip 归约 + 方向单测"练过一遍。
4. **clipmap 级联**——世界空间结构跟相机的大一统方案：8.3 CSM（光源空间）、VXGI（世界空间）、9.3 patch 池（Volume+Cell+cascade）三处同款，写熟一次处处省力。

## 4. 对 ash_renderer 的启示

- **步骤 8 开工即 3D cluster 已定案（2026-10-20 用户拍板）**：学习项目，2D tile 起步的省略不划算，3D 体素结构本身就是要练的东西。3D 特有两枚施工钉预告：**深度片按对数分布切**（近密远疏贴深度精度）；**体素总数内存账进 MemoryContract**（tile 数 × 片数 × 每体素列表）——这是 3D 比纸面多出来的两笔成本。
- **VXGI 不立项**：步骤 9 SCGI 的 patch 池（9.3）已是"世界空间记账、只记表面"的修正形态，世界空间分块记账的学习收益由 SCGI 兑现，VXGI 作独立专题边际价值不大。
- **通用件建议**：值得为复用精心设计的不是 cluster 数据结构本身，而是第 3 节第 1 件的分块求交→压缩→列表流水线——写成可参数化公共件（候选集/求交谓词/cell 形状进参数），步骤 8 分簇、9.3 patch 投放、将来 GPU 粒子密度场直接实例化（照代码生成规范 §2.3"重复模板下沉公共层"）。
- **VSM 不必上**：8.3 传统级联 shadow map 够用；VSM 的"GPU 判脏页"模式将来若做，构建端直接复用第 1、2 件。
