# 信号量设计缘由：CPU 不在场的队列间交接

呈现引擎在另一个进程里，它什么时候用完一张 swapchain image，CPU 不知道也不该轮询；渲染队列要等它，它也要等渲染队列写完才能上屏。这种等待的两端都是队列，CPU 只能在两次提交里登记"从哪个流水线阶段前等谁、执行完置位谁"，此后置位与等待都发生在 GPU 时间线上，CPU 摸不到状态。

名字借自 Dijkstra 并发原语，语义却收窄成一次性的通知：发出后必须被等待一次，才能再次使用。内存可见性则由交接本身隐含保证——等到信号，就同时保证发出方那批命令的全部写入对等待方可见，不需要再补屏障。这背后是一条不对称结构：等待一侧能选卡在哪个流水线阶段，发信号一侧固定等对面整批命令执行完，内存语义全量随交接到达（完整推导见《[同步模型](同步模型.md)》）。

**信号量是队列到队列的执行依赖，CPU 零参与；只有等待两端都不在 CPU 的交接才用它。**

## 1. 为什么要有它：等它的双方 CPU 都不在场

用本工程的 swapchain 双向握手看真正的等待者是谁：

- `image_available`：acquire 时图像还没画，呈现引擎**什么时候**用完这张图，CPU 不知道、也不该轮询——等它的是图形队列的提交前端。
- `render_finished`：等它的更是呈现引擎（DWM/显示控制器），根本不在本进程里，连它的命令流都摸不到。

如果用 fence，CPU 就得在两个方向上阻塞等待：acquire 后等渲染完才能 present（多帧在飞全废），present 后等呈现引擎用完才能重用 image（CPU 白转）。信号量把"我好了→你上"的通知压进两次提交的硬件层：CPU 只负责把等待条件**声明**在提交里（wait 信号量 + dst 阶段），等待本身由驱动在设备上兑现，CPU 从头到尾不参与。

## 2. 和 OS 信号量同名不同物

| | Dijkstra/OS 信号量 | Vulkan binary 信号量 |
|---|---|---|
| 计数 | 计数型 | 一次性：signal 后必须被 wait 掉才能再用 |
| 谁能操作 | 任意线程 P/V | 只有队列提交（signal/wait 都长在 SubmitInfo 上） |
| 能查询吗 | 能读值 | 不能，没有任何查询状态的入口 |
| 生命周期 | 常驻状态 | 一次性：未被等待前不能再次发出 |

所以它更接近"**队列间的 fence**"，而不是 OS 信号量。三种原语的分工才是设计全貌：

| 原语 | 两端是谁 | CPU 能做什么 |
|---|---|---|
| fence | 提交 ↔ CPU | host wait/reset/status，能摸 |
| 信号量 | 队列 ↔ 队列 | 只能挂到提交上，摸不到状态 |
| timeline 信号量 | 队列 ↔ 队列，CPU 也要在场观测 | 可查值、可 host signal/wait，是可查询计数值的信号量 |

选型只看一个问题：等待的两端有没有 CPU。两端都不在 CPU（一个队列等另一个队列）才用信号量；任何一端是 CPU，就升级成 fence（CPU 等完）或 timeline 信号量（CPU 可查、可发信号）。要带数值、能被 CPU 查询的完成凭据，用 timeline 信号量。

D3D12 把三种等待收进同一个 fence 对象（CPU wait 与 Queue Signal/Wait 兼管）；Vulkan 按等待的一侧拆成两种对象，代价是词汇多一个，收益是队列间的等待可以做成零 CPU 开销的专用件。

## 3. 呈现引擎为什么只能用它交接

呈现引擎是驱动/合成器侧的黑盒：没有命令缓冲可录、没有屏障可插，一切同步只能长在 `vkAcquireNextImageKHR` 和 `vkQueuePresentKHR` 的信号量参数上。规范还要求交给 present 的 binary 信号量必须未置位——"等掉旧信号、再交出去"这套步骤，本质就是 image 所有权交接的登记手续，不是可省的配对纪律：

- `image_available`：呈现 → 渲染（"这张图呈现引擎用完了，归你画"）；
- `render_finished`：渲染 → 呈现（"这张图渲染写完了，归你上屏"）。

两个 binary 信号量各管一个方向，谁也不能查询状态，只能信任提交接口的配对纪律。这也解释了为什么 acquire/present 的信号量不能复用同一只：present 完成信号量按 image index 分配，而 `image_available` 每帧槽一只，两者跟着不同的轮转走——复用同一只就同时承担了两个轮转的配对（完整推导见《[交换链与呈现](交换链与呈现.md)》）。

## 4. 真正模仿 IPC 的是 external_semaphore

进程内的信号量谈不上进程间通信。跨进程那档才是：`VK_KHR_external_semaphore`（Windows 上配 `VK_KHR_external_semaphore_win32`）把同一只信号量导出成 OS 句柄（共享 handle 一族），让两个进程的队列互发信号——典型场景是渲染进程与独立合成进程握手。同进程内它只是驱动代管的一次性通知；"模仿 IPC"这个评价只对外部信号量成立。

## 5. 工程落点：全工程三类信号量

三类：`image_available` 每帧槽一（`MAX_FRAMES_IN_FLIGHT`=2 个）、`render_finished` 每 image 一（N 个，随交换链重建重新分配）、上传完成计数（代码里叫 `ticket_semaphore`，全进程 1 根）——实例数 2+N+1。

| 信号量 | 类型 | 发出方 | 放行方 |
|---|---|---|---|
| `image_available`（每帧槽一，`frame_pool.rs`） | binary | 呈现引擎：`vkAcquireNextImageKHR` 完成时置位 | 图形队列提交在 `COLOR_ATTACHMENT_OUTPUT` 等待（`render/frame/record.rs` 提交等待列表首项） |
| `render_finished`（每 image 一，`swapchain.rs`） | binary | 图形队列提交 signal | `vkQueuePresentKHR` present 前 wait |
| `ticket_semaphore`（全工程唯一，`uploader.rs`） | timeline | transfer 队列每提交一批上传 signal 递增计数；mip 续批在图形队列等 transfer 的计数、生成完整 mip 链后再 signal 新的计数 | ① 图形帧提交在 `ALL_COMMANDS` 等备料快照的计数（transfer 写的跨队列可见性，计数为 0 不等待，防 VUID-03242）② 续批 blit 等 transfer 的计数 ③ CPU `vkWaitSemaphores`（staging 槽复用前等上批完成） |

两类信号量的选型差别就在这里：两个 binary 信号量管与呈现引擎的双向交接（两端都不在场）；上传计数选 timeline，恰恰因为 **CPU 要在场观测**（staging 槽复用要阻塞等完成）。这个计数必须能被 CPU 查到，也必须能作为图形队列的等待条件——完整生命周期与选型论证见《[timeline信号量](timeline信号量.md)》。

## 自测

1. 为什么 acquire→present 整条链上 CPU 不用阻塞一次？两个 binary 信号量各替 CPU 挡掉了哪次等待？
2. binary 信号量为什么不提供"读当前状态"？若能读，"先等掉旧信号再交出去"的所有权登记手续还成立吗？
3. 本工程上传计数若改用 binary 信号量 + fence，会丢掉哪两种消费方式？
