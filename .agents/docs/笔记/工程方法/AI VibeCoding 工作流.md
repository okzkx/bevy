# AI VibeCoding 边学边做工作流：六步一圈，长期项目不失控

6.3 粗粒度流送施工到验证那一步，压测④抓到一个真缺陷：关闭沿不重驻留，B 面（关掉驻留管理器的对照档）回不到基线——管理器一关，淘汰是停了，被淘汰的资产没有请求者，永远缺席；修复是把激活态下降沿的全行置脏，实抓即修，修复记入施工记录和提交信息。

**一段 = 一次会话能走完"立案→施工→收官"的量；计划是唯一施工依据，拍板点不可代行。**

在一个要持续几个月的学习项目里，让 AI 边学边做（vibe coding：用对话驱动 AI 调研、写代码、写文档），真正的风险不是某次写错代码，而是每一轮都从零开始：方向靠临场发挥，范围随对话膨胀，测试过没过说不清，昨天的结论今天找不到。本工程用一圈固定循环处理这些风险：定目标 → 立案（把这一段要做的事写成可施工、可验收的计划）→ 分支施工 → 四件产出（施工记录、流程导读、原理篇、状态流转，留给下一个会话接手）→ 用户验证 → 并回（把临时分支合回 main，固定做法叫灯笼合并）。每一圈只推进一小段，下一圈从上一圈的文档接着走；每一步的细则都在正本 Skill（该流程唯一的权威说明文件）与规则文件里，这里只给循环骨架和本工程落点，遇到不一致以正本为准。

## 一、六步循环总览

| # | 步骤 | 本工程落点 | 正本与工具 |
|---|---|---|---|
| 1 | 用户定目标，AI 调研并拆成步骤与段 | 入口篇写目标与 Bevy 使用边界；路线图写步骤 1~9（里程碑 M1~M8）与段；调研结论进 `笔记/` | `项目目标与Bevy使用指南.md`、`学习目标实现步骤.md` |
| 2 | 立案：先出设计文档与施工计划 | 段目录 `N.M-段名/` + 施工计划 + 段 README；路线图与步骤 README 标 ⬜ 已立案 | `$doc-plan-register` |
| 3 | AI 在临时分支施工并回归 | `goal/<段号>` 分支；判定线（这一段"怎么算过"的验收条件）逐条对账；三级测试、压测脚本、截图读图 | `$plan-execute`、`$auto-commit`、`测试规范与方式`、`画面功能视觉验证`、`tools/*.py` |
| 4 | 四件产出 | 施工记录 + 流程导读（含代码改动解析）+ 原理篇 + 状态流转 | `$plan-execute` 阶段三；落点见第五节 |
| 5 | 用户验证、原理问答与优化 | 判定线逐条对账、复述校准回写、步骤级验收归档、遗留挂账 | 段 README、`待修复清单/待修复清单.md`、`外置拓展需求/外置拓展需求.md` |
| 6 | 灯笼合并回 main | 源分支先变基（把提交重放到目标最新之上）再同链合并 → 推送 → 删临时分支 → 分批记账 | `merge-chain` |

六步不是六道审批：第 5 步验不过就回第 3 步修，第 4 步的文档随修复补记；循环在"一段收官"处结束，不在"代码写完"处结束。

Skill 落点：`$plan-execute` 在仓库 `.agents/skills/plan-execute/`；`$doc-plan-register`、`merge-chain`、`$auto-commit` 在用户级 `C:\Users\zengkaixiang\.agents\skills\`（`.zcode\skills\` 是镜像）。表里的变基（rebase）指把源分支的提交按原顺序重放到目标分支最新提交之上；灯笼合并的完整做法见第七节。

## 二、第 1 步：先有路线图，AI 才知道这一段该学什么

项目目标写在[入口篇](../项目目标与Bevy使用指南.md)：做什么、Bevy 用到哪、哪些自己实现。路线图[学习目标实现步骤](../开发步骤/学习目标实现步骤.md)把目标拆成步骤 1~9（里程碑 M1~M8），每步再拆段。步骤 6（M5）就是一条现成的依赖链：

- 6.1 Hi-Z 遮挡：用上一帧深度剔掉被挡住的物体；
- 6.2 GPU LOD：按屏幕占比换网格精度档；
- 6.3 粗粒度流送：世界大于显存时，按预算让整份资产进出；
- 6.4 细粒度流送：把驻留单位从整份资产下沉到 LOD 档；
- 6.5 低保真保底：高模不在时仍有低模可画；
- 6.6 GPU 缺口请求：GPU 报告缺哪些档，CPU 合并后补。

依赖链上顺序不可倒置；追加段排在当前步骤序列收官之后，不塞进下一步骤。一段的判定线过完再开下一段，几段同日连续施工是串行，不是并行。

方向性调研落进 `笔记/` 对应主题域，文末收工程启示——如 `笔记/渲染/` 的 SCGI、PBR、全局光照谱系、虚拟纹理、体素五篇。调研结论要反过来修订路线图：读懂了才发现某段该拆、某段该并、某段的边界写错了。

拆解粒度只有一个判据：一段的规模以一次会话能走完立案、施工、收官三件事为上限。本工程多数段是当日立案、当日施工、当日收官；一段做不完，就拆段，不把一段拖成跨周的任务。粒度定大了，计划会变成猜；粒度定小了，文档开销会超过施工本身。

## 三、第 2 步：立案把一段变成可施工、可验收的计划

立案不是写设计论文，是把"要做这一段"落到四个固定产物上，让下一次会话不用重新讨论方向：

1. 段目录 `N.M-段名/`，放在 `.agents/docs/开发步骤/N-步骤/` 下。
2. 施工计划 `施工计划：<段名>拆解.md`，固定栏目：定位与现状核实（先查现有代码和依赖到底什么样）、任务拆解 N.M.K（步骤 / 段 / 任务三级编号）、判定线草案、待决项、测试方案、底座指向（上游参照实现或既有段复用）。计划开头和每个 N.M 段都要用一句话交代：做什么、为后续哪段铺路、不主张什么。
3. 段 README：段索引与材料清单，开工时转成任务面板。
4. 登记：路线图总览表、当前闸门与步骤 README 同步标 ⬜ 已立案。立案走 `$doc-plan-register`，默认零代码改动、不提交、不推送；要入库时由用户明确授权提交。

判定线必须在立案时写进计划，先于代码，逐条可验证，不允许施工后补口径。6.3 的六条可以当样本：预算硬约束、可持续游历、未就绪不发布、淘汰不产生残留绘制、A/B（开关对照）成组记录、既有判定线零回退。写不出可验证的判定线，说明这一段还没拆清楚。

施工只认计划：无立案不施工；施工中重读计划全文，禁止凭记忆；立案即冻结范围。施工中发现计划没覆盖的结构问题，在被后续段依赖之前先提出，动不动由用户拍板，AI 不擅自改范围。

待决项是计划里明确"先不拍板"的清单（如 6.3 的淘汰单位、淘汰策略、预算口径、请求优先级、暖启动、chunk（场景生成器切出的区域）运行期归属六项）。它们随施工或验收落定，结论回写施工记录；AI 可以在计划里列选项、给倾向，但不能替用户裁决。

## 四、第 3 步：在临时分支施工，用判定线逐条对账

按 `$plan-execute` 开工。第一步是切临时分支：`git switch -c goal/<段号>`（如 `goal/6.1`）；同名分支已存在就接续，不重建、不复位。要同时开多个会话时，用 `git worktree`（同一仓库的第二份检出目录）给每个分支独立工作区，避免来回切分支打断在跑的测试。

调用 `$plan-execute` 即授权在该分支上按任务粒度分组提交（docs 与 feat 分开，提交信息走 `$auto-commit` 纪律）；推送、并回、删分支不在授权内，留到第 6 步由用户拍板。

测试按侵入程度三级递进，能 Remote 不重编译，能重编译不碰鼠标（细则见[测试规范与方式](../../rules/测试规范与方式.md)）：

1. Remote（BRP，Bevy Remote Protocol：从外部查询和操控运行中程序的接口）首选。`tools/brp.py` 是薄客户端，新操作优先扩宿主的 BRP 自定义方法族，可复用、零重编译。
2. 打 Log + 重新编译。Remote 看不到的渲染队列内容、管线选择、帧内时序，用日志取证。
3. 真实鼠标注入。只在用户声明"无人模式"的当次任务里执行，授权不跨会话（见[鼠标操作与输入注入纪律](../../rules/鼠标操作与输入注入纪律.md)）。

压测和回归脚本化：入口进 `tools/`，判定线逐条自动核对，收官后同一脚本可重建场景、重跑回归。现有的脚本族如 `hiz_test.py`、`scene_lod.py`、`scene_stream.py`、`scene_fine.py`，6.5/6.6 又加了 `scene_floor.py`、`scene_gap.py`；临时产物（截图、日志、转储）一律进仓库根 `.temp/`，不进 docs（见[临时文件与工具脚本存放](../../rules/临时文件与工具脚本存放.md)）。

画面类判定线按[画面功能视觉验证](../../rules/画面功能视觉验证.md)走：PrintWindow 抓目标窗口，当前会话模型直接读图，结论分通过、发现异常、无法判定三档如实记录。

代码验证线：按目标 crate 跑 clippy 全净；零 VUID（Vulkan 验证层零报错）；宿主 exit 0；库测试全过。格式化口径在 2026-11-09 改过：ash_renderer 整仓已统一为 rustfmt 排版（提交 `2f8f9392d`），收尾以 `cargo fmt --check` 全绿为准；"手工排版、禁止 fmt"是此前的旧口径，不再适用。

修复循环：测试暴露的问题修 → 复测 → 补提交，循环到判定线全过；仍过不了的，进第 5 步的遗留挂账，不硬凑"已过"。压测第一次实抓到的真缺陷要写进施工记录和提交信息，修复动作本身也是这一段的历史。

## 五、第 4 步：四件产出各有读者

施工结束不等于这段结束；要让下一个会话能接上，至少留下四件东西：

| 产出 | 落点 | 写给谁、写什么 |
|---|---|---|
| 施工记录 | 段目录 `N.M.K-<标题>.md` | 写"实际做了什么"：任务逐项、待决项怎么落定、实抓缺陷与修复。计划文档只流转状态，不回写实现细节。 |
| 流程导读（施工总结） | 段目录 `<段名>流程：<从…到…的各级账面>.md`，无任务序号前缀 | 新机制/新数据流段的收官定例：各级账本（谁在什么时候读写了哪份数据）的全景、新文件分工表、逐时刻走读、失败与稳态路径；文末附代码改动简要解析（按文件列要点与取舍，`git show --stat` 实数）——这份解析就是变更文档，不另起一篇。 |
| 原理篇 | 段内讲解篇，或 `笔记/` 专题 | 给想弄懂"为什么是这套形状"的人：机制与取舍、边界与反例。用户问答校准出的偏差回写这里。 |
| 状态流转 | 计划头部 + 段 README + 路线图 | 三处同步同一状态（⬜ 已立案 → 施工中 → ✅ 收官），标记用词先看路线图现行写法再落笔。 |

前两件和状态流转是 `$plan-execute` 阶段三的定例；原理篇按段的机制复杂度写，不是每段都有。

## 六、第 5 步：用户验证，答不上来的地方回写文档

验证分两层：段级按段 README 的验收状态和判定线逐条对账；步骤级做验收归档（逐条复核 + 归档轮 lint 收敛），先例见[步骤 4 验收复核](../开发步骤/4-可靠增量链路/4-验收复核.md)（步骤 4/7 已做，步骤 5/6/8 仍欠账）。验收结论只有用户能给，AI 的"已过"只是待核对的报告。

原理问答是这一步的重点：用户复述理解求校验，AI 从机制和取舍讲起，用 Unity/UE 的同类做法做对照；讲错的地方、被纠偏的理解都要回写文档——校准出的偏差也是知识，不写下来下一轮还会错。

代码校验优化：归档轮重跑 clippy/lint，收敛新告警；发现结构缺陷主动提出，不等用户问，时机在被后续段依赖之前。

没做和暂不做的去处分流：缺陷进[待修复清单](../开发步骤/待修复清单/待修复清单.md)；编号体系外的拓展需求进[外置拓展需求](../开发步骤/外置拓展需求/外置拓展需求.md)，每条写来源、内容、恢复条件、边界。挂账不是遗忘，是把"现在不做"的原因和"什么条件下再做"写清楚。

如实报告是这一步的底线：测试未过就是未过，修不动就列遗留项，不硬凑"已过"；失败信息如实进文档。报告里不要把"应该能过"写成"已过"，也不要把"没测"写成"通过"——下一段会拿这份报告当起点。

## 七、第 6 步：灯笼合并，先变基再同链合并

并回只在用户拍板后执行，走 `merge-chain`。这个 Skill 的固定叫法是"灯笼合并"：按"截止提交"把源分支同一链上的提交合入目标分支，截止之后的提交留在源分支；合并后把源分支推进到合并端点，下一批从端点重新分叉。多轮合并的图形成一串干净的台阶，像灯笼骨架，不会沿原始链条越挂越长，也不会因分叉丢上下文。

目标分支已经分叉时（例如之前被 squash 或 no-op 合并处理过；squash 指把一批提交压成一个，no-op 合并指内容相同、历史不同的空合并），处理原则是先把源分支变基到目标之上，再按同链合并，而不是直接硬合。变基会改写 SHA，下一次部分合并要按提交标题重新定位截止提交，不能沿用旧 SHA。

合并指令默认含推送授权，只推目标分支：本仓库 `main` 的上游是 `okzkx/main`，推完用 `git status -sb` 核对远端指针真的前进了。合并成功后删临时分支（源分支已推进到端点，`git branch -d` 必过）；分批推进时按批记账（第 N 批合入哪些段），报告里写清本批截止点和下一批从哪个端点继续。

## 八、谁拍板、谁执行

拍板点不可代行：左列的决定只有用户能做。AI 可以给方案、给证据、给建议，但不能替用户选；越过这条线，后面的"验证"就失去意义。

| 用户拍板 | AI 自主（如实报告） |
|---|---|
| 项目目标与路线取舍 | 调研、拆解草案 |
| 计划批准、待决项裁决 | 立案文档撰写与状态同步 |
| 结构缺陷取舍、是否返工 | 分支上按计划施工与分组提交 |
| 无人模式授权（仅此时允许真实鼠标注入） | 三级测试、判定线核对、修复复测 |
| 验收结论、遗留项定性 | 施工记录、流程导读、原理篇撰写 |
| 并回、推送、删分支 | 灯笼合并的技术执行（拍板后） |

## 九、样例走读：6.3 粗粒度流送的一天（截至 2026-10-19）

想看清六步在一天里怎么落地，可以对照 6.3 这段的真实记录：

1. 目标与拆解：路线图步骤 6（M5）拆出 6.3，与 6.1/6.2 构成依赖链——遮挡剔掉看不见的，LOD 换粗细，世界仍大于显存时靠流送按预算进出。
2. 立案：[施工计划：粗粒度流送拆解](../开发步骤/6-高级剔除LOD与流送/6.3-粗粒度流送/施工计划：粗粒度流送拆解.md)先做现状核实（4.3 的异步就绪与 4.4 的回收账是这一段的地基），再拆 6.3.1~6.3.6 六项任务，写判定线六条（预算硬约束、可持续游历、未就绪不发布、淘汰不产生残留绘制、A/B 成组记录、既有判定线零回退）和待决六项。
3. 分支施工：在 `goal/6.2` 分支上（6.2/6.3/6.4 同日连续施工）实现驻留管理器（决定哪些资产留在显存里的策略层：按 mesh 驻留字节设预算，请求=缺的资产重新标脏走既有上传链，淘汰=释放记进回收账，冷却窗防住刚淘汰又重请求），`tools/scene_stream.py` 超预算游历压测 7/7。
