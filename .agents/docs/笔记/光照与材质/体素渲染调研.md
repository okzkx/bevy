# 体素渲染调研：VXGI 为什么败给大场景，3D 光源分簇为什么能落地

假设一帧 1080p 画面里有八盏点光（从一个点向四周发光的灯），你想让每盏灯只照到它够得着的物体；或者再进一步，想让红墙把光反弹到白地板。两种需求都会把人引向同一类结构：把空间切成格，逐格存一份东西，着色时按格取用。

3D 光源分簇（cluster）切的是视锥（相机能看到的那块锥形空间）：屏幕分成 32 像素见方的 tile（屏幕上的小方块），再沿视深切成 32 个深度片，每个格子记录“哪些点光能照到这里”。VXGI（voxel global illumination，体素全局光照）切的是场景体积：每个体素（三维的小立方格）记录“这里有多少光”，更准确地说，是沿各个方向到达这里的辐亮度。渲染时用锥追踪估算间接光：沿一个圆锥方向在体素网格的 mip 链（同一份数据逐级缩小一半的序列）里步进采样，近似一次半球范围的入射光积分；间接光就是光在表面之间反弹后到达的光。两者都是切格存东西，行业结局却相反。要判断的不是“体素好不好”，而是这种“切格存东西”的结构在什么条件下值得做。

> **成本 ≈ 每格存的东西 × 格子数量 × 结构存活多久。存光源索引这类决定，格子便宜、一帧就扔，多算只损失性能；存辐亮度这类被采样的数据，格子昂贵、跨帧维护，算错直接上屏。**

行业对后者的修正路线也只有一句话：只记表面，不记体积。真实大场景的几何贴在二维表面上，体积网格里的空气格全是白存的；UE5 Lumen 的主缓存是表面卡片加网格距离场，Unity SCGI（Surface Cache GI，表面缓存全局光照）用贴在表面的 patch（一小块记录该处光照的缓存），都把格子从“整个体积”压回“几何表面”。

## 一、同一个结构，两种填法

先把两种结构的格子和每格内容说清楚，成本才有得算。

3D 光源分簇的格子由屏幕分辨率和深度片数决定，与世界多大无关。本仓的参数是 32 像素 tile、32 个深度片、视深 0.1~200 米；1080p 下 tile 数是 60×34，乘 32 片得到 65,280 个 cluster。每个 cluster 存一条记录：一个计数加最多 16 个光源索引，共 68 字节。两帧槽（CPU 与 GPU 并行时，每帧各用一份，共两份）合计约 9.4 MB（列表 8.9 MB 加计数 0.5 MB）。一张 1080p 的 RGBA16F 附件是 16.6 MB，所以这份“每格一份光源名单”的全部存储还不到一张 G-buffer（延迟渲染把材质、法线等写成的一组屏幕附件）附件大。换成 4K，格数涨四倍，列表约 18 MB 每帧槽，两帧槽约 36 MB（计数另加约 2 MB），仍小于一张 4K RGBA16F 附件（约 66 MB）。涨的是分辨率，不是场景尺寸。

作为示意，如果把 tile 缩到 16×16，1080p 下有 120×68 个 tile，乘 32 片约 26 万格；每格存一个计数加 8 个光源索引，约 9.4 MB。这个口径不是本仓参数，只用来说明格子大小与内存的线性关系；本仓 32px tile 的 9.4 MB 是固定 16 槽、两个帧槽的总和，两者不能直接对比。

VXGI 的格子由世界体积和体素分辨率决定。以 256³ 的一级网格为例，每格 RGBA16F 占 8 字节，基础层就是 128 MiB；再加逐级减半的 mip 链（3D 版每级每轴减半），约 146 MiB。512³ 的基础层是 1 GiB，带 mip 约 1.14 GiB。如果拿一张全分辨率网格硬铺 1 公里见方、体素 0.5 米，那是 2000³ = 80 亿格，RGBA16F 要约 60 GiB。所以真实实现不会这么铺，而是用 clipmap（以相机为中心嵌套的多级网格，近处细、远处粗）把内存压住；代价是远处分辨率变粗，这正是下一节第二条死因。

两者的差别不在“体素”这个词，而在三个变量：每格存什么、格子铺多大、这份结构活多久。VXGI 在这三项上都落在成本高的一侧。

## 二、VXGI 为什么败给大场景：四条死因

1. 内存按体积涨，不按表面涨。

   体素网格的格数是“覆盖范围 ÷ 体素尺寸”的三次方。体素尺寸减半，格数乘八；每个轴向的覆盖范围翻倍，格数也乘八。再加 mip 链的约 1/7，再乘 clipmap 的级数。作为对照：1 公里见方的一片地面，按 1 米一块表面缓存只需要 100 万格；同样 1 公里的立方体，按 1 米体素是 10 亿格。几何实际只贴在表面上，体积里的空气全是白存的。这就是“只记表面”能省下数量级的原因。

2. clipmap 让远处变糊。

   为了不让内存随世界尺寸膨胀，VXGI 用 clipmap 跟着相机铺几级网格：近处一格细，远处一格粗。大型场景的大部分像素恰好落在远处，锥追踪从粗级 mip 里采出来的间接光就是糊的；薄墙、栏杆这类小于远处体素的几何，在网格里可能根本不存在。小场景、贴脸镜头藏得住，大场景藏不住。

3. 动态更新税。

   体素化（voxelization）是把场景三角形光栅化（把三角形转成它覆盖的格子）进 3D 纹理：静态几何可以预先烘好、跨帧复用，动态几何每帧都要重新灌进网格。256³ 的网格有 1680 万个格，三角形只覆盖贴着表面的那一层；动态物体越多，每帧要重灌的表面格越多。结构是跨帧驻留的，任何移动、变形、开关灯都要让对应区域失效并重算；动态对象一多，体素化本身就成为主导成本。对比之下，3D 光源分簇每帧从光源位置现算，没有历史要维护，灯怎么动都不产生额外的维护成本。

4. 光渗和锥追踪走样是结构性的。

   光渗（light leaking）是薄墙漏光：一个体素如果横跨墙面，它只能存一个辐亮度值，墙两侧的光被平均在一起；从亮侧追踪时采到这个体素，光就漏到墙后。比体素更薄的墙甚至可能没被体素化进去。锥追踪则是用少量圆锥和 mip 层级近似半球积分：粗层级把不相干方向的辐亮度混在一起，层级切换处容易出现条带，锥数少则出现块状噪声。加滤波能压噪声，但滤波同时把漏光糊得更宽；加锥数能降噪，但成本上去。这是“存被采样数据”的结构性问题，不是调参能根除的。

行业时间线（行业调研口径，本仓未复现）：2014~2017 年热闹过一阵，NVIDIA 推出 VXGI，UE4 生态有实验性的 VCT（体素锥追踪）实现，少数 PC 游戏提供过体素 AO（环境光遮蔽）选项，例如《古墓丽影：崛起》的 VXAO。这阵热闹之后，大型项目基本转向三条路：烘焙（预先算好光照并存储）加探针、硬件光追（《赛博朋克 2077》的 RT Overdrive、《地铁：离去》增强版）、表面缓存类，例如 UE5 Lumen 用表面卡片（贴在物体表面的缓存卡片）和网格距离场，不用体素辐亮度网格做主缓存。

体素 GI 至今的例外是小而全动态的《Teardown》（拆迁）：整个世界本来就是体素，玩法需要可破坏几何，GI 搭在体素上顺理成章。这条例外恰好说明条件：只有“场景小、全动态、几何本来就要体素化”时，体积网格的成本才划得来。

## 三、3D 光源分簇为什么可行：同一结构的另一种成本

| | 3D 光源分簇 | 体素 GI |
|---|---|---|
| 每格存什么 | 一串光源索引（u32）加一个计数；本仓最多 16 盏 | 辐亮度（通常是 RGBA16F），有的实现还存不透明度和法线，外加 mip 链 |
| 格子铺多大 | 只铺视锥：屏幕 tile × 深度片，1080p、32 像素 tile 是 65,280 格 | 铺世界体积：clipmap 级联跟着相机，近细远粗 |
| 结构活多久 | 一帧；每帧从光源位置重建，没有历史 | 跨帧驻留；几何或光照一变就要增量刷新 |
| 错了会怎样 | 多列一盏只多算一次光照；漏列才会画面缺光 | 漏光、糊、条带直接上屏，滤波只能缓解 |

逐条对照四条死因：

1. 内存跟屏幕分辨率走，不跟场景大小走。

   格子数只由“分辨率 ÷ tile 边长 × 深度片数”决定；世界从 100 米扩到 10 公里，cluster 的存储不变。第一节算过：1080p 两帧槽约 9.4 MB，4K 约 38 MB，都小于同分辨率的 RGBA16F 附件。VXGI 那种“格数随体积按立方增长”的成本在这里不存在。

2. 没有 clipmap，远处不会因为网格变粗而糊。

   cluster 的屏幕 tile 始终是 32 像素，深度片远处变厚只会让列表多列几盏灯，不会把辐亮度平均；着色仍然是逐像素读自己所在格的列表，再逐灯算 BRDF（材质把入射光反射到视线方向的函数）。远处像素的光照不会像 VXGI 那样从粗体素里采样出来：列表只决定“这盏灯算不算”，不改变光本身的空间分辨率。

3. 每帧现算，零更新税。

   有东西要画时，cluster_build 每帧从头跑一遍：1080p 下 65,280 个 cluster，每 64 个格一个线程组（GPU 上一起调度的一组线程），共 1,020 个线程组；每个格对光源表里的灯逐个做球与 AABB（轴对齐包围盒，包住格子的最小长方体）求交。灯移动、灯增删都不需要 cluster 列表维护历史，下一帧重建就是新位置。光源表上限 256 槽，遍历上界是“用过的最大槽号 + 1”，空槽按半径 0 跳过。这个成本只随格数和灯数涨，不随场景三角形数涨；没有跨帧一致性要保证，也就没有 VXGI 那种“永久结构要持续维护”的成本。

4. 存的是决定，不是被采样的数据。

   每个格里的列表只回答“这几盏灯可能照到这里”，真正算光照仍在着色器里逐灯做 BRDF。列表用 tile 与深度片的 8 个角点反投影成世界 AABB，再与光源球求交；AABB 比真实的锥台格大，所以只会多列、不会漏列。多列一盏的代价是多一次光照计算，漏列才会让画面缺光。这份列表是每格的数据，不是屏幕上的逐像素掩码；掩码只能记住“这个像素算过没”，记不住“这个像素要算哪几盏灯”。

   列表里存的是索引，不是辐亮度；着色时按索引读光源表，光只从灯的位置发出，不会因为格子粗而把墙两侧的光平均到一起。最坏情况是某个格多列了一盏够不着的灯，算出来贡献接近 0。点光本身没有阴影，墙背可能被照亮，那是“点光阴影尚未消费”的另一条边界，不是 cluster 列表造成的。

   这条保守方向与[视锥剔除](../../开发步骤/5-GPU驱动与常驻大场景/5.2-GPU视锥剔除/README.md)、[Hi-Z 遮挡](../../开发步骤/6-高级剔除LOD与流送/6.1-Hi-Z遮挡/README.md)同源：不确定就保留，宁可多画/多算，不可漏判。列表一旦漏灯，画面直接少一块光，是可见的错误；列表多灯，只在性能上多付一点。

它的边界也要说清楚：只覆盖视深 0.1~200 米；单格最多 16 盏，超出只保留前 16 个索引；光源表 256 槽；只处理点光，方向光走 set1 的 UBO（随帧提交的小块常量缓冲），不进表；点光的阴影标志位只有记录，点光阴影尚未消费。这些边界不影响“这类结构可行”的判断，但决定了它现在能覆盖的光照范围。

## 四、四个能脱离体素 GI 单独用的工程模式

体素家族真正能跨场景复用的，不是某个数据结构本体，而是四个模式。它们可以脱离体素 GI 单独使用。

1. 逐格求交 → 计数 → 前缀和 → 填列表。

   完整形态是：第一遍对每个格判断候选集里哪些元素与格相交，把命中数写进计数；对计数做前缀和（把一串数累加成每项的起始偏移），得到每格在一条平坦列表里的位置；第二遍按偏移把索引写进去。这样列表长度可以随格变化，没有固定槽位的浪费，访存也连续。粒子密度网格、SPH（用粒子邻域求和模拟流体）的邻居查询、OIT（顺序无关透明：把每像素的多层颜色记下来再统一合成）的逐像素片段列表、GI 探针（在空间里采样光照的点）/patch 投放，都是这套流程。

   本仓的 cluster 是它的简化支路：一个线程管一个格，记录固定为“计数 + 16 个索引”，不做前缀和、不用原子、也不需要第二遍。原因是灯少、单格上限小，固定槽位的浪费可以接受；换来的是单次 dispatch（一次 GPU 通用计算的启动）、无跨格依赖、实现简单。8.1.3 的验收场景平均每格 3.1 盏灯，16 槽里大半是空的；按 1080p 的 65,280 格算，两帧槽仍只有约 9.4 MB，这个浪费换来了单遍、无原子的简单性。如果以后候选集变大、上限提高、或格子数随分辨率大涨，再换成前缀和形态更划算。

2. 先数后填两段 dispatch，第二段可以生成 indirect 命令。

   当输出长度不固定时，先跑一遍只数的 dispatch，再跑一遍按偏移填的 dispatch；如果第二遍顺带写绘制命令，命令数量也由 GPU 写进显存，CPU 只发一条 indirect 调用（绘制参数写在显存里的 draw 调用），不用读回“到底有多少个”。这套“先数后填”在屏幕空间的老形态是 stencil（逐像素掩码，标记这个像素要不要处理）：先标记再处理；GPU 计算版把掩码换成计数和偏移，粒度从像素变成格子。

   本仓的 build_indirect 是它的一遍特例：每个在场槽最多生成一条命令，可见性直接写进 instanceCount（0 或 1），所以不需要先数。透明层的命令环（循环使用的命令缓冲）也是同一方向：GPU 组装命令，图形阶段一次 indirect 消费。需要先数后填的，是“一个格里可能有任意多个元素”的变长输出。

3. mip 链归约。

   每一级都是上一级 2×2（3D 版是 2×2×2）个格子的归约，查询时按覆盖面积选层。Hi-Z 遮挡（用深度金字塔判断物体是否被挡住）用的是这条链：深度按 2×2 取 MIN 逐级降采样，reverse-Z（近平面深度为 1、远平面为 0 的深度约定）下 MIN 等于“该区域最远的已缓冲表面”，用它判遮挡恒保守；本仓 level 0 不派发，从 level 1 起可查，深度图 ×2 帧槽，帧 N 的遮挡测试读同槽两帧前的归约结果。VCT 的锥追踪用的是同一条链，只是每级存的是辐亮度、归约算子换成平均/加权平均：宽锥走粗级，窄锥走细级。结构相同，载荷和算子不同，保守的方向也随之翻转——深度要取 MIN 才不误判，辐亮度要取平均才不产生块状跳变。

4. 级联：同一结构按距离分成几级。

   同一个网格结构跟着相机重复几份，近处细、远处粗，这就是级联。8.3 的 CSM（级联阴影贴图：把相机视锥按距离切段，每段一张从光源视角渲染的深度图）是光源空间的版本：4 级、每级 2048²、按对数切 0.5~80 米，逐级拟合正交投影的包围盒。VXGI 的 clipmap 是世界空间的版本。步骤 9 的 9.5 patch 池方案也采用 Volume + Cell + cascade（体积、单元网格、级联）的近细远粗结构（已定稿，未施工）。

   这里说的“同款”是形状同款，不是数据结构同款：CSM 每帧把各级重新拟合到相机视锥的切片上，clipmap 保持世界对齐的固定网格。真正共用的是工程问题：级与级之间的接缝、分辨率切换处的跳变、相机移动时各级的更新规则。写过一遍 CSM，再做世界空间级联时，这些问题已经有答案。

## 五、对本仓的结论：3D cluster 已落地，VXGI 不立项

步骤 8 的 3D cluster 已经落地。实现在 `ash_renderer/src/render/passes/lighting/cluster.rs`，着色器在 `ash_renderer/shaders/gpu_driven/cluster_build.wgsl`；不透明光照累积（`gbuffer_composite.wgsl`）和透明前向（`transparent_forward.wgsl`）读同一份列表。8.1.3 的验收读数是 46,400 个 cluster、GPU 与 CPU 总指派 144,416、逐格零不一致；参数是 32 像素 tile × 32 深度片、指数分片 0.1~200 米、单格上限 16 盏、两帧槽。

两条与内存和分片有关的事实：

- 深度片按对数切。代码里是 `near·(far/near)^(s/S)` 的指数分片，近密远疏，与深度精度分布一致。
- 内存没有单独的字节预算。cluster 的列表、计数、均匀数据都走 `GpuBuffer` 的创建路径，`MemoryContract` 只负责选内存类型（必需/优先属性、堆索引），不记录每个子系统的字节数。上面的 9.4 MB 是按格数和记录大小算出来的，不是运行时统计；要查显存预算，只能看设备堆的预算/用量读数，不能按 cluster 单独核算。

VXGI 不立项，理由有三条。

- 成本结构与大场景目标相反：步骤 7 的 zero_day 是 500 MB 级资产、流送驱动的大场景，VXGI 的体积内存和动态体素化税会直接顶到预算上。
- 世界空间分块缓存的学习收益已经由步骤 9 的 9.5 patch 池方案承接：该方案已立案并定稿，采用表面 patch 而不是体积辐亮度，尚未开工；VXGI 作为独立专题会重复同一项学习内容，而且用的是更贵的结构。
- 决策侧的结构已经由 cluster 落地；数据侧没有必要为了“专门做一遍体素”再补一个行业已经在大场景放弃的方案。

通用件的建议：值得抽成公共件的是第四节的第一个模式，“求交 → 压缩 → 列表”。参数至少四项：候选集、求交谓词、格子形状、输出策略（固定槽位还是计数加前缀和）。当前只有 cluster 一个消费者，可以先不抽象；等 9.3 的 patch 投放落地，再把两者共有的部分下沉，按[代码生成规范 §2.3](../../../rules/代码生成规范.md)的“重复模板下沉公共层”处理。将来 GPU 粒子密度场、探针分配之类也可以直接实例化。

VSM（虚拟阴影贴图）是按页缓存 shadow map、只重画脏页（内容变过、需要重画的页）的做法，不必上。8.3 已经落地 4 级 CSM 加 PCSS（按遮挡物距离调整滤波半径的软阴影），当前几何负载和阴影精度够用；VSM 登记在[外置拓展需求条目 7](../../开发步骤/外置拓展需求/外置拓展需求.md)，恢复条件是出现阴影精度不足、阴影重画成本主导，或有 Nanite（UE5 的虚拟几何系统）级密集几何/超高分 shadow map 需求，它的主要卖点在当前负载里兑现不了。真要做时，脏页标记和重画调度可以复用本文第 1、2 个模式。

如果将来做的是“小而全动态、几何本来就是体素”的项目，VXGI 这一族值得重新评估；对本仓这种大场景加流送的目标，结论不变。
