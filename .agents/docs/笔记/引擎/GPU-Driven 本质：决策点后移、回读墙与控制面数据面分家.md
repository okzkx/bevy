# GPU-Driven 本质：决策点后移、回读墙与控制面数据面分家

> 2026-10-19 沉淀（6.1 Hi-Z 遮挡收官、6.2/6.3/6.4 立案后的问答：用户复述"CPU 从渲染主进程退化成资产管理服务器，GPU 变成渲染主进程"，两轮校准后钉成此篇）。
>
> **一句话说明**：这篇把 GPU-driven 的本质钉成三句——逐对象的画面决策从 CPU 提交时搬到 GPU 执行时；渲染输出可以在显存内被下一次渲染消费；流程编排权留 CPU、逐对象决策权归 GPU、策略层从未离开 CPU——再给两个好用的比喻钉上精度边界；本篇是正空间论述（买到了什么），收益边界与反例见姊妹篇《为什么引擎没有都上 GPU 驱动》，不做任何新施工主张。

## 0. 判定线

- **本质一句话：GPU-driven 把"逐对象的画面决策"从 CPU 提交时搬到 GPU 执行时。** API 层的形状就是决策点后移（[5.3 知识整理篇](../../5-GPU驱动与常驻大场景/5.3-indirect闭环/indirect闭环的边界与归属：API能力、dispatch驱动与布局契约.md)已钉：CPU 从"每帧 N 次调用的决策者"退位为"每帧 1 次调用的供数者"）——本篇把这条 API 级结论展开成管线级架构形状。
- **买到的东西：渲染的输出可以被下一次渲染在显存内消费，一次 CPU 往返都不发生。** Hi-Z（上一帧深度→遮挡判定）与 GPU LOD（画面覆盖→档位）是这个性质最早兑现的两笔利息——输入（深度金字塔、标记、LOD 状态）与消费端（build_indirect）同在 GPU 侧，决策环在显存内部闭合。它们在 CPU 驱动管线里不是做不了，是每次消费都要付一次读回税。
- **回读墙是性质问题不是量级问题**：CPU 管线里可见性一直是渲染的免费副产品（深度测试每帧都在判"谁被挡住"），但要拿它驱动绘制决策必须读回 = 同步往返 = 流水线停摆。CPU 不是没正路（软光栅、异步查询返回都真实可行），是每帧决策循环付不起一来一回的延迟。边界、行业现状与反例见姊妹篇[《为什么引擎没有都上 GPU 驱动》](为什么引擎没有都上%20GPU%20驱动：CPU%20镜像、回读墙与收益边界.md)。
- **分界线：流程编排权仍在 CPU，逐对象决策权归 GPU，策略层从未离开 CPU。** command buffer 每帧仍由 CPU 编排提交——pass 结构、屏障、dispatch 形状都出自 CPU 之手，GPU 拿到的是模板；资产加载/淘汰、显存预算、场景变更发现（4.1 账本、6.3 驻留管理器）仍是 CPU 的核心业务。GPU-driven 买走的是**提交循环的决策权**，不是把 CPU 从渲染里开除。
- **全部同步纪律共享一个前提：主进程绝不等服务。** 标记环读数允许陈旧 ≤2 帧、Hi-Z 吃 1 帧滞后、LOD 状态放 GPU 持久 buffer——宁可要旧数据（配合 fallback 兜底），不肯同步空转；这是控制面/数据面分家后所有跨面通道的共同形状。

## 1. 机制：决策点搬家前后的两条流水线

**CPU 驱动（旧形状）**：CPU 逐对象跑剔除/遮挡/LOD 决策（或查询结果），在 for 循环里把决策**固化**成逐 draw 命令——决策的输入要么是 CPU 自己算的保守近似，要么是上一帧读回的旧账；渲染产生的最新可见性（深度缓冲）躺在显存里够不着，消费它必须停线。

**GPU 驱动（新形状）**：决策输入与消费端搬进同一侧显存，决策发生在执行时——本仓库的锚点链：

```
视锥 compute（5.2）→ 遮挡 compute 吃上一帧深度金字塔（6.1）→ LOD 选档（6.2）
    → build_indirect 浇筑命令洞（5.3）→ 一次 cmd_draw_indexed_indirect
CPU 每帧只喂：帧级辅助数据（六平面 push、判据阈值、相机 UBO）+ 事件驱动的资产供给（4.1/6.3）
```

关键不是"GPU 更快"，而是**成本形状变了**：CPU 侧每对象每帧付一次决策成本（O(总对象数)）；GPU 侧摊进一次 dispatch，成本跟可见工作量走。5.5 压测的实测形状——CPU 提交侧 0.4ms 平坦、与实例数解耦，GPU 图形段主导（[分档性能记录](../../5-GPU驱动与常驻大场景/5.5-分档压测/分档性能记录：三档压测读数与瓶颈归因.md)）——就是决策权搬家在账单上的样子。

## 2. 两个比喻与其精度边界（机制先于比喻）

**比喻一：CPU 从渲染主进程退化成资产管理服务器，GPU 变成渲染主进程。**
贴切处：CPU 剩下的活确实是服务性质——按需供给（6.3 请求→上传→发布）、按预算配额（显存预算账）、按策略回收（淘汰）、变更发现走事件不巡场（4.1 账本）。这正是 UE AsyncLoadingThread、Unity 6 GPU Resident Drawer 背后资源服务层的形状。
不贴处：**"退化"不是变轻闲**——6.3 整段都是给这个服务器写核心业务逻辑，只是它的服务粒度从"每帧每对象"变成了"按事件与预算"；也别读成"GPU 成为独立进程"——GPU 每帧执行的命令流仍由 CPU 提交，进程还是一个。

**比喻二：CPU 是编剧，GPU 是导演。**
贴切处：每帧的流程模板（pass 结构、屏障、dispatch 形状）出自 CPU 编剧；导演（GPU）在执行现场给模板里的**数据洞**浇筑内容——每条 draw 画几实例、画哪档 LOD、谁被剔除。build_indirect 就是浇筑点，indirect 命令数组就是那排待浇的洞。
不贴处：导演只管"这一场怎么演"；整部戏的分镜与档期（资产组织、预算、场景结构）仍是编剧的事——对应判定线第四条的"策略层不搬"。

比喻只负责建立第一直觉；与机制冲突时以机制为准（[写文档纪律](../写文档纪律：帧流程三轮返工的教训.md)：机制先于比喻）。

## 3. 代价与未兑现的角落

- compute 决策本身是真实成本——6.1 的"免费"指无同步税，不是零成本（金字塔构建、遮挡 dispatch 都进 GPU 账）。
- 陈旧决策数据的误剔窗口靠 fallback 与滞后窗兜底，"宁可要旧数据"有画面代价（6.1 判定线 2 口径：不长期误剔除）。
- 决策权搬家不解决所有问题：透明排序的天花板在粒度不在执行者，行业形态是分层混合而非全量 GDR——见姊妹篇与[VisBuffer 篇](渲染管线模式与%20VisBuffer：GDR%20的着色层搭档.md)（着色层是另一条正交的轴）。
