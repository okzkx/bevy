# 为什么引擎不把所有物体都交给 GPU 驱动渲染

传统渲染里，CPU 每帧对场景中的每个对象做三件事：

1. **剔除**：判断它在不在视野内、有没有被挡住，不可见就不画；
2. **装配参数**：准备它的变换矩阵、材质等绘制参数；
3. **提交**：发一次 draw 调用。draw 调用是 CPU 让 GPU 画一个网格的一次 API 调用。

GPU 驱动渲染（GPU-driven rendering，下称 GDR）把前两件事搬进 compute shader（在 GPU 上运行的通用计算程序）。第三件事则换成间接绘制（indirect draw）：CPU 只录一条绘制命令，具体画几笔、每笔用什么参数，由 GPU 事先写进显存里的一块缓冲。GDR 省掉的就是 CPU 每帧逐对象执行的这个循环，没有别的。

既然只省这一样，引擎就不会把 GDR 当默认形态。它会逐类内容判断：这类对象的决策交给 GPU 划不划算。划算要求三个条件同时成立：

1. GPU 算出的结果（比如哪些物体可见）只用来画图，CPU 之后不再需要它；
2. GPU 计算要用的物体数据能长期放在显存里，不用每帧大量重传；
3. 物体多到 CPU 逐个处理的开销，超过 GDR 自身的固定开销。

> 同一种计算该放在哪里做，不看算法，看结果给谁用。结果只给画图用，就在 GPU 上算；结果 CPU 还要用，就在 CPU 上算。

## 例子：石头适合交给 GPU，角色不适合

设想一个场景：一万块石头，一百个带骨骼动画的角色，两类对象都要做视锥剔除。

**石头的走查：**

- GPU 剔除完，把可见石头直接写成 indirect 命令；
- 从头到尾，CPU 不需要知道哪块石头可见。三个条件全满足。

**角色的走查：**

- CPU 每帧要先更新角色的骨骼动画，再交给渲染；
- 引擎普遍会跳过屏幕外角色的动画更新来省 CPU。例如 Unity Animator 设为 `CullCompletely` 时，渲染器不可见就完全停掉动画；UE 的 `VisibilityBasedAnimTickOption` 也是同一类开关；
- 于是 CPU 在帧初就要知道"这个角色可见吗"。

如果角色的可见性在 GPU 上算，CPU 只剩三条路：

- 给全部一百个角色更新动画，GPU 剔除省下的工作被抵消；
- 读上一两帧前的 GPU 结果，结论过时，还要专门搭一条读回链路；
- CPU 自己再剔除一遍，GPU 那一遍对 CPU 没有任何帮助。

三条路都不比"CPU 剔除 + 传统提交"好。角色卡在条件一上。那么，GPU 的结论为什么不能直接给 CPU 用？

## CPU 要用的结果放到 GPU 上算，会晚两帧才拿到

GPU 算出的结论在显存里。CPU 要用它，就得读回（readback），也就是把显存里的数据拷回 CPU 可读的内存。读回慢的原因不在拷贝，而在 CPU 和 GPU 不是同时执行同一帧。

**以本仓库为例走一遍。** 本仓库最多允许 2 帧在飞（CPU 已提交、GPU 还没执行完的帧）：

1. 第 N 帧，CPU 录好命令提交，GPU 稍后才执行其中的剔除；
2. CPU 不等 GPU，接着准备第 N+1 帧；
3. 第 N 帧的 fence 发出信号时，CPU 通常已经在准备第 N+2 帧了。fence 是 CPU 用来确认 GPU 已执行完某次提交的同步对象。

所以 CPU 拿到第 N 帧的可见性时，已经晚了大约两帧。想在第 N+1 帧就用上，CPU 只能停下来等第 N 帧的 GPU 工作做完，两帧并行的流水线退化成串行。

**由此筛掉的对象**：凡是"可见之后 CPU 还要为它做事"的，都不该把可见性交给 GPU：

- CPU 更新骨骼的角色；
- CPU 模拟的粒子；
- 每帧在 CPU 上生成顶点的动态网格；
- 可见性会触发流送请求或玩法逻辑的对象。

能容忍两帧延迟的用途可以读旧结论，比如"最近被看到过"这类节流标记。但那是额外搭的异步读回，不属于 GDR 本身。

反过来也成立：GPU 决定画什么之后，CPU 不能为了决定画什么再去读回结论，否则每帧都要等，决策又回到 CPU 手里。剔除计数这类诊断数字可以读回给人看，但不能参与"画什么"的决定。读回为什么是性质问题而不是快慢问题，见《GPU-Driven 本质》。

结论只给绘制用还不够，GPU 做决策需要的输入也得在显存里。这些输入从哪来？

## 物体变化越频繁，把数据同步到显存越贵

GDR 的决策输入要常驻显存，包括网格范围、材质槽号、包围盒（包住物体的最小盒子，用来快速判断可见性）、变换矩阵。但场景的权威状态，也就是其他副本都以它为准的那份数据，不能搬进 GPU：

- 物理、动画、AI、网络、玩法逻辑每帧都要随机读写场景状态，访问细碎、写入频繁、分支多，这是 CPU 擅长的访问方式；
- GPU 擅长的是成千上万个线程做同样的事，没有便宜的细粒度加锁手段。

所以显存里那份只能是渲染副本：CPU 持有完整状态，GPU 只持有"画它"需要的字段子集。CPU 改了状态，就得把改动同步到副本。为了让同步只传改动，需要四样设施：

| 设施 | 作用 |
|---|---|
| 变更发现 | 找出本帧哪些对象新增、删除、移动、换了材质 |
| 固定槽位 | 每个对象在 GPU 表里有固定行号，只重写变了的行 |
| 延迟回收 | 删除对象后，槽位要等所有在飞帧都不再读它才能复用 |
| 多份轮转缓冲 | 按在飞帧数准备多份缓冲，CPU 写下一帧的那份时，不覆盖 GPU 正在读的那份 |

GDR 的工程门槛主要在这四样，不在 API。

**同步量用数字算一遍。** 本仓库每个对象在对象表里占 48 字节（网格范围、材质槽号、包围盒），变换矩阵另放，每行 64 字节。以一万块石头计：

- 对象表 480KB，写入一次后只有换网格或换材质才改；
- 每帧 1% 的石头移动：要传 100 × 64B = 6.4KB；
- 每帧所有石头都在动：要传 10000 × 64B = 640KB，和整表重传一样大，还多付了变更发现的开销。

对象变得越频繁，只传改动的好处越小。条件二筛掉的就是高频变动的内容。

**删除时，"哪些行可以画"仍然要由 CPU 决定。** 走一遍删除：

1. 表里有 1000 行，第 37 行的对象在第 100 帧被删除；
2. 第 99、100 帧的命令可能还在 GPU 上读第 37 行，所以这一行不能立刻清掉或复用，旧记录留在表里；
3. 如果 GPU 按"第 0 到 999 行都要处理"遍历，第 37 行会继续被画，直到槽位被新对象复用；
4. 如果这期间它引用的网格已经卸载、那段显存给了别的网格，画出来的就是另一个网格的几何。

解法是由 CPU 每帧明确告诉 GPU 哪些行可以画：要么下发可画行号列表，要么删除时同步把 GPU 记录标为无效。两种做法里，"哪些行可以画"的最终依据都在 CPU。

前两个条件谈的是结论和输入能不能放在 GPU，最后一个问题是：放了值不值。

## 物体少时，GPU 驱动省下的时间抵不上它的固定开销

GDR 省的开销随"对象数 × 帧数"增长，换来的是上一节四样设施的固定开销，外加调试开销：GPU 上的剔除结果没法直接打日志，要专门做读回统计。

**CPU 这一侧其实并不贵。** 剔除和提交两部分分开算：

- **剔除**：一个对象的视锥剔除是包围盒对六个平面各做一次判断，几十次乘加。一万个对象约几十万次乘加，现代 CPU 上在亚毫秒量级；
- **提交**：开销在逐对象的 API 调用、参数装配和状态切换。D3D11/OpenGL 时代常见的经验预算是每帧两三千个 draw；Vulkan/D3D12 的单次 draw 开销低得多，上限更高。

对象少时，省下的部分很小，固定开销照付。例如几百个对象的场景，CPU 剔除加按状态合批就够用。按状态合批指把共享着色器和状态的对象连续提交，减少状态切换，Unity 的 SRP Batcher 就是这种机制。

三个条件全满足的内容，交给 GPU 后也还有两件事没解决。

## 半透明排序放到 GPU 上做，结果并不会更准

混合（blend）是把新像素的颜色和画面里已有的颜色按透明度合成。合成结果跟先后顺序有关，所以半透明物体必须大致从远到近画。这是正确性要求，跟谁来排序无关。

**走查两块相交的玻璃 A 和 B：**

- 按物体中心排序，只能决定"整块 A 先画"或"整块 B 先画"；
- A 有一半在 B 前面、一半在 B 后面，无论选哪个顺序，总有一半是错的；
- CPU 排和 GPU 排得到同一个顺序，错误也一样。

GPU 排序能做的，是在 compute shader 里排好再生成 indirect 命令，省掉 CPU 的排序时间，精度不变。要做到每个像素都对，得靠顺序无关透明（OIT）：先把每个像素上的多层颜色都记下来，最后再按深度合成。这跟是否 GPU 驱动无关。

UE 的 Nanite（UE5 的 GPU 驱动几何系统）只接受 Opaque 和 Masked 两种混合模式，Translucent 材质会被替换成默认材质。Nanite 用可见性缓冲：先只记录每个像素属于哪个三角形，之后统一计算着色。而 blend 要求每画一层就读取并改写目标颜色，两者冲突。所以半透明在各引擎里都单独走一条前向渲染通道。

## 需要单独特殊处理的物体，会退回传统画法

玩法常有针对单个对象的特殊需求：选中高亮、只改一个物体的材质参数、渲染时触发脚本回调、调试绘制。

**以"一万块石头里高亮选中的一块"为例：**

- **CPU 提交路径**：循环到这块石头时换一个材质参数，多一个 if；
- **GDR 路径**：对象表要加一个"高亮"字段，shader 要读这个字段再分支，或者把这块石头移出 GDR，交给传统路径画。

每多一种定制需求，GDR 路径就要多一个字段或一个分支。引擎的普遍做法是让这类对象直接退回传统路径。

Unity 6 的 GPU Resident Drawer（Unity 的 GDR 实现）是现成的例子：

- **启用条件**：要在项目设置里手动开启，只在 Forward+ 渲染路径下工作，只接管 Mesh Renderer。Forward+ 是一种先按屏幕区块筛出光源、再逐物体着色的前向渲染路径；
- **自动排除**：以下几类对象会退回普通绘制：
  - 用了 `MaterialPropertyBlock` 的。这个 API 用来给单个物体覆盖材质参数；
  - 脚本挂了 `OnRenderObject` 这类逐对象渲染回调的；
  - 在同一帧两台相机的渲染之间被移动的；
  - 使用实时 GI（运行时计算的间接光照）的；
- **手动排除**：可以给对象挂 Disallow GPU Driven Rendering 组件。

传统路径始终存在，所以引擎得长期维护两条路径。抓帧、性能分析、单对象调试这些工具也得两边都支持。

## 实际引擎按物体类型分开处理，GPU 驱动只管其中一类

| 内容 | 走哪条路 | 原因 |
|---|---|---|
| 大批静态、实例化的不透明几何 | GDR | 三个条件全满足 |
| 要 CPU 逐帧准备的对象（骨骼角色、CPU 粒子、动态网格） | CPU 剔除 + 传统提交 | 不满足条件一 |
| 每帧大量变动的对象 | 传统提交 | 不满足条件二 |
| 需要逐对象定制的对象 | 传统提交 | 定制需求让 GDR 路径不划算 |
| 对象很少的场景 | CPU 剔除 + 按状态合批 | 不满足条件三 |
| 半透明 | 单独的前向渲染通道，近似排序 | 排序问题不因 GDR 消失 |
| 权威场景状态 | CPU | 不属于渲染决策 |

## ash_renderer 里的对应实现

三个条件在本仓库代码里各有对应。

**条件二：渲染副本**

- 权威状态在 Bevy World（Bevy ECS 存放全部实体和组件的容器）；
- `InstanceLedger` 是 CPU 侧的实例表，记录每个实体占哪个槽、哪些行变了，并把变了的行写进 GPU 对象表；
- 对象表只记网格范围、材质槽号、包围盒这些很少变的字段；每帧会变的变换矩阵单独放一组按帧轮转的缓冲（每帧一份，共 2 份）。

**条件二：哪些行可以画**

- CPU 每帧把可画行号列表写进一块缓冲；
- 生成 indirect 命令的 compute shader（`build_indirect`）只为列表里的行生成绘制命令；
- 资产还没加载好的行不进列表，GPU 侧不需要额外判断。

**条件一：不读回可见结果**

- 项目规定 CPU 不读回 GPU 的可见结果来决定画什么；
- 剔除计数等诊断数字可以读回，但只显示在 egui 调试面板和 BRP（Bevy Remote Protocol，从外部查询运行中程序的接口）里；
- 负责录制绘制命令的代码不读取任何 GPU 读回数据。

**条件三：规模**

- 默认的头盔场景只有十几个实例，按条件三是负优化；
- 照做是为了练整套常驻设施，不是产品选择；
- 在 5.5 分档压测里，CPU 提交侧耗时稳定在约 0.4ms，不随实例数增长。这说明 GDR 的收益要到大规模场景才显现。
