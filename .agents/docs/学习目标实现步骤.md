## 步骤 1：简单熟悉 Bevy 的结构

**目的**：建立“哪些是宿主、哪些是要绕开的渲染栈”的心智地图。熟悉到能组装即可，深度理解在后续施工中按需补。

**做什么**（已完成的学习范围）：

1. 跑 `hello_world`、`empty_defaults`、`3d_scene` 三个最小示例。
2. 读 `App` / `Plugin` / `SubApp` 与 `App::run()` 生命周期。
3. 把 DefaultPlugins 分成宿主族、渲染族、无关项，形成禁用清单。
4. 理解 Query、Resource、Commands、变更检测与系统排序。
5. 对照入口篇边界表识别需要使用和仅作参照的 crate。
6. 查窗口创建、事件进入 ECS 与 raw handle 的路径。

**产出**：[Bevy 结构笔记](1-熟悉Bevy结构/Bevy结构笔记.md)及该目录材料，回答帧循环、禁渲染后剩余职责、系统执行顺序、glTF 到实体四个问题。

**完成标准**：能解释帧循环时序和插件分类，能逐行说明 `3d_scene.rs`；不以读完所有源码为目标。

## 步骤 2：宿主壳（M1）

**目的**：验证禁渲染 Bevy、winit 窗口和自建 Vulkan 可以共存。

**做什么**（已落地的范围）：

1. 建 workspace member `ash_renderer`，复用本仓库 Bevy 依赖。
2. 组装 App，禁用渲染族及必要连带插件；保留资产、窗口和 ECS。
3. 通过 `PrimaryWindow` 上的 `RawHandleWrapper` 建 Win32 Surface，连接 Instance / Device / Queue / Swapchain。
4. 跑 acquire、清屏、present；处理 resize、最小化与退出。

**产出**：可运行宿主和[《宿主壳搭建记录》](2-宿主壳/2-宿主壳搭建记录.md)。

**完成标准**：清屏持续、窗口生命周期正常、无 wgpu 初始化。历史实跑已经通过；当前新增的同步复核闸门见上方，不据旧收官状态豁免。

## 步骤 3：静态取数链路（M2）

**目的**：先打通资产到 GPU 的正确静态版本，为增量和 GPU-driven 提供可复用资源基础。（✅ 2026-09-29 全段收官，逐段证据见[步骤索引](3-静态取数链路/README.md)）

**做什么**：按[五段施工计划](3-静态取数链路/施工计划：Bindless起步五段拆解.md)推进：

1. **3.1 ECS 取数**：glTF WorldAsset 实例化，材质、相机、灯光就位，PostUpdate 在变换传播后采集。
2. **3.2 buffer 上传**：顶点/索引池、合批 staging、transfer 提交、跨族共享或所有权转移、上传完成与内存复用。
3. **3.3 贴图与 bindless**：先验证最小 WGSL → SPIR-V 接口，再确定纹理/采样器 binding、descriptor indexing、槽位发布与安全回收边界。
4. **3.4 管线与绘制**：明确 CPU/shader 布局、反向 Z、viewport/绕向、颜色空间；从清屏长成直接绘制。
5. **3.5 对照验收**：统一调试条件检查几何、base color、UV 和光照方向，收官。

**前置契约**：

- PostUpdate 采集、Last 同帧提交；GPU 异步完成不等于 CPU 跨帧采集。
- 合批是减少提交的基础，独立 transfer 队列是所选路径，不预先保证它比同队列快；timeline 不替代队列族所有权转移。
- staging 等上传完成再复用；目标资源和描述符槽等最后一次使用完成再覆盖或回收。
- M2 的全量拓扑快照与逐 draw push constants 是阶段实现，不是步骤 5 的终态。

**验证**：FlightHelmet 六个 primitive 在统一不透明调试模式下核对完整几何；base color/UV 和方向光另做受控对照。原模型有 `BLEND` 镜片，不能一边丢弃透明材质、一边要求原样完整。Lambert 简化不要求与官方完整 PBR 像素一致。验证层实际启用，上传正常路径不逐资源 `wait_idle`，resize/退出与异常分支复测通过。

预备知识见[glTF 加载链路](1-熟悉Bevy结构/材料/glTF加载链路：从磁盘到Mesh3d.md)。frenderer 的逐 buffer staging 提交是结构参照，不是无需控制条件就能归因的性能基准。

## 步骤 4：可靠增量链路（M3）

**目的**：从“一次正确上传”发展成能长期处理变更、异步到货、删除和替换的资源链路。

**建议段落**（编号预留；开工时再立对应任务面板，不提前造空目录）：

| 段 | 交付范围 | 独立验收 |
|---|---|---|
| 4.1 对象增量 | 稳定的 Entity→GPU 实例槽关联；新增、矩阵变化、mesh/material 句柄替换、组件移除与 despawn；不再每帧重建完整上传清单 | 移动物体只更新相关实例数据；替换引用和删除不残留旧对象 |
| 4.2 资产增量 | Mesh / Material / Image 的 `AssetEvent`；同句柄内容变化、共享资产去重、关联材质/包围体失效 | 多实体共享资产时只上传必要的一份内容，各使用者正确更新 |
| 4.3 异步就绪 | pending、上传票据、可使用、失败与取消；到货时检查实体和引用仍有效 | 延迟到货、加载失败、等待期间删除或换柄，不读空槽、不错误复活对象 |
| 4.4 回收与热重载 | 在飞资源延迟销毁、槽位安全复用、容量变化；文件监听配置与 WorldAsset 重载回归 | 反复增删/热重载资源不持续泄漏，不覆盖 GPU 尚在读取的内容 |

**重要边界**：

- **增量上传 ≠ 增量发现。**`Changed<T>` / `Added<T>` 仍扫描匹配实体；先单独计量扫描成本，确认瓶颈后再考虑静态/动态分离或显式脏队列，不先重写 ECS。
- `RemovedComponents<T>` 不带旧组件内容，删除处理依赖自己保存的实例槽与旧资产关联。
- 资产内容变化不一定导致实体上的句柄变化；只监听 `Changed<Mesh3d>` 不足以实现资产热重载。
- 文件变更到磁盘读取、解析、子资产和 GPU 就绪是异步链，不能承诺“改文件当帧全部生效”。CPU 已就绪且在本帧采集前可见的变更，应进入本帧准备；GPU 消费必须受上传完成依赖保护，另记等待帧数。
- 整 WorldAsset 热重载可能 despawn 后重新 spawn，旧 Entity 身份和运行时附加状态不默认保留。

**产出**：对象/资产/上传状态与回收责任清单、增量系统、热重载回归记录。

**完成标准**：零变化时实例与资产上传为零；共享资源、换柄、同柄改内容、延迟到货、删除取消、反复加载卸载全覆盖。分别报告扫描数、上传字节、资源存量和处理耗时，不把“零上传”说成“零 CPU 每对象成本”。

## 步骤 5：最小 GPU-driven 与常驻大场景（M4）

**目的**：先让 GPU 独立决定画哪些实例，再扩大规模；不能用逐对象 CPU draw 的结果验证 GPU-driven 大场景目标。

| 段 | 交付范围 | 独立验收 |
|---|---|---|
| 5.1 常驻绘制数据 | 实例、mesh 范围、材质索引与包围体；从逐 draw push constants 过渡到 GPU 按实例索引读取 | CPU 不必逐对象推送绘制参数；非均匀缩放等变换下包围体保守正确 |
| 5.2 GPU frustum | compute 生成可见标记；明确 compute 写到绘制读取的依赖 | 不做 CPU 每对象可见性剔除，不回读可见集驱动绘制 |
| 5.3 indirect 闭环 | GPU 写 indirect 参数、GPU 可取得对象/材质索引、图形提交消费结果 | CPU 绘制调用不随对象数线性增长；固定槽位且不可见 `instanceCount=0` 即可起步 |
| 5.4 常驻大场景组织 | 共享资产大量实例、空间 chunk 身份与边界、整块增删；补基础 mip 链；数据先全常驻 | 对象复用和块边界可观察，合并不破坏独立运动、剔除与后续卸载粒度 |
| 5.5 分档压测 | 按本文验收协议测实例规模、静态/动态比例与成本增长 | 报告实际实例数、CPU/GPU 时间、显存与瓶颈，不只给“流畅”截图 |

**参照而非照抄**：bevy_city 可借鉴消息驱动加载、observer 补组件、静态变换优化和车型内部网格合并。它主要是全量生成的压力场景；`merge_car_meshes` 是车型内部合并再跨车辆复用，不是全城大网格或完整流送系统。默认先实例复用；必要时仅在兼容材质、运动方式与 chunk 边界内合并静态零件。

GPU 内核参照按当前 checkout 查 `mesh_preprocess`、`build_indirect_params`、`gpu_preprocess`，文件可能是 `.wesl` 而非旧资料的 `.wgsl`。学数据依赖和取舍，不搬整套 Bevy 架构。

**产出**：最小 GPU-driven 渲染路径、常驻大场景生成器、分档性能记录。

**完成标准**：小场景验证正确后再扩到 1 万、5 万、10 万档实际渲染实例；CPU 不回读可见集、不逐对象重建 draw list。1 万为起始档、5 万为目标档、10 万为压力档，能承载的规模由测量给出，不预先声称三档都能达到固定帧率。

## 步骤 6：高级剔除、LOD 与流送（M5）

**目的**：在常驻 GPU-driven 已成立后，减少不可见/过细工作，并让大于驻留预算的世界可持续加载卸载。

| 段 | 范围 | 验收重点 |
|---|---|---|
| 6.1 Hi-Z 遮挡 | 深度来源、层级深度生成、反向 Z 下的归约与保守测试、历史深度使用边界 | 快速移动/转镜头不长期误剔除；比较开关前后 GPU 成本与实际剔除量 |
| 6.2 GPU LOD | GPU 选择 mesh LOD，阈值/迟滞、包围体与 indirect 数据联动 | 远近切换稳定，不访问未驻留 LOD；同画面预算下测收益 |
| 6.3 粗粒度流送 | chunk/整资产级预算、请求、异步上传、可用发布、淘汰与回收 | 超出预算的场景可持续游历；无瞬时悬空引用、无无限显存增长 |
| 6.4 细粒度流送（进阶） | mip / 更细 LOD 驻留，缺页回退和请求合并 | 不与基础 mipmap 混为一谈；先有可用低精度回退，再做细粒度提质 |
| 6.5 descriptor buffer（独立专题） | `VK_EXT_descriptor_buffer` 能力查询、描述符存储与绑定实验 | 同一渲染内容、同一 GPU-driven 路径对照，记录 CPU/GPU/内存差异 |

**M5 主线验收为 6.1～6.3。**6.4 是流送深化，6.5 保留为明确的 Bindless 学习目标，但不阻塞 GPU-driven 主线收官。descriptor buffer 不是 Vulkan 1.4 核心，也不是 descriptor indexing 必须淘汰的终点；应按能力和实测选择是否替换。

**产出**：遮挡/LOD/驻留管理器及各自开关对照，流送压力记录；独立描述符实验单独报告。

不把完整 PBR、通用 RenderGraph、mesh shader、蒙皮、编辑器或 Web Console 插入主线必修；需要时另立有动机和完成标准的专题。（编辑器与 Web Console 方向已按此机制立案：追加段 3.10～3.12——egui 实体检视/编辑与 BRP CLI——见步骤 3 节尾。）

## 统一验收与性能口径

1. **计数清楚**：区分 World 总实体、可渲染实例、唯一 mesh/material/image、可见实例与实际 draw；`--size 50` 不代替实例计数。
2. **条件固定**：记录提交版本、GPU/驱动、Release、分辨率、材质/光照、抗锯齿、present 模式、节流配置、随机种子和相机轨迹。默认 60 Hz 节流下的帧率不是吞吐量；基准需区分真实工作耗时与主动等待，不拿 present 返回当上屏完成。
3. **指标成组**：CPU 的传播、采集/扫描、上传准备、提交分别计时；GPU 用对应工作区间计时；报告 p50/p95/p99、加载/增删尖峰、上传字节、提交次数、显存和待回收资源数。
4. **增长斜率**：1 万/5 万/10 万实例，分别测零变化、少量变化和全动态。静态场景仅移动相机时不应重传全部实例；若仍有 O(N) 查询扫描必须如实报告。
5. **预算先写后测**：以 60 Hz 的 16.7 ms 作为初始帧预算，在每段基准开跑前固定场景与通过阈值，记录实际达到的规模、p95/p99 和瓶颈；不以“肉眼流畅”替代数据。
6. **等待统计有边界**：上传热路径不得逐资源或逐批 `device_wait_idle` / `queue_wait_idle`；显式重建、退出和容量维护单列，不隐去停顿，也不把 fence/timeline 的必要复用等待称为违规。
7. **A/B 控制变量**：frenderer 保留为端到端参照；资产、画质、可见性策略等不同，只能报告系统差异，不能直接归因 bindless。描述符存储模型的收益优先在本渲染器内控制变量比较。
