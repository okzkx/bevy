# 三张表的设计决策：更新频率、写入方式与备选方案对照

> 2026-10-15 收官配套设计篇（机制深潜之一）。本文回答一个问题：**为什么是这三张表、为什么各自长这个形状**——把 5.1 施工时做过的每个备选方案摆出来对打，留下"当时为什么不选"的记录，供 5.2/5.3/5.4 扩展时回查。结构事实与代码细节在[对象表机制篇](对象表机制：GPU可见的场景名册——记录布局、set2与槽位生命周期.md)与[环机制篇](环机制：HostVisible数据的帧槽轮转与fence纪律.md)；新旧对照的入门叙事在[第一课](GPU驱动第一课：从逐draw推参数到实例索引读表——新旧两套写法对照.md)。

## §0 决策框架：给一份 per-object 数据定型前，先问三个问题

1. **多久变一次？**（不变 / 每帧可能变 / 偶尔变）
2. **量级随什么涨？**（实例数 / 唯一资产数 / 常数）
3. **谁来写？**（CPU 宿主直写 / GPU 命令写——这决定了可用的安全机制集合）

三个问题的答案组合起来，写入方式基本是唯一解：

| 答案组合 | 写入方式 | 安全机制 |
|---|---|---|
| 几乎不变 + 量级 O(实例) + CPU 命令写（经 transfer） | **每槽写一次**，变更 = 新槽 + 旧槽停尸房 | 读侧票据等待 + 写侧排空点帧侧等待 |
| 每帧可能变 + 量级 O(实例) + **宿主直写** | **环增量**（脏集 ×帧槽数） | 帧槽 fence（wait_for_slot） |
| 每帧可能变 + 量级 O(唯一资产) 或更小 + 宿主直写 | **环全量**（每帧重投影容器现状） | 同上 |
| 每帧变 + 量级 O(实例) + 宿主直写，但变更稀疏 | 环全量是错的（6.4MB/帧），增量是唯一解 | 同上 |

5.1 的三张表就是前三行的落地；第四行（model）与第二行同形状，量级论证见 §3。

## §1 三张表定妆照（决策结果）

| | 对象表 | 模型环 | 材质环 |
|---|---|---|---|
| 内容 | mesh 范围三参数、材质槽号、局部 AABB | model 矩阵 | base_color、贴图/采样器槽号 |
| 量级 | O(实例)，131072 槽 × 48B | O(实例)，×2 帧槽 × 64B | **O(唯一材质)**，×2 帧槽 × 32B |
| 内存 | DEVICE_LOCAL（新 DeviceStorage 角色） | HOST_VISIBLE（Storage 角色） | 同左 |
| 写者 | flush_uploads（staging 批次，transfer 命令） | draw_frame（宿主直写，增量） | draw_frame（宿主直写，全量） |
| 写频率 | 每槽写一次；更新=换槽 | 改动行每帧写、两帧写满两环 | 每帧全部可绘材质重写 |
| 在飞安全 | 票据（读侧）+ 停尸房排空（写侧） | 帧槽 fence | 帧槽 fence |
| 消费者 | VS（范围/材质槽）、5.2 compute（AABB） | VS | FS |

## §2 对象表：为什么是"写一次 + 换槽"

对象表的内容有一个共同点：**它们是物体的"定义"，不是物体的"状态"**。mesh 在池里的区间、用哪个材质、长什么样（包围盒）——这些只在入场/换绑/换网格时变。围绕这个定性，逐个排除备选：

### 备选 A：每帧全量重写（Bevy 的做法）

官方 bevy_render 的做法确实是每帧把全部 `MeshUniform` 重新写一遍（prepare 阶段 O(N)）。**我们不学它，理由是本仓库自己的历史**：4.1 立的判定线"零变化时实例与资产上传为零、如实分报扫描数与处理数"——每帧全量写等价于把 4.1 拆掉的 O(N) 每帧成本从"上传侧"改头换面搬回"绘制准备侧"。Bevy 的 prepare 全量重写是它整体架构（extract/prepare 两阶段流水线）的一部分，我们没有那条流水线，也没有理由为一张"几乎不变的表"付每帧全量的钱。

**但保留一个诚实注脚**：Bevy 的方案没有槽位生命周期（不需要停尸房、不需要换槽），简单性占优。如果将来出现"每帧大量对象定义都变"的场景（比如程序化重建整个场景），写一次+换槽的维护成本会反过来超过全量重写——到那时该翻面，判据记在 §5。

### 备选 B：原地更新（写一次不变式不存在，直接改槽内容）

这就是"移动一个物体 = 改 7 号槽的 model 字段"的方案——**否决，理由是规范级 hazard**：改写经 transfer 命令（vkCmdCopyBuffer），而上一帧的 draw 还在 GPU 上执行、正在读 7 号记录。transfer 写 vs 图形读，两个提交之间没有任何依赖 = 未定义行为。同步验证层对 buffer conflict 是执法的（会报 hazard VUID），我们的"零 VUID"判定线直接爆。

配套的"用 barrier/信号量排序"也救不回来：要么 flush 等"图形最后使用"再写（在飞窗口内全停，等于每帧 wait_idle），要么 graphics 提交反向等 transfer（帧 N 的绘制被帧 N 的上传卡住，流水线串行化）。两条都不可接受——**根本问题是让"写"和"读"挤在同一块内存里**，排序只是给挤车维持秩序，换槽是直接不挤。

### 备选 C：swap-on-commit（每次变更换新槽 + 旧槽停尸房）

对换绑/热重载（稀疏变更）这正是落地方案，照 4.2/4.4 的既有形状。它被否决的场景是**高频变更**：若 model 也在表里，1 万个动态物体 = 每帧 1 万次换槽——free list 被掏空，停尸房每帧非空，`drain_graveyard` 的"等全部帧槽 fence"**每帧全停**（停尸房排空的本意是稀疏回收，被高频变更打成每帧同步点）。这正是路线图闸门里"F1 槽位 churn 随步骤 5 容量/淘汰设计评估"钉子预感的坑——5.1 的解法不是修 churn，是让高频变更**根本不经过这张表**（model 出走，见 §3）。

### 落定的形状与它买来的东西

"每槽写一次"带来一条强不变式：**任何时刻读任意在用槽，内容都是完整的、属于当前占用者的**。这条不变式让 shader 和将来的 compute 可以**随时、乱序、并行地**读整张表而不需要任何同步——5.2 compute 剔除的并行读、5.3 indirect 写参，都直接站在这条不变式上。这是"写一次"最值钱的产出：不是省更新，是**读侧零同步**。

## §3 模型环：为什么 model 必须从对象表拆出来

§2 备选 B/C 的结论合并起来就是本节的论证链：

1. model 是**状态**不是**定义**——它是唯一"高频变"的 per-object 字段（移动）。
2. 它进对象表 → 撞备选 B（hazard）或备选 C（每帧全停），二选一都死。
3. 所以易变数据不能住"写一次"的表——它需要另一种写形状：**宿主直写的环**。

为什么宿主直写可行（对象表反而不可行）？看写入通道：model 环的写是 CPU 对映射内存的 `memcpy`（不是 GPU 命令），barrier/信号量都排不了它的队，唯一的安全证据是**CPU 侧时机选择**——`wait_for_slot` 的帧槽 fence 证明"本槽上一轮提交已跑完"。环 ×2 帧槽轮转让这个等待从"每帧全停"降级成"帧槽自然背压"（详细机制与时序图见[环机制篇](环机制：HostVisible数据的帧槽轮转与fence纪律.md)）。

为什么**增量**不是全量：model 是 O(实例) 数据，10 万实例全量 = 6.4MB/帧的宿主写 + 遍历；而移动是稀疏的（动的少、静止的多），脏集账本（`model_dirty[2]`，按帧槽奇偶两套）的维护费远低于全量写。判定线证据：移动一次 = `transform_updates_total` +1、上传 0 字节、模型环写 64B——静态场景两环零写入。

为什么**两套脏标记**：环按帧槽轮转，帧 N 写的是"本帧奇偶"那个环，另一个环上还躺着上上帧的旧值——不补写就会一帧新一帧旧地闪。改动行进两套奇偶集，两帧后两环都新鲜。

## §4 材质环：为什么全量不是增量

增量省的是写入字节（32B/材质），付的是"知道谁变了"的账本：变更事件接线（材质 Modified / 贴图 Modified 换指 / 复活）+ 双奇偶待写集 + 漏标闪变 bug 面。全量重写付的只是 O(唯一可绘材质数 × 32B)——**实例数爆炸时材质数基本不动**（共享资产大量实例化正是 5.4/5.5 的组织方式），头盔是 5 条 = 160B/帧，10 万实例大概率还是这个数。账本费 > 字节费，增量亏损。

全量重写还有两条语义红利：**环内容 = 容器当前状态的纯投影**（每帧从 `Assets<StandardMaterial>`/`ImageCache` 现读，材质 mutate、贴图换指、热重载自动次帧生效，flush 侧零新增通道——4.2"材质没有 GPU 驻留内容"的判断在新结构里原样成立）；**没有首写/补写路径**（新材质首次可绘，本帧重写自然带上）。

交叉点判据：哪天唯一可绘材质数上千（每帧 32KB+ 且容器遍历可见），这条该翻面成增量——翻面方式照抄模型环的双奇偶待写集，环结构不动。

## §5 决策判据与翻面条件（留给将来）

| 信号 | 触发的翻面 |
|---|---|
| 场景每帧大量对象的**定义**变化（程序化整场重建） | 对象表"写一次+换槽" → 评估全量重写（备选 A 的 Bevy 形状） |
| 唯一可绘材质数上千 | 材质环全量 → 增量（双奇偶待写集） |
| 动态物体占比极高（几乎全部每帧移动） | 模型环增量 → 全量重写（脏集账本费超过全量写） |
| 实例规模超出 131072 | 对象表容量上界报错 → 届时评估分页/多表/容量重建（5.4 常驻大场景的容量设计范围） |

三条共同的后盾：**读侧零同步是三张表共享的不变式**（对象表写一次、环按帧槽隔离），任何翻面都不得破坏它——这是 5.2 compute 并行读的前提。

## §6 与第一层/第二层账的关系（三层账全景）

| 层 | 账 | 键 | 记什么 | 归属段 |
|---|---|---|---|---|
| 资产层 | MeshPool/ImageCache residency | AssetId | 几何字节在池里的区间、贴图描述符槽 | 3.2/3.3/4.2 |
| 实体层 | InstanceLedger rows | Entity | 物体用哪些资产、当前矩阵、**实例槽号** | 4.1 |
| 实例槽层 | InstanceTables | 槽号（跨帧稳定） | 物体的 GPU 侧定义（对象表）+ 状态（模型环）+ 妆容（材质环） | 5.1 |

三层各记一个"身份→地址"的映射，方向单向：账本行（实体层）持槽号（实例槽层），槽号记录持资产槽（资产层）。删除沿同方向逐层交接（despawn → 清行 → freed_slots → 停尸房），任何一层都不反查上层——这是"账本零 Vulkan"边界能保住的原因（实例槽层只向上暴露整数，不要求账本层理解 Vulkan）。
