### 0.3 需要订正的上游口径

主计划 §2.1 的 10.1.1 与判定线 1 写的是"仅 `ray_tracing_stats` / `ray_tracing_dump` 请求时临时打开一帧并在之后恢复"。这个动作在现役架构里做不到"请求即得"：

- BRP handler 在 `RemoteLast`（`Last` 之后）同步执行，`draw_frame` 在 `Last`（`ash_renderer/src/remote/mod.rs:42`、`ash_renderer/src/driver/host/mod.rs:9`）；同一次调用里本帧 `draw_frame` 已经跑过，要拿新图必须等帧循环再回到 `Last`，在 handler 里等待会卡住帧循环。
- `ray_tracing_dump` 读的是当前帧槽最近一次提交的调试图；handler 在 `Last` 之后，本帧 `draw_frame` 已跑完，当场把 `debug` 置 true 再读，读到的仍是旧的关闭态图像。
- "开一帧后自动恢复"只能跨多次 BRP 调用完成，客户端仍要第二次调用取图，复杂度高于收益。

因此本段把契约改为"显式常驻 `debug`，默认 false，调用方开、取证后关"（R1）。本次立案同步只改文档措辞，不改代码；主计划 §2.1、判定线 1、D9 的写法以本文 R1 为准。

## 1. 立案期裁决

施工可以推翻以下裁决，但必须在 `10.1.x-*.md` 记录里写明"推翻哪条、为什么、替代方案怎么验收"；不得默默改口径。

### R1 `debug` 做成显式常驻开关，默认 false

- `RayTracingSettings` 增加 `pub debug: bool`，`Default` 为 false；`init.rs` 初始化也为 false。
- `prepare_ray_tracing` 的条件从 `instance_count > 0` 收紧为 `instance_count > 0 && settings.debug`；关掉时 `RayTracingFrameDraw.debug` 为 `None`，`record_debug` 直接返回，不录 UNDEFINED→GENERAL 屏障与 dispatch。
- 开启 `debug` 后，调用方要等至少一帧（脚本 `settle(1.0)`）再 `ray_tracing_dump`，因为本帧 `draw_frame` 已在 handler 之前跑完，设置要到下一帧才生效。
- 默认 false 的收益是每帧省掉约 1,440,000 条调试图射线与约 2.8 ms 的 Rays 段 GPU 时间；TLAS 仍随 `enabled` 运行（约 0.22 ms），不在节省内。这是本段希望看到的副作用，但判定线只要求"关时 rays==0、开时 rays==像素数"，不把"必然省 3 ms"写成验收条件。
- `enabled` 的默认值不变：仍由设备是否支持光线求交决定，不因 `debug` 改动。

### R2 BRP 只加字段，不改方法名

`ray_tracing_set` 参数：

```json
{"enabled": true, "view": 0, "debug": true}
```

- `view` 与 `debug` 都是可选；缺省表示保持当前值。`view` 仍只接受 0/1/2。
- 返回值增加 `debug` 与 `previous_debug`，保留原有的 `enabled`、`previous`、`view`、`supported`：

```json
{"enabled": true, "previous": false, "view": 0, "debug": true, "previous_debug": false, "supported": true}
```

`ray_tracing_stats` 的 `debug` 对象增加 `enabled`，表示"调试图此刻是否真的在跑"：

```json
"debug": {"enabled": true, "rays": 1440000, "hits": 720000, "hit_rate": 0.5,
          "last_tlas_ms": 0.22, "last_rays_ms": 2.81}
```

- `debug_active = supported && settings.enabled && settings.debug`。
- `debug_active == false` 时：`rays`、`hits`、`hit_rate`、`last_rays_ms` 归 0；`last_tlas_ms` 在 `enabled == true` 时保留（TLAS 仍在跑），`enabled == false` 时为 0。
- 顶层 `enabled` 仍表示"光线求交是否启用"，不改语义。

`ray_tracing_dump` 的检查顺序改为 view → enabled → debug：

- view 不匹配：报错，提示先用 `ray_tracing_set {"view":N}` 切到目标子视图。
- enabled 为 false 或设备不支持：报错，提示先 `ray_tracing_set {"enabled":true}`。
- debug 为 false：报错，文案明确"调试图未开启，先 `ray_tracing_set {"debug":true}`，等至少一帧后再 dump"。

### R3 rings 切成四段，且四段是对整段的完全划分

| 字段 | 起点 | 收口点 | 包含的工作 |
| --- | --- | --- | --- |
| `rings_shadow_ms` | `assemble_done()` 之后 | `shadow.write_ubo` 返回后 | 装配状态日志、view、`FrameLight::gather`、IBL 准备、场景 AABB、shadow UBO；名字短，记录里注明"含前置准备" |
| `rings_cluster_ms` | 上一收口点 | `cluster.write_slot` 返回后 | `post.write_slot_ubos`、cluster 写入 |
| `rings_prepare_gi_ms` | 上一收口点 | `write_frame_ubo` 返回后 | transparent 清理、gbuffer/ldr 句柄、`gi_ray_set`、indirect count、SCGI ensure、`prepare_gi`、SCGI 消费门控、frame UBO |
| `rings_tables_ms` | 上一收口点 | `rings_done()` 之前 | 四个环写入：model/material/presence/lod table |

- `rings_ms` 改为四段之和；`cpu_total_ms` 仍只加一次 `rings_ms`，不重复加子段。
- 四段的起止都落在现有的 `lap()` 边界上：`lap()` 取"距上次重置"的耗时并重置，所以连续三次中间收口加一次 `rings_done` 的和等于原 `rings_ms`（允许 f32 舍入）。
- 不给四个子段各建一套 GPU timer；本段只拆 CPU ring 段。GPU 侧继续用现有 `gpu_rt_sections` 与 `gpu_gi_ms`。

### R4 perf 只加读数，不加分位块

- `FrameSample`（`ash_renderer/src/render/stats/perf.rs:77-117`）增加四个 `f32` 字段，`rings_ms` 保留为四段之和。
- `stopwatch` 增加三个中间收口方法（如 `rings_shadow_done` / `rings_cluster_done` / `rings_prepare_gi_done`），`rings_done` 负责写 `rings_tables_ms` 与总和。
- `perf_stats.sections_mean` 增加四个均值键；`perf_samples` 每个样本增加四个键。
- 不新增 `percentiles` 子块；p50 由 `perf_samples` 现算，避免每加一个字段就多一组分位结构。

### R5 测试脚本显式开关 debug，并收紧 rays 断言

`tools/ray_tracing_test.py` 是 9.4 判定线的驱动，改它等于改 9 段取证口径，所以同一次提交里要同步 9.4.7 的记录。具体改动：

- ① 开始处显式 `set {"enabled": true, "debug": true}`，再 `settle`；stats 断言 `debug.enabled is true`。
- ① 的 `rays > 0` 收紧为 `rays == width * height`：先用一次 `frame_dump` 拿到 `width/height`（当前基线 1600×900，对应 1,440,000），不再只验正数。
- ① 与 ② 的每次 `ray_tracing_set` 都带 `debug: true`，避免脚本跑到一半被默认关掉。
- ④ 先保留原有"enabled 开 vs 关"的逐字节基线，再加一组"debug 开 vs 关"的逐字节比较：同一机位、同一帧槽，稳定帧后各 dump 一次，两者应逐字节一致（调试图不参与 LDR 链）。施工实测 auto 眼适应跨状态会差 1 LSB（改前基线即如此），故取证时先 `exposure_set {"mode":"manual"}`，收尾恢复原模式；这是 10.1.3 的落地细化。
- ④ 在 debug 关掉后读 stats，断言 `debug.enabled is false` 且 `debug.rays == 0`；再关 enabled，断言顶层 `enabled:false`。
- ④ 在 enabled 开、debug 关的状态下专门调用一次 `ray_tracing_dump`，期待"debug 未开启"的拒绝；随后关 enabled 再期待一次拒绝，覆盖两个前置条件。
- 收尾恢复 `{"enabled": true, "debug": false}`，不把测试机留在调试图全开状态。

### R6 本段只归因，不承诺削减

主计划写"先把 4.4 ms 归因，再按读数决定削减（材质环增量、未变化环跳过）"。本段把"决定"留在 10.1.3 之后：

- 若读数显示单一子段占 `rings_ms` 的 60% 以上，且削减改动不超过 80 行、不改变渲染结果，可由评审决定在本段追加 10.1.4；否则另立新段，不在本段偷偷扩范围。
- 即使追加，也只能动 CPU 侧跳过/增量化，不碰 GPU 环消费与画面。

### 10.1.2 rings 四段打点

1. `FrameStopwatch` 加 `rings_shadow_ms`、`rings_cluster_ms`、`rings_prepare_gi_ms`、`rings_tables_ms`。
2. 在 `frame.rs` 的三个中间边界调用收口：`shadow.write_ubo` 后、`cluster.write_slot` 后、`write_frame_ubo` 后；第四段由 `rings_done` 收口。边界不要在条件分支里漏调，否则四段和会小于原 `rings_ms`。

## 3. 边界：本段不主张什么

- 不改光线求交的数学、TLAS/BLAS 构建、命中着色与调试图三个子视图的内容；调试图仍然不是画面，不进 LDR 链。
- 不改 `enabled` 的默认值，不把光线求交默认打开或默认关闭；只加 `debug`。
- 不做 rings 削减、不做材质环增量、不做未变化环跳过；这些是 10.1.3 之后的独立决定（R6）。
- 不碰 SCGI 采样与缓存（9.11）、不碰 10.2 SSAO、10.3 SSR、10.4 阴影减负、10.5 egui。
- 不改 BRP 方法名，不加新 BRP 方法；只加字段。若评审坚持"请求时临时打开"，那需要异步 BRP 契约，属于另立段，不在本段硬塞。
- 不加屏显计数器、不加 overlay、不把调试图显示到窗口；取证仍走 PPM 与 JSON。
- 不承诺"省 3 ms"一定转化为帧率提升；帧率受 vsync、CPU 提交、窗口合成影响，本段只保证默认不再录调试图，并如实报告实测。
- 不改测试分辨率与画质档位；若施工机窗口不是 1600×900，用 `frame_dump` 返回的宽高做断言，不把 1,440,000 写死成唯一合法值。

## 4. 判定线草案

### 4.1 调试图门控

- 新进程、未调用 `ray_tracing_set`：`ray_tracing_stats` 的 `debug.enabled == false`，`debug.rays == 0`，`debug.hits == 0`。
- 同一机位：先切 `exposure_set {"mode":"manual"}`（auto 眼适应会差 1 LSB），debug 开时 `frame_dump` 一次，debug 关时再 `frame_dump` 一次，两张 PPM 逐字节一致；enabled 开/关的原有逐字节基线仍成立；收尾恢复原曝光模式。
- debug 关时 `ray_tracing_dump` 拒绝，错误文案包含"debug"与开启方法；enabled 关时也拒绝，两个前置条件分别可复现。
- debug 开、等至少一帧后：`debug.enabled == true`，`debug.rays == width * height`（1600×900 时 1,440,000），`0 < debug.hits <= debug.rays`，`ray_tracing_dump` 成功并落 PPM。
- 再关 debug、等一帧：`debug.rays` 回到 0，`debug.enabled` 回到 false；进程重启后仍是 false。

### 4.2 rings 四段

- `perf_stats.sections_mean` 与 `perf_samples` 都能读到 `rings_shadow_ms`、`rings_cluster_ms`、`rings_prepare_gi_ms`、`rings_tables_ms`。
- 300 个样本中，四段均非负；`perf_samples` 的四个键与 `rings_ms` 一致（`rings_ms` 按定义由四段相加，允许 f32 舍入）；改后四段 p50 之和与改前 `rings_ms` p50（4.38–4.49 ms）相差 ≤5%。
- 给出四段的 p50 与占比表；能一句话回答"4.4 ms 主要花在哪一段"。
- CPU 侧 `rings_ms` 与 `cpu_total_ms` 不高于改前基线（同一噪声带内）；GPU 侧默认 `gpu_ray_tracing_rays_ms` 约 0。若总帧时间有变化，如实记录测法与读数，不写成必然收益。

### 4.3 构建与回归

- `ray_tracing_test.py` 更新后全过；`gi_test.py`、`gi_estimation_test.py`、`gi_gather_test.py` 全过。
- 测试日志零 VUID/VK-ERROR；clippy 按项目现役命令跑净；`git diff` 无新增依赖。
- 9.4.7 的 rays 记录口径已同步为"默认 0，取证时显式开 debug"，并链接到本段记录。

### 4.4 契约不倒退

- `ray_tracing_set` / `ray_tracing_stats` / `ray_tracing_dump` 方法名不变；旧客户端不带 `debug` 字段时不报错，按现状保留（新进程默认 false）；`enabled`/`view` 语义不变。
- `enabled` 的初始化仍按设备支持；`debug` 默认 false，且不写进任何持久化配置。
- `view` 仍只接受 0/1/2；非法 view 的拒绝行为不变。
