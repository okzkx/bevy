## §1 时机：官方 Extract 缺位，帧末直读补位

官方机制（参照）：bevy_render 的 Extract 家族在 RenderApp 里把"这帧要画什么"从主世界抽进渲染世界，渲染管线只认抄件、不回头查场景。渲染族禁用后 Extract 不存在，但"渲染侧要从 ECS 拿数"这件事本身不会消失——改由我们在主 World 里自己拿，即 Unity 里"每帧把渲染可见数据抄一份给管线"的那一步（SRP beginFrameRendering 前的筛选/拷贝）。

时机两钉（都对着真实源码）：

- **钉在 PostUpdate**：GlobalTransform 的传播链（`mark_dirty_trees → propagate_parent_transforms → sync_simple_transforms`）由 TransformPlugin 链在 PostUpdate 的 `TransformSystems::Propagate` set（bevy_transform/src/plugins.rs:37-47）。挂在 Update 里读 `GlobalTransform` 会差一帧；帧末直读拿到的才是本帧终值——这正是施工计划 §2 表"采集时机"一行与入口篇既定架构。
- **排传播链之后**：`(collect_scene, report_scene_collected).chain().after(TransformSystems::Propagate)`，先采后验，且都晚于传播。

两处 API 订正（实施时核实，计划/任务行文沿用了旧版名）：

- `TransformSystems::TransformPropagate` → 本 checkout（0.20.0-dev）该枚举唯一变体叫 `Propagate`（bevy_transform/src/plugins.rs:13）；
- `GlobalTransform::compute_matrix()` → 0.20-dev 里出矩阵的方法是 `to_matrix()`（global_transform.rs:114）。

与 GPU 半边的关系（§2 图）：**同帧 relay**——Update 变更 → PostUpdate 传播定稿+采集 → Last 提交（`draw_frame` 2026-09-22 自 Update 挪正，缘由与 checklist 见 §6），收集与消费同帧闭环，与官方 bevy 未开流水线的"帧末收集、同帧提交"同形。§2 图原跨帧蓝折线待按同帧形状重制（3.2 开工首图），行文以施工计划 §2 表为准。

## §2 快照形态：只带拓扑，不带内容

`CollectedScene` 是每帧重建的资源，`CollectedPrimitive` 一行四样：

| 字段 | 是什么 | 消费方 |
|---|---|---|
| `entity` | primitive 实体 | 3.4 DrawList 排序/去重、排查定位 |
| `mesh` / `material` | 两个 Handle（柄） | 3.2 上传 pending、3.3 贴图槽位——**从柄去 `Assets` 容器取内容** |
| `model` | `GlobalTransform::to_matrix()` 终值矩阵 | 3.4 push constant 直用 |

**取舍：快照只带拓扑（柄 + 矩阵），不带顶点/贴图内容。** 理由：禁渲染后主世界 `Assets` 数据常驻（施工计划 §6.9），内容读柄即得；快照行窄（两柄一矩阵），每帧 clear + refill 的重建成本在 6 行规模上可忽略，不用先付"增量/脏标记"的复杂度（那是步骤 4 的活，§4 不做清单）。这跟官方 Extract 只抽 Handle + 变换、数据留容器是同构的。

## §3 容忍与核验（两 Tier 落点）

- **空帧容忍（正常态，不是失败）**：primitive 未展开（前几帧）或 `Assets::get` 为 `None`（资产未到货）都静默等下一帧——异步加载本就逐帧推进，warn/fail 都是错的。到货告警归 3.1.2 `report_scene_arrival`，采集侧不重复。
- **10s 未凑齐 → Tier① warn 一次**：primitive 已在场但三样凑不齐、或传播契约不过，warn 一次点根因方向（资产加载或 3.1.1/3.1.2 缝接线），本系统不修，之后不再打扰，帧循环照常。
- **核验内容（报一次即歇）**：实体数、每 primitive 顶点/索引数、材质容器数、贴图槽与去重数、传播契约（逐实体 `GlobalTransform == 父 GlobalTransform × 本地 Transform`，无父链则 == 本地）。
- **传播契约的诚实边界**：FlightHelmet 六节点扁平且全恒等（glTF nodes 无任何 translation/rotation/scale），种子值与传播值数值重合——本次核验守的是"读在传播之后 + 数据合法"（相机那种根实体种子即终值的对称命题，见 3.1.3 §2）；非恒等父链的逐帧正确性，3.4 拿真实矩阵绘制时由画面判定。
- **贴图槽 24 / 去重 15 的账**：6 材质 × 4 槽（base_color / metallic_roughness / occlusion / normal_map）= 24 槽；文件侧 15 张 = 5 材质 × 3 类图（BaseColor/Normal/OcclusionRoughMetal），Hose 无专属图——glTF 里 metallicRoughness 与 occlusion 指向同一 ORM 图，loader 按图片源去重后同柄，去重恰为 15，与 3.1.2 容器 Image 17（内置 2 + 文件 15）互证。

## §6 结构订正：draw_frame 自 Update 挪到 Last（2026-09-22，3.1.4 收官讨论触发）

本篇收官讨论中用户质疑"`draw` 在帧首（Update）、collect 在帧末（PostUpdate）"不是现代引擎形状——**质疑成立**：

- **现代引擎的形状**：帧末收集、同帧提交。官方 bevy 未开流水线：主 World 一帧跑完（PostUpdate 传播定稿）→ 同一 runner 迭代里 Extract → Prepare → Render 提交；Unity：LateUpdate 全部结束后才进渲染阶段；UE：帧末快照交 render thread，滞后一帧是**双线程流水线**，滞后买 CPU/CPU 并行。
- **原钉位的来历**：步骤 2 埋 `draw_frame` 时宿主壳里没有任何场景数据，清屏循环挂哪个槽都一样，随手钉了 Update；3.1.4 为守"编排不动"契约把采集放 PostUpdate，形成"N 帧末采、N+1 帧初画"。单线程宿主里这个跨帧滞后**买不到任何并行（伪流水线纯支出）**——官方 bevy 只有开了 PipelinedRendering（渲染线程真实存在）才赚回这一帧。
- **改动**：`host.rs` 的 `draw_frame` Update → Last，显式 `.before(OnAppExitSystems)` 钉退出帧次序（本帧照常画完，teardown 才反序拆除）；`WindowResized` 语义不受影响——消息缓冲在 `First` 换（bevy_app/src/sub_app.rs），winit 回调写入的消息本帧 Update/Last 都可读。
- **不动的部分**：快照的三条价值（提交收口在 draw_frame 一处 / 合批批窗口 / 变与不变分流）都不依赖跨帧，PostUpdate 采集 → Last 提交同帧同样成立；步骤 2 承诺的"编排住 host.rs + 录制段生长 + 函数名不动"原样兑现。
- **同步面**：施工计划 §2（采集时机/帧循环两行 + 图注标旧形状存档）、《2-宿主壳搭建记录》编排表与接口承诺 §6.1、本篇 §1 relay 段落。
