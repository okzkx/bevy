# 施工计划：持续监控与性能修复拆解（7.5）

> **一句话说明**：本计划把"默认场景 FPS 持续走低"的需求拆成四步——先装持续监控仪表（egui 面板 + BRP 采样通道），再无人值守持续监控取证，然后定位修复性能缺陷；本计划不主张渲染画质与机制特性，修复范围以监控证据钉明，超出小修独立立账转 7.6。

## 0. 现状核实（2026-10-21 立案期）

- **fps 快照已有**（属实，`ash_renderer/src/overlay/windows/debug_window.rs:68`）：`FpsMeter` 累计 0.5s 出一次平均快照，调试窗口显示一行 `fps xx (xx ms)`；无历史、无长窗统计，抓不到恶化形态。
- **显存读数已有但口径为"渲染器内部账"**（属实）：`MeshPool::usage()`（顶点/索引 used/capacity）+ `ImageCache::resident_bytes()/graveyard_len()`；无进程内存、无系统内存、无驱动侧显存预算。
- **BRP 采集通道已有**（属实，`ash_renderer/src/remote/perf.rs`）：`perf_stats`（分位数 + sections_mean + scale + memory）/`perf_samples`（原始样本导出，环形窗口 2048 帧）——缺进程/系统内存与驱动显存字段。
- **显存预算 API 属实**：ash 0.38 已有 `ash::ext::memory_budget::NAME` 与 `vk::PhysicalDeviceMemoryBudgetPropertiesEXT`（registry src 核实），设备创建已在 `vk::DeviceCreateInfo::push_next` 惯例上（`vulkan/context.rs:400`），加挂扩展 + properties2 查询即可。
- **进程内存 API 属实**：`windows` crate 0.62.2 已在 Cargo.lock（bevy 传递依赖）；`GetProcessMemoryInfo`（Win32_System_ProcessStatus）+ `GlobalMemoryStatusEx`（Win32_System_SystemInformation）按最小 feature 面声明依赖。
- **既有观察项**：F26 = zero_day 帧时间空洞 ~43ms 未计时区（挂账）；本段监控面板顺带给 Sponza 场景的恶化取证提供长窗形态，与 F26 计时器缺口不混同。

## 1. 任务拆解

### 7.5.1 监控面板（egui 持续 FPS/内存/显存）

- FPS 持续历史：环形历史（新 `MonitorHistory` 资源或扩 FpsMeter），快照间隔逐样本入环；面板画走势曲线（egui painter 折线）+ 长窗统计（min/p50/p95/max，窗口 ≥10 分钟可调）。
- 内存读数：进程工作集（GetProcessMemoryInfo）+ 系统总量/可用（GlobalMemoryStatusEx）。
- 显存读数：`VK_EXT_memory_budget` 各堆 budget/usage（设备创建加挂扩展，查询落独立小模块；扩展缺席时降级为隐藏读数不报错）+ 既有池/贴图字节读数并列（内部账 vs 驱动账两口径）。
- 面板落位：新独立监控窗口（照 `windows/` 家族样式，debug_hub 加开关），不塞调试窗口；刷新与 fps 快照同节奏。

### 7.5.2 BRP 采样通道

- `perf_stats` 增补或新方法（倾向新 `monitor_stats`，职责分离）：进程工作集/系统内存/显存 budget/usage/fps 当前值。
- `tools/brp.py` 增子命令；新增 `tools/monitor.py` 无人值守采样脚本（定间隔轮询落 CSV/JSONL，供取证与修复前后对照）。

### 7.5.3 持续监控取证（默认 Sponza 场景）

- 无人值守跑默认场景（不带 --scene，中庭机位静止），monitor.py 连续采样 ≥30 分钟。
- 采集物：FPS 曲线、进程内存曲线、显存 budget/usage 曲线、账面读数（ledger rows/object slots/贴图驻留字节/停尸房/票据号）——恶化形态必须与某项账面单调增长对上，形成证据链。

### 7.5.4 性能缺陷定位与修复

- 按 7.5.3 证据链定位根因；修复 → 复测（同配方 ≥30 分钟曲线对照，恶化消失且基线不劣化）。
- 既有判定线零回退：九脚本回归抽测（hiz/lod/stream/fine 至少各一）+ 库测试全绿。
- 修复超出小修范围（结构性改动/牵动机理面）时：本任务只收口证据链与最小止血，正式修复独立立账转 7.6。

## 2. 判定线草案

1. **面板读数口径一致**：FPS 历史统计与既有 FpsMeter 快照同源同值；内存/显存读数与任务管理器/驱动面板交叉核对同量级（各自记一组对照数）。
2. **采样通道无人值守**：monitor.py 连续采样 ≥30 分钟零中断，样本落盘完整（时间戳连续、无缺帧空洞）。
3. **恶化证据链闭合**：FPS 恶化形态与至少一项账面单调增长逐时刻对应，根因有代码级解释（哪条路径每帧/每事件漏收）。
4. **修复复测**：同配方长跑恶化消失，FPS 基线不劣化；九脚本抽测零回退、库测试全绿。
5. **工程闸门**：零 VUID、exit 0、clippy 全净。

## 3. 待决项

- **显存用量口径**：`heapUsage` 是堆系统级用量（含其他进程）语义，进程自身显存无法从本扩展单独拆出——面板以"budget/usage + 差值趋势"呈现，口径行文钉明，不冒充进程显存（施工时确认语义并落注释）。
- **windows crate feature 面**：按最小集声明（Win32_Foundation + Win32_System_ProcessStatus + Win32_System_SystemInformation），不引全家桶。
- **修复范围**：以 7.5.3 证据钉明；结构性修复不硬塞本段（转 7.6 先例：4.5/4.6 缺陷修复段）。

## 4. 测试方案

- 面板：PrintWindow 截图 + 当前会话模型读图（画面功能视觉验证规则），读数行与 BRP 同帧值对照。
- 采样通道：monitor.py 实跑 30 分钟级，样本完整性脚本自检。
- 修复：修复前后同配方曲线对照 + 九脚本抽测 + 库测试 + clippy；取证截图/数据进 `.temp/7.5/`。
