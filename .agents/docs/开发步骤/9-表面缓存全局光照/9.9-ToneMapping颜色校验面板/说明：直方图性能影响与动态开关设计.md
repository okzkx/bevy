# 说明：直方图性能影响与动态开关设计

> 2026-11-26 立案期补充（纯文档，9.9 未开工，无代码改动）。回答三件事：直方图让渲染流程多了什么、这些开销从哪来、有多大；并定下「开关动态启用」的语义与验收口径。施工拆解仍以[施工计划：9.9 ToneMapping 颜色校验面板](施工计划：ToneMapping颜色校验面板（9.9 追加）.md)为准——**计划定做什么，本文定它的成本边界**。
>
> 除注明「实测」外，所有毫秒数与字节数都是 **RTX 2060 @ 1600×900** 的估算（依据一栏写清算式）；开工后按 §5 实测并回填 `9.9.K-判定线与计量.md`，估算被推翻就改本文。

## 0. 结论先行

| 状态 | GPU 增量 | CPU 增量 | 同步停顿 | 画面 |
|---|---|---|---|---|
| **关闭（默认）** | 0：不录 dispatch、不回读、不重建描述符集 | 0 | 无 | 与立案基线逐位一致 |
| 开 8 Hz（本文推荐形态） | 峰值帧 +0.05～0.2 ms；秒均摊 ≈0.4～1.6 ms | 0.2～0.5 ms/样本 | 无（帧槽异步） | 不变（只读） |
| 开 30 Hz / 逐帧 | 每帧 +0.05～0.2 ms（60 fps 的 0.3～1.2%） | 同上 | 无 | 不变 |
| 开 8 Hz（朴素原子 + 同步回读，反面形态） | 峰值帧 +0.5～2 ms | 同上 | 每 8 Hz 一次 0～16 ms 的尖峰 | 不变，但会周期性卡顿 |

结论：**这个功能的价值不是「免费」，而是「把 11.5 MB 的 HDR 全帧回读压成 28.8 KB 的计数表」**。全帧回读（三域 ≈30 MB/次、8 Hz 即 240 MB/s 且必然同步）不可行；直方图把"看颜色"从"搬像素"变成"读计数"，代价压在 GPU 采样与原子这一侧，并且可以做到默认零成本。

## 1. 渲染流程改变了什么

### 1.1 改前 / 改后

```text
改前（现状，post_chain.rs:53-97）
  exposure → bloom → tonemap(写 LDR) ⇢ color_to_sampled(post_chain.rs:92) → SMAA edge/blend → neighborhood → UI

改后（enabled = true；新增段在 color_to_sampled 之后、SMAA edge 之前）
  exposure → bloom → tonemap(写 LDR) ⇢ color_to_sampled
      → [color_scope compute：读 hdr / bloom / LDR / 曝光状态 → bins SSBO(28.8 KB)]
      → [copy bins → staging[slot]]            ← 与帧同一次提交，不另起提交
      → SMAA edge/blend → neighborhood → UI
  ……2 帧后该帧槽 fence 等完 → map staging → CPU 解析 → egui/BRP 快照

改后（enabled = false，默认）
  exposure → bloom → tonemap(写 LDR) ⇢ color_to_sampled → SMAA edge/blend → neighborhood → UI
  （与改前逐命令相同；面板/BRP 只读最后一份陈旧快照）
```

录制点选在这里的理由（计划 §1 已定）：此时 LDR 已是 `SHADER_READ_ONLY`（`post_chain.rs:92` 刚转），hdr 与 bloom 链也早就是只读，**scope 全是采样式读取，不需要为它新增任何图像屏障**；反过来若放在 tonemap 之前，C 域（校色输出）根本不存在。

### 1.2 新增的资源与描述符

| 资源 | 规格 | 说明 |
|---|---|---|
| bins SSBO ×2 槽 | 7 199 × `u32` ≈ 28.8 KB/槽 | 每帧槽一份：compute 写本槽、CPU 读 2 帧前那份，互不相撞 |
| staging ×2 槽 | 32 KB/槽（对齐后的 28.8 KB） | `HOST_VISIBLE`，`readback_buffer` 的现成形态 |
| 描述符集 ×2 槽 | COMPUTE 阶段，7 个绑定 | hdr 视图 + blit_sampler + bloom 视图 + bloom_sampler + Bloom 参数 UBO + 曝光状态 UBO + bins SSBO |
| 常驻增量 | ≈ 122 KB | 无新增纹理、无新增附件、无新渲染目标 |

描述符集与 present 的四个集不能复用：present 全在 `FRAGMENT` 阶段（计划 §0.0 第 29 行），compute 绑定要单建一套；只在**绑定视图变化**时重建（照 `exposure.rs:372` 的 `bound_hdr` 做法），不是每帧重建。

### 1.3 同步与顺序

- 读侧：hdr/bloom/LDR 三个视图在录制点都已是只读布局，无进场屏障。
- 写侧：bins 由 compute 写、紧接着 transfer 读拷贝——需要一条 **compute → transfer 的 buffer 屏障**（与 `readback.rs:28-34` 同型：`ALL_COMMANDS/MEMORY_WRITE → TRANSFER/TRANSFER_READ`），这是 scope 引入的**唯一新增同步**。
- 槽间：bins 与 staging 都按帧槽分 2 份，2 帧在飞（`context.rs:104`），写入与回读永远在同一槽、相隔 2 帧，天然无竞争。
- 与 present 的关系：tonemap 读曝光状态、scope 也读同一份状态 UBO；scope 在 tonemap 之后，读到的是本帧最终值。

### 1.4 回读路径：两种形态，成本差一个数量级

| | A：`readback_buffer`（计划 9.9.3 原案） | B：帧槽异步（本文推荐） |
|---|---|---|
| 做法 | 8 Hz 触发时调 `readback_buffer`：新建 cb → 拷贝 → `finish_and_read` | 帧内把 bins 拷进 staging[slot]，随帧提交；2 帧后该槽 fence 已等完（渲染循环本来就要等），直接 map |
| 提交次数 | 每次回读 +1 次提交 | 0（搭帧的便车） |
| 同步 | 等 fence，独占一次提交——`readback.rs:1-3` 明写"不在帧循环内调用，每次调用独占一次提交并阻塞到 fence" | 0 额外等待，读数陈旧 ≤2 帧 |
| 风险 | 与两帧在飞交错时每次触发插一个停顿，表现为 8 Hz 周期性尖峰 | 无；代价是快照最多晚 2 帧 |
| 结论 | 只作退路（设备/驱动对 staged copy 有意外时） | 首选；plumbing 与 `readback_ldr`（`smaa.rs:462`）同源 |

> 计划 §3 闸门④原本写的是"`readback_buffer` 在现有帧槽 fence 体系下安全（一次性提交，不与后台帧交叠）"——它确实安全，但**安全不等于不卡**。B 形态把同一份 28.8 KB 从"额外提交"降为"帧内 copy"，回读成本从"每次一个同步点"变成"一次 memcpy + 一次 map"。

### 1.5 不在流程里的部分（避免误解）

- 公共片段抽取（`shaders/common/tonemap_shared.wgsl`）：`// #import` 是编译期展开，**运行时零成本**、流程不变；风险只在 ABI，靠判定线①逐像素一致兜底。
- egui 侧：只在面板可见时画 4 张图（8 Hz）；CbCr 64×64 以 `ColorImage` 上传一次/样本（≈16 KB），不占 GPU 管线。
- BRP：只读 CPU 快照，不触碰 GPU。

## 2. 成本从哪来（机制分解）

一句话回答「是不是只多一个统计 compute 和 staging 回读」：**结构上确实只是「一个 compute pass + 一次 copy + 一次 staging 读取」，但成本不在「多一个 pass」这个结构上，而在 pass 里面**——空 dispatch 只要 5～20 µs，填满它却要读 28.8 MB 纹理、打数百万次原子；28.8 KB 的 copy 不到 5 µs，真正贵的是「什么时候等谁」。可按层拆开看：

| 层 | 具体内容 | 量级 |
|---|---|---|
| 结构固定开销 | 1 次 dispatch + 1 条 compute→transfer 屏障 + 1 次 28.8 KB copy | ≈0.02～0.03 ms/帧（16.7 ms 的 0.2%） |
| 可变开销（pass 内） | 36 万样本 × 4 次线性取样 ≈28.8 MB 读；原子计数 | 0.08～0.2 ms/帧（其中带宽下限 0.086 ms） |
| 回读形态 | 帧槽异步：map + memcpy；`readback_buffer` 同步：每次等 fence | 异步 ≈20 µs；同步每 8 Hz 一次 0～16 ms 尖峰 |
| CPU 解析 | 7 199 个 `u32` → 统计量 | 0.05～0.2 ms/次（8 Hz 下的 1%） |
| 常驻内存 | bins 28.8 KB×2 + staging 32 KB×2 + 每槽一份描述符集 | ≈122 KB（不随开关变化） |

更一般的成本模型（换到别的 pass 也成立）见[直方图成本模型：采样账与原子账](直方图成本模型：采样账与原子账.md)。

结论：**开关关掉省掉的是整张表**（结构 + 可变 + 回读全为 0）；开着时由采样与原子决定均值、由回读形态决定尖峰，staging 本身几乎不花钱。

### 2.1 采样带宽

**80 B 是这么来的**（一次双线性取样最多摸 4 个 texel）：

| 取样 | 格式 | 每 texel | 双线性 4 texel | 说明 |
|---|---|---|---|---|
| A：hdr luma | RGBA16F | 8 B | 32 B | `HDR_FORMAT`，与 B 同 uv |
| B：bloom luma | RGBA16F | 8 B | 32 B | bloom 链也是 HDR 格式 |
| C：LDR | RGBA8 | 4 B | 16 B | `LDR_FORMAT`（`smaa.rs:127`） |
| 合计 | | | **80 B/样本** | A/B 共用 hdr 取样时可降到 64 B |

- 36 万样本 × 80 B = **28.8 MB/帧**（最坏取数口径）；按 336 GB/s 记账 ≈ **0.086 ms**。
- 但这 28.8 MB 不是 DRAM 流量：相邻样本共享 cache line（hdr 8 B/texel，64 B 行 = 8 texel = 4 个样本），真正从显存读的是**唯一字节**——hdr 11.5 MB + bloom(800×450) 2.9 MB + LDR 5.8 MB ≈ **20 MB → ≈0.06 ms**。取数请求量大于显存流量，差额被 L1/L2 吸收。
- 所以采样这一层是 **0.05～0.09 ms**：量小、线性、可预测，是成本的地板，不是风险点；stride 4 直接减半。

### 2.2 原子竞争（最大变量，也是唯二需要设计取舍的地方）

**原子为什么贵**：`atomicAdd(&bins[h], 1)` 是对显存里同一个 4 字节的读-改-写（RMW）。不同地址的原子可以在 L2 的不同分片并行；**同一地址必须排队**，一条 4 B 地址能串行到多少就是吞吐上限。GPU 上原子不经过 SM 的寄存器缓存，每次都要走 L2，延迟几十到几百 ns，靠并发掩盖。

- 原子次数：计划 §4 口径"约 7 次/样本"（≈2.5 M/帧）；按上限实算——A/B 各 luma+RGB 4 次、C luma+parade 4 次、CbCr 2 次 ≈ **14 次/样本（5 M/帧）**。估算按上限做，实测再回填。
- 分场景算账（TU106：30 SM、约 12 个 L2 分片、1.4 GHz）：

| 场景 | 原子分布 | 估算 |
|---|---|---|
| 主场景、256 箱摊开 | 每箱约 2 万次，分散在多个分片 | **≈0.3 ms/帧** |
| 一般画面（亮部集中） | 少数热门箱吃掉大头 | **0.4～2 ms/帧** |
| 纯色/天空测试图 | 几乎全部落进同一个箱 = 单地址串行 | **≈10～15 ms/帧**（5 M × 2～3 ns） |

- 这就是「朴素全局原子不可取」的定量理由：它不是一个稳定常数，而是**随画面集中度退化**——最坏用例正好是校色时最该看的纯色/天空。
- 合并方案（推荐，且不超预算）：
  - A/B/C 的 luma+RGB（12 个 256 箱，共 12 KB）放 **tile 内共享内存**：每 tile 32×32 像素，1600×900 ≈ 1 450 tile，每 tile 只向全局合并 12 个箱 → 全局原子 ≈ **1.7 万次**（相对 5 M 降了两个数量级），共享内计数虽仍是 5 M 次，但只在本组、无全局争用。
  - CbCr 64×64（4 096 箱）**直接走全局原子**：每样本 2 次 ≈ 72 万次，但箱多、摊得开，争用小；硬塞共享内存要 16 KB，会把每 tile 的共享占用推到 28 KB 并超出默认 16 KB，没必要。
  - 共享占用 12 KB/tile，落在 Vulkan 最低保证的 16 KB 内，无需 opt-in 更大共享配置。
- 为什么这样能降一两个数量级：原子总数没变（5 M 次），但**地址空间从「全网共享的 1 KB」换成「每个 SM 私有的 12 KB」**——共享内存原子在 SM 内完成，不占 L2 带宽、不跨 SM 争用；全局那层只剩每 tile 12 次合并写（1.7 万次），从瓶颈变成噪声。共享内存按 32 bank 并行，直方图相邻箱会撞 bank，所以箱数取 256（=8 箱/bank）时随机分布的冲突可控。
- 该方案预估原子侧 **0.03～0.12 ms/帧**（共享 5 M 次 + 全局 74 万次），叠加 2.1 的采样 ≈ **0.08～0.2 ms/帧**——这就是 §0 表里"推荐形态"的来源。

### 2.3 dispatch 与屏障

- 800×450 线程 / 8×8 = 5 625 组；一次 dispatch + 一条 buffer 屏障，**5～20 µs** 量级，且与后处理同队列顺序执行，不引入新提交。
- 常数开销不是问题；问题只在 2.2 的原子与 2.4 的同步。

### 2.4 回读与同步

- 28.8 KB 的 copy：GPU 侧 <5 µs，可忽略；CPU 解析 7 199 个 `u32` ≈ 0.05～0.2 ms。
- 真正贵的是**同步**：A 形态每 8 Hz 等一次 fence，最坏等于剩余帧时（60 fps 下 0～16 ms）；它抬高的是 p99 尖峰而不是均值，帧统计页上会表现为"每 125 ms 抖一下"。
- B 形态：0 额外同步，只有 map + memcpy（≈20 µs）。

### 2.5 UI 与 BRP

- egui 4 张图 + 统计表 @8 Hz：0.1～0.3 ms CPU；面板收起后为 0（不重绘、不采样）。
- BRP `color_scope_get` 只读 CPU 快照，无 GPU 成本；CSV dump 是 CPU 侧的字符串拼接，按需触发。

## 3. 影响多大：三档账

| 形态 | 每帧 GPU | 每秒 GPU | CPU | 尖峰 |
|---|---|---|---|---|
| 关 | 0 | 0 | 0 | 无 |
| 开 8 Hz，tile 合并 + 槽异步 | +0.08～0.2 ms | 0.6～1.6 ms | 0.2～0.5 ms/次 | 无 |
| 开 8 Hz，朴素原子 + 同步回读 | +0.5～2 ms | 4～16 ms | 同上 | 每 125 ms 一次 0～16 ms |
| 开 30 Hz，tile 合并 + 槽异步 | +0.08～0.2 ms | 2.4～6 ms | 8 Hz×3.75 | 无 |

- 对比基准：9.9 计划 §4 给的上限是 **≤0.3 ms @1600×900**；本表的推荐形态留了 1.5 倍余量。
- 降级阶梯沿用计划 §4：stride 4 →（已默认）共享内存 → 4 Hz。补一条：**stride 4 时 256 箱只有 9 万样本**，p1/p99 会抖，面板必须显示样本数并在 <5 万时标"统计不足"，不要拿它下结论。
- 帧率影响换算：60 fps 帧预算 16.7 ms，+0.2 ms ≈ 1.2%；若原本就贴着 60 fps 上限，这一档可能让 p99 掉 1～2 帧——所以默认关、按需开。

## 4. 动态开关设计

### 4.1 开关的语义

```rust
pub struct ColorScopeSettings {
    pub enabled: bool,   // 默认 false：不录 dispatch、不回读、不重建描述符集
    pub hz: u32,         // 默认 8；1..=30
    pub stride: u32,     // 默认 2（每轴隔 1 取 1）；可选 4
    pub domains: u32,    // 位掩码 A=1 B=2 C=4，默认 7；关 C 省 1/3 采样
    pub one_shot: bool,  // true：下一帧采一次后自动回 false（BRP/截图取证）
}
```

- **默认关**。这是诊断工具，不是画面功能——默认开等于让每次截图、每轮压测都背一笔 +0.1～0.3 ms 的隐性税，还会污染 9.8 的帧时间基线。
- **面板展开不自动开启**：用户可能只是想调曝光滑杆。颜色页顶部给一行显式控件；另提供"打开面板即启用"偏好（默认关），供自己用。
- **单帧模式**：`one_shot` 只采 1 帧（≈0 摊薄成本），给 BRP 脚本与读图留档用；采完自动关，面板显示"最后一帧 N 帧前"。
- **域掩码**：只关心曝光时 `domains=3`（A+B），C 域连同 CbCr 一起不采，成本降 1/3。

### 4.2 接口

- egui（颜色页顶部一行）：
  - `[ ] 启用直方图` 复选框；`[单帧采样]` 按钮；频率 `8/15/30 Hz` 与步长 `2/4` 下拉；右侧状态：`帧龄 N`、`stale`、跳过原因（`mode!=0` / tonemap 关 / 窗口最小化）。
  - 关闭时整页只剩状态行 + 最后一帧快照（灰显），不重绘 4 张图。
- BRP：
  - `color_scope_set { enabled?, hz?, stride?, domains?, one_shot? }` → 回显 `applied`/`current`，越界/非有限值拒绝。
  - `color_scope_get` → 快照（头区、三域统计、bins、`frame_age`/`stale`）+ 当前 `ColorScopeSettings`，与面板同源。
  - 面板与 BRP 写同一份设置，读回一致（判定线沿袭计划第 7 条的口径）。

### 4.3 关闭路径必须保证什么

1. **零命令**：`record_to_ldr` 里不写任何 scope 命令、不更新描述符集、不 map、不提交；命令序列与立案基线同序（判定线①）。
2. **快照保留**：关闭后保留最后一份快照并标 `stale`，`frame_age` 随帧增长——判定线②用它证明"真的停了"。
3. **不销毁资源**：开/关只切录制与回读，bins/staging 常驻（≈122 KB）；100 次切换零 VUID、零泄漏、无重分配抖动。
4. **不自动翻转**：`mode!=0` 或 tonemap 关时跳过录制（C 域不存在），但 `enabled` 保持用户设置；面板显示跳过原因，不得偷偷把开关关掉。
5. **帧边界生效**：设置写入后从下一帧录制开始生效；同一帧内不出现"半开"（描述符集与录制判定读同一快照）。

### 4.4 与既有"面板展开才采样"的关系

计划 §0.4 原来的节流是"面板展开 8 Hz、收起即停、BRP 按需"。本文把它拆成**正交的两层**：

- 第一层 `enabled`：总闸，决定 GPU 有没有这段工作；
- 第二层 `hz`/`one_shot`：采样节流，决定开了以后多久采一次。

面板展开只是"可能想看的信号"，不再是唯一的开关——这样 BRP 远程开、脚本单帧取证、面板关了但保持采样（录一段颜色漂移）都成立，且**所有路径共用一套成本口径**。

## 5. 怎么测（开工后回填 9.9.K）

### 5.1 A/B 差分（不改代码）

- 用 `perf_stats` / `perf_samples`（`remote/census/perf.rs:59`、`:129`）：同场景、同相机、锁 300 帧，取 `gpu_present_ms`、`gpu_total_ms`、`frame_wall_ms` 的 p50/p95/p99，做"关 / 8 Hz / 30 Hz / 单帧"四组差值。
- 注意 scope 落在 `PostUi` 区间内（`perf.rs:65-66` 的段界：后处理 + UI），所以 `gpu_present_ms` 与 `gpu_total_ms` 都含它——**只能用差值，不能读绝对值当结论**。
- 场景三组：主场景、程序化天空（分布集中，原子最坏）、纯色测试图（单 bin 极端）。

### 5.2 直接量（可选，≈20 行）

- `QUERIES_PER_FRAME` 12 → 14（`perf.rs:43`），`TimestampPoint` 追加 `ScopeBegin`/`ScopeEnd`（现表在 `perf.rs:48-73`，T11 之后顺延），在 dispatch 前后各写一次；`FrameSample` 加 `gpu_color_scope_ms` 并在 `perf_stats` 暴露。
- 收益：直接拿单段 GPU 时间，不再靠差分；`perf_stats` 里也能看出"关掉后这一段消失"。

### 5.3 判据

- 关：与立案基线 p50 差 ≤1%（噪声级），且 `frame_age` 不增长。
- 开 8 Hz：p95 增量 ≤0.3 ms，p99 不出现 >1 帧的尖峰（出现即说明回读退回了 A 形态）。
- 开 30 Hz：每帧增量 ≤0.3 ms。
