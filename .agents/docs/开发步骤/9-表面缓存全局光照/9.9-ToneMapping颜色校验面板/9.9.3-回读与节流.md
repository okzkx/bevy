# 9.9.3 回读与节流

**状态：✅ 已完成并验证（2026-11-26）。** 面板与 BRP 读同一份 `ColorScopeSnapshot`；面板 8 Hz 节流、关闭零回读；单帧采样走录制侧消费。

## 为什么要节流

直方图本质上是一帧快照，人眼也不需要 60 Hz 的统计。每帧回读会强制 CPU 等 GPU、把 `vkQueueSubmit` 的并行度吃掉。所以设计成：录制可以按需/连续开，**回读只在面板展开且开启时以 125 ms（8 Hz）执行**，BRP 的 `force` 才立即读一次。

## 实现

`ash_renderer/src/render/passes/post/color_scope.rs`：

- `ColorScopeTargets::read_bins(&self, ctx: &Context, slot: usize) -> Result<ColorScopeSnapshot>`：`OneShotReadback::begin(ctx, COLOR_SCOPE_BINS_BYTES)` → `cmd_copy_buffer`（bins → staging，整块 28796 B）→ `finish_and_read`。one-shot 是单独 command buffer、单独 submit，队列序保证看到该槽最近一次完整帧。
- `ColorScopeSnapshot { header: [u32; 16], bins: Vec<u32>, frame_index: u64 }`：`from_bytes` 校验长度（28796）与 4 字节对齐，暴露 `magic_ok / extent / frame_index / exposure_state / luma(domain) / rgb(domain, ch) / counts(domain) / cbcr / axis_bin_ev(bin) / mean_log2(domain) / ratios(domain) / expected_b_mean()`。
- `ColorScopeReader`（Resource，`interval` 默认 125 ms）：`refresh(ctx, targets, slot, force)` 在 `!force` 且距上次读数不足 interval 时直接返回 `Ok(false)`；成功更新快照并清错误，失败记 `last_error` 并向上抛。节流状态在 reader 里，面板只管调用。
- 单帧采样：`ColorScopeSettings { enabled, once }`；`color_scope_draw` 判断 `enabled || once`，`once` 在**录制侧**被消费并清掉，否则会出现"单帧开关一直重复采样"。BRP `color_scope_set {"once":true}` 与面板按钮写同一个字段。

## 域基址的坑

`ColorScopeDomain::base()` 最初返回 `0 / 1029 / 2058`，而 shader 里 `BASE_A = HEADER_U32 = 16`。结果面板和 BRP 把 16 u32 的头区当成了 A 域直方图（曝光快照被当成 bin 计数），看起来"图全错但账平"。修法是 `base()` 返回 `COLOR_SCOPE_HEADER_U32 + match domain { A => 0, B => 1029, C => 2058 }`（A/B/C = 16 / 1045 / 2074），`cbcr()` 基址改成 `16 + 3 * 1029 = 3103`。

教训：shader 常量与 Rust 常量是两份声明，必须用单测钉死。新增 `domain_bases_are_after_header` 断言三域基址与 `16 + 3*1029 + 4096 == 7199`。

## 判定线⑤的口径修正

头里的 `avg_log2` 是**测光乘法前**的值，而 B 域已经乘过曝光 `scale`，直接比会固定偏 `log2(scale)`（实测偏 0.39 EV，正好是 `log2(0.7598)`）。所以新增 `expected_b_mean()` = `exposure_state[2] + log2(scale)`（scale 非正返回 None），面板与 `color_scope_check.py` 都按这个期望值比。这不是放宽标准，而是把"B 域定义里含曝光"这件事算进期望值。
