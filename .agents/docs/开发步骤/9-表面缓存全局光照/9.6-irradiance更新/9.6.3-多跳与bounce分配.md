# 9.6.3 多跳自查询与 bounce 分配（施工记录）

> 2026-11-24。依据[施工计划](施工计划：irradiance更新与多跳.md) §9.6.3 与 §0.4。
> 本记录写"实际做了什么"与"裁决结果"，计划文档只流转状态。

**一句话**：命中点按"级联/桶/cell"查自己所属的 patch，读**上一帧**那份辐照度、求值成 E(n)
后乘命中点 `albedo/π` 加进辐射亮度——多跳就这么形成了；cell 里没有 patch 且本 patch 是
rank 0 时往请求表追加一条，同帧末尾的小 dispatch 用与播种同一套 `CellAllocationMarks` 仲裁
补出 rank 1 的 patch。实测自查询命中 18344 / 落空 2996、请求 70 条/帧，patch 数 3320 →
13752、`failed` 仍为 0，多跳开/关让 8 条 patch 的辐照度总和从 62.87 变到 97.35。

## 裁决与偏差（相对计划）

1. **请求在同帧消费，不跨帧**：计划写"bounce 分配首版走下一帧的第二条小 dispatch"。改同帧
   是被 per-slot 资源逼出来的：请求表与计数器都按帧槽分（2 槽），上一帧写下的请求落在**另一个
   槽**的缓冲里，下一帧的管线绑的是本槽的集——跨帧读要另开共享缓冲与跨槽计数，代价远大于收益。
   同帧消费只需把 bounce_alloc 录在 estimation 之后（一道 compute→compute 屏障），新 patch
   下一帧起参与估计，语义与计划一致（只是"分配晚一帧"变成"估计晚一帧"）。
2. **两路共用一个分配入口的仲裁**：`bounce_alloc` 用与播种**完全相同的纪元标签**
   （`frame.x | 1`）做 `cell_marks` 仲裁，所以同帧同 cell 只会有一次分配；这也是把 `ring_append`
   提到公共片段的原因（避免两条路径各写一份水位逻辑）。
3. **新 patch 的种子留零**：`bounce_alloc` 不跑 `seed_irradiance`（那要帧 UBO 与 IBL 集，会再把
   集数抬上去）。因为新 patch 的 `update_count == 0`，下一帧的估计会整体替换种子，零种子不超过
   一帧。**但 rank = 1 不享受预热**（预热条件是 `update_count == 0 && rank == 0`，Unity 同款），
   所以 bounce patch 的收敛是每帧 1 样本的慢速收敛——它们本来就在屏幕外，属于设计取舍。
4. **只有 rank 0 能请求**：`can_allocate = frame.z != 0 && rank == 0`，所以 bounce 出来的
   rank 1 patch 不会再申请分配，这条路径不会自激。
5. **读数代理桶错位率**：命中点用的是命中重建的插值法线，播种用的是深度差分平面法线，
   光滑曲面上两者不同源（9.5 §0.5 的已知例外）。本段不修，改为把"自查询命中 / 落空"两路计数
   读出来（`counters[8]` / `counters[15]`）——落空率就是"桶错位 + 覆盖不足"的合并读数代理。
6. **淘汰分支的风险已评估**：`eviction.wgsl` 在 `frame.z != 0` 时把 rank 0 降为 rank 1 并刷新心跳
   （本轮不淘汰）。稳态推演：屏幕 patch 每帧被播种刷回 rank 0、心跳本来就新；bounce patch 进池
   即 rank 1，之后不再被刷新、4 秒后被正常淘汰。所以池不会无界增长——实测 6 秒内 3320 → 13752、
   水位 14711、`failed` 0，与"每帧约 30 个新 cell 存活 4 秒"的推演一致。真正的取舍（射线预算随
   活跃数涨）归 9.6.5。

## 待决项落定与顺延

- §5 待决落定：rank 0→1 的触发只由"bounce 分配置 1 + 淘汰侧降级"两处写；自查询读上一帧
  由帧奇偶决定（写 A 读 B），不依赖线程调度。
- 顺延：桶错位率的**修法**（补平面法线重建 / 按法线差回退相邻桶）仍待定——本段只给了读数；
  判定线①的正式 A/B 读图在 9.6.7；预算随活跃数降档在 9.6.5；视图 9～13 在 9.6.6。
- 已知边界：bounce patch 无预热、收敛慢；请求按"样本命中"去重而非按 cell 去重（同一 cell 的
  多条请求会浪费请求表槽位，占满 4096 时按超限丢弃并计数）；透明层不参与。
