# 9.6.2 直接光另两路：光源侧采样清单与自发光三角形（施工记录）

> 2026-11-24。依据[施工计划](施工计划：irradiance更新与多跳.md) §9.6.2 与 §0.2、§0.3。
> 本记录写"实际做了什么"与"裁决结果"，计划文档只流转状态。

**一句话**：把"点光怎么进 GI"和"自发光怎么进 GI"各自落成一条与 patch 数解耦的 GPU 侧通路——
128 条光源侧采样清单（灯位向外打射线，命中点留位置/法线/反照率/1-pdf）+ 每帧重建的自发光
三角形表（均匀抽三角形 + 解析面积权重，不建 CDF）；estimation 里两路各自独立归一化后再合流。
实测清单 124/128 命中、自发光体注入后三角形表 12 条，`emissive_intensity` 1→0 让 8 条 patch
的辐照度总和从 89.96 掉到 16.33、点光关掉让同一批从 128.97 掉到 93.51。

## 数学链（两路各自的归一化）

**光源侧清单**（照 Unity `SamplePunctualLightBounceRadiance` 的可读版，换算成本工程的衰减口径）：

```
隐面点被灯照亮的辐亮度 = albedo/π · color·intensity · smooth窗口(d², 1/range²)/d² · cos_bounce
patch 方向上的辐射亮度 = 上面 · cos_rec/d_rec² · 1/pdf        （面积测度 → 立体角）
```

- 全向点光的 `1/pdf = 4π · 灯数`，直接写进记录的 `hit_normal.w`；`estimation` 只再除样本条数。
- 衰减用 `brdf.wgsl` 的 `getSquareFalloffAttenuation`（与合成端的点光同一口径），而不是 Unity 的
  `SharpPunctualLightRangeWindow`——两边的强度单位不同，混用会整段偏亮。
- 重连接射线打 `d_rec - 0.02`：只判"有没有东西挡在中间"，不要求命中同一三角形（Unity 同理）。
- 归一化按**全部样本条数**除，不按"有效条数"除：死灯、背半球、被挡都是合法的零贡献样本，
  跳过后再除会系统性偏亮（Unity 按 valid 除，这是它的已知偏差，本工程不跟）。

**自发光面积采样**：

```
pdf(面积测度) = 1/(N · area_i)      → 1/pdf = N · area_i
辐射亮度权重 = N · area_i · |cos_tri| / d² · emissive_intensity
贡献 = 自发光辐亮度 · 上面的权重        （阴影射线被挡 = 0）
```

## 裁决与偏差（相对计划）

1. **自发光不建 CDF/前缀和**（计划 §9.6.2 写"面积 CDF + 前缀和两遍"）：naga 30 对 workgroup 聚合
   会发 Offset/ArrayStride（9.5 defrag 的教训），单线程串扫 32768 条是毫秒级；而面积加权采样
   可以完全绕开前缀和——**均匀抽三角形 + 解析面积权重**（上式），无 CDF、无第二遍 dispatch、
   无额外屏障。代价是三角形面积差异大时方差高；是否补 CDF、以及和 Unity 的
   `EmissiveTriangleAddition/Removal` 增量表相比的收敛差，进 9.6.5 的读数（判定线③的降档观测量）。
2. **不做 MIS**（计划 §5 待决"MIS 是否保留"）：迹线那一路**只累加方向光**，命中自发光面不贡献
   任何辐射亮度；自发光只从面积采样那一路进。两条通路因此在数学上互斥，不需要平衡启发式——
   `power_heuristic` 已备但首版不用，A/B 与"要不要在迹线侧也计自发光 + MIS"留 9.6.5。
3. **聚光仍按点光近似**：`LightRecord` 只有 pos/作用半径，没有锥角；清单按全向球面采样，
   聚光会照亮锥外（漏光）——记进 9.8 的局限清单，补字段的方案保留在 §5 待决。
4. **光源紧凑表每帧重写**（16 KiB 主机写）：cluster 的光源常驻表是持久分配的环形槽（槽号 ≠ 紧凑
   下标），而清单的 1/pdf 需要一个"0..N-1 连续"的活灯表；相比做增量与映射，每帧 16 KiB 的
   memcpy 更简单且读数确定。
5. **两路的归一化顺序**：一开始把点光那路加在"半球缩放 2π/N"之前，会被连带放大 2π——改为
   两路各自归一化后再合流（`total = 半球 · 2π/N + (点光 + 自发光)/N`），改法写在 shader 注释里。
6. **`spawn_shape` 加 `emissive` 参数**：判定线④ 需要一个可复现的自发光几何体，而默认场景材质
   全是非自发光（列表条数 0）。这是测试工具面的最小扩口，不进渲染管线语义。

## 现场证据（2026-11-24，debug 版，1080p 档）

| 脚本 | 检查 | 读数 |
|---|---|---|
| `.temp/gi96_light.py` | 无点光：清单条数 0 | `{lights:0,count:0,valid:0}` |
| | 注入点光后清单条数 | 128（`lights=1`） |
| | 清单里有命中样本 | **valid = 124 / 128** |
| | 点光关掉后 patch 辐照度下降 | 8 条 patch 总和 128.97 → 93.51（Δ = 35.46） |
| | 移除灯后清单归零 | count = 0 |
| `.temp/gi96_emissive.py` | 注入自发光体后三角形表 | **12 条** |
| | 未超容量 | 12 ≤ 32768 |
| | `emissive_intensity` 1→0 | 8 条 patch 总和 89.96 → 16.33（Δ = 73.63） |
| 两个脚本 | 零 VUID / VK-ERROR | 可疑行 0 |

代码验证线：`cargo test -p ash_renderer --lib` 115 项全过（含两条新管线的布局契约对账、
清单/重建的 push 与组数单测）、`cargo clippy -p ash_renderer` 零告警。

调试期踩到的一个坑（记下来省下一次）：`gi_stats` 读清单"有效条数"时把偏移写成 `i*64+48`
（那是 `info.x` = 灯号），于是不管命中多少都读成 0，一度误判"清单全线未命中"；正确偏移是
`+52`（`info.y`）。清单与自发光两路的**读数解析**要和 WGSL 的字段偏移逐字节对齐，
`LightSample` 的布局因此也写进了跨端片段的注释。

## 待决项落定与顺延

- §5 待决落定：清单长度默认 128（Unity 同款，容量上限 256）、自发光上限 32768、MIS 首版不做；
  `emissive_intensity` 默认 1；聚光锥角维持"按点光近似 + 记 9.8 局限"。
- 顺延：多跳自查询与 bounce 分配（9.6.3）、方差引导时域与常量天空 πL 自检（9.6.4）、
  预算降档与面积方差读数（9.6.5）、视图 9～13 与 egui 面板（9.6.6）、判定线脚本正式化（9.6.7）。
- 已知边界：透明/alpha 裁切自发光不参与；自发光增量增删（Unity 的 Addition/Removal）不做，
  每帧全量重建；清单的灯按全向点光采样，聚光锥外漏光。
