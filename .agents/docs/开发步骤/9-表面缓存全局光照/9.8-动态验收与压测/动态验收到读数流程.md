# 动态验收到读数流程

9.8 把「SCGI 能跑」变成「SCGI 可验收」，靠的不是单个测试，而是一条固定链路：
**BRP 驱动场景 → 固定条件 → 采样读数/抓帧 → 差分判定 → 证据与报告**。
这篇导读说明这条链路怎么跑、读数怎么读、哪些数不能拿来判定。

## 1. 三个脚本的分工

| 脚本 | 入口 | 职责 | 证据落点 |
| --- | --- | --- | --- |
| `tools/gi_acceptance.py` | `baseline` / `tour` / `dynamic` / `lighting` / `boundary` | 判定线①②的收敛、残影、边界与光照验收 | `.temp/gi98/<command>/<run-id>/` |
| `tools/gi_stress.py` | 全矩阵，`--only`/`--list` | 判定线③⑤的成组压测与 draw 恒定对照 | `.temp/gi98/stress/<stamp>/` |
| `tools/gi_limits.py` | 全流程 | 判定线④的九项局限与五组 A/B | `.temp/gi98/limits/<stamp>/` |

三者共享 `gi_acceptance.py` 里的 `Brp`、`Host`、`Session`、`diff_frames`、`build_field`。
`Host` 先探测端口：已有宿主则 attach（`--keep` 的基座），否则按 `ASH_BRP_PORT` 自启 release 可执行文件，并把 stdout/stderr 写进运行目录的 `host.log`。

## 2. 一次完整验收怎么跑

```bash
# 0. 先重建 release（脚本默认指向它）
cargo build --release -p ash_renderer

# 1. 基座：条件单 + 四机位基线 + 噪声底
PYTHONDONTWRITEBYTECODE=1 python tools/gi_acceptance.py baseline --keep

# 2. 静态游历（回位姿要等 30 s，见 §4）
PYTHONDONTWRITEBYTECODE=1 python tools/gi_acceptance.py tour

# 3. 动态几何、动态光照、Volume 边界
PYTHONDONTWRITEBYTECODE=1 python tools/gi_acceptance.py dynamic
PYTHONDONTWRITEBYTECODE=1 python tools/gi_acceptance.py lighting
PYTHONDONTWRITEBYTECODE=1 python tools/gi_acceptance.py boundary

# 4. 压测（每格独立进程，约 15–25 min）
PYTHONDONTWRITEBYTECODE=1 python tools/gi_stress.py

# 5. 局限与 A/B（等压测退出后再跑，避免争 GPU）
PYTHONDONTWRITEBYTECODE=1 python tools/gi_limits.py
```

端口约定：验收 15703、压测 15704、局限 15706。压测每格都新起进程，跑完即退出；
验收可用 `--keep` 保留宿主，后续子命令直接 attach，省去重复加载 Sponza。

## 3. 固定条件与读数通道

`baseline` 写的条件单包含：HEAD、分支、exe 的 sha256 与 mtime、GPU/驱动/显存、分辨率、
预算（16.7 ms 先写后测）、GI/SCGI 设置、sky/IBL 状态、曝光模式、太阳角度。

读数通道：

- `perf_stats`：wall/CPU/GPU 各分段以及 `gpu_gi_ms`、`gpu_ibl_capture_ms` 的 p50/p95/p99；
- `perf_samples{last:240}`：逐帧原始样本，用于确认窗口内没有尖峰；
- `gi_stats`：patches、rays、failed、pool 水位、cell 占用、显存；
- `scgi_stats`：只取 `coverage` 与 `alpha`；`l0_*` 不作判定（9.7.7 已证不可靠）；
- `ibl_stats.capture`：捕获次数与单次 GPU 耗时，用来验证按需捕获而不是逐帧；
- `frame_dump`：唯一可靠的画面取证（PrintWindow 在窗口失焦时会重复同一帧）。

抓帧后统一转 sRGB 再比较：`frame_dump` 写的是线性 UNORM PPM，直接看会偏暗；
`gi_acceptance.py` 的 `snapshot()` 负责转 PNG 并计算显示域均值/分位/黑占比。

## 4. 判定口径

- **静态游历**：分两层。账本层是硬线——`ledger_rows`、`upload_bytes_total`、
  `command_count`、residency 的 `requested/ejected` 增量必须为 0；池层只需稳定——
  patch 随相机移动播种/回收，`active` 回到同一位姿后允许小幅差，但 `failed=0`、
  `memory` 不增长、`watermark` 有界。
- **回位姿静置时间**：`EVICT_AGE=240` 帧（约 4 s），过期 rank0 还要再走一轮 rank1
  才释放，所以 5 s 不够。tour 回位姿后静置 5 s，再每 2 s 采 15 次，取末 10 次中位数；
  实测约 20–30 s 才回到起始水位。
- **残影**：同一机位比较动态前后两张 sRGB 帧，整屏均值差 ≤ `max(1, 2×噪声底)`、
  p99 ≤ `max(3, 2×噪声底)`、>16 灰阶的变化像素占比 ≤ 0.5%。噪声底按场景分别测：
  Sponza 测试场 p99=1，原点 chunk 区域 p99=6，不能混用。
- **压测**：60 Hz 节流下 `wall ≈16.95 ms` 是等待，不是吞吐量；判瓶颈看
  `gpu_*` 的 p95/p99 与 `gpu_gi` 占比，并注明每 rep 只取 240 帧（`perf_samples`
  没有时间戳，这是近似窗口）。

`局限自检：…md`，结论回填段 README 与路线图。原始 JSON 不进提交，报告里引用路径。

## 6. 常见坑

- **`tools/__pycache__` 会毒化 Cargo workspace**：根 `Cargo.toml` 的 `members`
  含 `tools/*`，Python 生成的 `__pycache__` 会被当成 crate。所有脚本已设
  `sys.dont_write_bytecode = True`，命令行也带 `PYTHONDONTWRITEBYTECODE=1`。
- **release 重建前先退渲染器**：Windows 上进程占用 exe 会让链接失败。
- **`gi_stats.gi_ms` 在 release 常为 0**：GPU 计时槽回落到 0，压测一律用
  `perf_samples.gpu_gi_ms`。
- **点光强度太小测不到**：5–20 的强度在自动曝光下整屏变化 <0.01 灰阶，
  至少用 5000 以上才看得到局部差异。
- **自动曝光会掩盖 A/B**：所有 A/B 与能量回归都先 `exposure_set{mode:"manual"}`。

## 7. 代码改动解析

本段唯一的行为无关改动在 `ash_renderer/src/remote/census/perf.rs`：
`perf_samples` 的逐帧 JSON 增加 `"gpu_gi_ms": s.gpu_gi_ms`。`FrameSample` 与
`perf_stats` 的分位块本来就有这个字段，只有原始样本漏导；补上后压测才能按 rep
算 GI 的 p50/p95/p99。它不改变渲染路径、计时点位或任何默认值。

其余产物都是 `tools/` 下的验收脚本与文档，不进入渲染器运行时。
