## 4. 分组结论

### S1 Sponza（静态，103 行）
- GI 关闭时 GPU p50 8.22 ms；开 GI 后 low/mid/high 为 13.61/14.29/14.55 ms，GI 自身 p50 5.00/5.76/5.95 ms。
- mid 的 GPU p95 16.51 ms 贴着预算，high 的 p95 17.68 ms 已超 16.7 ms；high 的 p99 18.80 ms。1600×900 + RTX 2060 上，samples=4 + 时域滤波的默认高画质不能在 16.7 ms 内稳住。
- wall p50 被 present 节流钉在 16.9 ms，low/mid/high 的 wall p95 升到 33–37 ms，说明 GPU 排队已越过一个 vsync；wall 不能当吞吐量。

### S2 zero_day（静态，7,159 行）
- GI 关闭 GPU p50 11.19 ms；low/mid/high 12.92/13.25/13.34 ms，GI 自身 1.81/1.93/2.03 ms。几何/材质比 Sponza 重，GI 占比反而更小。
- 四档 GPU p95 12.65/14.56/15.05/14.80 ms，均在 16.7 ms 预算内；high 的 p99 15.37 ms 也留有余量。
- 首跑（`20261126-140023`）的 S2 三格在场景载入完成前就开启 GI，日志各出现 14 行 `VUID-vkCmdDispatch-None-08114`（Set 2 Binding 1/2 未更新），且首 rep 只有 85–113 个样本。`tools/gi_stress.py` 现对**所有格**等待 `instance_rows` 非零且两次相同后再写 GI 设置；复跑后 VUID 0、每 rep 240 样本，表内改用复跑读数。旧格的 VUID 属既有 BRP 边缘（载入中重建并开启 GI），不是 9.8 引入，已记入遗留。

### S3 大 Volume（zero_day + 8000 实例，15,159 行，size=512）
- 显存从 43.71 MB 升到 52.10 MB（cell 池 16.78 MB + patch 池 22.28 MB 不变，misc 增大），说明大 Volume 的成本主要在 misc/元数据与更大级联，不在 patch 池。
- 可见行只有 13（其余 15,146 被剔除），但 GPU p50 已到 15.94/18.56/19.01/19.02 ms，全部越过 16.7 ms；GI 自身仅 2.2–2.7 ms，主要成本是 15159 行的扫描/组装/透明收集。
- patches 只有 84–125：相机看到的表面很少，Volume 虽大但活跃 patch 不多；这格测的是“大 Volume + 大量常驻行”的固定开销，不是大面积 GI 覆盖。

### S4 实例档（Sponza + 10,000 实例，10,103 行）
- 静态 none：off 11.17 ms → mid 16.95 ms，GI 5.78 ms；GPU p95 19.66 ms 超预算。
- few（workload rows=100）：off 10.38 ms → mid 22.33 ms，GI 11.98 ms；patches 58,244，p95 29.49 ms。
- all（rows=10000）：off 11.06 ms（p95 31.85 ms，CPU 旋转本身已把帧顶穿）→ mid 25.04 ms，GI 12.59 ms，p95 48.26 ms，p99 53.08 ms；wall p99 121.96 ms。
- `workload` 的选择是查询序前缀，不保证只包含生成的实例；few/all 很可能旋转到了 Sponza 自身实体，因此这两格应读作“全场景动态”而非“仅实例动态”。这也解释了 few 的 patch 数（58k）高于 all（50k）。
- 动态档的 GI 成本从静态 5.8 ms 涨到 12–13 ms，patch 数从 13.9k 涨到 50–58k；瓶颈是动态几何导致的 patch 重播种/重估，不是池容量（active 远低于 65536）。

## 5. 未测档与结构性阻塞

- 5 万/10 万实例档未测：`透明行收集` 的上限是**全部在场行** 16384（`transparent_targets.rs:31` 与三份 WGSL），100k 场景报 `在场行数 100103 超出透明行容量 16384——显式报错不截断` 后渲染链退出；zero_day + 1 万也报 17159 超限（因此 S3 降到 8000）。
- 试过把容量扩到 131072：50k/100k 可跑，但典型场景 S1-low 的 GPU p50 从 11.67 ms 涨到 15.37 ms（+3.7 ms，约 +32%），因为 bitonic sort 每帧按满容量跑网络。该改动已回退，5 万/10 万档列为结构性遗留，需改成“只收集透明行”或动态排序容量后再测。
- 跨进程重复性：S1-low 的 GPU p50 在三次独立运行中读到 11.7/14.8/13.6 ms，波动约 ±15%。本报告只做同一次运行内的模式对照；跨运行绝对值不可直接比较。

## 6. 判定

- 判定线③“压测报告成组，不拿流畅截图代替读数”：**通过**（18 格成组，条件单、p50/p95/p99、显存、patch 数、draw 数齐全；未测档与原因明写）。
- 判定线⑤“GPU-driven 闭环不回退”：**通过**（全矩阵 `draw_calls_recorded=1`，与 5.3/5.5 口径一致；`command_count` 随实例行数增长但仍是 1 次 draw）。
- 预算结论：Sponza low 可在 16.7 ms 内；mid 贴线、high 超线。zero_day/S3/S4 的 mid/high 与动态档均超预算，默认画质在 RTX 2060 + 1600×900 上不满足 16.7 ms，需在质量档/分辨率/硬件上取舍。
