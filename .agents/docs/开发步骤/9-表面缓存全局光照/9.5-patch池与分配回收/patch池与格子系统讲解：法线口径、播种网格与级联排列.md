# patch 池与格子系统讲解：法线口径、播种网格与级联排列

写 9.5 之前，任何一版实现都要先回答三件事：patch 朝哪个方向算、屏幕上的样本怎么落到世界里、级联随相机怎么排。这三件事互相牵制，任一选错，后面的调参都会失去依据——本文只讲这三件，pass 的顺序与验收放在[施工计划](施工计划：patch池与分配回收.md)里。

全篇只有一条不变式：

> **一条 patch 的身份 = (级联, 世界体素, 方向桶)；而"世界体素 → 存储槽"的映射与相机位置无关。**

读懂这条，后面的选择基本都能自己推出来。

## 三个词先定清：Volume、cell、patch

**Volume**（体积）是缓存覆盖的那块世界空间：一个以相机为球心的嵌套结构，越靠近相机体素越细。**cell**（格子）是"体素 × 方向桶"的槽位，是查表的地址。**patch**（缓存条目）是池里的一条记录，被某个 cell 占用；一个 cell 至多一条 patch，一条 patch 只属于一个 cell。

起步参数（与 Unity 默认体积同档）：`Res = 32`、`4` 级级联、`Size = 128 m`。体素边长由一条公式定死：

```
体素边长 v_i = Size / (Res · 2^(级联数−1)) · 2^i
              = 128 / (32 · 8) · 2^i = 0.5 · 2^i 米
```

于是四级分别是 0.5 / 1 / 2 / 4 米。每级有 `32³ × 16 = 524,288` 个 cell（16 是方向桶数），四级合计约 **210 万** 个 cell。而 patch 池只有 **65,536** 条——**预算只够覆盖 3.1% 的 cell**。

这个 3.1% 解释了后面所有取舍：patch 太贵，每一条都必须是有用的。

## G-buffer 里的法线看着最顺，但它会让一个体素裂成十六条 patch

先看基线。我们的 G-buffer 存的不是面朝向，而是**着色法线**：几何法线打底，再让法线贴图经一个屏幕空间算出来的切线坐标系扰动（`shaders/scene/gbuffer/gbuffer_write.wgsl:71-88`）。它已经在那儿、一次 `textureLoad` 就能拿到，看起来比什么都顺。

问题在于它的语义和用途对不上。播种要法线做两件事：选方向桶（patch 朝哪半边天），以及定义 patch 所在的平面（后面校验重投影种子）。这两件事要的是**几何面**的朝向，而着色法线是"这个像素看起来朝哪"——它带着贴图细节，也带着视点。

三个具体代价，从便宜到贵：

**一、一个体素会裂成很多条 patch。** cell 索引里带桶号（`cellIdx = 16·(x·Res²+y·Res+z) + 桶`），而桶是法线的方向分类。一面平墙如果因为法线贴图细节让不同像素落进不同桶，同一个体素里的 16 个 cell 会各分到一条 patch，最多 16 条。池只有 3.1% 的余量，等于把最稀缺的资源乘 16 倍；每条 patch 只拿到 1/16 的屏幕样本，全都处于"覆盖不足"的状态。用平面法线，这面墙只占 1 条。

**二、它是视点相关的，相机一动桶就变。** 那套切线坐标是 `cotangent_frame` 用 `dpdx/dpdy` 现算的（`gbuffer_write.wgsl:29-47`，Schüler 2015 的做法）。屏幕空间导数的值随距离、倾角、mip 变化，所以**同一个世界点的着色法线**在不同机位会差几度。差到跨过桶边界，桶就变了——静态场景里 patch 会随相机移动被创建和释放，稳态不再稳态。

**三、它会让下游用法失真。** patch 上存下的法线是 9.6 半球射线的轴：轴被贴图细节改变方向，采到的半球也跟着偏，同一个 patch 的估计值随"最后是哪个像素写的"变化，方差上升。它同时也是种子校验的平面基准，法线一偏，正确的种子会被判成"不在同一平面"。

Unity 的选择和我们一致：屏幕播种用的不是它自己的 G-buffer normal，而是另跑一个 `FlatNormalResolution.compute` 从深度重建出来的平面法线，播种 shader 里叫 `_CurrentFullResScreenFlatNormals`；射线命中那条路径用的则是命中的三角面法线。

我们的做法更省：不另开 pass，在播种的 compute 里用深度一阶差分重建平面法线——每个 1/4 分辨率样本多读 3～4 个全分辨率深度，代价可以忽略。唯一的坑是**深度不连续的采样点**（前景和背景在同一块像素里相遇）：那里的差分会算出毫无意义的法线，必须在差分时剔除深度差超过阈值的邻居，全被剔除就跳过这个样本，不播种。

还有一种便宜的补丁：把法线**量化到最近的桶中心**再选桶，相当于给桶加迟滞。这能压住第一条（碎片），压不住第二、第三条——视点相关和半球轴倾斜都还在。所以它只适合当过渡。

## 播种网格是屏幕上的采样格，不是世界里的体素格

**播种**（seeding）是给池子提请求的过程：我们需要知道"世界上哪些表面值得一条 patch"，又不愿意为此发射线或做可见性查询，于是直接拿当前帧屏幕上的可见面当请求源——每个像素有深度，反投影就得到世界位置，再换算成 cell。屏幕像素因此是 patch 请求的种子。

**播种网格**指这个请求源的采样密度，它有两级：

| 维度 | 规则 | 结果（1920×1080） |
|---|---|---|
| 空间 | 每 4×4 全分辨率像素取 1 个点 | 480×270 = 129,600 个线程 |
| 时间 | 块内子像素按 `frame×7 % 16` 轮转 | 16 帧 × 129,600 = 2,073,600 = 全分辨率像素数 |

第二行不是巧合：4×4 块有 16 个子位置，16 帧正好把所有子位置各点一次，等于每 16 帧把整个屏幕按全分辨率走了一遍。细到只占部分子像素的几何（栏杆、树枝、铁艺）因此不会永远被漏掉，代价是它可能出现得晚一两帧。

为什么 1/4 就够：cell 是 0.5 米，而 1080p、5 米距离上一个像素约 5 毫米，一个 4×4 块约 2 厘米——**一个 cell 本来就会被几十个屏幕样本重复命中**。重复的命中在 `CellAllocationMarks` 的原子换入面前是空操作（只刷新几何与心跳），全分辨率只是把这份重复工作放大 16 倍。

还有一个容易忽略的细节：每帧虽然覆盖所有 1/4 像素，但**处理顺序要重排**（用帧号做哈希把低分辨率像素序重排一遍）。因为 ring 的分配是原子的"先到先得"，如果 dispatch 顺序固定，池子将满时就会变成"屏幕左上角先占满"，右下角永远分不到预算。重排之后，各屏幕区域的分配机会相等。

## 级联排列的算术：每帧三步，每样本五步

参数定死之后，剩下的全是整数运算。先看每级的覆盖：

| 级联 i | 体素边长 | 立方外沿 `Res·v` | 球判据半径 `v·(Res/2−0.5)` |
|---|---|---|---|
| 0 | 0.5 m | 16 m | 7.75 m |
| 1 | 1 m | 32 m | 15.5 m |
| 2 | 2 m | 64 m | 31 m |
| 3 | 4 m | 128 m | 62 m |

判据是球不是盒：位置到 Volume 中心的距离小于 `v·(Res/2−0.5)` 才算落在这一级（`PatchUtil.hlsl:260-270`）。所以四个级联是四个嵌套的球，角落的 cell 本来就判到界外，不分配。

### 每帧一次（CPU）

1. 焦点 `p` ← 相机世界位置（9.5 不做 Focus Target）。
2. 每级算整数体素偏移：`offset_i = ⌊p / v_i + 0.5⌋`。这一步就是"按体素对齐"，相机在体素内部移动时 `offset_i` 不变，跨过体素边界才变 1。
3. 比较本帧与上一帧的 `offset_i`：任何一级变了，本帧才需要跑滚动（释放出界 cell）。

### 每个样本一次（GPU 播种）

1. 从最细级开始试，第一个满足球判据的级就是归属，得到 `cascade = i`。
2. 体素坐标：`pv = clamp( int(p_sample/v_i − offset_i + Res/2), 0, Res−1 )`。
3. 存储槽：`storage = (pv + offset_i) mod Res`（有符号正模，`PatchUtil.hlsl:244-258`）。
4. 桶：`bucket = direction_to_bucket_index(平面法线, 4)`，4×4 八面体映射、16 个桶（`shaders/common/octahedral.wgsl:29-41`）。
5. `cellIdx = 16·(storage.x·Res² + storage.y·Res + storage.z) + cascade·(Res³·16) + bucket`。

**走一个具体样本。** 相机在 `(10.3, 1.7, −4.2)`，最细级 `v = 0.5`，屏幕上某个样本落在 `(10.6, 1.7, −4.0)`，法线朝上 `(0, 1, 0)`：

```
offset  = ⌊(20.6, 3.4, −8.4) + 0.5⌋ = (21, 3, −8)
pv      = int((21.2, 3.4, −8.0) − (21, 3, −8) + 16) = (16, 16, 16)
storage = ((16,16,16) + (21,3,−8)) mod 32 = (37, 19, 8) mod 32 = (5, 19, 8)
平面下标 = 5·1024 + 19·32 + 8 = 5736
桶      = 法线 (0,1,0) → 方图 (0.5, 1.0) → 格子 (2, 3) → 3·4 + 2 = 14
cellIdx = 5736·16 + 14 = 91,790
```

`pv` 落在 `(16,16,16)` 说明相机几乎在 Volume 的正中心——这正是"焦点跟相机"的含义。

### 把第 2、3 步代进去，会得到一个反直觉的结论

级联内部 `pv` 落在 `0..31`，此时 `int()` 截断与 `floor` 一致，于是：

```
storage = (pv + offset) mod Res
        = (p/v − offset + Res/2 + offset) mod Res
        = (p/v + Res/2) mod Res
```

**offset 被消掉了。** 世界体素到存储槽的映射是一张**世界对齐的环形瓦片**，与相机走到哪无关：同一个世界体素（同一级联内）永远落在同一个槽上。由此得到两个推论：

- **滚动不需要搬运数据**。相机移动时 patch 不换槽，滚动只负责把"已经落在球外"的槽释放掉。第一版实现最容易在这里走错——把 offset 当成窗口原点去重算整张表。
- **静态几何上的 patch 是稳定的**。相机走开再回来，只要期间没被淘汰，patch 仍在原来的槽里，辐照度历史也还在。

要注意"同一级联内"这个限定：相机退远时某个体素会从细级联换到粗级联，那是另一套 cell 与另一条 patch，属正常换代。

### 时间轴上的节奏

| 周期 | 动作 | 9.5 起步档的取值 |
|---|---|---|
| 每帧 | 滚动 | 仅 `offset` 变化帧；把出界 cell 三连释放 |
| 每帧 | 淘汰 | 心跳超过 240 帧（60 fps 下 4 秒）就回收 |
| 每帧 2 槽 | 整理 | 把 ring 内容区间里的空位前移；走完全池约 3.3 万帧，可配 4/8/16 |
| 每帧 | 播种 | 1/4 网格 + 16 帧子像素轮转 |

顺序固定为 **滚动 → 淘汰 → 整理 → 播种**（Unity 的 preparation 阶段也在 update 之前，`SurfaceCache.cs:609-628`）：先把空间腾出来，本帧播种就能用到刚释放的槽。反过来排在播种之后，就要等一帧才能复用，池子将满时会把失败率推高。

## 三个口径怎样互相约束

分开看是三个决定，合起来是一个系统：

- **采样密度决定池压力**。1/4 网格对 0.5 米 cell 已经是几十倍过采样；再加密不会提高覆盖，只会让同一个 cell 被重复命中更多次。真要提高覆盖，该动的是级联数与池容量，不是采样密度。
- **法线口径决定 cell 需求**。平面法线下"一个体素一条 patch"，着色法线下最坏"一个体素十六条"。池的余量只有 3.1%，这个系数直接决定池够不够用——所以法线不是画质选项，是预算选项。
- **对齐粒度决定滚动频率**。`offset` 按整个体素变，最细级 0.5 米一跳；若改成按更细的量化（比如半个体素）去对齐，滚动会频繁触发，每帧扫描 `Res³×4` 个 cell 的开销就浪费了。宁可让相机在体素内部移动而不触发对齐，也不要让它每帧滚一次。
- **16 帧轮转决定新表面的延迟**。一块刚进入视野的表面，最快当帧、最慢 16 帧后才被采到并分配 patch。这个延迟对静态场景无所谓（下 16 帧内一定补上），对快速运动要心里有数：一帧里掠过屏幕的物体可能一条 patch 都没分到。

## 要看见它：视图该回答的四个问题

上面全是算出来的，真跑起来还得能看。一个够用的 patch 视图要能直接回答四件事：

1. **覆盖有没有洞**：可见表面上有没有"本该有 patch 却没有"的地方。
2. **位置贴不贴表面**：patch 存的位置和它覆盖的像素之间，差值应该远小于一个体素（Unity 的调试视图用 0.1 体素做阈值）。
3. **同一平面有没有被拆成多条**：按桶着色时，一面墙如果出现整片条纹，说明法线口径错了。
4. **池子稳不稳**：水位与分配失败随游历是收敛还是持续上涨。

两种实现路线，上游都有先例：Unity 走**屏幕空间逐像素**——全屏 compute 读深度、着色法线、平面法线，给每个像素算它属于哪个 cell / 哪条 patch，再按视图模式上色，屏幕顶部留 5% 做池占用条（`Debug.compute`，模式 1～10；`_ShowSamplePosition` 会把"离 patch 位置不到 0.1 体素"的像素涂亮）。Kajiya 两种都做——`ircache_draw_debug.hlsl` 逐像素输出查表结果并在顶部画占用条，`raster_origins_vs.hlsl` 则给每条缓存条目画一个 2 厘米立方体，用一次实例化 draw 把所有条目的位置摆进场景。

我们的选择与理由写在[施工计划 §0.7 与 9.5.6](施工计划：patch池与分配回收.md)里：主形态是"把 patch 画在网格表面"的覆盖图（每像素按自己的表面算归属，所以它天然贴在表面上），辅以一次实例化的小方片看位置与朝向。
