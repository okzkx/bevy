# 程序化天空盒算法原理

屏幕背景那片渐变和太阳盘不是贴图，是一个**把"看的方向"映射成颜色的解析函数**：

> `sky_radiance(dir, include_sun)` 收一个归一化方向，返回该方向上的线性辐亮度（pre-exposure 域）。

函数只有三十来行（`ash_renderer/shaders/common/sky.wgsl`），没有纹理、没有采样器、没有历史帧。本篇讲这个函数为什么这么写；它在帧里怎么被调用、写完 HDR 之后还会被谁改，见[渲染流程](程序化天空盒渲染流程.md)。

## 为什么参数是方向，不是世界坐标

天空在无穷远：相机平移一米还是一百米，看到的天空都一样；只有**转动**才改变画面。

所以天空的颜色只能是方向的函数——如果把相机位置写进参数，就得为每个位置准备一份"天空"，而这份数据本身还会随位置变化，等于把问题做复杂了。用方向参数化，"无限远"这件事自动成立，也不需要任何物体或包围盒来承载它。

函数签名里的 `dir` 是**单位向量**（调用方归一化）。实现里只读它的 `y` 分量（渐变）和它与太阳方向的点积（圆盘/光晕），所以方向在世界空间里怎么定义都行，只要调用方保持一致。

## 三段渐变：两个幂把三个颜色接成一条连续的曲线

```wgsl
let up   = saturate(dir.y);
let down = saturate(-dir.y);
var c = mix(horizon, zenith, pow(up,   horizon_exponent));
c     = mix(c,       ground, pow(down, ground_exponent));
c     = c * intensity;
```

- **顺序**：先把地平线色混向天顶色，再把结果混向地面色。向上的方向 `down = 0`，第二次 `mix` 的权重为 0，上半球完全不受地面色影响；向下的方向同理。
- **地平线无缝**：`dir.y = 0` 时两个幂都是 0，两次 `mix` 都退到 `horizon`。地平线两侧从同一点出发，不会出现一条亮线或暗线——这是"两个幂都取地平线色而不各管各的"的原因。
- **幂的语义**：`pow(up, e)` 在 `up ∈ [0,1]` 上，`e` 越小越快切到天顶色。默认 `horizon_exponent = 0.5`：离地平线 10°（`up ≈ 0.174`）就已经混了 `√0.174 ≈ 42%` 的天顶色，45° 时 `≈ 84%`。`ground_exponent = 1.5` 则让地面色只在明显俯视时出现：俯角 10°（`down ≈ 0.174`）只有 `0.174^1.5 ≈ 7%`。
- **没有第四个颜色、没有色带查找表**：三个颜色 + 两个幂足够表达"天顶暗、地平线亮、地面更暗"的观感。想要晨昏的暖色，就改地平线色；想要更陡的过渡，就调幂。

## 太阳圆盘按角度算，不按点积比阈值

太阳方向直接用帧 UBO 里的 `dir_to_light`（方向光 `transform.back()` 的语义：表面指向光源）。圆盘判定写成：

```wgsl
let theta = acos(clamp(cos_theta, -1.0, 1.0));
let disc  = 1.0 - smoothstep(radius * 0.8, radius, theta);
```

为什么不直接在点积上开一个窗口？因为**近圆心的点积差几乎是 0**。半径 0.01 弧度对应 `cos` 的差只有 `1 - cos(0.01) ≈ 5×10⁻⁵`；软化带（0.8r 到 r）在点积空间只有约 `1.8×10⁻⁵` 宽。f32 在 1.0 附近的精度约 `1.2×10⁻⁷`，这个带能表示，但整条带只落在几百个可表示值上，低分辨率下容易出现一圈圈色阶。

换成角度域以后，软化带的宽度是 `0.2 × radius` 弧度，与屏幕像素覆盖的角度同量纲，`smoothstep` 的过渡是均匀的。

顺带一提，圆盘的实际观感半径约 `0.9r`：`0.8r` 以内全亮，`0.8r ~ r` 线性退到 0。

## 太阳位置可以和屏幕像素对上

圆盘落在屏幕上的位置只由两个量决定：太阳相对相机轴线的角度，和投影的焦距。

本工程透视投影竖直 FOV 45°，客户区高 900 物理像素，焦距 `f = 450 / tan(22.5°) ≈ 1086 px`。相机俯仰 0°、太阳仰角 `el` 时，圆盘中心应在屏幕中心上方 `f · tan(el)` 像素。实测（`tools/capture_window.py` 抓图，客户区按标题栏 38 px 折算）：

| 太阳仰角 | 实测圆盘中心（客户区 y） | 理论值 `450 − f·tan(el)` |
|---|---|---|
| 5° | 354 | 355 |
| 10° | 257 | 259 |
| 15° | 158 | 159 |

三个点都在 1～2 px 内。这说明"太阳方向 → 屏幕位置"这条路（方向光 `back()` → 帧 UBO → `dot` → 角度 → 圆盘）没有多一转、少一转，也让"圆盘随方向光移动"这件事有了可复算的判据，而不只是"看着像在动"。

`radius = 0.01` 弧度对应的屏幕半径约 `f · r ≈ 11 px`——比真实太阳（约 0.0047 弧度）大两倍多，取这个默认值是为了在 720 pt 的窗口里看得见，不追求物理精确。

## 光晕是一个低频补丁，强度单位是方向光颜色

```wgsl
let glow = pow(saturate(cos_theta), glow_falloff);
c += light_color.rgb * (sun_gain * disc + glow_intensity * glow);
```

- 光晕项只依赖太阳方向的余弦，是一个各向同性的低频项——它给"太阳在那边"一个方向感，不承担任何高频细节。
- 圆盘和光晕都用 `light_color.rgb` 着色（线性色 × illuminance，量级约 `2×10⁴`），`sun_gain` 与 `glow_intensity` 只是相对倍数。这样太阳的颜色不需要额外参数：改方向光颜色，天空里的太阳跟着变。
- **坑在单位**：`glow_intensity = 0.15` 听起来很小，乘上 `2×10⁴` 就是 3000 的附加辐亮度——比天空本体（约 800）还亮，会把整片天空刷白。默认取 `0.02`（约 400），光晕只在太阳附近 10° 内可见。

## 天空与直接光必须同处曝光域

帧 UBO 里的 `dir_to_light`、`light_color` 是**未曝光**的物理量级（方向光 20000 lux 级别），天空的返回也是同一域。合成 pass 在输出前统一乘 `EXPOSURE = 0.00016`（`shaders/common/brdf.wgsl`），天空与受光像素才不会差一个数量级。

数值走查（默认参数）：

| 位置 | 辐亮度（线性） | × EXPOSURE |
|---|---|---|
| 天顶（蓝通道） | 0.42 × 2000 = 840 | 0.134 |
| 地平线（蓝通道） | 0.72 × 2000 = 1440 | 0.230 |
| 太阳圆盘 | 20000 × 1.5 = 30000 | 4.8 |

圆盘那 4.8 是有意的过曝（真太阳在相机里就是过曝的）；渐变那 0.13～0.23 落在 tonemap 的线性段。

关掉天空的分支返回清屏色 `CLEAR_COLOR`，**不乘曝光**——它是显示端要逐位复现的旧基线，任何"等价变形"都会破坏这一点。

## 观感是 tonemap 的结果，不是函数本身

同一片天空，经过完整 ACES（tonemap 前还有 1.667 的亮度增益）之后，亮部和饱和的蓝色都会被压向白。首版默认参数选得偏亮（地平线系数 0.62、强度 2500，乘曝光后约 0.25），落在曲线肩部，结果地平线一片灰白、天顶—地平线的色差被吞掉。把地平线降到 0.40×2000（约 0.128）后回到线性段，渐变才显出来。

所以"默认梯度"是按**这条后链反推**的：它保证出厂画面不难看，不表示这些数字对别的曝光/tonemap 曲线也成立。要换观感，改 `SkySettings` 或直接在天空面板/`sky_set` 里调，函数不用动。

## 太阳圆盘为什么不进环境 cubemap

函数有一个 `include_sun` 参数，可见天空传 `true`，9.2 的环境 cubemap 捕获会传 `false`。

原因不是性能，是**频率**：环境 cubemap 要投影成 SH 低频系数、要预滤波成不同粗糙度的高光链，一颗几千倍于背景的亮斑会在低频系数里留下一个大到失真的常数项，并在低粗糙度的预滤波结果里拖出一条假的亮带。真实光照里太阳的贡献由方向光直接承担（直射 + CSM 阴影），环境项只该描述"其余方向的光"。Unity 的环境捕获用它自己的 `_SUNDISK_NONE` 做同一件事。

`include_sun` 也把"哪些项属于太阳"这件事钉在了函数内部，9.2 不需要再重复一遍圆盘公式。

## 没做的部分与已知边界

- **没有大气散射**（Preetham/Hosek 模型）、没有云、没有星空、没有镜头光晕。段边界就是"解析渐变 + 一个圆盘 + 一个低频光晕"。
- **没有遮挡**：天空是背景分支的返回值，只在"没有几何写深度"的像素上出现。室内看到天空是正常的——那不是天空算错了，是环境光遮蔽（9.4 起的 GI 与 SSAO 类手段）该管的事。
- **太阳在地平线以下时圆盘自然消失**：`dot(dir, sun_dir) > 0` 只对太阳所在半球成立，`sun_dir.y < 0` 时圆盘整个落在地平线以下，不需要额外分支。
- **换模型的接口**：以后要接 Preetham 或加云，只换 `sky_radiance` 的实现，调用方（合成 pass、9.2 捕获）不用改；参数形状（三色 + 强度 + 两个幂 + 太阳四项）也是按"换实现不改调用方"设计的。
