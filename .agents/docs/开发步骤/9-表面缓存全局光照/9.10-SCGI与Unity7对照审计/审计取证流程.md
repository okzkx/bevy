# 审计取证流程：9.10 对照审计是怎么做出来的

## 1. 为什么要做这次审计

9.4–9.7 的实现是"读 Unity 代码后按功能语义重写"，但从来没有人把 40 个 Unity 文件逐行对账过。结果就是两类风险：**看起来对但数值错的实现错误**（例如 9.6 的光源多跳多乘了 `cos_b/d²`，能量回归却碰巧过了）和**以为缺了其实只是机制不同**的误判。9.10 的目标是把这两类风险都摊开：40 文件全覆盖、三清单逐条给证据、≥20 项参数对照、三组运行时读数。

## 2. 对照面的组织

40 文件按"实现段"分组，而不是按目录：

| 组 | Unity 侧 | 本仓库落点（示例） | 负责内容 |
|---|---|---|---|
| 9.4 场景接驳 | 6 文件（`SurfaceCacheWorld.cs` 等） | `src/scene/mechanism/assets/ledger.rs`、`ray_tracing/`、`resident/tables/` | 什么进 GI、以什么身份进（实例/材质/自发光/灯） |
| 9.5 池与分配 | 10 文件（`Common.hlsl`、`PatchUtil`、`Scrolling`、`Eviction`、`Defrag`、`PatchAllocation`…） | `gi_cell.wgsl`、`gi_ring.wgsl`、`patch_alloc/defrag/eviction/scrolling.wgsl`、`allocation.rs` | cell↔patch 指针、环形缓冲、淘汰与碎片整理 |
| 9.6 估计链 | 8 文件（`Estimation`、`PathTracing`、`PunctualLight*`、`Emissive*`） | `estimation.wgsl`、`light_sampling.wgsl`、`gi_sampling/gi_light_sample/gi_bounce` | 采样、投影、多跳、自发光 |
| 9.7 屏幕侧 | 9 文件（`IrradianceCompression`、`Spatial/TemporalFiltering`、`ScreenResolve*`、`Debug`） | `screen_gather/denoise/upsample/spatial_filter/temporal_filter`、`gi_compression`、`patch_view` | 压缩、滤波、查表、去噪、上采样、调试视图 |

为什么按实现段而不按目录：Unity 的一个 `.compute` 常被本仓库拆成"共享函数 + 多个入口"，按目录对会漏掉跨文件的语义；按段对才能问出"这一步的输入输出在两边是否一致"。

## 3. 一个文件怎么对

每一行固定四问：

1. **职责**：Unity 侧这个 kernel/函数在算什么？（记录 kernel 名与行号区间）
2. **落点**：本仓库哪几行在做同一件事？（给 `file:line`，不给目录）
3. **判定**：等价 / 机制不同但等价 / 实现错误 / 缺漏 / 冗余 / 不适用。
4. **证据**：如果是"实现错误"，必须能给出一组会变的数值（画面差分、读数、方差、计数）。

第 4 条是这次审计的关键改进：只写"公式不一致"不算发现，必须写出"不一致导致的量级"，例如"3 m 灯注入被压到 1/9"、"方差放大 61×"、"rank1 patch 每 240 帧重建一次"。

## 4. 判"机制不同"的纪律

计划 §0.1 明确：机制不同但等价物存在，**不计缺漏**，写"机制不同，等价物在 X"。这条纪律防止两类噪声：

- 把 Unity 的 `ObjectDispatcher` 增量当成本仓库缺功能（实际有 ECS `Changed` 查询）；
- 把 `FallbackMaterial.shader` 当成缺材质（实际合成端 `mix(ibl, albedo·Fd·E, irr.a)` 更连续）。

本次共 11 处判"机制不同、等价"，全部在报告 §2.2 给了等价物 `file:line`。

## 5. 证据链

```
读码（两边 file:line）
  ├→ 四组只读 subagent 交叉复核（9.4/9.5/9.6/9.7）
  ├→ 主 Agent 逐条复核 P0（重推公式、重读判据）
  ├→ 基线判定线：gi_test 25/25、gi_estimation_test 12/13、gi_gather_test 7/12
  │    └→ 两个失败用探针证伪为脚本前提失效（未钉 manual 曝光、预算未真降档）
  ├→ P0 修复 → 一次构建 → 回归 25/25、13/13、7/12
  │    └→ 修 gi_gather_test 钉 manual → 12/12
  └→ 运行时三组 BRP 读数 + 3 张读图
```

关键点：**基线失败先证伪再定性**。`gi_estimation_test ③` 与 `gi_gather_test ①` 在修前都是红的，如果直接当成"本段缺陷"就会去改产品代码；探针证明前者是预算档位没真降（8→8）、后者是自动曝光在 3 s 里漂了 0.003（scale 0.131635→0.128574），产品能量本身在 ±1%（manual 下 IBL 118.73 / SCGI 118.55 = 0.9985）。

## 6. 顺延项怎么核销

9.7 留下的 6 项一律按"结论 + 证据 + 是否为缺陷"三条写：

- 视图 16：本段可实现 → 实现 + 读图核销；视图 17：判 P2（与 9.8 工具重叠）。
- `scgi_ms`：先查现有读数，发现 `gpu_gi_ms` 已覆盖整段（标记点在 `gi.record()` 之后）→ 不新增，核销。
- `GI_COUNTER_WORDS` 扩容：先查占用（0..15 全满）与新增视图是否真的需要计数（逐像素分类不需要）→ 判定不扩。
- 透明 A/B：先查透明层是否消费 SCGI（不消费、只绑 IBL）→ 无观测面，代码取证核销并登记局限。
- rank1：用 `gi_stats` 多跳开/关对照（bounce_requests 11→0）。
- Volume 边界环/振铃：用 coverage、view_holes、non_finite、negative 与收敛比证明"未观测到"，同时把真实的边界缺陷（A4 环包老槽）修掉。

## 7. 这次审计的边界

- 不做 1:1 移植，不把 Unity 资产/代码搬进仓库；
- 不评天空/IBL 本体（9.1–9.3 已收官）；
- 不改 9.5 池布局与 ring 深度（只修判据）；
- 不替 9.8 跑长时压测；
- 不为对齐 Unity 牺牲 GPU-driven 与 6 GB 预算——所以 P1 10 项选择"另立"而不是本段硬塞。
