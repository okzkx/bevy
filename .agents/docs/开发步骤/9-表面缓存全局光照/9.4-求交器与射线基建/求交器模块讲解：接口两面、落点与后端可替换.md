# 求交器的模块边界：接口独立，生命周期跟驻留走

把求交器做成独立模块的直觉是对的：射线怎么打、打到什么，应该和 GI 的格子、patch、滤波分开。但"独立"要分两件事看：接口可以独立，BLAS 的生命周期不能独立——它必须跟着资产驻留走。

核心判断：**独立文件夹和双面接口：是；独立 crate：否；BLAS 生命周期挂驻留：有意的耦合。**

## 接口有两面：宿主侧 RayScene，shader 侧 raytracing.wgsl

求交器不是纯 CPU 库，也不是纯 shader 库，它的接口天然分两半：

- **宿主侧** `RayScene`：负责建/更新/销毁 BLAS 与 TLAS、维护地址表、暴露描述符给消费 pass、报统计。它不把 `vk::AccelerationStructureKHR` 这类硬件类型漏出去。"查询入口"指把 TLAS 与池绑定交给消费 pass，不是 CPU 逐条 raycast。
- **shader 侧** `shaders/common/raytracing.wgsl`：只放结构体和函数——`trace_scene(tlas, origin, dir, tmin, tmax, mask) -> SceneHit`、`hit_geometry(instance_slot, primitive, bary) -> HitGeometry`、`hit_world_pos/normal/uv`。所有 ray query 调用收在这一个片段里。

`enable wgpu_ray_query;` 必须由入口 shader 的第一行携带，不能放进公共片段：build.rs 的 `#import` 是文本展开，指令混进被多处展开的片段会重复出现。

换后端（例如将来做软件求交）时，换的是这份 WGSL 片段加 `render/ray_tracing/` 的后端模块，消费方（9.6 的 GI）不动。这是"接口独立"的实际含义。

## 四个落点与依赖方向

| 落点 | 内容 |
|---|---|
| `render/ray_tracing/` | `RayScene`、`BlasRegistry`、`TlasFrame`、`RayTracingSupport`/`RayTracingSettings`、统计 |
| `shaders/common/raytracing.wgsl` | 公共结构、`trace_scene`、命中重建 |
| `shaders/scene/ray_tracing/` | 入口 shader：`tlas_build.wgsl`、`ray_debug.wgsl` |
| `render/passes/ray_tracing/` | 调试图 compute 管线的资源与录制 |

依赖方向是单向的：`ray_tracing` 读 `core` 的缓冲/描述符设施、读 `resident` 的对象记录与网格池区间；`resident` 不认识 `ray_tracing`。驻留侧计划新增的 b10 地址表只存 `u64`，不引用加速结构类型，所以这条反向依赖被挡在类型层面。

新管线和新描述符集要在 `layout_registry` 登记（`ALL_SETS` / `ALL_PIPELINES`），否则库测试 `every_shader_entry_has_a_pipeline` 会报。

## 为什么 BLAS 生命周期必须挂驻留

资产驻留（residency）管理哪些资产在显存里活着。BLAS 的构建输入是 `MeshPool` 的区间，池的 commit（资产首次驻留）、replace（同一资产换内容）、retire（资产退场）决定了区间何时有效。三个事件都要联动：

- **commit**：新资产驻留，若它命中"锚档变体"规则（LOD 组里最粗的已驻留变体），排一个待建 BLAS；下一帧 ② 段构建，成功后把地址写进 b10 地址表。
- **replace**：同一资产换了网格内容，旧 BLAS 排销毁，新 BLAS 待建；地址表在切换的那一帧换成新地址或先写 0。
- **retire**：资产退场，BLAS 排销毁，地址表写 0；销毁要等在飞帧（已经提交给 GPU 但还没执行完的帧）用完，不能立刻 `vkDestroyAccelerationStructureKHR`。

如果把这层耦合拆掉、让求交器自己按"资产 id"管理 BLAS，会出现两个真问题：

1. **悬空地址**：池扩容或替换后旧地址失效，而求交器不知道，TLAS 实例仍指向旧内存。
2. **提前销毁**：资产退场时 GPU 上还有帧在查这个 BLAS，销毁即 use-after-free，轻则验证层报错，重则设备丢失。

所以 9.4 计划的归属是：**BLAS 按 `AssetId<Mesh>` 缓存，生命周期由驻留事件驱动，求交器只执行构建与查询**。这与常见的引擎做法一致：BLAS 挂在网格资产上，实例只引用地址。

## 为什么不拆成 crate

独立 crate 的收益是编译隔离和强制接口；成本是错误类型、日志、构建脚本、注册表都要跨 crate 重做一套。按项目已有的拆分原则，底层拆 crate 的触发条件是出现第二个消费者——现在只有 9.6 的 GI 更新消费 `trace_scene`/`hit_geometry`，9.5 和 9.7 都不碰求交器。一个文件夹加一份公共 WGSL 片段已经能划清边界，拆 crate 的收益为负。

将来如果求交器要在 `ash_renderer` 之外被复用（例如独立的工具或第二个渲染器），再按"第二消费者"原则拆。

## 9.4 的边界：只做基建，不改画面

求交器本段不产生 GI 缓存、不消费 GI 样本、不接任何现有 pass 的着色。调试图走独立 compute，不塞进 `gbuffer_composite`——含 `RayQueryKHR` 的 shader 在非 RT 设备上建不了管线，塞进去会破坏"光线求交关 = 与 9.3 逐位一致"的降级路径。

本段也不做：软件求交、AS compaction、增量 TLAS、RT 管线、多相机/多 TLAS、蒙皮/形变网格的 AS 特殊化、alpha 裁切。软件后端若将来要做，登记进外置拓展需求再立项，不占 9.x 段号。

对后续段的接口很窄：

- 9.5（patch 池）不消费求交器；
- 9.6（irradiance 更新）用 `trace_scene` 和命中重建取数；
- 9.7（屏幕 gather）只读 patch 缓存；
- 9.8（验收）沿用本段的 `ray_tracing_stats` 口径做压测。
