# 求交器要往 GPU 放什么：几何复用、射线不落地

准备求交器时最容易先想到两个大缓冲：一个存射线，一个存三角形。9.4 两个都不新建。三角形已经在 `MeshPool` 里，射线在着色器寄存器里现场生成；真正新增的是加速结构、实例数组、地址表和几张描述符绑定。

核心判断：**几何不复制，射线不落地；每帧变化的只有实例数组。**

## 三角形不复制：BLAS 建在 MeshPool 的区间上

`MeshPool` 的顶点池是 32 字节交错：位置 12 字节、法线 12 字节、UV 8 字节；索引池是 U32。每个 `MeshSlot` 记录两段区间（`vertex`、`index`）和计数，上传时按 bump 分配（从池头往后依次切区间），扩容时整段迁移。

BLAS 构建输入直接指这两段：

- `vertexFormat = R32G32B32_SFLOAT`，`vertexStride = 32`（位置在前 12 字节）；
- `indexType = U32`，`maxVertex = vertex_count - 1`；
- 几何的起始位置由 buffer 设备地址加区间字节偏移表达，`firstVertex = 0` 是相对这个起点的。

这要求顶点/索引池在 光线求交开启时多带两个 usage（缓冲用途标志）位：`ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY_KHR`（VUID-03673 要求）和 `STORAGE_BUFFER`（命中重建要用 storage 读；storage buffer 是着色器可读的显存缓冲）。不复制几何的好处是显存只付一份、流送与命中读数天然同步、扩容迁移只处理一个池。

几何档位按 9.4 的裁决：每个 LOD 组只给最粗的已驻留变体建一份 BLAS，无 LOD 组的资产自为组。漫反射 GI 只吃低频遮挡，不值得为每个 LOD 变体各建一棵树。

## 射线不落地：线程自己生成

硬件 ray query 的射线不需要缓冲。每个 compute 线程在自己的寄存器里拼一个 `RayDesc`：

| 字段 | 含义 |
|---|---|
| `origin` | 起点，世界空间 |
| `dir` | 方向，通常归一化，`t` 以世界单位计 |
| `tmin` / `tmax` | 有效区间；`tmin` 用来避免自交 |
| `cull_mask` | 与实例 mask 按位与 |
| `flags` | 例如强制双面 |

9.4 计划的调试图从帧 UBO（存放帧常量的只读 uniform buffer）的 `inv_view_proj` 和 `camera_pos` 反投影出主射线，线程号就是像素号。9.6 的 GI 从格子/表面缓存播种，线程号是格子或 patch 号。两者都没有"射线数组"这个中间物；一条射线通常只活在一个线程的几十条指令里。

将来如果做软件求交后端，或者需要按格子排序/压缩射线，才会出现显式射线缓冲。9.4 的接口留了这个位置（后端可替换），但硬件路径不需要。

## 真正新增的 GPU 数据

下表按 9.4 的施工计划列资源；AS 指加速结构，scratch 是构建期驱动用的临时工作区。实际落点由开工后的施工记录另写。

| 数据 | 形状 | 谁写 | 谁读 | 生命周期与绑定 |
|---|---|---|---|---|
| BLAS 对象 + 存储 buffer + scratch | 每 mesh 资产（锚档变体）一份 | 宿主查尺寸并建对象；构建命令写 | ray query 经 TLAS 引用 | 随资产驻留；scratch 只在构建期有效 |
| 实例槽 BLAS 地址表 | `u64 × 槽容量`，按帧槽各一份 | 宿主增量写（与对象记录/模型环同批） | `tlas_build` compute | 常驻的帧槽环；set2 新增 b10 |
| TLAS 实例数组 | `64B × 实例数`，按帧槽各一份 | `tlas_build` compute 全量写 | TLAS 构建命令经设备地址读 | 每帧重写；set2 新增 b11 |
| TLAS 对象 + buffer + scratch | 每帧槽一份 | 构建命令写 | ray query 读 | 容量不足时重建 |
| 光线求交描述符集 | b0 TLAS / b1 顶点池 / b2 索引池 / b3 调试图 / b4 统计 | 建集时写一次 | 调试图或 GI 的 compute | 按帧槽各一套，b0 要指向本帧槽的 TLAS |
| 调试图 + 统计缓冲 | RGBA16F 图 + 原子计数器 | `ray_debug` compute 写 | `ray_tracing_dump` 按需拷回 | 随 swapchain（呈现到窗口的图像链）尺寸重建 |

尺寸账：顶点 32B、对象记录 48B、TLAS 实例 64B、地址 8B/槽。TLAS 实例数取本帧 `indirect_count`（宿主已知的在场行数），不读 GPU 计数。容量按在场高水位向上取整，不够时重建。

## 一帧的数据流

在场环记录本帧可绘实例的槽号，模型环存每槽的模型矩阵，地址表存每槽 BLAS 的设备地址。

```
mesh 资产驻留（commit）
  └─ BLAS 构建（宿主查尺寸 → 建 buffer/AS → ② 段录构建命令 → 取地址写 b10 地址表）

每帧 ② 段：
  ① tlas_build.wgsl：读在场环/模型环/地址表 → 写 b11 实例数组（缺席实例引用写 0）
  ② 屏障：COMPUTE → ACCELERATION_STRUCTURE_BUILD_KHR
  ③ vkCmdBuildAccelerationStructuresKHR：用实例数组构建 TLAS
  ④ 屏障：ACCELERATION_STRUCTURE_BUILD_KHR → COMPUTE
  ⑤ 消费 dispatch：ray query → 调试图/统计（9.6 起是 GI 更新）
```

空场景（`indirect_count == 0`）不录 compute 与构建命令，宿主侧直接跳过；不依赖 0 长度命令的边角合法性。

## 一次 dispatch 能打多少条射线

没有"一次调用 N 条"的 API。并行求交数就是 dispatch（一次 compute 启动命令）的线程数：

```
线程数 = gx × gy × gz × workgroup_size
```

- 1080p 全屏每像素一条 = 2,073,600 个线程；项目惯例 64 线程/组时约 32,400 个工作组。
- Vulkan 只保证每维至少 65535 个工作组，2060 驱动实际更大，网格尺寸不是瓶颈；瓶颈是帧时间。
- 单个线程可以在循环里打多条射线（例如一个 patch 打 16 个方向），没有 API 上限，只受 `tmax` 与命中逻辑约束。
- 9.6 的真实播种量是活跃格子/patch 数，通常远小于像素数；预算应当按"这一帧给 RT 多少毫秒"反推射线数。

对照：RT 管线的 `vkCmdTraceRaysKHR(width, height, depth)` 才是批量发射形状，一次调用指定三轴条数；9.4 不用它（原因见[执行篇](求交器执行讲解：dispatch、队列、RT Core 与 API 选型.md)）。

调试图分辨率（全分辨率还是 1/4）是 9.4.6 的待决项：全分辨率读图清楚但射线数 ×1，1/4 分辨率省 16 倍线程，按验收读图的精度选。

## 地址与对齐：五条容易撞 VUID 的细节

| 细节 | 要求 | 出处 |
|---|---|---|
| BDA（设备地址）缓冲的内存分配 | `MemoryAllocateInfo` 链 `MemoryAllocateFlagsInfo { DEVICE_ADDRESS }` | VUID-03339 |
| AS 存储 buffer 的用途 | 必须带 `SHADER_DEVICE_ADDRESS` 与 `ACCELERATION_STRUCTURE_STORAGE_KHR` | VUID-09542 |
| AS 在 buffer 内的偏移 | 256 的倍数；首版每 BLAS 独立 buffer、offset 0 | VUID-03734 |
| 实例数组对齐 | 基址与偏移 16 字节对齐 | VUID-03715 |
| 构建输入 buffer | 顶点/索引/实例数组要带 `ACCELERATION_STRUCTURE_BUILD_INPUT_READ_ONLY_KHR` | VUID-03673 |

还有一个不是 VUID、但一定会踩的：**池扩容后设备地址会变**。地址不能缓存，宿主每次现取；扩容后要把新地址重写进地址表的两个帧槽。AS 本身不受影响，它已经自含构建结果。
