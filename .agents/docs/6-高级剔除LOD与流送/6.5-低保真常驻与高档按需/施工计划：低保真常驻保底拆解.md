# 施工计划：低保真常驻保底拆解（6.5，立案）

> 2026-10-20 立案（用户指令，纯文档立案）。6.5/6.6 追加段的详细施工计划——6.4 收官后补立，修的是 6.4 留下的"保底方向"缺口：本仓最细基准一旦被预算淘汰，行就整行消失，没有行业常见的"最粗保底常驻"。本计划保持立案时点原貌，状态追记只在本行追加。
>
> **一句话说明**：这一段给每个可驻留资产建立一张可靠的最低保真 mesh 表示并令其常驻显存，把"行可绘"的锚从最细基准档迁到保底档，高档与最细基准改为按需上传——高档/基准缺席时画面退到低保真继续画，而不是整行消失；它为 6.6 的 GPU 稀疏缺口请求补上"缺席时有东西可画"的前提。本段不做 GPU 请求回读（归 6.6），不动页级虚拟纹理（仍挂[外置拓展条目 6](../../外置拓展需求.md)），也不把现有白图占位冒充低清原图。对应[路线图](../../学习目标实现步骤.md)步骤 6 追加段 6.5。
>
> 场景口径：沿用 6.2～6.4 定例——测试场景用 BRP 方法族生成、生成序列录成 Python 脚本持久化（tools/ 一键重建），测试先用测试几何体与程序化资产，真实资产场景归步骤 7（6.5/6.6 施工后复验）。

## 0. 判定线（验收草案）

1. **缺高档仍有画面（红线）**：最细基准与所需高档被预算淘汰后，引用行仍以低保真表示持续绘制——远景不因高档缺席消失（压测游历 + 与 6.4 现状对照读图：同预算下 6.4 整行消失、6.5 退到保底档）。
2. **回退零悬空（红线）**：引脚与采样两条回退路径在"高档缺失、基准缺失、只剩保底"各档位组合下零悬空——验证层零告警 + 读图无黑洞/花屏；`pick_lod_entry` 改造后终点恒有落点。
3. **上传按需**：脏行盘点仅针对需求档（含保底档），非需求档不再被顺手整组重传——盘点清单与需求集读数对账一致。
4. **预算/回收如实**：保底档进预算账或明确豁免口径（二选一钉明，读数如实）；淘汰循环永不触保底档；先撤引用后回收的幽灵防线在新可绘锚下仍闭合（零幽灵绘制）。
5. **A/B 与回归**：6.5 开关对照（关 = 6.4 现状：基准缺席整行暂缓）；既有判定线（4.1~4.4、5.x、6.1~6.4）零回退；零 VUID、WM_CLOSE exit 0、clippy 全净、库测试全过、resize×2 不炸。

## 1. 定位：现状与要补的东西

6.4 收官后驻留机制是"预测驱动"的：CPU 算需求集、置脏重传、超预算淘汰；GPU 查已发布的引脚表画。这条链缺一块**保底**：

- **可绘锚钉在最细基准上**：DrawList 组装以基准 mesh 驻留为可绘前提（`ash_renderer/src/driver/host/drawlist.rs:60`——`pool.resident(row.mesh.id())` 查无即整行暂缓）。基准被 6.3 mesh 预算淘汰后该行从在场环消失，画面上就是"这块世界没了"——不是降级，是蒸发。这正是 6.4 CPU/GPU 交互篇点名的"本仓基准一旦被预算淘汰就没有绘制保底"。
- **6.4 的"基准永驻"只在档位循环内**：fine_grained 需求集 `needed[0] = true`（`ash_renderer/src/scene/mechanism/residency.rs`，6.4.2 段）只保证档位淘汰不碰基准；但 6.3 的 mesh 预算淘汰循环按身份聚合、**不排除基准身份**——预算收紧时基准照样出账。两段口径打架，保底方向缺失的根源在此。
- **GPU 回退终点也在基准上**：`pick_lod_entry`（`ash_renderer/examples/shaders/build_indirect.wgsl`）从选档向细档（level 递减）找常驻条目，全哨兵时回退**对象记录的基准引脚**——基准缺席时这个兜底本身就没有落点（行已暂缓，进不了命令宇宙）。
- **上传不按需**：`flush_uploads` 对脏行盘点 LOD 组**全部缺席变体**（`ash_renderer/src/driver/upload.rs`，6.2.2 段），不按目标档过滤——"需求集为基准+所需档"是策略口径，不是上传动作的保证。6.5 要把两者对齐。
- **纹理侧无低清保底**：缺图采样落永驻白图 0 号槽（1×1 单级，`ash_renderer/src/vulkan/descriptors.rs`）——是"占位"不是"低清原图"；图像无"部分 mip 存在"的常规形状（5.4 mip 链整链一次上传全驻留）。低清保底形式见 §5 待决 4。
- **资产容器前提不变**：本仓步骤 6 无磁盘分块 IO 承诺——"预载"的可选范围见 §5 待决 5；RAM→显存上传与磁盘→RAM 预读是两个时标，不混写。

一句话：6.5 把可绘判定的锚从"最细基准常驻"迁到"最低保真常驻"，其余高档全部改为按需供给；这是 6.6"GPU 发现缺口→异步补货"能安全工作的先决条件——没有保底，任何请求延迟都直接变成画面消失。

顺序理由：账面与锚迁移先行（6.5.1→6.5.2 是本段主体，没有锚迁移其余全是 6.4 现状）；上传/淘汰修正随后（依赖新锚的语义），按需供给与纹理保底再次，验证通道最后。

**与冻结边界的关系**：对象表/材质表/标记环/命令环布局不动（6.2/6.3 同款边界）；`pick_lod_entry` 与 DrawList 是消费端逻辑改动，不动环布局；若待决 3 选"对象记录加保底引脚字段"，属对象记录语义扩容（5.1 增量重写链同款扩法），随施工列出解冻清单。

## 5. 待决问题（施工时钉明，不写死）

1. **保底表示形式**：复用最粗变体档（level 3）常驻——零新资产形状，但要求阶梯资产必须有最粗档（无档资产的保底语义另行钉明）vs 独立保底代理资产（测试几何体可程序化生成粗模，资产来源与登记方式随 6.5.1 钉明）——倾向前者起步。
2. **可绘锚迁移形状**：单锚（保底档驻留即可绘，基准降为普通高档）vs 双锚（基准或保底任一驻留即可绘）——单锚语义最简，但无档资产的行（非 LOD 组）需要保留基准锚；两口径并存的判定式随 6.5.2 钉明。
3. **`pick_lod_entry` 终点改造**：全细档缺失时改查保底档 b7 引脚（保底也是变体档，表内自洽）vs 对象记录新增保底引脚字段（消费端零查表）vs 维持基准回退、由 DrawList 保证基准在场（= 双锚退化，放弃"基准可淘汰"目标，不符本段动机）——倾向第一种。
4. **纹理低清保底形式**：常驻低 mip（无部分 mip 驻留先例，视图 mip 范围截断可行性随施工实测）/ 替换式低清整图（4.2 swap-on-commit 形状）/ 白图维持现状（本段纹理侧零施工，取舍入档）——交互篇已钉死"白图 ≠ 低清原图"这条口径，三选一之外不得用白图顶替。
5. **"预载"的范围**：交互篇"CPU 粗粒度预载"若指磁盘→RAM 预读，超出步骤 6 的 IO 承诺（无磁盘分块 IO）；倾向本段"预载"钉明为"资产容器已到货前提下的 RAM→显存按需供给"，磁盘侧预读留步骤 7 随真实资产评估。
6. **HLOD/chunk 代理**：多物体合并的低模远景代理（真 HLOD）不在本段——交互篇明确"不把最低单物体 LOD 称 HLOD"；需要时另立设计，不借本段立案越界。
