# Hi-Z遮挡原理：深度金字塔与保守遮挡判定

> 面向想弄清"为什么是这套形状"的读者：本文只讲原理与论证——每个保守取向为什么成立、方向为什么不可取反、滞后为什么可以接受。一帧里的数据怎么流转归[流程导读](Hi-Z遮挡流程：从渲染后深度到遮挡标记的各级账面.md)，判定线证据与施工钉子归[施工记录](6.1.1-6.1.6-Hi-Z遮挡施工记录：测试实体载具、深度金字塔、遮挡第二pass与A_B计量.md)。

## 0. 先立住三句话

1. **Hi-Z 遮挡回答视锥剔除答不了的另一半问题**：实例在视野内，但会不会一个像素都画不出来。
2. **做法**：把上一帧深度归约成逐级 2×2 取 MIN 的金字塔——每级 tile 记"该区域最远的已缓冲表面"；逐实例用 AABB 投屏 + 4 tap 比较，只有证明"全身都在一切已缓冲表面之后"才剔除。
3. **全部规则围绕一条不变式**：只删能证明画不出来的，一切存疑判可见。保守性是这套东西能免回读、免精确求交的全部本钱，也是取错方向就系统性错杀的原因。

## 一、问题：视锥剔除答不了的半边

视锥剔除只做空间几何判定：实例的包围盒与相机视锥六个平面有没有交集。它与场景里**别的实例**长什么样毫无关系，所以可以免费、精确、逐帧重算。

遮挡剔除引入了场景内容：实例在视野内，但前面立着一堵墙。回答"看得见吗"需要知道墙在哪——这恰恰是渲染的产物，而剔除决策发生在渲染之前。CPU 时代的三条老路各有代价：

| 路线 | 做法 | 代价 |
|---|---|---|
| 预计算 | PVS / portal / occlusion bake | 离线烘焙，动态场景失效（Unity 传统 occlusion culling 烘焙即此类） |
| 读回 | GPU 画一帧小深度，CPU 读回再决策 | CPU-GPU 同步点，流水线排空（回读墙：可见性本是流水线免费副产品，帧首决策点把它变成等待） |
| CPU 软光栅 | CPU 上光栅化代理几何求可见性 | 每帧 CPU 成本，几何代理维护 |

GPU-driven 路线的前提是**决策权整体搬到 GPU**（5.2~5.3 已完成视锥剔除与 indirect 闭环），剔除也必须留在 GPU 闭环内——不能为了"要不要画"把 CPU 拉回来等。Hi-Z 遮挡的答案：**用上一帧的渲染副产品（深度）当这一帧的证物**，测试本身是纯 GPU compute，零回读。

## 二、核心命题：用"最弱的遮挡者"下结论

深度缓冲是一张"已缓冲表面地图"：每个像素记着当前离相机最近的表面。剔除命题可以精确陈述为——

> 物体的投影区域内，**每一个**已缓冲表面都比它更近 → 它画出来的每个像素都会被覆盖 → 一个像素都不出 → 安全剔除。

"每一个"没法逐像素验，也不需要：对区域内的表面集合，只有一个标量结论是可靠的——**物体连其中最远的那个都够不着，就够不着任何一个**。用遮挡能力最弱的成员下结论：被最弱者挡住 = 被所有者挡住；反过来用最强者下结论（"被最近表面挡住"）只能证明"被某个表面挡住"，会错杀只是被部分遮挡的物体。

于是每个 tile 只需存一个数：区域内最远已缓冲表面的深度。本仓深度是 reverse-Z（近平面 1、远平面 0，clear 0），"远" = 值小，所以最远 = **MIN**：

- 归约取 MIN → tile 值 = 该区域遮挡能力的下界 → 用它判遮挡恒保守（[`hiz.rs:49`](../../../../ash_renderer/src/vulkan/hiz.rs) `reduce_tile_reverse_z`，单测钉方向）；
- 正向 Z（远 = 值大）的镜像写法是 MAX——**方向相反，取错 = 系统性错杀**：MIN/MAX 之差不是精度损失，是把"宁多画"翻转成"宁漏画"，这是 Hi-Z 全链最危险的单点，6.1 用 CPU 纯函数 + shader 注释同源双钉。

背景像素（clear 0 = 最远）混进 MIN 还顺带处理了"部分被挡"：tile 里只要有一个像素是背景，MIN 就被拉到 0，整个 tile 失去遮挡力 → 恒判可见。一堵只占 tile 99% 的墙也挡不住这个 tile 里的东西——这保守得近乎浪费，但方向永远正确。

## 三、金字塔：一摞粗细不同的挡板地图

对 level 0（全分辨率深度）做 2×2 MIN 得 level 1，再对 level 1 做 2×2 MIN 得 level 2……每一级都是"该粗细网格下、每格最远已缓冲表面"的挡板图。任意 level L 的一个 tile 覆盖 2^L × 2^L 个像素，是 level 0 上对应 2^(L+1) 见方区域的最远表面。

为什么需要多级而不是只查最细的一级：逐实例测试要 O(1)，tile 粗细要与物体投屏大小匹配（见 §四选层）——小物体用细 tile（覆盖准），大物体用粗 tile（tap 数不随物体大小增长）。金字塔就是把"任意粗细的挡板图"预计算成一摞，逐实例按需取层。

构建时机与取材的两个工程事实：

- **为什么归约成 R32F 而不是直接采样深度**：遮挡测试要往金字塔里写（storage image），深度附件不能当 storage 目标；且深度附件默认 usage 不可采样（6.1 立案时核实，须扩 usage + storeOp STORE）。所以金字塔是独立 R32F mip 链，level 1 的归约源才是深度附件（以 DEPTH_READ_ONLY 布局采样），L≥2 的源是上一级。
- **本仓 level 0 不派发**：bevy 的形状是 mip0 = 深度拷贝，本仓省掉这次全屏拷贝，可查层从 1 起（2px tile）。代价是小于 2px 的物体查不到更细的层——对遮挡判定无关紧要（2px 物体本来也难构成"必须剔"的收益）。

## 四、逐实例判定：投屏、选层、四点采样

测试对象不是真实几何而是**对象表里的 AABB**（occlusion.wgsl 读 ObjectRecord 的 aabb_min/max）。AABB 比真实几何胖——胖盒子的投屏更大、最近角点更近，两头都更难被判遮挡，方向保守。代价是剔除力折损：细长斜放的物体，AABB 可能大出几何好几倍。

判定分四步（[`occlusion.wgsl`](../../../../ash_renderer/shaders/occlusion.wgsl) `occlusion_verdict`，CPU 参照 = hiz.rs 纯函数三件 + occlusion.rs 投屏参照）：

1. **投屏**：AABB 8 角点经 model × view_proj，透视除法后转像素矩形。必须在角点级投屏——透视不是仿射，"世界 AABB 投屏再取包围矩形"与"逐角点投屏再取包围矩形"不等价。任一角点 w ≤ 0（在相机平面背后）→ 恒判可见。
2. **选层**：`level = ceil(log2(AABB 像素最大边))`，clamp 进级数、下限 1。设最大边为 s，则 2^(L−1) < s ≤ 2^L：tile 边长 ≥ AABB 边 > tile 半边 → AABB 每轴至多横跨 2 个 tile → 以投屏矩形左上角锚定的 2×2 tap **必覆盖全部相交 tile**。过覆盖（tap 读到 AABB 之外的 tile）只会让 MIN 更小、遮挡者更弱 → 更保守。这一式是"4 tap O(1)"成立的全部前提，多 tap、逐 tile 循环都不需要。
3. **物体深度参照**：8 角点 NDC z 取 MAX = 最近角点。clip z/w 对盒是拟仿射（分子分母皆仿射、w > 0 时分母恒正），比值沿盒内任意线段单调，极值必在角点——所以角点 MAX 就是整个盒的深度值上界（最优点）。用它判遮挡意味着"连最近点都过不了才剔"。越过近平面的角点（z > 1）自动把物体推成可见：occluder ≤ 1 < z_max，比较式天然处理，无需特判。
4. **比较**：`obj_max < occluder` → 剔除。reverse-Z 下含义：物体最近角点比覆盖区域内最远的已缓冲表面还远 → 全身都在一切表面之后。

**保守性总账**——每种存疑情形的落点：

| 情形 | 落点 |
|---|---|
| 角点 w ≤ 0（背后/过近） | 可见 |
| 越过近平面（z_max > 1） | 可见（比较式天然） |
| tap 越界/离屏 clamp | 可见（坐标 clamp 后不引入假遮挡） |
| tile 含背景（0 混入 MIN） | 可见 |
| 深度相等（obj_max == occluder） | 可见（`<` 严格比较） |
| AABB 比几何胖 | 更难剔（两个方向都保守） |

没有任何一条路径能把"可能可见"判成"剔除"——**相对于参照深度**。

## 五、时间维：判定参照是"上一帧"，不是"这一帧"

这是 Hi-Z 遮挡最需要诚实声明的一条。§二的全部保守论证有个隐含主语：**参照深度**。测试保证的是"相对上一帧深度不会被错杀"，不是"相对当前帧真值不会错杀"。

为什么只能如此：遮挡测试发生在**绘制之前**（它的结论决定画不画），而深度是绘制的产物——决策时刻，当前帧的真值尚不存在。这不是实现取舍，是逻辑顺序：剔除决策永远只能引用过去的渲染结果。

本仓的滞后是 2 帧：金字塔 ×2 帧槽轮转，帧 N 的遮挡测试读同槽 s，其内容是帧 N−2 的归约输出。为什么不是帧 N−1：帧 N−1 写的是另一槽，其 fence 在帧 N 首尚未通过；同槽 s 的 fence 在帧 N 首已过——**读两帧前的数据是免费的，读一帧前的要新增同步**。滞后加深的代价见下。

滞后引入的新错误方向（相对当前真值）：

- **遮挡物移开**：墙在帧 N−2 挡着、帧 N 已移开 → 物体按旧深度判遮挡，晚一帧出现。画面上是"出现迟滞一拍"，不是永久丢失。
- **相机快速转动**：整个参照深度大面积失效，错杀从"一帧税"退化成"持续黑屏"。

对第二条，OcclusionGate 做了闸门：比较本帧相机与两帧前（与滞后窗对齐），两帧窗累计位移超 0.5 或旋转超 15° → 整段跳过遮挡 dispatch（b3 保持视锥纯结果、b6 全可见），稳定两帧后自动恢复。它只关最刺眼的窗——物体自身快速移动的错杀不在闸门内（6.1 遗留项）。闸门的设计判断是：滞后在参照深度失效时会从"可接受的税"变成"不可接受的错杀"，fallback 把失效窗口收敛到"宁可全不剔"。

金字塔未就绪（首建/resize 重建后 warmup 2 帧）走同一个 fallback 出口，理由同构：内容未就绪的参照深度比没有参照深度更危险。

## 六、复杂度账与收益形状

每帧成本两笔：**构建** O(像素)——全屏逐级归约链（GPU 计时单列 `gpu_hiz_ms`）；**测试** O(实例) 常量——每实例 8 角点投屏 + 4 tap，无循环、无逐像素。总账与场景实例数线性、与遮挡复杂度无关——这正是它适配 GPU-driven 大场景的原因。

收益形状由场景决定：

- **受益**：实例多而小、深度层次复杂（前景遮挡后景）——大量实例被 4 tap 便宜地杀掉。
- **不受益**：少数铺满屏幕的大物体（AABB ≈ 全屏 → tap 必含背景 0 → 恒可见，天然自动退出，不亏）；近平面单层平坦场景（没东西可挡）。

所以剔除量是场景形状的函数而非功能常量——6.1 验收场景"遮挡开档 7 剔 1"只是该场景的读数。这也是 A/B 开关（`occlusion-set`）与 cull_stats 遮挡分列存在的意义：收益是测量对象，不是验收目标。

业界同构对照：UE 的 HZB culling、Unity GPU Resident Drawer 的 GPU Occlusion Culling，形状都是"深度金字塔构建 + 逐对象包围盒保守测试 + indirect 消费"，与本仓同构、亦与 bevy `occlusion_culling.wesl` 参照同构。差异在工程外延（UE 加屏幕覆盖率阈值与部分遮蔽计数等），不在核心命题。

## 七、不主张与边界

- **保守非精确**：本方案保证"不剔错"（相对参照深度），不保证"剔尽"——tile 粗、AABB 胖、背景混 MIN 都在持续削弱剔除力。剔除量下限是 0。
- **屏幕空间法的天花板**：证物只有上一帧画面内的表面。被相机外/屏幕外的遮挡者挡住的物体判可见（多画，方向仍保守）；这是所有 HZB 方案共有的，不是本实现缺陷。
- **不管透明**：透明不写深度，本来就当不了挡板；被透明挡住的前向不透明物体照常绘制。
- **收益规模未压测**：1 帧滞后的视觉伪影程度、大场景净收益（扣除归约成本后）都是遗留项，归后续段。
