# 施工计划：GPU 稀疏缺口请求拆解（6.6，立案）

> 2026-10-20 立案（用户指令，纯文档立案）。6.5/6.6 追加段的第二份段施工计划——前置依赖 **6.5 施工收官**（保底先可靠，顺序不可倒置，见[步骤 6 README](../README.md)边界段）；保底缺席可画成立后，GPU 报缺口才有"延迟无害"的前提。本计划保持立案时点原貌，状态追记只在本行追加。
>
> **一句话说明**：这一段让 GPU 在选档/查驻留索引时把"本帧命中而未驻留"的资产身份写成稀疏缺口清单——GPU 侧去重、聚合优先级并限额，每隔若干帧经 readback 环跨帧异步读回，CPU 把缺口与 6.4 相机预测、显式预载合并后按预算/IO/冷却裁决上传；CPU 不当帧等 GPU，读回延迟期间 6.5 保底持续可画，丢请求只推迟升级不丢画面。本段不做外置 VT 页表，不做 GPU 发起 IO，不做当帧同步等待闭环，缺口清单不驱动淘汰（补货专用）。对应[路线图](../../学习目标实现步骤.md)步骤 6 追加段 6.6。
>
> 场景口径：沿用 6.2～6.4 定例（BRP 生成 + Python 脚本持久化，测试几何体与程序化资产），真实资产场景归步骤 7——6.6 的 A/B 对照与升级时延计量在超预算游历场景下取证。

## 0. 判定线（验收草案）

1. **请求稀疏且有界（红线）**：缺口清单只含"本帧命中且未驻留"的身份，同身份多实例去重后条目数有硬上限——读数对照场景全部资源数/逐实例理想档数，证明不是全量广播（交互篇钉死的反面=“每帧广播全部资源需求”）。
2. **无当帧等待（红线）**：CPU 消费的是已完成旧帧的缺口清单（fence 纪律），当帧提交不被 GPU 读回阻塞；读回延迟期间 6.5 保底持续可画——延迟注水负例下读图无空洞、无消失。
3. **溢出与丢失可恢复**：限额溢出/读回丢帧只推迟升级，不炸、不永久哑火——溢出计数读数如实，后续帧缺口重报自然覆盖（无 ACK/无重试协议，持续信号模型）。
4. **CPU 权威不变**：上传/预算/淘汰裁决仍在 CPU（6.3/6.4 管理器同体扩展）；缺口只补货——负例：缺口清单恒空时淘汰与回收照常工作（缺口≠淘汰信号）。
5. **A/B 与回归**：GPU 缺口请求与 6.4 CPU 预测 A/B 成组对照（请求量/升级时延/上传字节数）+ 既有判定线（4.1~4.4、5.x、6.1~6.5）零回退 + 零 VUID、WM_CLOSE exit 0、clippy 全净、库测试、resize×2 不炸。

## 1. 定位：现状与要补的东西

6.5 收官后（目标态）：缺席有保底可画、高档按需上传、CPU 掌管预算与供给——但需求信号仍是 **CPU 单源预测**（6.4 重算期望档 + 相机启发式）。GPU 每帧真实知道的东西比 CPU 多：哪些实例被遮挡（b6）、实际选了哪档（b8）、哪些引脚缺席（b7 哨兵）。6.6 把"命中且缺席"这个 GPU 一手差集变成稀疏清单读回 CPU，作为预载的第三输入源——**GPU 出意见、CPU 拍板**（6.3 原理篇钉定的混合形态，自主权阶梯第③层的跨帧缓存环形状）：

- **判定点现成**：选档 compute 写 b8、build_indirect 查 b7 哨兵——"期望档 ∧ 未驻留"的差集在 GPU 执行时已经算过一次，缺的只是把它记下来。
- **读回先例现成**：标记环 b3/b6、档位环 b8 全是 HOST_VISIBLE compute 写 + 帧奇偶 + fence 纪律宿主直读（`ash_renderer/src/vulkan/occlusion.rs:137`）——6.6 读回环是同族新成员（专用小载荷 + 低频消费），不是新机制；5.5 的 QUERY_RESULT_WAIT 挂死钉子反向钉死纪律：读回一律 fence 等旧帧，不 busy wait。
- **缺口身份是真空**：对象记录 48B = 引脚三字段 + 材质槽 + AABB（`ash_renderer/src/vulkan/instance_table.rs:94`），**无资产身份字段**——GPU 现在报不出 AssetId；实例槽号是唯一可写身份，CPU 经账本反查 AssetId（待决 1）。
- **去重结构半边现成**：标记环逐槽位图是先例；原子 append 有界列表无先例（待决 3）。
- **CPU 合并入口现成**：`residency_tick` 请求/淘汰两分支就是裁决点——缺口清单是新输入源（策略层扩展），不是第二本账（4.3/4.4 执行底座不变）。
- **为什么不是 6.4 的升级替代**：缺口清单与 CPU 预测是两个输入源不是两条路线——A/B 对照（判定线 5）要求两者并行可开关；合并后的裁决永远在 CPU。

一句话：6.5 解决"缺席时不坏"，6.6 解决"什么时候变好"——升级时机从纯 CPU 猜测改为 GPU 一手证据参与，供给权不挪窝。

顺序理由：身份与判定点先行（没有可写身份缺口清单无从谈起）；去重限额次之（有界性是读回安全的前提）；读回环再次（通道依赖前两步的载荷形状）；CPU 合并与验证通道最后。6.6.1~6.6.3 是本段主体。

**与冻结边界的关系**：对象表/材质表/标记环/命令环布局不动（6.2/6.3 同款边界）；缺口环是新成员（set2 compute 专属 binding 续号 + HOST_VISIBLE 帧奇偶纪律，照 b7/b8 扩法）；若待决 1 选增字段，对象记录语义扩"旁路身份表"（记录布局不动、旁路新表——随施工列出解冻清单）；residency_tick 参数表继续膨胀按既有 `#[expect(too_many_arguments)]` 惯例或收拢。

## 5. 待决问题（施工时钉明，不写死）

1. **缺口身份表达**：GPU 写实例槽号（CPU 经账本反查 AssetId——零新字段，同身份多行重复靠 CPU 侧去重兜）vs 旁路身份表（GPU 可索引的资产号，位图去重的前提，新表新形状）——倾向槽号起步（CPU 反查便宜、去重天然在 CPU 合并点），位图路线留压测证明 CPU 去重成本不可接受时再评估。
2. **标记执行点**：选档 pass 附带写（离差集最近）vs build_indirect 写（查 b7 哨兵处）vs 独立小 pass（开关归因最干净）——随 6.5 落地后的 pass 形状定。
3. **去重结构**：GPU 原子有界列表（append + CPU 去重，结构新）vs 逐身份位图（需身份可索引，依赖待决 1）vs 槽号位图（实例槽粒度去重、CPU 再聚合——标记环先例最近）——倾向槽号位图起步。
4. **读回频率与深度**：每 N 帧固定低频（交互篇口径，倾向）vs 脏触发；readback 环深度与"等哪个旧帧"（fence 纪律内最旧可用帧）——随 6.6.3 钉明；QUERY_RESULT_WAIT 挂死教训=禁 busy wait。
5. **优先级载荷**：缺口条目纯身份（CPU 按账本行距离自排序——倾向，GPU 侧零额外计算）vs 带距离/屏占比权重（GPU 出优先级意见）——先纯身份，行业"GPU 出意见"的完整形（UE 流送优先级小 buffer）留升级口子。
6. **6.4 CPU 预测去留**：A/B 三态（判定线 5 要求并行可开关——硬约束）+ 默认形态（双源合并 vs 缺口优先预测兜底）随 6.6.4 钉明；6.4 路径永不删除（关闭档=既有基线语义）。
