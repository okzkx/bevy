# 粗细粒度流送的 CPU 与 GPU 交互：现状与稀疏请求

> 本篇对照 6.3/6.4 **已经实现的链**与后续 6.5/6.6 的**待施工目标**。只讨论 mesh LOD 与整张贴图的驻留，不把页级虚拟纹理的 feedback 当成本仓 6.4 的通道；页级机制另见[外置拓展条目 6](../../外置拓展需求.md)。流程细节见[6.3 流程篇](../6.3-粗粒度流送/粗粒度流送流程：从预算账到请求与淘汰动作的各级账面.md)和[6.4 流程篇](细粒度流送流程：从整资产账到子资产条目的各级账面.md)。

## 0. 四个问题不能合成一句“GPU 要什么就加载什么”

1. **期望画哪档**：6.2 GPU compute 按投屏尺寸与迟滞写档位环 b8（level 0 最细，level 3 最粗）。它不直接命令 CPU 上传资产。
2. **当前能画哪档**：GPU 的 `build_indirect` 查 b7 引脚表（`index_count=0` 代表未驻留），从所选档号**向 0 递减**找在场的更细档；如果都缺，回退对象表的最细基准引脚。这个回退只对基准 mesh 仍驻留、已进入 DrawList 的行成立。
3. **什么值得进出显存**：6.3/6.4 的 CPU `residency_tick` 读账本、相机与驻留缓存自行决策；当前**没有把 b8、遮挡标记或任何 GPU 请求读回 CPU**。
4. **何时能上传**：CPU 侧资产容器已有内容时，脏行经 `flush_uploads` 重传并发布；若资产未到货，4.3 的就绪账保持待处理。步骤 6 没有磁盘分块 IO、跨帧上传优先级队列或“需要时立即加载”的承诺。

这里没有“GPU 每帧向 CPU 广播所有美术资源明细”这条链，也没有“GPU 已决定目标档，所以 CPU 自动知道目标档”的隐式传递。GPU 的绘制决策与 CPU 的驻留策略可各用同一公式，但它们通过**已发布的资源表**间接衔接，不通过当帧请求回读衔接。

## 一、当前 6.3：按资产身份搬，CPU 决策、GPU 消费

`residency_tick` 在 CPU 上把引用行按**基准 mesh 的 `AssetId<Mesh>`**聚合，以最近引用行距离判断是否进入请求半径，以视锥外优先、距离远优先排序预算淘汰。一个身份可能被多行共享，但 `SceneChunk` 本身不是运行时请求/淘汰单元；当前也没有整块 HLOD 低模远景代理。

```text
CPU：账本行 + 相机 + MeshPool 驻留账 + mesh 字节预算
     ├─ 非驻留、半径内、冷却已过 → 引用行置脏
     └─ 超预算 → ejection 账 → flush 移除驻留 → 等在飞使用 → 回收区间
CPU：flush 扫脏行 → 从 CPU 资产容器找数据 → 上传/提交 → 更新对象表与引脚
GPU：DrawList 只枚举基准 mesh 可驻留的行 → compute 选档/组装命令 → 绘制
```

关键是两种缺席不能混为一谈：**基准 mesh 缺席 → 整行不进入 DrawList**；**基准还在、某个 LOD 变体缺席 → GPU 表内向更细档回退**。因此现有 6.3 不是“相机走远后保留最低 LOD 持续绘制”的大世界分块流送。预算 0 表示不限；预算不足时半径内资产也可能被淘汰，并不保证处处有画面。

## 二、当前 6.4：CPU 计算档位目标，GPU 不回传档位

6.4 沿用同一个 CPU 管理器，另对登记 LOD 组计算 `{0, 各引用行期望档}` 的**目标需求集**。期望档在 CPU 上以 `aabb_screen_rect + lod_raw_level` 重算，使用相同阈值和屏幕尺寸，但**不读取 GPU 的 b8，也不复刻 GPU 的迟滞状态**；请求半径与淘汰冷却承担另一层时间过滤。level 0 是最细基准档，只是不被 6.4 的“淘汰非需求变体”循环处理；它**仍可能被 6.3 的基准 mesh 预算淘汰**，绝非无条件最粗档常驻。

需要把目标与上传实际动作拆开：管理器发现目标档缺失会给引用行置脏，然而当前 `flush_uploads` 对这个脏行**盘点整组所有缺席的非基准变体**，不按目标档过滤。因此“目标集为基准+所需档”是策略口径，不是“显存里只会有这两档”的保证；逐档淘汰可能与随后脏行补传相互影响，真实场景需要单独测。

贴图是另一列预算：CPU 可整张淘汰，GPU 缺图时采样永驻白图 0 号槽；**没有 mip 逐级驻留或低清贴图逐级变清**。当前贴图预算内主动请求分支从“已驻留图片聚合”中寻找缺图，不能单靠该分支发现已经淘汰的图；行因其他原因置脏时，材质盘点可重传。白图/恢复的两态读图不证明任意淘汰贴图都会自动回访恢复。这是尚需补齐的请求来源，不是本文暗示已实现的闭环。

## 三、为什么这仍是 GPU-driven 绘制，而不是 GPU-driven IO

GPU 每帧负责可见性、期望 LOD、查 b7 有效引脚、生成 indirect 命令并绘制；CPU 管相机启发式需求、预算、资产容器、上传提交与安全回收。两侧决策的用途不同：GPU 决定**这帧已有资源怎么画**，CPU 决定**后续哪些资源进入或离开显存**。本仓的 6.4 只是 CPU 预测的档位驻留，不是 GPU 需求直接触发 IO。

“读取 GPU 需求”并非逻辑上绝对不可行；不可取的是本帧 GPU 算完、CPU 阻塞等结果、上传完再让**同一帧**继续画的同步闭环。跨帧读取少量结果而不等待，可以只影响画质提升的时机，不阻断绘制提交；但前提是资源缺席时有可用的降级表示。当前最细基准常驻**不是**行业常见的最粗保底——本仓基准一旦被预算淘汰就没有这一条绘制保底。

## 四、后续施工分界：6.5 先建保底，6.6 再让 GPU 出稀疏请求

**6.5（待施工，低保真保底与高档按需）**：建立可验证的最低保真 mesh 表示在 GPU 常驻，把可绘判定的锚从最细基准迁到保底代理；CPU 负责粗粒度的预载/资产供给与上传，高精度 mesh 档按需驻留，缺高档时 GPU 绘制低档。纹理侧需明确“低清保底”是常驻低 mip、替换式低清图还是白图占位——现有白图不等于低清原图，且目前无部分 mip 驻留。必须配套改 fallback 搜索方向/终点、LOD 表、对象记录与回收时序，不能只改 `needed[0]`。磁盘→RAM 的预测预载与 RAM→显存的上传是两个时标；“几帧后画高清”只在数据已就绪且上传完成时成立。更远的 HLOD/chunk 代理是否合并多物体需单独设计，不把“最低单物体 LOD”直接称为 HLOD。

**6.6（待施工，GPU 需求驱动的细粒度流送）**：在 6.5 保底已可靠后，GPU 在选档/选资源时查**可见的驻留索引**：命中且驻留就画目标档；命中而缺席则画可用保底，并写**缺席资产身份**。按资源身份在 GPU 侧位图去重、聚合优先级并限额，而非每帧把场景全部资源或逐实例理想档回传 CPU。每隔若干帧把小的缺口清单复制到 readback ring，CPU 等已完成的旧帧结果、不阻塞当帧，再与相机启发式预载和显式预加载合并，由 CPU 按预算、IO 带宽、冷却与依赖决定实际供给；上传/提交后更新 GPU 驻留索引，后续帧自然选到高档。这**仍是 GPU→CPU 回读**，但没有同步等待；丢失/延迟请求只会推迟升级，不影响当帧绘制。稀疏缺口列表只适合**补货**，不能直接推出“哪些已驻留资源无人需要”——淘汰还须 CPU 视锥/距离、缓存年龄、预载窗口等信息，或另设计使用反馈。

```text
6.4 已有：CPU 预测需求 → 置脏/上传/淘汰 → GPU 查已发布引脚绘制
6.5 待做：低保真 GPU 常驻 + CPU 预载/按需高档 → 缺高档画低档
6.6 待做：GPU 标记缺席且需要的 ID → 去重/限额 → 跨帧异步读回
          → CPU 合并其他信号并裁决 → 上传 → 更新驻留索引 → 后续帧升级
```

判定线：6.5 要证明最细资产被淘汰时仍能绘制低保真表示（零悬空引脚/采样、预算如实收账）；6.6 要证明 GPU 请求列表只含缺口、同身份多实例去重、有上限与溢出恢复、**无当帧 CPU 等 GPU**、反馈延迟时回退持续可画，并与 6.4 CPU 预测 A/B 对照。具体数据布局、缓存分层与测试规模应在各段立案时核实，不在本篇宣称已经实施。
