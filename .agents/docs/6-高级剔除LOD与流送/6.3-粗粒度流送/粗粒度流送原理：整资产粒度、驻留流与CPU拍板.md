# 粗粒度流送原理：整资产粒度、驻留流与CPU拍板

> 面向想弄清"为什么是这套形状"的读者：本文只讲原理与取舍——粒度到底指什么、"流"流的什么、驻留决策为什么留在 CPU 而不是做成 GPU 驱动。一帧里账目怎么流转归[流程导读](粗粒度流送流程：从预算账到请求与淘汰动作的各级账面.md)，判定线证据与施工钉子归[施工记录](6.3.1-6.3.6-粗粒度流送施工记录：驻留管理器、超预算游历与A_B基线.md)。

## 0. 先立住三句话

1. **粒度 = 驻留决策的进出单位**：6.3 的预算候选是基准 mesh 的一个 `AssetId<Mesh>`，它的顶点+索引整体进出；这不是把一组 LOD 的四个独立 Mesh 资产绑成一个不可分割的资源包。6.4 才对变体档逐档算需求，并给整张贴图增加独立预算。
2. **流的是驻留，不是文件**：资产内容早已在 CPU 侧容器里（4.x 加载完毕），没有磁盘分块读取、没有渐进解析；流动的是"数据在 CPU 内存 ↔ GPU 显存之间的驻留关系"，由相机驱动、被预算约束。搬运动作零新通道——请求 = 引用行脏标走既有重传链，淘汰 = 出账走既有回收账。
3. **决策留在 CPU 是层级分工**：剔除/LOD 是"帧内、实例级、GPU 产出 GPU 消费"的决策，必须进显存闭环（5.2/6.2 已做）；驻留是"跨帧、资产级、执行端在 CPU"的决策——权威账本与 IO 都在 CPU，把决策搬上 GPU 等于自造回读墙。GPU 在流送里的正确岗位是**需求信号生产者**（出意见），不是拍板者。

## 一、粒度：进出的最小单位

流送要回答"什么东西可以不在显存里"，粒度就是这个"东西"切多细——它是整套管理的记账单位与决策单位。6.3 的裁决（[residency.rs](../../../../ash_renderer/src/scene/mechanism/residency.rs) 模块注释钉明）：

- **按资产身份聚合**：同一个基准 mesh 被 N 个实例引用，只算一份驻留账、同进同出；如果 chunk 中恰好共享这一身份，效果像 chunk 一起进出，但代码没有按空间棋盘格加载，也没有 HLOD 远景代理。
- **组的"位置" = 引用行的最近距离**：所有引用该 mesh 的实体里，离相机最近那个的距离。
- **测试场景 unique 资产 = 粒度退化成行级（最细可测）**：独立资产模拟不出"共享身份同进出"，但能把"世界大于驻留"压得更狠——压测场景用 `--unique` 就是这个原因。
- **预算按这个单位收账**：mesh 驻留字节（顶点+索引）一列，超支按"视锥外优先、距离远优先"逐个整资产淘汰。

粒度阶梯的定位：

| 粒度 | 进出单位 | 状态 |
|---|---|---|
| 6.3 mesh 预算 | **基准 mesh 身份**整体进出，按引用行聚合 | `fine_grained=false` 时不逐档淘汰变体；脏行上传会盘点该组缺席变体 |
| 6.4 档位管理 | **level 1..3 的变体 Mesh**逐档进出；level 0 是最细基准档 | `fine_grained=true` 时按 `{0, 各行期望档}` 算需求；基准档不参与这一段的逐档淘汰，但仍可能被 6.3 的 mesh 预算淘汰 |
| 6.4 贴图预算 | **整张贴图**独立进出，缺席用永驻白图槽 | 没有部分 mip 驻留、没有页级寻址 |

这里的"细"是**变体资产级 + 整图预算级**，不是 mip/page 级。6.3 的基准 mesh 一旦被预算淘汰，该行在 DrawList 暂缓，不会靠常驻最低档继续画远景；这与"所有资源最低 LOD 永驻"的完整大世界方案不同。

## 二、流式：流的是驻留，不是文件

驻留管理器自己**零新搬运通道**（纯 CPU 侧资源层新账，零新 Vulkan 形状）——它只做决策，搬运全部复用既有链：

```
请求（进）: 半径内 ∧ 非驻留 ∧ 冷却已过 → 引用行 mark_dirty（脏标）
             → flush_uploads 既有重传链：容器取资产 → 转换 → 上传 → commit
             → 4.3 就绪语义：就绪才发布（不会画到半份资产）

淘汰（出）: used > 预算 → 视锥外∧距离远逐个 eject_mesh → 卸载回收账
             → 下帧 flush 出驻留条目 → 停尸房排空（等在飞 draw）→ free list
             → 撤引用在前、回收在后：行未驻留 = DrawList 暂缓不进在场环
```

所以"流式"的全部表现是**账本上多了一个每帧 tick 的策略层**：`residency_tick` 挂 Last、先于 flush_uploads（动作进同一帧上传账），每帧做三件事——请求侧、淘汰侧、冷却走账。它不碰 Vulkan、不碰上传逻辑、不碰 DrawList；那些都是 4.1/4.3/4.4 已经建好的链路。段名里"粗粒度"对"细粒度"的分工在此：**流送 = 给增量系统加一个"什么东西值得驻留"的动态策略**，不是新修一条数据通道。

流式的可观测行为（压测四站环游、预算 = 全量 1/3 实测）：

1. **走近数帧内出现**：进入请求半径 → 脏标 → 重传链消化（就绪才发布，有搬运延迟且如实计量）。
2. **走远+超预算消失**：先从 DrawList 撤引用（画面消失），下帧才回收显存——顺序反了就是 5.3 幽灵对象老毛病，靠"枚举源头"语义自动兜住。
3. **预算边界不抖**：刚淘汰的身份进 60 帧冷却表——站在预算边界上不会"淘汰→重请求→再淘汰"逐帧拉锯；回访多等冷却，如实进计量。
4. **装不下有缺口**：预算不足时即使请求半径内的基准 mesh 也可能被淘汰，相关行在 DrawList 暂缓；`over_budget` 只表示候选淘汰后仍超预算，**不能**用它判断请求区是否已全部满足。6.2 的表内回退仅适用于基准仍驻留的可绘行，不能代替整行缺席时的 HLOD 远景代理。

## 三、为什么 CPU 拍板：执行端、账本与成本形状

剔除与选档的结果当帧由 GPU 组装 indirect 命令消费，所以计算留在 GPU 侧；驻留决策则要结合 CPU 账本、显存预算、上传和回收。当前 6.3/6.4 的资产已在 CPU 容器中，**没有磁盘按需流送或 GPU→CPU 需求读回**。管理器在 CPU 上逐帧走访账本，作半径请求和预算淘汰；`flush_uploads` 再负责上传/回收，GPU 根据更新后的表绘制。这不是说 GPU 不可能参与驻留决策，而是本阶段没有引入一条跨帧读回链。

当正式场景引入磁盘 IO、压缩包或 GPU 稀疏需求时，CPU 仍需掌握预算、依赖和上传调度。GPU 可以产生小规模请求建议并异步读回；**异步读回并非禁止事项**，禁止的是为了本帧继续绘制而同步等待 GPU 的结果。请求的滞后只能由已有驻留资源兜底，而不能假装资源在同帧就绪。

**本仓现状**：6.3 管理器在 CPU 上按 mesh 资产身份聚合引用行，用相机距离和视锥估计需求，再与 `MeshPool` 的驻留账核对；请求、预算淘汰和冷却都在 `residency_tick` 执行。6.4 的期望档位也在 CPU 侧用 6.2 的投屏公式重算，**没有从 GPU 读回档位请求**。GPU 的选档结果用于本帧绘制；`build_indirect` 另查 b7 的驻留引脚，在选中档缺席时从该档向**更细的低编号档**寻找，最后回到 level 0 基准档。选“想画哪档”和选“现有哪档可画”是两步，不能把后者说成 GPU 不知道驻留。

**可选升级（尚未实现）**：若真实资产场景证明 CPU 近似需求不够，可让 GPU 在选档后对照一份只读驻留索引，只为**所需但缺席**的资产置位，再在 GPU 去重、计优先级、限额，跨帧异步读回少量缺口 ID 给 CPU。CPU 仍把它与相机启发式、显式预载合并，掌握预算、IO、上传和淘汰；稀疏缺口只供补货，不能单靠它推断“没人需要”的淘汰集合。此处**仍然发生回读**，但绘制靠已驻留档回退，不等待这次读回返回；也不能直接把现有 b8 当作 CPU 已收到的请求。是否划算要实测聚合、读回延迟和 CPU 处理成本。页级纹理需求机制归[外置拓展条目 6](../../外置拓展需求.md)，不属于本段的 mesh 驻留链。
