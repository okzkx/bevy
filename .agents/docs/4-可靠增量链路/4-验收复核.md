## 2. P1：影响收官的主要问题

### 2.1 问题 1：贴图原槽重写必须避开仍在使用该槽的提交

**状态：未关闭。证据：源码与 Vulkan 规范核对；本轮未做 GPU 竞态复现。**

落点：[descriptors.rs:604–650](../../../ash_renderer/src/vulkan/descriptors.rs#L604)、[upload.rs:468–474](../../../ash_renderer/src/driver/upload.rs#L468)。

`rebind` 将 `UPDATE_AFTER_BIND` 解释为“GPU 正在使用该槽时也可覆盖，读到新旧任一个都安全”。这个前提不成立：该标志允许绑定之后、提交之前的更新被后续提交观察，但不授权覆盖仍被未完成命令使用的描述符。规范对 UAB 的消费窗口明确为提交时至 shader 执行之间，并要求在可能开始消费至命令完成期间不改写其内容。

当前路径先提交新图上传，随即重写旧纹理槽。此前的 draw 可能仍读取该槽，也没有等待新图的上传票据。下一帧再等待 fence 并销毁旧图，只约束了销毁，不能追溯修复已经发生的覆盖。

**修复方向与复验条件**：覆盖前完成相关图形使用等待，或发布新槽并延迟回收旧槽；复验需覆盖旧 draw 在飞、新图上传未完成的交叠窗口，不能只以旧图仍存活或零 VUID 判通过。规范来源见第 7 节。

### 2.2 问题 2：共享采样器必须具有独立于单张贴图的寿命

**状态：未关闭。证据：源码所有权与发布、回收路径核对；本轮未做 GPU 悬空访问复现。**

落点：[images.rs:437–453](../../../ash_renderer/src/vulkan/images.rs#L437)、[descriptors.rs:565–592](../../../ash_renderer/src/vulkan/descriptors.rs#L565)。

多张图按功能键共享采样器槽，但槽内 `VkSampler` 的本体由某张 `GpuImage` 持有。`publish/rebind` 会把共享槽写成最新发布图的 sampler。若 A、B 共享槽，槽最终指向 B 的 sampler，卸载 B 时，代码因 A 仍共享而保留槽，却会将 B 整体放入停尸房销毁；A 后续仍引用的 sampler 因此可能悬空。等待已有帧完成不等于未来存活引用已经消失。

此外，最后使用者检查只扫描 `ImageCache`，没有计入 fallback 和字体图集；采样参数改变后的旧键槽回收也没有完整闭合。上述问题属于同一所有权边界：保留槽号不等于保留槽内资源。

**修复方向与复验条件**：按共享采样器自身管理所有权与引用；覆盖 A/B 共享后先卸载实际句柄所有者、fallback/图集共享、采样键改变三个场景，确认后续绘制引用有效且旧槽最终可回收。

### 2.3 问题 3：回收排空还必须证明上传已经完成

**状态：未关闭。证据：源码与冻结的双条件契约核对；本轮未做最小化期间的 GPU 回收复现。**

落点：[upload.rs:149–155](../../../ash_renderer/src/driver/upload.rs#L149)、[images.rs:407–428](../../../ash_renderer/src/vulkan/images.rs#L407)、[frame.rs:169–178](../../../ash_renderer/src/driver/host/frame.rs#L169)。

停尸房排空只等待图形帧 fence，资产退休时却丢掉了上传票据。正常绘制帧会等待最新上传，所以正常路径容易表现为双条件同时满足；但窗口最小化时 `flush_uploads` 仍可提交上传，`draw_frame` 会直接返回，不产生覆盖新上传的图形提交。

此时再卸载或替换资源，全部图形 fence 完成不代表独立 transfer 队列已经完成上传，旧图可能在上传仍使用它时销毁。网格回收账同样没有保留票据；本文不将每种网格复用路径都写成已运行复现。

**修复方向与复验条件**：退休记录保留并检查上传完成凭据，或在回收安全点显式收口上传侧；最小化期间连续加载、替换、卸载后，再恢复窗口，验证销毁前双条件均成立。

### 2.4 问题 4：失败恢复不能依赖两个无序系统谁先运行

**状态：未关闭。证据：本轮 CPU 复现与调度注册核对。**

落点：[asset_readiness.rs:236–239](../../../ash_renderer/src/scene/mechanism/asset_readiness.rs#L236)、[asset_readiness.rs:289–304](../../../ash_renderer/src/scene/mechanism/asset_readiness.rs#L289)、[asset_events.rs:194–198](../../../ash_renderer/src/scene/mechanism/asset_events.rs#L194)。

`track_asset_failures` 与 `propagate_asset_changes` 都只排在 `update_ledger` 后面，彼此无明确顺序。前者收到 `Added` 时清除失败标记，后者必须看见该标记，才会给已经出队的引用行重挂脏标。资源可变借用保证不会并发访问，却不保证所需的先后顺序。

对同一失败身份写入同一 `Added` 事件，直接执行当前源码得到：

```text
先运行 propagate_asset_changes：dirty=1
先运行 track_asset_failures：dirty=0
```

**修复方向与复验条件**：由单一入口统一执行复活与引用行重挂，或明确保证其必要顺序并移除相互抵消的处理；恢复结果不得随合法调度顺序变化。

### 2.5 问题 5：动态加载入口应将非法路径返回为协议错误

**状态：未关闭。证据：本轮直接调用真实加载封装复现 panic；未经运行中 BRP 发包复测。**

落点：[object_ops.rs:140](../../../ash_renderer/src/scene/mechanism/object_ops.rs#L140)、[remote_assets.rs:173](../../../ash_renderer/src/remote_assets.rs#L173)；官方解析落点为 [path.rs:109–112](../../../crates/bevy_asset/src/path.rs#L109)。

`load/reload` 直接将外部字符串交给 `AssetServer`。Bevy 的 `String → AssetPath` 转换会调用可 panic 的解析器；`file.gltf#` 会立即产生 `MissingLabel` panic，而不是异步加载失败，因此不会经过 `AssetLoadFailedEvent` 的出队处置，也不会正常返回 BRP 参数错误。

本轮在 `load_mesh_rebind` 上复现 `panicked=true`，探针通过 `catch_unwind` 捕获，不是宿主已正确处理该错误。

**修复方向与复验条件**：统一用 `AssetPath::try_parse` 校验后再加载、重载，返回协议错误；非法标签和 source 语法均应满足零 panic、宿主存活、无半创建对象。

## 3. P2：状态机和计量的确定问题

### 3.1 问题 6：每次转换拒绝都要记失败，不能受日志去重控制

**状态：未关闭。证据：源码路径推演；本轮未运行完整上传系统复现。**

落点：[upload.rs:286–292](../../../ash_renderer/src/driver/upload.rs#L286)，贴图同类分支为 [upload.rs:309–315](../../../ash_renderer/src/driver/upload.rs#L309)。

`expel_mesh/image` 位于 `warned.insert(id)` 条件内。资产第一次转换失败后，`Modified` 可以将其复活；若修改后仍是不支持的内容，日志去重集合已包含身份，第二次拒绝就不会再次进入 failed 集，脏行因而持续重试。

**修复方向与复验条件**：将状态转换移出日志去重条件；“拒绝→Modified 复活→再次拒绝”后，应重新失败出队，转换次数不再逐帧增长。

### 3.2 问题 7：材质恢复分支被早退条件截断

**状态：未关闭。证据：本轮 CPU 复现。**

落点：[asset_events.rs:211–245](../../../ash_renderer/src/scene/mechanism/asset_events.rs#L211)。

材质 `Added` 恢复时加入 `modified_materials`，但后续早退条件没有检查该集合。若本帧只有材质恢复，系统清除了失败标记却没有重挂引用行，材质中新引用、尚未驻留的贴图不会进入上传链。该问题即使在问题 4 的有利执行顺序下仍发生。

本轮结果：`failed=false`，`dirty=0`。

**复验条件**：只发送材质恢复事件，引用行重新入队，材质的全部必要贴图腿能继续完成准备。

### 3.3 问题 8：未曾加载成功的资产不能只靠 Removed 清理失败记录

**状态：未关闭。证据：本轮 CPU 复现，包含官方资产释放事件测试。**

落点：[asset_events.rs:188–193](../../../ash_renderer/src/scene/mechanism/asset_events.rs#L188)，材质与贴图同类分支；官方释放语义见 [assets.rs:491–511](../../../crates/bevy_asset/src/assets.rs#L491)。

加载失败且从未进入 `Assets` 的资产，在最后强柄释放时只发 `Unused`，不发 `Removed`。当前读侧只在 `Removed` 清理失败记录，`Unused` 只计数，反复请求不存在路径并删除引用会使失败身份集合持续增长。

本轮两项互证：未到货保留柄释放得到 `Unused=true / Removed=false`；向项目读侧发送 `Unused` 后，失败标记仍保留。

**复验条件**：从未到货的失败身份失尽引用后退出失败集合；重复 N 轮，当前失败集规模回基线，同时保留累计失败计数。

### 3.4 问题 9：同身份卸载后重插需要重新驱动上传

**状态：未关闭。证据：本轮 CPU 复现，GPU 后果由上传消费路径核对。**

落点：[asset_events.rs:188–198](../../../ash_renderer/src/scene/mechanism/asset_events.rs#L188)；卸载消费见 [upload.rs:155–172](../../../ash_renderer/src/driver/upload.rs#L155)。

强柄不会阻止显式 `Assets::remove`。对仍被实体引用的资产执行 `remove → insert`，读侧收到 `Removed + Added` 后安排回收旧驻留，但 `Added` 只有命中 failed 集时才重挂行。原本干净的行仍然干净，CPU 新内容存在，GPU 驻留却会被回收而没有新的上传驱动。

本轮结果：`retired=1, dirty=0, cpu_asset_exists=true`。这也否定了源码与施工记录中“能发 Removed 必然无行引用”的无条件表述；该推论只适用于强引用归零的释放路径。

**复验条件**：同帧及跨帧的显式移除、同身份重插均能恢复上传，其他共享引用者同步更新且没有驻留空洞残留。

### 3.5 问题 10：事件统计应区分当帧值、累计值和当前存量

**状态：未关闭。证据：本轮 CPU 复现与统计赋值核对。**

落点：[asset_events.rs:240–275](../../../ash_renderer/src/scene/mechanism/asset_events.rs#L240)。

空事件帧在刷新统计前返回，`asset_events.frame`、`frame_dirty_rows` 保留上一次事件帧的非零值；`asset_invalidations_total` 被赋为当前失效集合长度，而不是累计失效数；部分事件也未进入标称的总事件计数。

本轮先发送一个 `Modified`、消费失效凭据并清空消息，再运行空事件帧，仍得到 `events=1, dirty_rows=1, invalidations_total=1`。

**修复方向与复验条件**：当帧字段每帧刷新，累计量只增，当前集合规模另列；每种事件均按约定计数。稳态帧应归零，累计差值应能和驱动操作逐项对账。

### 3.6 问题 11：多项 mutate 应先校验，再执行修改

**状态：未关闭。证据：本轮 CPU 复现。**

落点：[asset_ops.rs:104–118](../../../ash_renderer/src/scene/mechanism/asset_ops.rs#L104)。

接口注释承诺“单项失败整体拒绝，不留半完成”，实际却边校验边修改。请求同时给出合法 `base_color` 与不存在的 `slot_base_color_from`，颜色先变更，随后返回错误而不回滚。

本轮结果：`returned_error=true, color_changed=true`。

**修复方向与复验条件**：执行前统一预校验，或明确采用部分成功语义并返回准确结果。若维持现有整体拒绝承诺，组合请求失败后，资产内容与事件副作用都不应留下半完成状态。

| 4.4 回收与热重载 | 回收出口、free list、真实文件重载通道 | 共享所有权、双条件排空、失败账清理、卸载重插 |

### 4.2 架构正面评价

- 对象账、资产身份账、GPU 驻留账分开，以身份去重，不因多个实体共享而重复上传。
- BRP 只做协议入口，操作函数不直接维护账本；UI、BRP、其他代码写入方可共用变更发现机制。
- Bevy 负责加载与 WorldAsset 实例化，ash 负责 GPU 生命周期，没有另造一套宿主。
- 上传准备从每帧全量快照消费改为脏行驱动，是实质性的增量改造；DrawList 仍有逐对象成本，不能称“零 CPU 每对象成本”。
- Vulkan 操作失败基本接入统一错误通道，未重新堆出大量业务错误处理样板；非法路径 panic 是该正面结论的明确例外。

**需要补齐的核心不是更多功能，而是：状态转换由明确责任方完成、共享资源有正确所有者、销毁动作有完整完成凭据。**
