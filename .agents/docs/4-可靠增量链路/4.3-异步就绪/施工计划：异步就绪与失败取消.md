# 施工计划：异步就绪与失败取消（4.3）

> 2026-10-12 立案（用户开工指令），**未施工**——本文为立案时点原貌，任务拆解与判定线均为草案，施工时修订并转段 README 任务面板。对应[路线图](../../学习目标实现步骤.md)步骤 4 第三段，接在已收官的[4.2 资产增量](../4.2-资产增量/README.md)之后：4.2 管"资产已到货之后内容变了"这条通道，本段管"资产还没到货"这条时间线——pending、就绪门、失败与取消，以及到货瞬间的有效性检查。4.2 计划 §5 明确留口：异步到货（pending/票据状态机/就绪门/失败与取消）归本段。

## 0. 判定线（验收草案）

1. **延迟到货不读空槽**：资产未到货期间，引用它的实体按现行"未到货跳过、行保持脏标"处置，画面照常渲染既有内容；到货帧内容正确上屏，不读空槽、不崩宿主。
2. **失败可见且不无限重试**：加载失败（路径不存在等）后，失败身份出重试队列、不再每帧重试（防僵尸脏行）；失败对计量与读数可见（失败数、失败原因），宿主存活不 panic。
3. **等待期间删除或换柄不错误复活**：资产到货时账本行仍有效才转换上传——行已清账（实体 despawn）不上传不错误复活对象；行已换柄只服务新句柄，旧句柄到货不误入账。
4. **零变化零上传不回退**：4.1/4.2 稳态基准（稳态帧零盘点零上传、事件不误伤）保持；pending 数、等待帧数、失败数、到货数、上传字节分开报——不把"零上传"说成"零事件读成本"。
5. **既有判定线零回退**：3.5 三模式截图对照、全程零 VUID（含拆 Device）、WM_CLOSE exit 0、clippy 全净、4.1 五类变更、4.2 判定线（同柄改内容/共享去重）全量回归。

计量口径对齐步骤 4 完成标准：pending 数、等待帧数（按资产或按行，施工钉明）、失败数、到货数、上传字节、处理耗时分开报。

## 1. 定位：现状与要打通的东西

4.2 之后上传链的形状是"账本脏行 → 按资产身份查驻留（查无**或失效**才传）→ 转换上传 → 提交成功发布票据"。本段面对的是这条链的前置问题：**资产还没到 CPU 时怎么办**。立案时点核实（详见文末附录），现状是三处隐式兜底加三处缺口：

**现状兜底（已有，隐式）**：

- flush_uploads 对 `Assets::get` 查 `None` 的行跳过计数（"异步加载未到货，下帧脏行重试"），行保持脏标跨帧重试（`ledger` 的 dirty 集即跨帧重试队列）——"等"这件事成立，但没有账面。
- "上传完成才可使用"由 3.2.4 的单调 timeline 票据承担：提交成功才发布票据，图形侧 draw 挂票据信号量等待——GPU 侧的就绪门**机制已现成**，本段票据侧只补账面与计量，不新增 Vulkan 机制。
- 到货时实体已 despawn 的情形，现状部分天然安全：行由 despawn 通道清账，flush 只盘点在账的行——但这条安全链**未经针对性验证与计量**，换柄交错帧的次序语义也未验证。

**缺口**：

- **失败失明**：`AssetLoadFailedEvent` 全仓零读侧（grep 零命中）。加载失败的资产永不到货，脏行每帧重试永不成功——僵尸重试队列每帧照付成本，失败本身只有"未到货计数悄悄变大"这一种不可读表现，与判定线"失败可见"直接冲突。
- **pending 无账面**：未到货只是 flush 内每帧的临时计数，没有跨帧 pending 集，等待帧数、到货延迟不可观测；"稳态 pending 是否清零"没有读数口径。
- **动态加载无入口**：运行期没有任何"加载新资产"的驱动——`AssetServer` 只有启动场景加载在用（`scene/content/world_asset.rs`），BRP spawn 只能克隆既有柄。验收"延迟到货"需要一条可驱动的异步加载链（3.11 范围修订已把"动态加载新资产"并回 4.2/4.3 的"异步到货（加载）"，落点在本段）。

## 2. 拆解：账面 / 失败取消 / 驱动入口

| 线 | 交付 | 落点 |
|---|---|---|
| ① pending 账面与就绪门 | 未到货资产的显式状态账（pending 集）取代 flush 内隐式计数；就绪判定（Assets 命中，`LoadedWithDependencies` 事件作事件侧锚点）；等待帧数/到货计量 | `scene/mechanism/`（账面归属施工钉明）+ `driver/upload.rs` |
| ② 失败与取消 | `AssetLoadFailedEvent` 读侧：失败身份出重试队列 + 错误落账 + 计量；取消 = 等待期间实体 despawn / 换柄 / 资产 `Removed` 时不上传不入账；到货瞬间有效性检查（不读空槽、不错误复活） | `scene/mechanism/asset_events.rs`（事件读侧扩展）+ `driver/upload.rs` |
| ③ BRP 动态加载方法族 | 运行期触发异步加载的 BRP 入口（新实体挂新资产 / 替换既有实体句柄）+ 资产状态读数（pending/failed 计数入 `increment_stats` 族） | `remote_objects.rs` / `remote_assets.rs` + `tools/brp.py` |

三线是一次状态机补全的三个面，同段施工不拆段（4.1/4.2 惯例）；任务拆解见 §3。

## 3. 任务拆解草案（开工时转段 README 任务面板）

| 任务 | 内容 | 验收锚点 |
|---|---|---|
| 4.3.1 pending 账面与就绪门 | 未到货资产的显式状态账（账本行内状态 vs 独立资源，施工钉明）；flush 与账本对账共用同一份口径；等待帧数计量 | §0.1/§0.4 可测；pending 数稳态清零 |
| 4.3.2 失败与取消读侧 | `AssetLoadFailedEvent` 读侧接入；失败出队与错误落账；到货有效性检查（行在、句柄未换才传） | §0.2/§0.3 可测；负例宿主存活 |
| 4.3.3 BRP 动态加载方法族 | 加载驱动（路径→`AssetServer.load`→挂实体/换柄）+ 资产状态读数；`tools/brp.py` 子命令（沿 BRP 优先纪律） | 延迟到货有驱动入口；读数进计量报告 |
| 4.3.4 验收回归 | 判定线全量 + 计量报告 + 既有判定线零回退 | §0 全过 |

顺序理由：先有账面（知道谁在等、等了多久），再接失败与有效性（把"永远等不到"和"等到时人已不在"接住），最后补驱动入口（能触发异步链做验收）。4.3.3 依赖 4.3.1 的状态口径定形后写。

## 4. 测试方案：BRP 驱动与证据形态

**驱动纪律沿 4.1 定案：变更驱动一律优先 BRP**（[测试规范](../../../rules/测试规范与方式.md)"扩建优先级"条）。本段要新驱动的是"触发异步加载并观察就绪"，对象侧五方法与 4.2 mutate 已够用：

| 驱动 | 手段 | 状态 |
|---|---|---|
| 动态加载新资产 | BRP load 方法（路径→load→挂新实体或替换既有实体句柄） | ⬜ 本段新增 |
| 加载失败 | 同方法传不存在路径 / 非法扩展名 | ⬜ 本段新增（复用同入口） |
| 等待期间删除/换柄 | load 后 BRP despawn / replace 与到货竞速（时序组合施工钉明） | ⬜ 本段新增（组合既有方法） |
| 资产状态读数 | increment_stats 族扩展（pending/failed/到货计数） | ⬜ 本段新增 |

**证据形态**（判定线 §0 的证据来源）：

- **计数日志定状态机**：pending 数跨帧曲线（未到货帧>0、到货帧清零）、等待帧数、失败数；关键读数=失败后 pending 归零且不再重试（每帧重试计数停止增长）。
- **截图定画面**（PrintWindow + 读图，按《画面功能视觉验证》执行）：到货前实体不可见或占位（现行语义施工钉明）、到货后内容正确上屏。
- **负例**：不存在路径、等待期间 despawn、等待期间换柄——宿主存活、不错误复活对象、错误按[两 Tier 宪法](../../错误处理/错误处理体系：两Tier思想与优雅退出.md)分级（非必要不 panic，具体分级施工钉）。
- **回归矩阵**：3.5 三模式、零 VUID 含拆 Device、WM_CLOSE exit 0、clippy 全净、4.1 五类变更、4.2 同柄改内容与共享去重零回退（重点：pending 重试与 Modified 失效叠加不串账）。

## 5. 待决问题（施工时钉明，不写死）

- **pending 账面位置**：账本行内加状态字段 vs 独立资源（AssetId→状态映射）；与 4.2 的 `AssetInvalidations` 的关系（并存还是统一成"资产状态账"）。
- **就绪判定依据**：`Assets::get` 命中即就绪 vs 等 `LoadedWithDependencies`（依赖链完整性——glTF 材质/贴图是依赖资产，主资产先到时依赖可能未齐）；两条口径的差异对本宿主加载形态是否实质成立，施工探针钉明。
- **失败重试策略**：一次失败即出队（报账不重试）vs 有限次重试；失败后文件被修复的恢复路径是否依赖 4.4 热重载（倾向：本段只出队报账，自动恢复归 4.4）。
- **"延迟到货"的可复现驱动手段**：真实大文件（构造大 glTF/贴图）vs 人工延迟（调试 hook/自定义 loader）——可复现性与真实性取舍施工钉明。
- **WorldAsset 整场景异步链**：启动场景的两段式加载（loader 草稿 World→反射展开）对依赖到货次序的现行处理是否已覆盖本段判定线，开工先探针钉明，避免重复造官方已有。
- **到货帧与采集时序**：路线图边界"CPU 已就绪且在本帧采集前可见的变更应进入本帧准备"——读侧/flush 挂点是否满足，同帧还是次帧生效，施工验证钉明（4.1/4.2 均为次帧生效同拍）。

## 6. 边界：不在本段主张什么

- **回收**（`Removed`/`Unused` 后的 GPU 资源回收、池区间归还、停尸房/孤儿区间销毁常态化）→ 4.4；本段对 `Removed`/`Unused` 只主张"取消上传、不入账"。
- **热重载**（文件监听、WorldAsset 重载回归、失败资产修复后自动恢复）→ 4.4；本段不接文件监听。
- **在飞资源延迟销毁与槽位复用**（graveyard 排空时机常态化、pool 容量变化）→ 4.4；本段复用 4.1.1 帧侧等待闸门现状，不改其责任边界。
- **票据的 Vulkan 机制**（timeline 信号量、图形侧等待、复用前查计数）3.2.4 已建，本段零新增 Vulkan 代码方向，只补 ECS 侧账面与计量。
- **实例数据迁 GPU / GPU-driven**（实例表/indirect）→ 5.1/5.3，本段不动 push constant 现状。
