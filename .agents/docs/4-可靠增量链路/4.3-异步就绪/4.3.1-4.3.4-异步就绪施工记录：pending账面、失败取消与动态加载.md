## 1. 4.3.1 pending 账面与就绪门

**面板要求**：未到货资产的显式状态账取代 flush 内隐式计数；就绪判定口径钉明；等待帧数计量。
**实现原理**：pending 是**资产身份粒度**的账（跨行共享身份只记一份），账本行是实体粒度——两层各自键控（与 4.2 失效凭据按 AssetId 同理），故落点=独立资源 [`AssetReadiness`]（scene/mechanism/asset_readiness.rs）不进账本行。发现侧只有 flush_uploads 一个写入点（mark_pending/arrive/expel/reconcile），它是最先撞见"查无"与"到货"的地方。
**过程与落点**：`asset_readiness.rs`（账面本体 + 失败读侧，292 行）；`upload.rs` 盘点段三态判定改造（完成/失败/pending 逐腿判）+ 转换段 mark_pending + commit 段 arrive + 帧末 reconcile（含空批早退路径）。
**待决落定**：
- **就绪判定=`Assets::get` 命中，逐腿递归**——Mesh/Image 内容自包含；StandardMaterial 的依赖由 flush 逐五槽判（材质本体就绪而槽内贴图未到=贴图腿各自 pending）。`LoadedWithDependencies` 的"递归依赖全齐"是容器级语义（glTF/WorldAsset 整体），本宿主账本行只挂叶级资产，不消费该事件（维持 4.2 的只计数口径）。探针实证：运行期 load glTF 子资产到货即完整可用，容器级依赖链不经过账本行。
- **pending 账面位置=独立资源**：不进账本行（行是实体粒度，pending 是资产身份粒度）；与 `AssetInvalidations` 并存不合并——失效凭据是"已驻留要换内容"的负向凭据，pending 是"未驻留在等"的正向账，生命周期相反。
- **材质 pending 沿用行级计数**（材质无 GPU 驻留内容，无身份账可记；材质失败走 failed 集身份记账）。

## 2. 4.3.2 失败与取消读侧

**面板要求**：`AssetLoadFailedEvent` 读侧接入（立案时全仓零读侧）；失败出队与错误落账；到货有效性检查。
**实现原理**：**读侧只记账不裁决**——失败读侧（`track_asset_failures`，PostUpdate after update_ledger）把失败身份进 failed 集 + 计量 + 一次可见 warn；行是否出队由 flush 盘点结合**整行状态**统一判定：行有 pending 腿（任何资产还在到货路上）就保持脏标，无 pending 腿且有失败腿才出队（清脏标）——失败身份不再进重试批，防僵尸脏行。失败 ∪ 转换/规格拒绝统一进 failed 集（同为"不会再传的身份"）；`Added`/`Modified` 事件复活身份（重载/修数据重试放行，自动恢复上限归 4.4）。
**过程与落点**：失败读侧在 asset_readiness.rs；盘点三态判定与失败出队在 upload.rs；`clear_dirty` 语义不变（pub(crate)，flush 独占调用）。
**待决落定**：
- **失败重试策略=一次失败即出队（报账不重试）**：无引用者的失败也计数（事件不误伤的镜像面——失败不因无人等待而失明）；文件修复后自动恢复归 4.4 热重载，本段重试放行口只留 `Added`/`Modified` 复活。
- **取消语义=当帧失去全部引用行即出账计取消**：despawn 清行 / 换柄改指的次帧 reconcile 判定（pending 身份不在 marked 集里）。到货后无行可服务=不上传不入账，"错误复活对象"在结构上不可能（flush 只盘点脏行，行没了就没有上传凭据）。
- **错误处理分级**：失败读侧 warn+记账（Tier①，不影响运行）；flush 内 Vulkan/账本失败维持既有 Tier② 冒泡口径不变。

## 3. 4.3.3 BRP 动态加载方法族

**面板要求**：运行期加载驱动 + 资产状态读数 + brp.py 子命令（BRP 优先纪律）。
**实现原理**：操作本体在 object_ops（可复用层，与将来 egui 面板共用）：`load_mesh_rebind`（换到既有实体）/`spawn_with_loaded_mesh`（克隆源结构挂新实体）/`load_image_slot`（换目标材质 base_color 槽）；BRP 薄壳 `ash_renderer/load_mesh`（entity|source 二选一）与 `ash_renderer/load_image` 在 remote_assets；读数扩 `increment_stats` 的 readiness 段（十项分列）。受理即返回加载中柄（AssetId 已定型），pending/到货/失败经 readiness 段对账。
**过程与落点**：remote_assets.rs（+94 行）、remote_objects.rs（+36 行）、object_ops.rs（+98 行）、remote.rs 注册、brp.py（+41 行，`load-mesh`/`load-image` 两子命令）。
**共享材质语义钉明**：`load_image` 原位改写目标材质的 base_color 槽，全部引用者同变（与 4.2 mutate 贴图槽同语义）——实测：水贴图换槽后共享 LensesMat 的护目镜与异步克隆体同变。

## 5. 钉子汇总（四枚）

1. **glTF 子资产显式 load 触发一次 Modified 重传**：`server.load("x.glb#Mesh0/Primitive0")` 到货后管线追加一个 `Modified` 事件（bevy_gltf/bevy_asset 上游行为），4.2 通道照常失效→换条目重传一次（152B，同内容）。4.2 机制正常对账非缺陷；若将来做上传去重可按"Added 后首帧内的 Modified 折叠"优化，归 4.4 评估。
2. **宿主 ImageLoader 只开 png 支持扩展**（bevy 默认 feature 口径，jpeg/ktx2 拒载）——失败路径如实收账（"invalid image extension"），属宿主 feature 口径非 4.3 缺口；要支持 jpeg 给 bevy 依赖加对应 feature 即可。
3. **失败探测有延迟窗口**：路径不存在的失败在 ~0.4s 后才被 AssetServer 探测到（IO 任务链），期间身份 pending 等待（25 帧）——账面如实记录这段等待，"失败"不是瞬时判定。
4. **brp.py 的 entity 解析**：BRP 实体号字符串（如 `439v0`）经 serde 反序列化直接得 Entity，自定义方法与官方方法同口径。
