# AssetId 变更语义：两条变更通道、Id 稳定性取舍与驻留失效实现

> 2026-10-10 入档，4.2 开工前机制讲解篇（当日两轮设计问答沉淀）。回答三个问题：同 Id 改内容时各层账本动不动、为什么 AssetId 锚身份不锚内容（"新内容换新 Id"为什么不行）、4.2 的实现要动多少同步机制。配套立案文档见[施工计划：资产增量与同柄内容变化](施工计划：资产增量与同柄内容变化.md)。

## 0. 判定线

1. **两条变更通道判定特征相反**：换柄 = 动实体行、不动资产内容（4.1 已收官）；改内容 = 动资产条目、不动实体行（4.2 本段）。
2. **同 Id 改内容，实体账本一行不动**：`InstanceRow` 存的是 `Handle<Mesh>` 不是 GPU 槽位，绘制侧每帧按 AssetId 现查驻留——重传发布后所有引用者自动画新内容，零实体侧动作。
3. **失效与重传按 AssetId 记账**：N 个引用者只有一份重传。失效若错挂在实体层，退化成 N 份重传——做错。
4. **AssetId 锚"身份"不锚"内容"**：热重载、路径去重、依赖图都要求 Id 先于内容存在且跨内容变化稳定；"内容变→换 Id"会让热重载退化成全库重接线。
5. **不可变边界落在"跨入 GPU 驻留"处**：CPU 侧 `Assets<T>` 容器可变（ResMut 系统级互斥，不靠不可变性）；内容一旦上传成驻留版本即为只读，要改 = 新版本换上 + 旧版本等在飞读完退场。`AssetEvent::Modified` = 版本号 +1 的广播。
6. **4.2 对底层同步零新增机制**：上传批/timeline 票据/UAB 表/帧侧等待闸门全部复用；唯一的新排序决策（旧区间替换时机）用 4.1.1 既有闸门解决。

## 1. 两条变更通道：换柄 vs 改内容

渲染器里有两条都会改"实体画什么"的通道，账面动作正好相反：

| | 换柄（4.1 对象增量） | 改内容（4.2 资产增量） |
|---|---|---|
| 触发 | 实体的 `Handle<Mesh>` 改指向另一个 AssetId（BRP replace / 组件替换） | `Assets::get_mut` 原位改同 Id 资产，触发 `AssetEvent::Modified` |
| AssetId 变不变 | 实体行指向的 Id 变 | Id 不变，内容变 |
| 实体账本（InstanceLedger） | 该实体行重绑（`rebound_rows`）+ 脏标重挂，**只有它一行动** | **一行都不动**：柄没变，行里关联原样有效 |
| 资产层驻留账 | 仅当新 Id 未驻留才上传；旧 Id 引用减一（回收归 4.4） | 该 Id 驻留条目**失效 → 重传恰一份**（新区间/新图 publish 到同名下） |
| 其他引用者 | 不受影响（各画各的柄） | **全部自动吃到新内容**——经"每帧现查" |
| 生效机制 | 行脏标 → flush 重传/换绑 | 失效标记 → flush 重传 → publish 覆盖同 Id 槽位 |

"零实体侧动作"能成立的机制锚点有两处（0.20.0-dev checkout，本仓库 ash_renderer）：

- `InstanceRow` 存柄不存槽位（`scene/mechanism/assets/ledger.rs:41`：`pub mesh: Handle<Mesh>`）——行是 AssetId 锚定的，不是区间锚定的；
- 绘制侧**每帧现查**，不缓存槽位（`driver/host/frame.rs:232`：`pool.resident(row.mesh.id())`）——重传 publish 完成后，下一帧所有引用者现查拿到的就是新内容。

## 2. 为什么 Id 锚身份不锚内容

`AssetId` 的本职是**引用身份**：谁指着它、强引用计数归谁、同路径重复 load 去重到哪。若改成"内容变了就换 Id"，三个具体麻烦：

1. **热重载退化成全库重接线**。文件监听发现磁盘资产变了，热重载的全部价值是"引用者什么都不知道、也不用知道"——实体、组件、材质槽里的柄原样不动，下一帧自动是新内容。换 Id 则每个持有者都要被通知、被改写。
2. **路径去重要求 Id 先于内容存在**。同一文件加载两次必须得到同一资产——Id 实质是"路径的身份"，在内容读出来之前就得定下来。内容寻址（哈希即 Id，git 形状）对存储层优雅，但 git 没有"活引用"：每次引用都重新解析，对文本文件便宜，对运行期已焊进实体组件的引用是灾难。
3. **依赖图与元数据挂在旧 Id 上**。glTF 场景资产持一族子资产柄、loader 的 meta/label 体系按路径键控——内容一变全员换代，依赖图整体重建。

行业实际形状是"**Id 稳定 + 内容原位替换**"：Unity 的 `.meta` GUID 在 reimport 前后纹丝不动，动的只是 GUID 底下的导入产物，GPU 侧贴图/网格被原位替换；UE 对象 GUID 同构。用户主张的"新内容新 Id"是纯不可变值语义（FP/内容寻址存储），在"引用可廉价重解析"的世界赢，在"引用已被运行期持有"的世界输。

同时要承认：**"加载后只读"是主流路径，`get_mut` 是少数派逃生舱**。引擎必须留这条逃生舱（编辑器改参数、程序化修改、热重载一定会用），具体游戏可以赌不用——不接文件监听、不写 `get_mut`，4.2 这条通道一辈子零流量，享受的仍是纯只读模型；只是引擎得把通道修好等着。

## 3. 不可变边界：CPU 容器可变，GPU 驻留只读

"不可变数据免同步"这笔账两边都对，只是分界线不在资产容器，在**上传边界**：

- CPU 侧 `Assets<T>` 是 World 里的独占资源（ResMut），系统级互斥，改它不需要不可变性；
- 真正被多阶段并发消费的是 GPU 驻留内容——而它恰恰是只读模型：内容跨过上传边界进池区间/图集，就是一份不可变版本，想改不是原地写，是**新版本换上来、旧版本等在飞读完退场**；
- `AssetEvent::Modified` 在这套结构里的真实身份就是**版本号 +1 的广播**：上游容器被改了，下游所有按"Id → 不可变内容"建的缓存（MeshPool、ImageCache、描述符槽）必须知道并自己重建版本。

映射到本仓库：GPU 侧从 3.2 起就是纯只读模型（驻留缓存按 Id 键控、查无才传、传完不动），静态场景稳态零上传是白拿的（4.1 判定线）。代价是引擎赌了一个假设——"Id 命中驻留 = 内容没变"——当前 `flush_uploads` 对同 Id 内容变化天然失明（`driver/upload.rs`：`pool.resident`/`image_cache.resident` 查无才进批）。**4.2 的全部工作就是给这个赌注补账单**，且不破坏 GPU 侧只读模型：重传走的仍是"新内容做成新版本 → publish 换上"，不是对在飞内容原地写。

## 4. 实现方式：动哪些层、动多少

**各资产类型的驻留内容与失效范围**：

| 资产 | GPU 驻留内容 | 内容变化的牵连 |
|---|---|---|
| Mesh | 池区间（顶点/索引） | 区间替换或原地重传（施工钉明）；账本行持柄不变，无实体侧动作 |
| Image | `ImageCache` 驻留 + bindless 槽位 | 重建/重传后槽位重发布，引用它的材质槽与实体跟着换 |
| StandardMaterial | 参数走每帧 UBO 统一给值（`frame.rs:235-243` 直读），**无驻留内容**；驻留的只有贴图槽指向的 Image 与采样器槽 | 参数变化画面自动生效（可作事件读侧的观测锚）；贴图槽变化 → 关联 Image 失效传播 |

**新增代码的性质**（4.2 施工计划 §3 任务拆解的机制依据）：

- `AssetEvent` 读侧：一个读消息的系统（`MessageReader<AssetEvent<A>>`），纯 CPU 簿记，零 GPU 同步；
- 驻留失效：把某 AssetId 的缓存条目标成过时——标记位级别；
- `flush_uploads` 判定条件从"查无才传"改成"**查无或已失效才传**"——一个或条件；
- 资产→实体关联重挂脏标：与对象五类变更并轨进同一份脏行队列（4.1 定案"写侧刻意不碰账本"，本段加的是发现侧第二条入口）。

**同步面：全部复用既有机制**：

| 4.2 需要 | 已有机制 | 出处 |
|---|---|---|
| 新内容安全进 GPU | staging 环 + transfer 队列 + timeline 票据——重传就是再走一遍既有上传批 | 3.2 上传链 |
| 画到新内容前等它就绪 | draw 提交本就等上传票据（`ALL_COMMANDS` timeline） | 3.2/3.4 `record_frame` |
| 描述符表在飞可更新 | UAB + 只写新槽 publish 纪律 | 3.3.4 |
| 销毁旧资源前等帧侧读完 | `FramePool::wait_all_inflight` 帧侧等待闸门 | 4.1.1（4.2 前置闸门） |
| 变更进账本 | 脏行队列 | 4.1 |

**唯一的新排序决策**：改 mesh 内容时"新拷贝写区间"必须排在"在飞 draw 读旧内容"之后。两条路都走既有闸门：原地重传前先等在飞清空（简单，那一帧 stall 一次），或迁新区间 + 旧区间挂延迟回收（不 stall，回收动作归 4.4）。这不是新机制，是 4.1.1 帧侧等待闸门的第二次兑现——责任边界契约（上传票据 ∧ 图形最后使用双条件）在 3.2 就冻结了，4.2 的区间替换是同一契约的第二次兑现。失败路径也干净：3.3.4"提交成功才 publish、失败不留半更新"纪律保证重传失败时条目保持旧内容或保持失效，不出现一半新一半旧。

复杂度真正的落点不在同步，在**回收时序的边界划分**：旧区间/旧 VkImage 何时可安全销毁——这部分划给 4.4，4.2 只保证"旧内容在没人读之前不被销毁"。
