## 1. F24 根因与修复（面向下一个改这段代码的人）

**症状**：属性面板按住旋转 DragValue 拖动时物体闪烁（姿态跳变）。

**根因**：面板拖拽期间每帧"整组回写"——旋转三元组 = 快照值 + 被拖框的 egui 累加值。快照的欧拉角是四元数经 `to_euler(YXZ)` 的**一个表示分支**；被拖分量的 egui 内部值累加域钉在**按下帧的分支**。拖拽分量跨过欧拉分解分支边界（±90°/±180°）时，`to_euler` 会翻转另两位（±180°）——下一帧的回写把"拖拽值（旧分支域）"与"快照（新分支）"混合，`from_euler` 合成出错误旋转；再分解、再混写形成双稳态振荡 = 闪烁。分支翻转与拖拽反馈耦合时还会失稳跑飞（48° 显示 vs 132° 实际）。

**修复**（`overlay/entity_tree_window.rs` + `ui.rs`）：新增 `TransformDragCache` 资源——旋转任一框被按住（`Response::dragged() || is_pointer_button_down_on()`）的整段期间，欧拉三元组缓存冻结在按下帧的表示分支，DragValue 只改被拖的那位；松手（本帧无人按住）缓存作废，下帧从快照重建。平移/缩放分量相互独立、无表示分支问题，维持原快照回写。正确性依据：欧拉任一分量 ±360° 周期等价，"同分支三元 + 单分量替换"恒为合法分解，混分支则否。

**测试协议**（可复跑）：`tools/brp.py` mouse 族点选树节点 → mouse-move 到旋转框 → 按住 +60 步 ×5pt 慢拖 + `tools/capture_window.py` 连拍读图。修复前 d 系列（闪烁帧）与修复后 e 系列（0→50→185→240 单调）均在 `.temp/`。

## 2. 钉子

1. **DLP 全屏海报遮挡是 PrintWindow 的死穴，副显示器是活路**：主显示器被 CcWaterMarkWindow 全屏盖住时 PrintWindow 整幅白图，TOPMOST 提顶无效（提顶带内 Z 序赢不了轮播重刷）；**把目标窗口挪到副显示器后 PrintWindow 正常**（`.temp/f24_clean1.png` 起全部截图实证）。视觉验证遇白图先查遮挡、再试副屏。
2. **egui DragValue 拖拽 + 欧拉回写的分支混写**是通用陷阱：任何"立即模式控件值域 + 每帧快照回写"组合都要问一句"这个量的表示是否多分支"。
3. **SetWindowPos 的 flags 漏 `SWP_NOSIZE` 会把窗口改成 0×0**：本段实验中 `0x0014`（应为 `0x0015`）把宿主窗缩成 0×0，winit 进静默让路态——挪窗脚本一律带 NOSIZE；0×0 后直接弃实例重启，恢复尺寸也未必回得来。
4. **PowerShell 脚本块作 EnumWindows 回调不可靠**（多轮零命中），窗口枚举/挪动用 Python ctypes（与 capture_window 同款口径）。
5. **Windows.Graphics.Capture 在 Win10 19045 不可用**：`windows-capture` 包无条件切 border 旗标，本机 API 不支持（报 "Toggling the capture border is not supported"）——WGC 路线在本机不可用。
6. 面板欧拉数组语义 = `[yaw(Y), pitch(X), roll(Z)]` 对应三框从左到右——Unity 习惯读作 [X,Y,Z] 的用户会把第二框当"Y 轴"。本次复现按第二框（=pitch/X 轴）执行即复现用户所见；框序语义未改（用户未投诉，留观）。
