# 施工计划：回收与热重载拆解（4.4）

> 2026-10-12 立案（用户增补），**未施工**——本档是立案草案，开工时转段 README 任务面板（段 README 开工时立）并按施工定稿修订；对应[路线图](../../学习目标实现步骤.md)步骤 4 收官段，接在已收官的[4.3 异步就绪](../4.3-异步就绪/README.md)之后。4.3 计划 §6 明确留口三笔：回收（`Removed`/`Unused` 后的 GPU 资源回收、池区间归还）、热重载（文件监听、失败资产修复后自动恢复）、在飞资源延迟销毁与槽位复用——本段一次还清，收官即步骤 4 完成（M3 验收：反复增删/热重载资源不持续泄漏，不覆盖 GPU 尚在读取的内容）。

## 0. 判定线（验收草案）

1. **反复增删不持续泄漏**：BRP 驱动"加载→使用→卸载/删除"循环 N 轮后，资源存量账面收敛——驻留条目数（MeshPool/ImageCache）、池区间用量、贴图停尸房张数、failed 集规模、账本行数各有读数，稳态回到操作前基线，不随轮次单调增长（对账 4.2.3 注释"旧槽位孤儿化"的现状反转）。
2. **销毁不等错时序**：旧资源（替换换下的旧内容、卸载的资产）销毁受"上传票据 ∧ 图形最后使用"双条件保护，不覆盖/不悬空 GPU 尚在读取的内容——贴图侧停尸房机制（4.2.3 现成）扩展到 mesh 孤儿区间与卸载路径，[责任边界契约②](../../3-静态取数链路/3.2-buffer侧上传/责任边界冻结：上传完成、图形消费与退出排空的时序契约.md)的回收半边落点钉明。
3. **热重载内容正确上屏**：文件监听开启后修改资产文件（单资产与 glTF 场景两档），重载链走通——`AssetEvent::Modified` → 4.2 失效联动 → 重传 → 票据发布 → 画面更新；WorldAsset 整场景重载（官方 spawner despawn+respawn）后层级/材质/相机关系正确，旧 Entity 身份与运行时附加状态不默认保留（路线图步骤 4 边界既有口径）。
4. **失败资产修复自动恢复**：4.3 留口的 revive 链接通——failed 集中的资产经文件修复 + 重载事件（`Added`/`Modified` 复活口）自动恢复重试并上屏，失败计数清零可读；恢复有上限防损坏文件循环重试（上限策略施工钉明）。
5. **零变化零上传不回退**：4.1/4.2/4.3 稳态基准（稳态帧零盘点零上传、事件不误伤）保持；计量分列不回退——驻留条目数、回收字节数、停尸房张数、重载延迟（文件改→上屏帧数）、上传字节分开报。
6. **既有判定线零回退**：3.5 三模式截图、零 VUID（含拆 Device）、WM_CLOSE exit 0、clippy 全净、4.1 五类变更、4.2 同柄改内容/共享去重、4.3 pending/失败/取消判定线全量回归。

## 1. 定位：现状与要打通的东西

4.3 之后资源链路的形状是"账本脏行 → 按资产身份查驻留（查无或失效才传）→ 转换上传 → 提交发布票据"，加 4.3 的 pending/失败/取消账面。本段面对的是这条链的**出口问题：资源不再被需要之后去哪**。立案时点核实（详见文末附录），现状是三处现成机制加四处断头：

**现成机制（复用，不重造）**：

- **贴图侧停尸房**：4.2.3 内容重传的旧图先进停尸房（在飞安全），`drain_graveyard` 在帧侧等待的安全点销毁，失败保留次帧重试——"延迟销毁"在贴图内容替换这一条道上**机制已现成**。
- **描述符原槽重写**：贴图槽不因内容变化增长（"只写 free list 的新槽"，槽位复用侧已有纪律）；池容量变化走 `ensure_capacity`（4.1.1 补齐帧侧等待闸门）。
- **官方 WorldAsset 热重载**：`WorldAssetSpawner` 对 `AssetEvent::Modified` 做 unload/reload（despawn+respawn），宿主场景进场走官方 `WorldAssetRoot` spawn——重载执行底座现成，本段不新造。
- **复活口**：`AssetReadiness` 的 `revive_*`（4.3.2）已把 `Added`/`Modified` 事件作复活锚点，自动恢复链只差事件来源（文件监听）接上。

**缺口（本段工程量）**：

- **mesh 侧孤儿区间**：4.2.3 mesh 内容重传走 `replace` 换条目，旧区间孤儿化、区间空间随池同寿（upload.rs 注释明写"回收归 4.4"）——反复热重载同一 mesh 池区间单调增长，无归还路径。
- **资产卸载零读侧**：`AssetEvent::Removed`/`Unused` 全仓只计数不动作（asset_events.rs 注释明写"回收语义归 4.4"）——资产卸载后驻留条目（mesh 区间/贴图显存/描述符槽）不释放，failed 集与 pending 账也不随之出账。
- **文件监听未开**：宿主 bevy 依赖未开 `file_watcher`，watch 开关 `watch_for_changes_override.unwrap_or(cfg!(feature = "watch"))` 现值为 false——运行期零重载通道，判定线 3/4 无驱动来源。
- **在飞安全销毁只覆盖一条道**：停尸房只在贴图内容替换路径上存在；mesh 孤儿区间、资产卸载、池容量收缩没有对应的"延迟销毁"落点，销毁时序与契约②的对账缺位。

## 2. 拆解：卸载回收 / 在飞销毁与槽位复用 / 热重载链

| 线 | 交付 | 落点 |
|---|---|---|
| ① 资产卸载读侧与驻留回收 | `AssetEvent::Removed`/`Unused` 读侧：资产失尽引用后驻留条目出账（mesh 区间归还 / 贴图条目卸载走停尸房 / 描述符槽归还 free list）；failed 集与 pending 账联动出账；驻留读数扩展 | `scene/mechanism/asset_events.rs`（读侧扩展）+ `vulkan/pool.rs` / `vulkan/images.rs`（归还 API）+ `driver/upload.rs` |
| ② 在飞安全销毁与槽位复用 | mesh 孤儿区间与卸载旧资源的延迟销毁（复用停尸房形状：安全点排空、失败次帧重试）；槽位复用语义统一（mesh free list 建立 / 贴图槽既有纪律核对）；池容量收缩策略（收缩触发与幅度施工钉明） | `vulkan/pool.rs` / `vulkan/images.rs` + `driver/upload.rs`（排空点） |
| ③ 热重载链 | `file_watcher` feature 开关决策与 `watch_for_changes_override` 配置；单资产与 WorldAsset 两档重载回归；失败资产修复自动恢复（revive 接重载事件）；重载延迟计量 | `ash_renderer/Cargo.toml` + 宿主启动配置 + `scene/mechanism/`（revive 链接线） |

三线依赖单向：先有回收出口（①），销毁时序与复用跟着落（②——停尸房从"替换专用"泛化为"回收通道"），热重载链（③）把 4.2/4.3 的失效/复活机制接到真实文件变更上做全链验收。同段施工不拆段（4.1~4.3 惯例）；任务拆解见 §3。

## 4. 测试方案：BRP 驱动与证据形态

**驱动纪律沿 4.1 定案：变更驱动一律优先 BRP**（[测试规范](../../../rules/测试规范与方式.md)"扩建优先级"条）。本段新驱动的是"反复增删循环""资产卸载""热重载触发与观察"：

| 驱动 | 手段 | 状态 |
|---|---|---|
| 反复增删循环 | BRP spawn/despawn（4.1 方法族既有）组合加载方法（4.3 load_mesh/load_image）跑 N 轮 | ⬜ 组合既有方法 |
| 资产卸载 | `Assets::remove` 触发 `Removed` 的 BRP 入口（薄封装，官方 despawn/remove 不重复） | ⬜ 本段新增（待决是否必要，见 §5） |
| 热重载触发 | 文件监听自动触发（真实改文件）为主；BRP 手动重载入口（`AssetServer.reload` 形状施工核实）为可复现对照 | ⬜ 本段新增 |
| 驻留/回收读数 | `increment_stats` 族扩展（驻留条目数/池用量/停尸房张数/回收字节/重载延迟） | ⬜ 本段新增 |

**证据形态**（判定线 §0 的证据来源）：

- **存量对账定泄漏**：N 轮增删前后驻留条目数/池用量/停尸房张数/账本行数逐项对账回基线；关键读数=循环轮次与资源存量解耦（第 1 轮与第 N 轮存量差为零）。
- **截图定画面**（PrintWindow + 读图，按《画面功能视觉验证》执行）：热重载前后内容正确替换、WorldAsset 重载后层级/材质不丢、失败修复后内容上屏。
- **负例**：卸载仍在引用的资产、修复前反复触发重载、损坏文件循环——宿主存活、不悬空不覆盖、恢复上限生效（不无限重试），错误按[两 Tier 宪法](../../错误处理/错误处理体系：两Tier思想与优雅退出.md)分级。
- **回归矩阵**：3.5 三模式、零 VUID 含拆 Device、WM_CLOSE exit 0、clippy 全净、4.1 五类变更、4.2 同柄改内容与共享去重、4.3 pending/失败/取消全量零回退（重点：停尸房泛化后 4.2.3 既有语义不回退）。

## 5. 待决问题（施工时钉明，不写死）

- **mesh 区间归还策略**：整段归还 free list（首次适配可复用）vs 碎片合并 vs 只记账不归还等池销毁——与现行 `alloc` 分配策略（4.2 版首次适配形状）的对账，学习收益与复杂度取舍施工拍板。
- **池容量收缩**：池只增不缩现状 vs 支持收缩（触发条件=空闲比例阈值？）；收缩涉及池迁移（3.6 立账、4.1.1 补闸门的那条道），收益与风险施工钉明——倾向：本段只主张容量**读数**，收缩留待实测成为瓶颈后再议。
- **`Unused` 触发时机的实际形状**：`Unused`（无强引用）与 `Removed`（显式卸载）在本宿主的触发场景各自是什么（共享材质部分卸载？），读侧对两者是否同策略，开工先探针钉明避免过度设计。
- **手动重载入口的必要性**：文件监听已是自动通道，BRP 手动重载是否值得加（可复现性 vs 入口冗余）——取决于真实改文件的测试可自动化程度，施工拍板。
- **WorldAsset 重载对宿主附加物的冲击面**：官方 despawn+respawn 后，宿主侧附加物（材质 hook、BRP 自定义实体、egui 选中态、相机轨道给值）各自的行为——回归范围与"不默认保留"口径的逐项对账，开工先盘点清单再定验收集。
- **恢复上限策略**：revive 后再次失败是否二次进 failed（防损坏文件无限循环）——上限次数/退避策略施工钉明，与 4.3"失败一次出队"口径对齐。
- **`file_watcher` 依赖面核对**：feature 链 `file_watcher = [notify-debouncer-full, watch, multi_threaded]` 引入的传递依赖（notify 系列）与宿主现有特征面的叠加影响，开工先核对 Cargo.lock 变更再拍板开关位置（宿主 features vs workspace dev 集合）。

## 6. 边界：不在本段主张什么

- **实例数据迁 GPU / GPU-driven**（实例表/indirect）→ 5.1/5.3；本段不动矩阵 push constant 现状，账本行仍是 ECS 侧事实。
- **流送与驻留管理器**（mip/LOD 驻留、按优先级换入换出、缺页回退）→ 步骤 6；本段回收是"引用消失才回收"的**生命周期闭环**，不是"驻留按预算管理"——6.4 细粒度流送以本段回收为前提但不在此主张。
- **AssetMode::Processed / asset_processor**（cook 管线对标）不进本段；`AssetReader` 可插拔、Processed 模式的对照已在[资产加载方案对照篇](../4.3-异步就绪/资产加载方案对照：frenderer、Addressables、UE与Bevy的异步加载拆解.md)记录，实装归后续扩展需求。
- **停尸房/帧侧等待的责任边界重写**：复用 4.2.3 停尸房与 4.1.1 帧侧等待闸门现有形状，本段是"泛化使用者"不是"改契约"；若回收路径确需新 Vulkan 机制（如池迁移销毁的图形侧等待扩展），施工钉明并回契约②对账。
- **网页 console / 远程检视面板**：BRP 读数只入既有方法族读数段，web console 是另立的候选拓展需求，不在本段。
