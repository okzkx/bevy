## O1. Cluster 职责拆分

将光源分簇资源与透明物体命令链的职责边界重新划清，为第 7 站阅读 `render/passes/lighting/cluster.rs` 及后续独立施工铺路；本条不主张改变多光源、透明排序或合成画面的算法与效果。

**已核实的现状。** [`ClusterTargets`](../../../ash_renderer/src/render/passes/lighting/cluster.rs) 同时持有分簇光源数据和透明命令链的 buffer，并在一个 set layout 里声明 b0～b7；`TransparentPasses` 同时持有 `cluster_build` 与透明 collect/sort/gather compute。`CompositePipeline`、`TransparentPipeline` 和多个 compute 消费这套布局；创建依赖从 [`init.rs`](../../../ash_renderer/src/driver/host/init.rs) 可见。第 1 站的 [命名错位与拆分评估](第1站：入口与初始化链.md#五clustertargets-与-transparentpasses-的名字交叉错位) 记录了起因与候选形态。

**候选方向。** 分别界定光源分簇资源、透明命令资源及其 compute 管线；可评估 `LightClusters`、`ClusterBuildPass`、`TransparentTargets` 和收窄后的 `TransparentPasses` 四个平级职责，但命名、模块落位、描述符集数量和布局复用方式尚未定案。改名本身不构成拆分验收。

**边界与先后。** 不改分簇算法、透明物体筛选／排序语义和 GPU-driven 决策归属；保持不透明合成与透明前向绘制取到同一份光源数据。开工前先列清各 shader 的 set/binding、描述符写入、逐帧绑定与 resize 重建链，再决定是否真的拆成两套 descriptor set：多一个 set 会改动 pipeline layout、shader group 编号及录制绑定，不是只把 Rust struct 拆开。O2 如先实施，以 O2 的布局契约表达拆分后的两个资源族；O1 如先实施，O2 后续以实际分拆结果为准，不预设两项必须同期开工。

**验收草案。** 资源职责与名称一致；创建、resize、录制、拆除各路径均能对上新的归属；验证层零新增错误；多点光的不透明合成与透明前向绘制、透明排序及 resize 前后效果与基线一致。具体场景、读数与截图判定线待独立施工计划敲定。

**待决（已在施工中裁决）。** 是否拆 descriptor set，还是先拆 Rust 所有权但保留共用 set；若拆，怎样在不透明与透明管线间共享光源布局并安排 set 编号；资源生命周期的实际依赖与 teardown 顺序如何核对。

**施工结果（2026-10-28）。** 拆成两套 descriptor set。理由：拆前各 shader 用到的 binding 本来就分成两组——光源侧 b0～b3、透明侧 b4～b7，唯一交叉是 `transparent_collect` 读 b0 的 `view_proj` 算深度键；而且透明命令链容量固定，和窗口尺寸无关，拆开后 resize 不再重建它。

- 光源分簇留在 [`cluster.rs`](../../../ash_renderer/src/render/passes/lighting/cluster.rs)：`LightClusters`（b0 均匀数据 / b1 光源常驻表 / b2 列表 / b3 计数，COMPUTE|FRAGMENT，随 resize 重建）+ `ClusterBuildPass` + CPU 参照。binding 编号没变，`cluster_build`、`gbuffer_composite`、`transparent_forward` 三个 shader 的绑定声明都没动。
- 透明层移到新文件 [`transparent.rs`](../../../ash_renderer/src/render/passes/transparent.rs)：`TransparentTargets`（b0 索引列表 / b1 深度键 / b2 命令环 / b3 计数，只给 COMPUTE，不随 resize 重建）+ 收窄后的 `TransparentPasses`（collect/sort/gather）+ `TransparentPipeline`。shader 改绑：collect = [set2, 光源分簇集, 透明集]，sort = [透明集]，gather = [set2, 透明集]。
- 两族共用的“N 个 storage buffer 布局 + 每帧槽一集”抽成 [`storage_sets.rs`](../../../ash_renderer/src/render/core/storage_sets.rs)。
- 帧侧：`cluster_build` 的 dispatch 与光源分簇集从 `TransparentFrame` 挪到 `FrameDraw`（合成与透明前向共读，录制位置不变，仍只在在场行数 > 0 时派发）；`draw_frame` 的参数束拆成 `ClusterInput` 和 `TransparentInput`，`FrameInput` 字段数到达 16 的上限，再加字段前得先合并分组。
- 拆除顺序：`TransparentPipeline` → `TransparentPasses` → `ClusterBuildPass` → `TransparentTargets` → `LightClusters` → `LightTable`。删掉了没有调用方的 `readback_index_list`。

**验证。** `cargo check`/`clippy --all-targets` 零警告，库测试 62/62 通过。Sponza 实跑（验证层开）：注入 4 盏点光后 `cluster_census` 显示 GPU/CPU 总指派 9271=9271、零 mismatch；把 3 个实体的材质 alpha 改成 0.4 后有 10 行透明，census 显示 52701=52701，`transparent_sort_check` 零 issues；用 BRP 改窗口分辨率到 1280×720 后，cluster 网格重建为 40×23×32，census 显示 33494=33494、排序零 issues；截图画面正常；正常关窗拆除完成，整份日志零 VUID、零 WARN/ERROR。没做逐像素的拆前/拆后基线对比。

## O2. 管线资源布局声明

将散落在资源构造与 Pipeline 创建代码中的裸 `vk::DescriptorSetLayout` 拼装提升为可审计的绑定契约，为后续管线演进提供 set/binding 对账；本条不主张让 Vulkan 从实际 buffer/image 句柄自动推断 shader 意图，也不改变现有 bindless 或帧槽语义。

**已核实的现状。** `BindlessTables` 自建 set0/set1（含 descriptor indexing 的 `UPDATE_AFTER_BIND`、`PARTIALLY_BOUND` 与容量），`InstanceTables` 自建 set2，G-buffer、阴影、Bloom、SMAA、Hi-Z 等也各有布局；[`GBufferPipeline::new`](../../../ash_renderer/src/render/passes/gbuffer/gbuffer_pipeline.rs) 按位置接收 set0/set1/set2，[`ComputePipeline::new`](../../../ash_renderer/src/render/core/compute_pipeline.rs) 接收裸 set-layout 切片和 push 大小，再创建各自的 `VkPipelineLayout`。[`build.rs`](../../../ash_renderer/build.rs) 已通过 Naga 解析/校验 WGSL 并检查部分记录尺寸，但尚未逐入口将 shader 使用的 set/binding 契约与宿主创建的布局核对。这些是当前实现的观察，不意味着现有管线已经不合法。

**候选方向。** 让每个资源族持有明确的 set 布局描述（编号、binding、描述符类型/数量、阶段、binding flags、布局 flags 等），由集中入口创建原生布局；Pipeline 以语义身份和有序 set 需求组装自己的 pipeline layout 与 push-constant ranges，减少在 `init.rs` 及管线构造函数里手排裸句柄。优先建立“声明与组装”的单一依据，再考虑缓存；布局去重是否值得做、谁拥有缓存及句柄、哪些版本和动态变体可共享，需设计时核实，不为抽象而加缓存。

**安全闸门。** 构建期基于现有 Naga 模块，对每个实际使用的入口点比较 `(set, binding, 资源种类, 数组形状, 可见阶段)`；宿主声明侧检查编号/类型/容量/flags、启用的设备特性与限额，运行时仍保留 Vulkan 验证层。必须显式覆盖 set0 的固定容量 Vulkan UAB 布局与 WGSL runtime binding array 的对应、部分绑定与安全兜底、set1 帧槽 UBO，以及不同管线对同一布局的复用；不把“资源实例包装类型”误当作完整 shader ABI 证明。push constants、附件格式是相邻但独立的 Pipeline 契约，是否纳入同一描述对象待设计。

**参考边界。** Filament 以语义化布局描述供 Program/后端使用；Bevy 的 `AsBindGroup` 从声明生成布局与绑定代码，wgpu 在创建/绑定阶段校验。两者都不是从裸 `VkImage`/`VkBuffer` 自动读出任意 shader 契约。此处借鉴“声明→创建→核验”的结构，不照搬 Filament 的紧凑 Vulkan binding 表示或 Bevy 的 bindless 材质 slab；参考源码以本机 `F:/okzkx/filament` 与本仓库 `crates/bevy_render/` 的当前检出为准。

**验收草案。** 管线创建调用点不再靠无名的裸 layout 顺序表达其业务绑定；同一份声明能够导出 Vulkan 布局并支持 shader ABI 对账；有意改错 set/binding、描述符类型或阶段的负例能在构建期/创建期被明确拒绝；正确配置下 bindless 发布/回收、各帧槽写入、合成/透明/后处理/compute、resize 及退出拆除行为不回退，零新增 VUID。负例覆盖范围和可复现脚本待独立设计。

**待决。** 先做轻量的语义 set 标识 + 显式布局声明，还是同时引入统一缓存；跨模块共用声明放置哪里才不制造依赖环；shader 入口使用集合与 Vulkan 布局超集如何比较；哪些检查适合构建期，哪些必须依赖设备能力在运行期裁决。
