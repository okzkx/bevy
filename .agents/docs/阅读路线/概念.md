# 概念

读代码前先把这些词的意思定准。每个词只讲三件事：它解决什么冲突、在本项目里长什么样、代码在哪。

## 一份资产有两份内容

Bevy 的 `Assets<Mesh>`/`Assets<Image>` 是 CPU 侧的内容真身；GPU 侧的 `MeshPool`/`ImageCache` 是另一份。账本只记实体到实例槽的关联，GPU 足迹（池区间、贴图槽）按资产身份现查驻留缓存。**不要把“实体、资产、GPU 槽位”混成一层账。**

## 帧槽是按在飞帧数复制的资源组

`MAX_FRAMES_IN_FLIGHT = 2`。每个帧槽有一套命令缓冲、`image_available` 信号量、in_flight fence 和深度附件。CPU 最多领先 GPU 两帧；**帧槽和 swapchain image 是两个独立循环**，重建交换链时帧槽对象原地不动。

## fence 是 CPU 等 GPU 的凭证

`FramePool::wait_for_slot` 等本槽上一轮提交完成，之后才重录本槽。fence 只在提交前一刻重置：帧首重置的话，任何提前 return（acquire 过时、重建失败）都会留下一个永远没人 signal 的 fence，下一帧死等。`wait_all_inflight` 等全部帧槽，用于回收旧资源。

## 信号量是 GPU 等 GPU 的凭证

binary 信号量管两次提交之间的交接：`image_available`（呈现引擎 → 图形提交）、`render_finished`（图形提交 → 呈现引擎，按 swapchain image 分配）。timeline 信号量管上传队列到图形队列的交接，值就是 `Ticket`（单调 u64，0 保留给空批）。**fence 证明提交执行完，不证明呈现引擎已消费；同一条 image 再次 acquire 才证明上一轮 present 完成。**

## 屏障回答两个问题

stage 掩码回答“谁等谁执行完”，access 掩码回答“谁对谁可见”。布局迁移本身是一次写，也要算进 src access。`ImageBarrier` 额外带 old/new layout，固定作用于 mip0/layer0（本仓帧级图像都是单级）；需要多 mip 范围的布局迁移只在上传器里裸构造 `vk::ImageMemoryBarrier`；`MemoryBarrierDesc` 只做执行/可见性，不动布局。图像必须走图像屏障，buffer 屏障不覆盖布局。

## 描述符集是“一组绑定的整份快照”

`SetLayoutDesc` 声明每个 binding 的编号、种类、数量、阶段和旗标；`DescSet` 是按这份布局分配的整份集。非 `PARTIALLY_BOUND` 的 binding 必须写满，漏一个就是绑定时读未定义描述符。`DescriptorWriter` 在 `vkUpdateDescriptorSets` 之前按声明校验，报错带声明名和 binding 号。

## set 编号是管线配方里的位置

同一份布局声明在不同管线里可以排不同的 set。场景管线是 `bindless / frame / instance`，剔除管线是 `instance / shadow`，合成管线是 `frame / gbuffer / clusters / shadow`。WGSL 的 `@group(n)` 对的是**管线配方**的第 n 项，不是布局自己的属性。

## bindless 是一个描述符数组加一个下标

本项目不止贴图：网格引脚、模型矩阵、材质、贴图槽、光源全是按槽号直取。set0 的两个数组各 1024 项，带 `UPDATE_AFTER_BIND`（绑定后还能写）和 `PARTIALLY_BOUND`（没写过的槽不能被访问）。槽 0 是白色兜底图和线性采样器，永不回收。

## 实例槽和材质槽是两套索引空间

实例槽是对象表、模型环、剔除标记、遮挡标记、LOD 表、缺口标记共用的下标，131072 个，走延迟回收。材质槽是另一套，65536 个，只增不回收，量级等于唯一材质数。对象记录里的 `material_index` 指的是材质槽。

## indirect 命令把“画什么”写进 buffer

`VkDrawIndexedIndirectCommand` 20 B：`index_count / instance_count / first_index / vertex_offset / first_instance`。`first_instance` 写实例槽号；`instance_count` 写 1（可见）或 0（不可见/透明）。VS 的 `@builtin(instance_index)` 就等于这个槽号，所以图形侧没有逐对象 push。CPU 只发一条 `cmd_draw_indexed_indirect`。

## GPU-driven 是决策点后移

CPU 只给两样东西：可绘行列表（在场环）和常量（相机、开关、阈值）。可见、遮挡、档位由 GPU 上的 compute 决定；命令条数 = 在场行数，CPU 知道，GPU 决定的是每条命令的 `instanceCount`。**CPU 仍掌握可绘行的准入和资产驻留**，GPU 不决定上传。判断一个环节该不该搬 GPU，看三条：结论是否只供绘制、输入能否常驻、规模是否值得。

## 旧数据回收有三种策略

- **双份**：每个帧槽一份，CPU 只写本槽；旧读者读另一份。光源表、模型环、材质环用这个。
- **换槽 + 延迟回收**：新内容写新槽，旧槽进回收账，等 GPU 不再读才复用。对象表、bindless 贴图槽用这个。
- **等设备空闲**：`device_wait_idle` 后原地改/重建。只在 resize、退出这类冷路径用。

对应的证明也不同：双份靠帧槽 fence，换槽靠票据 + fence，冷路径靠设备空闲。三种“完成”不要混用。

## 账本和脏集是 CPU 侧的唯一真相

`InstanceLedger` 每个可渲染 primitive 一行，`PostUpdate` 的 `update_ledger` 消费组件变更，标脏行。上传链只消费脏行；DrawList 组装缓存只在账本变更点重估。静态场景的稳态是“零脏行、零上传、零组装走访”，不是“每帧全量扫一遍”。

## 跨端记录是逐字节契约

对象记录 48 B、材质 64 B、LOD 条目 12 B、indirect 命令 20 B、光源 64 B、每帧 UBO 208 B、shadow UBO 736 B。三处互证：Rust 侧 `offset_of!` 静态断言、`build.rs` 的 `HOST_LAYOUT_GATE`、管线建立的 ABI 对账。改字段要三处一起改。
