# 阅读路线总览

ash_renderer 全库阅读顺序：沿一帧数据的生命周期分九站读，每站先讲意图与数据流，再逐个校验要点对照源码。本文只定顺序与校验点，不主张代码改动；路上发现的问题记入《[代码阅读优化计划](代码阅读优化计划.md)》或《[待修复清单](../开发步骤/待修复清单.md)》。

> 数据口径：源码快照 `b594ba04c`（2026-11-02），`ash_renderer/src` 共 29,926 行；各站行数为该快照 `wc -l`，只供量力安排。进度：九站均未读。

## 读序依据

- **沿一帧数据走**：开机 → 设备 → 帧槽节拍 → 屏障 → 资产进显存与 shader 查表 → GPU 可见性 → 渲染功能 → 场景账本 → 整帧编排。
- **顺依赖方向**：顶层 `common ← render ← scene ← {overlay ∥ remote} ← driver`；render 内部 `core ← resident ← passes ← frame`（原文见 `render/mod.rs`、`render/core/mod.rs` 模块文档）。每站用到的类型都在前面读过。
- **三条学习主线**：bindless（第 5 站）、GPU-driven（第 6 站）、大世界流送（第 8 站）。

## 各站细读

每站按列出的顺序读，前一个读完，后一个就不会出现没见过的类型。

### 第 1 站：入口与装配

1. `main.rs`：禁掉 Bevy 渲染族插件（`RenderPlugin`、`PbrPlugin`、`UiPlugin` 等），装上 driver、scene、overlay、remote 的插件。
2. `lib.rs` 模块文档：六个顶层模块的分层图与允许的依赖方向。
3. `driver/host/mod.rs` 的 `AshHostPlugin`：系统进哪个调度。
4. `driver/host/init.rs` 的 `try_init_vulkan`：按"设备根 → 帧级执行件 → 常驻表/池 → 管线"的顺序建资源，失败时反序拆除。只当目录读，不钻构造函数。

校验：init 里每个资源对应后面哪一站；Bevy 侧还剩哪些插件在跑。

### 第 2 站：设备地基

1. `render/mod.rs`、`render/core/mod.rs` 模块文档：render 五个目录与 core 五个子目录的职责和依赖。
2. `context.rs` 的 `Context`：instance、physical device 选择、device 与 graphics/transfer 两条队列、特性链；`MAX_FRAMES_IN_FLIGHT = 2`。

校验：bindless 用到的 descriptor indexing 特性（`PARTIALLY_BOUND`、update-after-bind、runtime array）哪些只查支持、哪些真启用；timeline semaphore 的启用点（第 5a 站票据依赖它）。

### 第 3 站：交换链与帧槽

1. `swapchain.rs`：present mode 选择、`SWAPCHAIN_COLOR_FORMAT`（UNORM 底板 + SRGB view）、`AcquireOutcome`、过时重建。
2. `frame_pool.rs` 的 `FramePool`/`Frame`：每帧槽一套命令缓冲、fence、信号量与深度目标。
3. `frame_sync_settings.rs` + `driver/host/frame_sync.rs`：帧率同步设置怎样落到 Bevy 的更新节奏。

校验：一帧占一槽、等本槽 fence 后才能复用本槽资源；同步对象不挂在 swapchain image 上，重建 swapchain 时不受影响。后面所有"何时可写"的问题都回到这个模型。

### 第 4 站：屏障语义

`barrier.rs`：`ImageBarrier`（含 `color_to_sampled` 等常用构造）、`image_barrier`、`image_barrier_with_memory`。

校验：stage + access 两组掩码分别回答"谁等谁""谁对谁可见"；布局迁移本身算写。另有直接调 `cmd_pipeline_barrier` 的地方（uploader 图像段、Hi-Z、compute `Handoff`），读到时用同一套语义核对。

### 第 5a 站：数据进显存

1. `memory/role.rs` → `contract.rs` → `buffer.rs`：`BufferRole` 每种角色的 usage 与内存属性规格；`MemoryContract` 冻结设备内存事实并按规格选类型；`GpuBuffer` 是全库唯一的 buffer 形态（恰量分配、持久映射、非 coherent 时自动 flush/invalidate）。
2. `transfer/types.rs` → `transfer/uploader.rs` → `transfer/uploader/image.rs`：`UploadBatch` 合批；`Ticket` 是 timeline semaphore 上单调递增的票据（0 = 空批次）；`Uploader` 的 staging 槽轮转（init 配 2 槽、1MB 起步，不够时扩容），复用前等本槽上一张票据；贴图 mip 链在 graphics 队列上 blit 生成，续批等 transfer 票据。
3. `resident/assets/mesh_convert.rs` → `pool.rs`：Bevy `Mesh` 转成池内顶点格式；`MeshPool` 顶点/索引大池的分配、扩容与延迟回收。
4. `resident/assets/image_spec.rs` → `images.rs`、`resident/sampler.rs`：贴图格式核对与 mip 级数；`ImageCache` 按资产身份驻留，每张图一块 dedicated memory；`SamplerKey` 给采样器去重。

校验：staging 何时可复用（上传票据与第 3 站 fence 是两套完成信号）；图像段为何单独录、不套 buffer 屏障；必需内存属性不满足时是报错冒泡，不静默降级。

### 第 5b 站：shader 查表

1. `set_layout.rs`：`SetLayoutDesc` 静态声明 binding 编号、种类、数量、阶段与旗标；建布局前先跑宿主自检；descriptor pool 容量从声明推导；`DescSet` 带声明身份。
2. `descriptor_writer.rs`：每次写入按声明校验种类与越界，提交前查完备性（非 `PARTIALLY_BOUND` 的 binding 必须写满）。
3. `slot_allocator.rs`：`SlotAllocator` 两种归还——`release` 立即复用，`retire` + `drain_retired` 延迟回收。
4. `tables/` 四张表：`bindless_texture_table.rs`（set0，贴图/采样器 bindless 数组）、`frame_uniform_table.rs`（set1，每帧槽一份 UBO）、`instance_table.rs`（set2，对象/材质/模型/LOD 表与各种环；模块文档的 hazard 纪律是第 9 站环写入的依据）、`light_table.rs`（点光 storage 表，每帧槽一份；方向光走 set1）。
5. 对照 `ash_renderer/shaders/common/` 的 `frame.wgsl`、`instance.wgsl`、`mesh.wgsl`：shader 侧怎样按槽号取数。

校验：bindless 槽"按槽发布、从不写满"怎样同时满足 `PARTIALLY_BOUND` 与写入器的完备性检查；实例表用延迟回收、光源表不用的理由；set1 UBO 与光源表都在 `wait_for_slot` 之后写。

### 第 6 站：GPU 可见性链

1. `build.rs` 的 `reflect_abi`、`assert_host_layout`：naga 校验后逐入口列出实际用到的 `(set, binding, 种类, 数组形状)` 与 push 字节数，生成 `OUT_DIR/shader_abi.rs`。
2. `shader_abi.rs`：include 生成表，每个 shader 一个 `Shader` 静态项（含 spv 字节）。
3. `pipeline_layout.rs`：`PipelineDesc` 配方（shader、入口、按 set 序排好的声明、push 范围、附件格式），`build` 统一做对账 → 组装 → 建 module。
4. `core/pipeline/compute.rs` + `core/record/compute.rs`：建管线与录制两半；`Handoff` 六个变体对应 dispatch 后的不同下游（VS 读、compute 读写、透明 FS 读、indirect 命令读）。
5. `passes/visibility/` 按帧内录制顺序：`cull` → `occlusion` → `lod` → `indirect`；`hiz` 放最后，它在透明层之后归约本槽深度金字塔，供下次轮到本槽时的遮挡测试使用。
6. `readback.rs`：诊断用同步回读，独占一次提交并阻塞到 fence；只被 remote 读数方法、Hi-Z 与透明层诊断调用，不进帧循环。

校验：每个 `Handoff` 变体的 stage/access 是否覆盖它的真实下游；Hi-Z 同槽读为什么不需要额外同步（本槽 fence 已证明上次写完成）；对账口径"布局是超集，shader 没用到的 binding 不算错"。

### 第 7 站：渲染功能

1. 图形与全屏标准件：`pipeline/graphics.rs`（`PipelineHandle`）、`pipeline/fullscreen.rs`（`FullscreenPipeline`）、`record/graphics.rs`（录制句柄 `PipelineRef`；绑定、顶点/索引、viewport/scissor）、`record/fullscreen.rs`、`target/`（attachment、color、depth）。
2. `binding/storage_sets.rs`：只含 storage buffer、每帧槽一集的 set，光源分簇与透明层共用。
3. `passes/` 按功能读，顺序自选：`gbuffer`（目标 + 写入管线）、`shadow`（`cascades` 级联矩阵、`shadow_build` 命令组装、`shadow_map` 深度图与管线）、`lighting`（`cluster` 分簇构建、`composite_pipeline` 延迟合成）、`transparent`（collect/sort/gather 三段 compute + 前向管线）、`post`（`bloom`、`present_tonemap_pipeline`、`smaa`）、`overlay`（egui 的 GPU 侧：图集、管线、UI 顶点环）。
4. `layout_registry.rs`：`ALL_PIPELINES`（22 条）与 `ALL_SETS`（13 份）全量登记；配合 `layout_contract_tests.rs` 看对账正例与负例。

校验：配方里的附件格式与目标、`SWAPCHAIN_COLOR_FORMAT` 是否一致；resize 时哪些目标和集重建（见 `driver/host/frame.rs` 的 `rebuild_size_dependent`）；`transparent_collect` 读光源分簇集是两套 storage set 唯一的交叉。BRP 只读方法 `ash_renderer/layout_contract` 可现场查看声明表。

### 第 8 站：场景账本

1. `scene/mod.rs`、`scene/mechanism/mod.rs`：机制半边（assets、editing、generation、host、interaction）与业务半边 `content`。
2. 优先三件：`mechanism/assets/ledger.rs`（实体粒度的行账）→ `residency.rs`（资产粒度的驻留管理）→ `content/collect_report.rs`。
3. 资产到货链按需展开：`asset_events`、`asset_readiness`、`lod_registry`、`assembly_cache`。

校验：一份资产的两份真身（CPU 容器 + GPU 显存）各由谁持有；行账的脏行怎样交给第 9 站的 `flush_uploads`；回收方向在哪里断开、由谁负责。

### 第 9 站：整帧编排

按 `Last` 调度的执行顺序读：

1. `driver/upload.rs` 的 `flush_uploads`：回收停尸房 → 扫脏行 → 准备资产 → 合成一个批次提交；全程只走第 5a 站的出口。
2. `driver/host/drawlist.rs`：`assemble_update` 枚举可绘行槽位，`write_rings` 写模型/材质/在场/LOD 表四个环。
3. `driver/host/frame.rs`：`FrameInput` 由 16 个字段构成（Bevy 系统参数上限）；`draw_frame` 走 resize 闸门 → 等 fence → acquire → 写 UBO 与环 → 录制提交 → present；后半的 `cull_half`、`occlusion_half`、`lod_half`、`indirect_half`、`shadow_marks_half` 各对应第 6、7 站的一个环节。
4. `render/frame/frame_draw.rs` 的 `FrameDraw::record_frame`（约 630 行）：compute 段（cull → occlusion → lod → indirect → shadow_build → cluster_build → 透明 collect/sort/gather）→ 阴影深度 → G-buffer → 合成 → 透明前向 → Hi-Z 归约 → Bloom → tonemap → SMAA → UI → present 布局，用 T1～T7 七个计时点分段。`render_mode.rs` 顺带。

校验：环写入是否全在 `wait_for_slot` 之后；上传票据怎样成为图形提交等待的信号量；`record_frame` 每段进出屏障能否用第 4 站语义逐个对上；`FrameInput` 再加字段前要先合并分组。

## 走法

- 每站先讲三样：意图、数据流、在整条链上的位置；再逐个过校验点。
- 随时提问质疑，结论分歧以源码为准；一站校验完再进下一站，第 7 站适合按需跳读。
- 讲解中确认的结论写进本目录的分站笔记（一站一篇），跨站通用的机制另立知识点文档。
