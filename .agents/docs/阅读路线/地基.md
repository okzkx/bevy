# 地基

这一篇读三件事：程序怎么把 Vulkan 资源建起来，帧用什么节拍转，屏障用什么语言描述依赖。读完应该能画出资源目录，并解释一帧里每一次等待在等谁。

## 一、启动只做装配

`src/main.rs` 里没有 Vulkan 调用。它只做四件事：

- **禁用 Bevy 的渲染族**：`RenderPlugin`、`PipelinedRenderingPlugin`、`CorePipelinePlugin`、`PostProcessPlugin`、`AntiAliasPlugin`、`SpriteRenderPlugin`、`UiRenderPlugin`、`GizmoRenderPlugin`。
- **连带禁用** `UiPlugin` 和 `PbrPlugin`。前者没有消费者；后者在 `build` 里无条件加载 shader 库，需要 `RenderPlugin` 注册的 `Assets<Shader>`，不连带禁会在启动时失败。`GizmoPlugin` 不能禁：它的内部插件仍会注册 `update_gizmo_meshes`，禁主插件后缺资源反而报错。
- **资产根指到仓库根** `assets/`。默认按 `CARGO_MANIFEST_DIR` 或 exe 目录解析，`cargo run` 与直接跑 exe 都到不了仓库根。
- **一次装好错误通道**：`set_error_handler(tier_handler)` 把 system 返回的 `Err` 按严重程度分流；`fatal_gate` 挂 `First`，致命错误尽早写 `AppExit`。

随后装场景、资产账本、上传、宿主桥、egui、BRP 各插件。插件顺序不是依赖顺序，真正的调度位置由各插件在 `build` 里声明。

`AshHostPlugin` 只做接线：

| 时机 | 系统 | 职责 |
|---|---|---|
| `Startup` | `init_vulkan` | 一次建好全部 Vulkan 资源，全有或全无 |
| `Last` | `flush_uploads`（`AshUploadPlugin` 注册） | 盘点账本脏行，合批上传，先于 `draw_frame` |
| `Last` | `draw_frame.run_if(resource_exists::<Context>)` | 帧循环 |
| `Last` | `teardown_vulkan`（`OnAppExitSystems`） | 窗口销毁前反序拆除 |

禁渲染后有两件运行期职责没人做，由本插件补上：`CompressedImageFormatSupport` 自报支持格式，`ImageLoader` 注册图片加载器。两者原本由渲染插件的 `finish()` 完成，缺了贴图会一直停在 `Loading`。

## 二、init 是一张资源清单

`init_vulkan` 是 system：取窗口句柄、定错误级别、把资源插进 World。`try_init_vulkan` 是普通函数：按依赖顺序建资源，返回 `InitChain` 值。分两层守两条边界：

1. **错误只在一处定级。** 内层错误是 `VulkanError`，一路裸 `?`；外层只写一次 `.or_fatal(...)`。压成一层的话，每步 `?` 自动转成的 `BevyError` 默认级别是 `Severity::Panic`，只能靠 handler 兜底；每步都写 `.or_fatal` 又违反“业务代码错误处理只许一行”。
2. **全有或全无。** 内层不碰 `Commands`；外层拿到 `Ok` 才 `insert_all`。边建边插的话，中途失败会留下半套资源，`run_if(resource_exists::<Context>)` 会放行帧循环。

失败路径靠作用域清理：已建资源都是局部变量，返回 `Err` 时逆序析构。退出路径先 `device_wait_idle` 再逐个移除。`GpuBuffer`/`GpuImage` 的 `Drop` 都不等 GPU，所以“退出前排空”不能省。

两个会提交上传的构造函数（`BindlessTextureTable::new` 传白色兜底贴图、`SmaaTargets::new` 传两张查找表）都在构造内当场等完票据。这样失败路径丢掉半建对象时，不会出现“拷贝还在写、对象已销毁”。

窗口句柄不能用 `Single` 参数取：`Single` 匹配不到实体时整个 system 被静默跳过，结果是 Vulkan 永不初始化、程序也不退出。这里用 `Query` + `single().or_fatal(...)`。

### 创建链五段

1. **设备根**：`Context`、`Swapchain`。全局一份，其余资源都向 `Context` 借 `Device`。
2. **帧级执行件**：`FramePool`、`Uploader`、`UiVertexRing`、`FrameUniformTable`、`GpuTimer`。按在飞帧数开多份，每帧轮换。
3. **常驻数据**：`MeshPool`、`ImageCache`、`BindlessTextureTable`、`InstanceTables`、`LightTable`。池和缓存先建，GPU 表再引用它们。
4. **渲染目标**：`GBufferTargets`、`LightClusters`、`TransparentTargets`、`ShadowTargets`、`BloomTargets`、`SmaaTargets`、`HizPyramid`。它们向下一段出借描述符布局。
5. **管线**：先把各资源族的布局登记进 `SetLayouts`，再建各管线；管线只收 `&layouts`，按自己的配方取句柄。

**只看参数就能读出依赖**：`frames.depth_view(s)` 传给 `GBufferTargets`、`frames.depth_image(s)` 传给 `HizPyramid`，说明深度图本体归 `FramePool`；`light_table.ring_buffer(s)` 传给 `LightClusters`，说明光源表 buffer 由分簇集绑定；`&mut uploader` 传给两个会提交上传的构造函数。

### 资源六类

| 类 | 装的是什么 | 成员 |
|---|---|---|
| ① 设备根 | instance、device、queue、surface、swapchain | `Context`、`Swapchain` |
| ② 帧级执行件 | 命令池/缓冲、同步对象、每帧槽瞬态缓冲 | `FramePool`（另持有各帧槽深度附件）、`Uploader`、`UiVertexRing`、`GpuTimer` |
| ③ GPU 表 | 按索引/槽位组织、供 shader 或描述符访问的数据 | `BindlessTextureTable`、`FrameUniformTable`、`InstanceTables`、`LightTable` |
| ④ 常驻池与缓存 | 多资产共用的显存大块与身份映射 | `MeshPool`、`ImageCache` |
| ⑤ 渲染目标 | 附件图像/中间 buffer + 采样它们的集 | `GBufferTargets`、`LightClusters`、`TransparentTargets`、`ShadowTargets`、`BloomTargets`、`SmaaTargets`、`HizPyramid` |
| ⑥ 管线 | 只有 `vk::Pipeline` + `vk::PipelineLayout` | 图形、全屏、compute 三种骨架，见《[绘制](绘制.md)》 |

`FrameUniformTable` 在帧级阶段创建（它跟帧槽走），职责上仍属于 GPU 表。判断归属看“它装什么、谁读写”，不看它在第几段被建。`HizPyramid` 名字不带 `*Targets`，但它是渲染目标，内部还嵌了一条归约管线——归约描述符按（帧槽, 级）各一套，跟金字塔图像一起重建。`AtlasGpu` 在拆除表里，但由 overlay 插入，创建链不建它。

### 拆除顺序

`init_chain!` 的声明顺序就是拆除顺序，规则是**谁在运行期还要用别人的对象，谁先拆**；`Context` 最后拆，因为 `Device` 归它销毁。

- `OcclusionPass` 排在 `HizPyramid` 前：遮挡测试用后者提供的 `HIZ_OCCLUSION_SET_DESC` 建集。
- `GBufferTargets` 排在 `FramePool` 前：G-buffer 采样集引用各帧槽的深度视图。
- `LightClusters` 排在 `LightTable` 前：分簇集绑定光源表的 ring buffer。
- 拆除顺序不是创建顺序的完全倒序：`HizPyramid` 几乎最后建，却第二个拆。
- 没有运行期借用关系的相对顺序不承载语义。管线与目标之间没有统一先后：布局句柄在创建 pipeline layout 时已经消费，管线对象本身不再保存它。

## 三、设备与队列

`Context` 管进程级的一份设备状态：

- instance、物理设备选择、`Device`、surface。
- **两条队列**：图形队列族（GRAPHICS+COMPUTE+PRESENT 同族）和专用 transfer 队列族。同族设备上两者是同一个队列。
- **启用的特性**：`timelineSemaphore`、`dynamicRendering`、`runtimeDescriptorArray`、`shaderSampledImageArrayNonUniformIndexing`、`descriptorBindingSampledImageUpdateAfterBind`、`descriptorBindingPartiallyBound`、`multiDrawIndirect`、`textureCompressionBC`。
- **`VK_KHR_swapchain_mutable_format` 是扩展，不是 feature 位**：它配合 swapchain 的格式清单与 `MUTABLE_FORMAT` 旗标，支撑“UNORM 底板 + SRGB view 别名”；不支持就初始化报错。
- `synchronization2` 是关的：屏障走传统 `vkCmdPipelineBarrier` 形状，不依赖 sync2 的 stage/access 新枚举。
- `MAX_FRAMES_IN_FLIGHT = 2`；`MemoryContract` 在这里冻结（见《[数据](数据.md)》）。

读 `Context` 时重点看“查询支持”和“真正启用”是不是两回事：日志会把 `features[支持→已启用]` 打出来，不是查到了就开。

## 四、交换链

`Swapchain` 的输出编码是 **BGRA8-UNORM 底板 + SRGB view 别名**：

- image 格式选 `B8G8R8A8_UNORM`；渲染时套同一张图的 SRGB view 写，ROP 写出时自动做 sRGB 编码；present 读 image 原样上屏。着色器全程线性。
- 合法需要三样：启用的 `mutable_format`、格式清单包含两种格式、`MUTABLE_FORMAT` 旗标。
- 格式是常量 `SWAPCHAIN_COLOR_FORMAT`；surface 不支持就报错退出，不静默降级。

**呈现模式**：MAILBOX 优先，FIFO 兜底。MAILBOX 至少要 3 张 image（一张显示、一张排队待替换、一张给下一帧画）。FIFO 只作兜底——它的 acquire 在显示队列满时会阻塞，曾有最小化死锁和拖拽冻结的问题。

`PresentTarget` 是每次 acquire 的四件套：image、view、extent、render_finished。它按 **swapchain image index** 取，不按帧槽轮转。重建交换链时 `rebuild` 先 `device_wait_idle`，但 **`device_wait_idle` 不证明呈现引擎已消费 `render_finished`**：同一个 image 再次 acquire 才证明它上一轮 present 完成。

## 五、帧槽

`FramePool` 持有 `MAX_FRAMES_IN_FLIGHT` 组：

- 一条命令缓冲（`RESET_COMMAND_BUFFER`，每帧整体重录）。
- 一个 `image_available` binary 信号量：present 引擎 → 图形提交。
- 一个 in_flight fence：GPU → CPU。
- 一份深度附件：`D32_SFLOAT`，随交换链尺寸重建。

`render_finished` 不在这里：它按 swapchain image 分配，住在 `Swapchain`。

**fence 只在提交前一刻重置。** 帧首 `wait_for_slot` 只等不重置；如果帧首就重置，之后任何提前 return（acquire 过时、重建失败）都会留下一个没人 signal 的 fence，下一帧 `wait_for_fences(u64::MAX)` 永久卡死。

`wait_all_inflight` 等全部帧槽的 fence，用于回收旧资源；它只等不重置。

## 六、一次提交在等谁

`record_frame` 末尾的 `queue_submit` 挂两组等待：

| 等待 | 阶段 | 证明什么 |
|---|---|---|
| `image_available`（binary，值 0 占位） | `COLOR_ATTACHMENT_OUTPUT` | acquire 到的 image 可以写了；之前的工作可与 acquire 重叠 |
| 上传票据（timeline，值 = `UploadWait` 快照） | `ALL_COMMANDS` | 本帧备料前发出的全部上传都完成；同时承担 transfer 写对图形读的跨队列可见性 |

完成时 signal `target.render_finished` 和本槽 fence。present 用 `render_finished`，不等 fence。

**acquire 成功之后的 Vulkan 真失败必须致命退出**：同步状态已无法恢复，warn 后继续会等一个永远无人 signal 的 fence，直接死锁。acquire 过时（OUT_OF_DATE/次优）是“让路重试”，不是失败。

## 七、屏障

`src/render/core/record/barrier.rs` 只有两件东西：

- `ImageBarrier`：image、aspect、old/new layout、src/dst stage、src/dst access。常用构造包括进场丢弃、深度附件进场、转采样、深度转只读、转附件。`record` 单独录，`record_with_memory` 顺带录 `&[MemoryBarrierDesc]`（一次 `vkCmdPipelineBarrier` 可带多条全局内存依赖）。
- `MemoryBarrierDesc`：只描述执行/可见性，不动布局。

读屏障时只问两句：**谁等谁执行完**（stage）、**谁对谁可见**（access）。布局迁移本身是一次写，src access 要把旧布局的写算进去；`ImageBarrier` 固定作用 mip0/layer0（本仓帧级图像都是单级），需要多 mip 范围的迁移（贴图上传）只在上传器里裸构造 `vk::ImageMemoryBarrier`。

一帧里的典型用法：

- 进场：颜色 `UNDEFINED → COLOR_ATTACHMENT_OPTIMAL`，深度 `UNDEFINED → DEPTH_ATTACHMENT`，G-buffer 三附件与 HDR 目标同样进场丢弃。旧内容不要，src access 为空是合法的——本槽上一轮已被 fence 等完。
- 合成前：G-buffer 三色转 `SHADER_READ_ONLY`，深度转 `DEPTH_READ_ONLY`。
- 透明前：HDR 从合成写转透明读写（两次动态渲染之间没有光栅序保证），深度转回附件。
- Hi-Z 前：深度转回只读，供归约采样。
- 出场：swapchain image `COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR`。

## 八、光源表为什么两份

光源表逻辑上一张，物理上两份（`MAX_FRAMES_IN_FLIGHT = 2`）。原因不是缓存，是 CPU 直接往 GPU 可见内存里改，而上一帧的 GPU 可能还在读同一块：

- 第 N 帧录制时，第 N-1 帧可能仍在读；只有一份的话，改一盏灯可能改到正在读的字节，同一帧前一半像素用旧灯、后一半用新灯。
- 两份时第 N 帧只写 `rings[N % 2]`。`wait_for_slot` 保证上一个用这份的帧（N-2）已跑完，N-1 读的是另一份。
- 代价是每次改动分别写两个帧槽，多一份 256 × 64 B 的存储。
- 现状约束：脏账记“剩余写次数 = 2”，不是“已写过哪些槽”；同一槽号连续两次 `write_dirty(0)` 会重复写槽 0 并清账，槽 1 仍留旧值。正常交替调用不触发。

对象表、模型环、材质环各走哪种策略，见《[数据](数据.md)》与《[概念](概念.md)》的“旧数据回收有三种策略”。

## 九、检查点

- `init_vulkan` 与 `try_init_vulkan` 两条边界各防住什么？压成一层会出哪两个问题？
- 资源六类里，`FrameUniformTable`、`HizPyramid`、`AtlasGpu` 为什么这么归？
- 拆除顺序为什么不是创建顺序的倒序？举三条有真实借用关系的“A 先于 B”。
- 为什么是两帧槽？帧槽和 swapchain image 为什么是两个循环？
- fence、binary 信号量、timeline 票据各管哪一段等待？
- fence 为什么在提交前一刻才重置？
- 屏障的 stage 和 access 分别回答什么？为什么布局迁移算一次写？
- `device_wait_idle` 为什么不证明 present 已经消费完？
