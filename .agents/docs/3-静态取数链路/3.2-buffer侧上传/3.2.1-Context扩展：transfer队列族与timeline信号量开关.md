## §1 已实现范围与当前状态

1. **队列族选择**：在选中设备上寻找有 TRANSFER 且无 GRAPHICS 的族，找不到则使用 graphics 族；设备选择不为凑 transfer 族而换卡。
2. **Vulkan 1.3 基线**：物理设备 `api_version < 1.3` 则跳过，全部不符合时返回初始化错误。学习工程不加低版本设备兼容分支。
3. **设备队列声明**：不同族创建两条队列；同族只声明一次，避免重复声明 queue family。
4. **Context 字段**：`transfer_queue_family_index`、`transfer_queue`；同族回退直接与图形字段同值。
5. **timeline 状态**：初版 `e0acf1989` 显式启用；`ebc2f9304` 删除 Vulkan12Features 链，当前生产代码仅链 dynamicRendering，却仍打印 `timelineSemaphore=on`。日志是固定文案，不是启用证据。

**完成状态**：队列与 1.3 基线已实现，timeline 启用必须修复并复测后重新验收。主循环仍是清屏，不因这些字段存在就称上传链完成。

## §2 transfer 队列的取舍

**我们选独立 transfer 提交来练合批与跨队列依赖，不预先保证性能收益。**合批减少碎提交是直接目标；独立队列提供调度分流机会，是否映射独立 DMA、是否能与具体图形工作并行由硬件与负载决定。

当前筛选条件“TRANSFER 且无 GRAPHICS”仍可能选中带 COMPUTE 的族，不能从这个条件推出“必是纯 DMA”。本机记录的族 1 为 TRANSFER(+SPARSE_BINDING)，确实没有 GRAPHICS/COMPUTE；这一观察不能外推到所有设备。

同族回退保留相同的 pending/票据接口，不为学习工程引入另一套上传器。但 **EXCLUSIVE 资源跨族时需要 release/acquire，退回同族时不转移 ownership**，下游必须按族号分支处理，不能说完全无同步差别。timeline 负责执行/内存依赖，不传递所有权本身。

历史设备记录：RTX 2060，图形族 0，transfer 族 1，API v1.3.289。下列日志末尾的 `on` 只记录当时输出，不作为当前能力启用结论：

```text
Vulkan 进程级上下文就绪: API v1.3.289  设备 NVIDIA GeForce RTX 2060 (DISCRETE_GPU)
  图形队列族 0  transfer: 族 1（专用 transfer 族（无 GRAPHICS））  timelineSemaphore=on
```

## §3 timeline：机制、支持与启用

### 二值握手与单调进度

binary semaphore 表达一次 signal 与对应 wait 的握手；wait 消费其信号，不由 CPU 调用 reset。现有 image_available/render_finished 的 WSI 使用形态仍是 binary。

timeline semaphore 持有单调递增的 64 位值。提交可 signal 到某个值，也可 wait 到某个值；CPU 可以用 `vkGetSemaphoreCounterValue` 查进度，或 `vkWaitSemaphores` 带超时等待。它不等同于 CPU 每次提交前先阻塞：通常 CPU 配好 GPU wait 后即可提交，队列执行受依赖约束。

D3D12 的带值 fence/queue wait 是有用类比，但不能把 API 与生命周期规则说成逐项相同。这里选择 timeline 是因为一批一个值便于追踪上传和回收，不是 binary 配合额外 bookkeeping 在原理上完全无法表达多批工作。

### 1.3 基线不代替显式启用

**支持、启用和实际使用是三件事。**Vulkan 1.3 设备要求支持 timeline 和 dynamicRendering，但使用前仍须在逻辑设备创建时显式启用相应 feature。普通 Vulkan 自 1.2 起就要求支持 timeline，并不存在“1.2 可选、1.3 默认启用”的转折。

- `VkPhysicalDeviceVulkan12Features` 收纳晋升到 1.2 的 feature；1.3 应用仍使用它声明 timeline 等能力。结构名字不是老设备兼容开关。
- `VkPhysicalDeviceVulkan13Features` 只列本批聚合的 feature，没有再次列 timeline，不代表 timeline 的启用约束消失。
- `vkGetPhysicalDeviceFeatures2` 查询 true 证明支持，不会修改后来创建的逻辑设备。
- 如果改用 `vkQueueSubmit2`，还必须启用 `synchronization2`；本机“支持 true”同样不能代替 enabled。

规范依据（固定 v1.3.289）：

- [Features，105～106 行](https://github.com/KhronosGroup/Vulkan-Docs/blob/v1.3.289/chapters/features.adoc#L105-L106)：逻辑设备使用的细粒度 feature 必须在设备创建时启用。
- [timeline 支持要求，7941～7942 行](https://github.com/KhronosGroup/Vulkan-Docs/blob/v1.3.289/chapters/features.adoc#L7941-L7942)：普通 Vulkan 1.2 的 mandatory support 条款。
- [Semaphore 创建规则](https://github.com/KhronosGroup/Vulkan-Docs/blob/v1.3.289/chapters/synchronization.adoc)：`VUID-VkSemaphoreTypeCreateInfo-timelineSemaphore-03252`，未启用 timelineSemaphore 时不得创建 TIMELINE 类型。
- [QueueSubmit2 规则](https://github.com/KhronosGroup/Vulkan-Docs/blob/v1.3.289/chapters/cmdbuffers.adoc)：`VUID-vkQueueSubmit2-synchronization2-03866`，必须启用 synchronization2。

### A/B 探针：保留观察，撤回错误裁决

会话外新增 `ash_renderer/examples/timeline_probe.rs`（`68fdafa88`），`43c2e9029` 记录 RTX 2060 上两组 PASS：

- A：不链任何 feature，创建 timeline、查初值、`queue_submit2` signal 5、host wait 5、复查。
- B：只链 timelineSemaphore=true，执行相同步骤。
- Features2 查询 timeline/dynamicRendering/synchronization2 等均 true。

**这些是该驱动接受了这些调用的运行观察，不能证明合法，更不能推翻 valid usage。**本轮保留记录，未重跑探针；源码检查发现：

1. 探针没有请求验证层或建立诊断收集；未记录外部层注入，不能据 PASS 声称验证层通过。
2. 两组都使用 `queue_submit2`，却都没有启用 synchronization2；B 组也不是干净的有效用法对照。
3. “如果违规，驱动必返回 ERROR_FEATURE_NOT_PRESENT”的前提错误。应用违反 valid usage 时，不能要求驱动替它检查并返回某个固定错误；`vkCreateDevice` 启用不支持 feature 的失败规则不能套到“应用未启用却使用”的路径。
4. A 与生产 Context 也非逐字段相同：生产设备启用了 dynamicRendering，A 完全无 feature。两者的共同问题是缺 timeline 启用，不能把 A 写成完整生产配置复现。

因此撤回旧版“探针实证闭案 / 无需启用”的结论。后续修正探针需隔离变量、启用验证层、两组正确声明提交 API 所需能力，再用 VUID/无告警分别证明非法/合法路径；修复前不反复执行已知无效路径当正常基准。

### Features2 与 Properties2 勘误

旧记录把“features 结构不能接到 Properties2”归咎 ash extends 矩阵漏标，这也应撤回。**feature 支持查询走 `VkPhysicalDeviceFeatures2`，properties/limits 查询走 `VkPhysicalDeviceProperties2`；两条链的结构种类不同。**12/13 features 缺少 `ExtendsPhysicalDeviceProperties2` 是类型约束，不是缺陷，不能用裸指针强接绕过后再凭驱动未填充判错。
