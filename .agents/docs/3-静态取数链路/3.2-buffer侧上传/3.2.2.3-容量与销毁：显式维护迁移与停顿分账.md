# 3.2.2.3 容量与销毁:显式维护迁移与停顿分账

对应[施工 3.2](README.md)任务 3.2.2.3。代码落位 `ash_renderer/src/vulkan/pool.rs`(`MeshPool::ensure_capacity` 的维护分支 + `MaintenanceLedger`)。任务口径:不足时走明确的维护/扩容路径,不写越界;等待旧使用完成后迁移/销毁,记录维护停顿,正常上传与维护分账。

**状态:已实现并验收(2026-09-24)。**探针组 C 实抓:1MiB 池被 1.2MiB 资产逼出一次显式扩容,整段迁移后新旧内容逐字节复核一致;App 实跑无维护发生(静态需求一次收齐,分账为零)——"正常上传与维护分账"两侧都有证据。

## §1 定案

| 项 | 定案 | 依据 |
|---|---|---|
| 触发 | `ensure_capacity` 发现"现有驻留 + 新增"超出容量,才进维护;够用直接返回 | 维护是异常路径,不搭正常上传的便车 |
| 新容量 | `max(需量 ×4/3, 现有 ×2)` 再对齐 1MiB | "收齐的静态需求加余量";×2 保证不会小步频扩(频繁增长留步骤 4) |
| 迁移前等待 | 等全部在飞上传票据完成(`wait_all_uploads`) | 迁移拷贝的源(旧池)可能正被上一批上传在写——不等待就是读写竞争 |
| 迁移本体 | 一次 transfer 批:旧顶点池 [0, used_v) → 新顶点池、旧索引池同理;等迁移票据完成才销毁旧池 | bump 布局保证 [0, used) 就是全部有效数据;迁移批共用 Uploader 的单调票据序列 |
| 停顿分账 | `MaintenanceLedger { grow_count, pause_ms_total }` 记录每次维护的完整停顿(等待在飞 + 提交迁移 + 等迁移票据) | README 验证 3"容量维护另列";不冒充"正常上传零 idle" |
| 销毁纪律 | 旧池在迁移票据完成后销毁;`MeshPool::drop` 本身**不等 GPU**(在飞等待归维护与退出排空) | 与 `GpuBuffer::drop` 同一边界(3.2.2.1 §4);退出排空由 teardown 的 `device_wait_idle` 先行(D4) |

## §2 机制

### 2.1 为什么"等待 → 新分配 → 迁移 → 等迁移 → 销毁旧池"的顺序不可调换

- **等待在新分配之前**:维护停顿的实体是"旧数据还被 GPU 引用"——先等完,后面的每一步都不再有在飞引用面。若先分配,分配失败(内存枯竭)时旧池完好,失败路径干净。
- **迁移在销毁之前且共用票据**:迁移拷贝是一次普通 transfer 提交,票据序列与上传批次同源——"迁移完成"也是可等待、可查询的一等公民,不是隐式约定。
- **DevicePool 角色 3.2.2.1 就带 TRANSFER_SRC**:迁移把池当拷贝源,这条 usage 当时就为此冻结——本任务无需再改契约,引用即可。

### 2.2 "不写越界"的结构位置

越界防护不在 alloc 运行期,而在结构上:`ensure_capacity` 是 `alloc` 的唯一前置,分配永远发生在"容量已保证"之后;维护路径里新池容量 = 需量加余量(必然 ≥ 现有驻留),迁移拷贝的尺寸就是旧 `used` 值。没有"先写后补容量"的代码形状存在。

### 2.3 图形侧最后使用的等待面(冻结,待 3.4 接线)

迁移等待的是**上传在飞**;图形侧对池数据的最后使用在 M2 尚不存在(帧循环只清屏)。一旦 3.4 的 draw 开始消费池数据,扩容维护还须等"图形最后使用完成"——该等待点与 acquire 机制在[责任边界文档](责任边界冻结：上传完成、图形消费与退出排空的时序契约.md)冻结,3.4 按票接线,不在本任务假装已具备。

## §3 证据

- **探针组 C**(`upload_probe`,2026-09-24,RTX 2060,验证层 + 同步验证零 VUID):
  - 小资产先收 → 初建顶点 1MiB(需量加余量);
  - 1.2MiB 顶点 + 240KiB 索引的大资产 → 触发维护:扩容 1 次,新容量顶点 2MiB/索引 2MiB,迁移 128+240024 字节,大资产批拿票据 #3(迁移批耗掉 #2——维护与上传**共用单调票据序列**的活证据);
  - 迁移后新旧两资产四段读回逐字节一致(整段迁移没搬坏数据);
  - `累计停顿 0ms`:等待路径执行了,但本机 GPU 完成快于 CPU 推进,**未观测到实际阻塞**——诚实记录:停顿计量存在且计入分账,阻塞时长依赖设备速度,不以 0ms 冒充"无等待",也不编造等待时长。
- **App 实跑**(同日):6 资产一批收齐,全程零维护——分账为零即正常上传路径未搭维护便车的证据。

## §4 边界

- **不做增量/流送扩容**:频繁小步增长、预算化流送留步骤 4~6(施工计划 §4);本任务只有"够用返回 / 不足一次性 ×2+余量"两条路。
- **不淘汰资产**:见 [3.2.2.2 §4](3.2.2.2-池与缓存：DEVICE_LOCAL大池、bump分配与资产身份去重.md)。
- **停顿分账只计维护**:swapchain 重建等待、退出排空等待各有自己的账(缺陷文档 D4、责任边界文档),不混记。
