## 1. 结构定案：取数/显示/写值三段分离

3.10 的详情区（Query 直读）长成 3.11 属性区时换了架构，两个硬约束决定形状：

1. **反射读取需要 World 访问，而 `&World` 与任何 `ResMut` 同系统冲突**——`run_egui_pass` 有六个 `ResMut`，`&World` 进不去。反射组件的字段行只能由一个只读系统产，再交给 pass 渲染；
2. **编辑写值不能在渲染函数里顺手做**——`show_details` 是纯渲染，写路径独立成队列，3.12 的 BRP 写方法才能复用同款实现（立案要求：不养两份逻辑）。

由此定案**三段分离**（与官方"后端数据收集/前端展示"分工同形，用户定案学数据组织不学 UI 表现）：

```
collect_selected_details（Update，独占 &mut World 直接写）
    → SelectedDetails 纯数据快照（Resource）
        → run_egui_pass 属性区渲染（含 DragValue，改值产 TransformEdit）
            → TransformEditQueue（Resource 队列）
                → apply_transform_edits（Update 尾，链式清账，&mut World）
                    → PostUpdate 传播 → collect_scene → Last 绘制（同帧 relay）
```

- **采集**：`collect_selected_details` 每帧对选中实体产一份纯数据快照（单实体量级，全帧成本可忽略）。**独占系统（&mut World）直接写资源**——首版只读 &World + Commands 落账的方案实跑翻车，牵出 `exists` 恒 false 的清账回路 bug（§4.4），改独占后直接写、语义零歧义。
- **显示**：属性区只渲染快照，零 World 访问。选中实体 despawn 后快照带 `exists = false`，属性区借它清账（`SelectedEntity` 清空）。
- **写值**：egui `DragValue` 读快照值进副本，任一量被拖改即整组回写（未动的组发原值，覆盖等价于原地）；`TransformEdit` 逐组 `Option`（None = 不动）。`apply_transform_edit(world: &mut World, entity, edit)` 是**唯一实现**——egui 队列系统与 3.12 的 BRP `set_transform` 调同款。

## 3. 前置闸门探针结论（临时探针，已撤）

### 3.1 AppTypeRegistry 注册覆盖面（8s 一次性打账）

- **注册类型总数 1130**；World 全部组件类型 305 种，其中反射注册 73 种、可读（有 `ReflectComponent`）68 种；
- **可读清单覆盖全部场景关键组件**：Transform、GlobalTransform、Name、Visibility/InheritedVisibility/ViewVisibility、ChildOf、Children、Mesh3d、MeshMaterial3d\<StandardMaterial\>、Camera、DirectionalLight、Projection、WorldAssetRoot、GltfMaterialName、GltfMeshName 等 68 种；
- **未注册集 = 纯内部/资源持有实体**：`Assets<T>`、`Messages<T>`、`GizmoStorage<..>`、`Observer ×109`、AssetServer，以及本项目自建资源（SelectedEntity/TransformEditQueue/Swapchain/MeshPool 等）——它们住资源实体上，树的相关性过滤本就不显示。

**结论：反射只读展示按"全部注册组件"全量做，无需白名单**；已注册但展示位重复的七类进 `SKIP_REFLECT`（Transform/GlobalTransform/Name/Mesh3d/MeshMaterial3d/Children/ChildOf——编辑与精确展示已有专行，重复上反射行只添噪）。未注册组件在面板降级为名字-only 行（Tier①），不影响清单完整性。

### 3.2 写路径验证（3.11.2）+ 快照数据链转储（3.11.1，无人验证轮补）

探针 8s 起程序化选中首个 primitive（Hose_low.HoseMat，379v0，原平移 (0,0,0)），每 2.5s 推一次 `TransformEdit`（translation.y 原位 ↔ +0.300 振荡）并读回当前值：

```
读回 y +0.000，推编辑 → +0.300
读回 y +0.300，推编辑 → +0.000    ← 上一轮编辑真实落进 World 的证据
…（连续多轮干净振荡，无漂移无丢拍）
```

读回值即地面真值：**队列 → apply_transform_edits → apply_transform_edit → Transform 组件**全链生效；同帧 relay 的 Update→PostUpdate 传播→Last 绘制为调度序保证，配合零 VUID。

选中生效后快照内容转储（SelectedDetails 即属性面板渲染数据源，逐行打日志）一次全绿：

- 名字 `Hose_low.HoseMat`、Mesh `AssetId<Mesh>{0,0}`、材质 `AssetId<StandardMaterial>{1,0}`；
- **贴图槽 4 条非空**：base_color #2、metallic_roughness #1、normal #0、occlusion #1——metallic_roughness 与 occlusion 同图同柄，与 3.1.4 判定线互证；
- **组件清单 = archetype 全量 14 项**：SKIP_REFLECT 七类按设计降为名字-only；反射行带真值（`InheritedVisibility(true)`、`Aabb{center/half_extents}`、`GltfMeshName("Hose_low")`、`GltfMaterialName("HoseMat")`）；Children 缺席（primitive 无子）与树形证据一致。

首版探针 3s 触发时场景未到（双实例并发拖慢 glTF 加载，只看到 1 种组件类型），改 8s 后数据完整——**探针触发时机对加载并发敏感**，是 3.10"诊断跑太早"钉子的复现。

## 4. 钉子

### 4.1 bevy `debug` feature 必开（探针首跑实抓）

宿主默认 feature 下 `ComponentInfo::name()` 返回的 `DebugName` 全部降级为 `"<Enable the debug feature to see the name>"`——bevy_utils 的 debug_info 在无该 feature 时是占位符（**组件名清单展示依赖实名，探针也因此只看到 1 种组件**）。解法：`ash_renderer/Cargo.toml` 给 bevy 加开 `debug` feature（官方 `local_inspector` 示例同款口径），只影响类型名字符串、无行为差异；与 step1"默认 feature 审计口径"的偏差已在 Cargo.toml 注释里记明。

### 4.2 API 形状钉（0.20-dev 实测）

- **`Archetype::components() -> &[ComponentId]`**（archetype.rs:535，切片非迭代器）；`ComponentInfo::name() -> DebugName`（info.rs:43）、`type_id() -> Option<TypeId>`（info.rs:70）；`DebugName::shortname() -> ShortName`（debug_info.rs:108）。
- **`ReflectComponent::reflect(impl Into<FilteredEntityRef>)`**（bevy_ecs/src/reflect/component.rs:205）——`EntityRef` 直接 `Into`（entity_ref.rs:318 有 `From`），读值拿 `&dyn Reflect`。
- **`impl Debug for dyn PartialReflect` 存在**（bevy_reflect/src/reflect.rs:517）——反射字段值直接 `format!("{v:?}")`，无需 serde/ReflectSerializer。
- **`Struct` trait 在 `bevy_reflect::structs` 模块**（lib.rs:614 是 `pub mod` 非根 re-export），但 0.20-dev 给 `dyn Struct` 提供了固有方法（`field_len`/`name_at`/`field_at`），导入 trait 反而 unused——按编译器收账不导入。
- **`World::get_entity(entity) -> Result<EntityRef, EntityNotSpawnedError>`**（world/mod.rs:932，单实体 fetch 也是 Result）；`World::iter_entities()` 直接产 `EntityRef`（world/mod.rs:991）。

### 4.3 clippy 两处（照旧全收）

`TEXTURE_SLOTS` 的函数指针表触发 type_complexity（抽 `TextureSlotGet` 别名）；采集与探针的两处嵌套 `if let` 折叠（collapsible_if，改 `and_then` 链）。

### 4.4 `exists` 恒 false 的清账回路（无人验证轮实抓的真 bug，最高价值钉）

首版 `SelectedDetails::default()` 的 `exists: false` 在**成功路径上从未翻 true**——而属性区的清账逻辑是"`!exists` 就把 `SelectedEntity` 清回 None"。后果是一条**自清回路**：程序化选中 Some → 采集产快照（entity=Some 但 exists=false）→ 属性区看到 `!exists` → 清空选中 → 下帧采集只见 None → 快照恒为默认值 → 属性区永远只显示提示行。**生产路径同样中招：属性面板在任何选中下都长不出内容**。

排查链（临时探针逐层钉）：dump 不触发 → `details.entity=None` 永恒 → collect 侧观测看到过一次 `Some` 随即被清 → 回路定性。修复一行：成功路径 `exists: true`（结构体初始化带出，失败分支保持 false）。修复后快照转储立即全绿（§3.2）。

**附带教训**：排查初期曾误诊为"Commands 在 &World 系统里不生效"并改写为独占系统——真因是 exists 回路，Commands 可能本就正常。保留独占写法（直接写、语义零歧义），但"未验证先归因"的误诊记一笔；`Local<Option<Entity>>` 变化观测 + 2.5s 节拍的 dump-待发日志是这次定位的主力工具。

### 4.5 同窗口双 ScrollArea 的自动 ID 撞车（像素证据轮实抓）

解锁窗口的截图里出现 egui 重复 ID 警告红条："First/Second use of ScrollArea ID 3275 / widget ID 6A57"——树滚动区（3.10）与组件清单滚动区（3.11）都没给 id_salt，两个匿名 ScrollArea 在同一 Window 下自动生成同一个 ID。后果不止告警：**滚动状态共用会把两处的滚动位置搅在一起**。修复：两处显式 `id_salt`（"实体层级树"/"组件清单"）。钉子：**同容器里放第二个 ScrollArea（或任何可聚焦容器）必须显式 id_salt，egui 的重复 ID 检测红条在 debug 断言里如实上屏**。

## 5. 视觉验证：仪器谜底与无人验证轮（2026-10-09 深夜～10 日凌晨，用户声明无人模式后）

**白图谜底（三层归一，非构建问题）**：PrintWindow 抓图系统性全白，逐层排查钉死根因链——

1. **机器被锁屏**：用户离座锁屏（`LogonUI.exe` 在跑，飞书 IT 助手安全海报为锁屏背景，`CcWaterMarkWindow` 双屏 TOPMOST 全幅轮播）；
2. **被 TOPMOST 全屏覆盖的窗口，DWM 拒绝内容重定向**——PW_RENDERFULLCONTENT 对完全遮挡的窗口整幅返回近白（仅标题栏非白 ≈5%）；解锁前即使把目标窗口 TOPMOST 提顶也无效；
3. **注入输入不可达**：锁屏是安全桌面边界，SendInput 落不到会话窗口——`WindowFromPoint` 返回 `LockScreenBackstopFrame`，桥层零事件日志（用户的【桥】诊断在场且安静，反向证明事件没到应用）。

**应用渲染全程健康**：解锁时段的 PrintWindow 抓到完整画面（FlightHelmet Lambert 光照 + 三 egui 窗口 + 层级树 + fps 60 + 常驻表 30/1024），用户实例（旧代码）对照同样成立；日志侧帧循环/上传/图集全程无恙、零 VUID。

**处置**：
- `tools/capture_window.py` 加白图自愈——非白占比 <10% 时自动 TOPMOST 提顶重试 PrintWindow 后回落 NOTOPMOST 复原；stdout 标注通道（白图→提顶重试）。**明确不用屏幕区域抓取兜底**：全屏遮挡物存在时它会抓到遮挡物而非目标窗口，制造假证据。
- 解锁时段已抓到的证据：树窗/总控/统计窗/场景全貌基线（3.10 零回退 + 3.11 属性区提示行就位）。
- **拖拽手感与拖选卡死复现：锁屏下注入不可行，留用户解锁后人工轮**（写路径读回振荡探针已闭环 3.11.2 链路的其余环节）。
- 锁屏会话内追加的活证据：写路径探针读回振荡持续（+0.300↔+0.000 干净往复）、零 VUID。
- **§4.4 的 `exists` 清账回路 bug 正是这条无人验证链抓出来的**——若非锁屏逼出"程序化选中 + 快照转储"的验证路径，属性面板"永远长不出内容"的缺陷要到用户亲手点击时才会暴露。
- **解锁窗口像素证据（2026-10-10 00:16，监视器自动连拍）**：选中面板完整上屏——选中头、Mesh/材质 AssetId、贴图四槽（base_color #2 / metallic_roughness #1 / normal #0 / occlusion #1）、Transform 编辑网格（平移 y=0.30 即振荡实时值）、全局跟随、组件 14 项，且**画面里头盔被真实抬高**（编辑→渲染同帧 relay 的像素证据）；同轮实抓 §4.5 的 ScrollArea ID 撞车红条并修复。
- **注入交互全序列（2026-10-10 09:37+，解锁窗出现后手动补打）**：TOPMOST 保活后注入点选 RubberWood_low → 属性面板上屏（编辑网格+组件 9）；拖 DragValue **缩放.y 1.00→1.95**（画面木支架竖向拉伸、面板同步）与**平移.y →-4.90**（全局跟随 -4.900、头盔整棵下沉）；全程 egui 内拖拽相机零转动（3.9 仲裁门成立）；**树标签拖选无卡死**（fps 60、树窗平滑滚动）——拖选卡死在 3.11 终版代码上未复现。经验钉：PrintWindow 自愈抓完会把窗降回 NOTOPMOST，**注入交互前必须 TOPMOST 保活**（否则点击全落进遮挡窗口；`WindowFromPoint` 一查便知）。
- 锁屏会自动回卷（离开工位策略）：解锁窗仅数分钟，注入拖拽判定线挂"解锁即交互爆发"脚本自动执行（点选→拖 DragValue→相机仲裁门正负控→拖选卡死复现尝试），结果落 `.temp/burst_*.png`。
