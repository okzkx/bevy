# 环机制：Host-Visible数据的帧槽轮转与fence纪律

> 2026-10-15 收官配套机制篇（机制深潜之三）。本文是"环"的完整机制档案：宿主直写的易变数据为什么只有环这一条合法形状、×N 份轮转和 fence 各自负责什么、增量环的双奇偶脏集怎么防闪变。为什么 model 走环、材质环为什么全量（设计取舍）见[设计决策篇](三张表的设计决策：更新频率、写入方式与备选方案对照.md)；入门叙事见[第一课](GPU驱动第一课：从逐draw推参数到实例索引读表——新旧两套写法对照.md) §4。

## §0 判定线（环的完整定义，缺一半就是 bug）

**环 = 按帧槽轮转的 N 份 host-visible 副本 + 帧槽 fence 纪律**。环解决"物理重叠"（正在被读的和正要被写的不是同一块），fence 证明"时机安全"（写的那一刻，这一块上一轮的读者已退场）。**只有环没有 fence = 空间错开了但时机在赌；只有 fence 没有环 = 每帧全停**——两者是组合拳，不可拆。

## §1 为什么宿主直写、为什么 host-visible

环装的是**易变的 per-object/per-frame 数据**（model、材质参数）。这类数据有两条可选的写入路：

| 路 | 机制 | 为什么环不走 |
|---|---|---|
| **命令化更新**（GPU 写） | CPU 录 `vkCmdCopyBuffer` → transfer 队列执行 → 图形提交在 GPU 侧等票据 | 每帧为易变数据提交 transfer 批次：命令录制 + staging 环占用 + 票据等待，换来的还是"数据在 GPU"——host-visible 直写少一跳、少一套票据生命周期 |
| **宿主直写** | `vkMapMemory` 映射指针 `memcpy`（`GpuBuffer::write`） | ✓ 但只能配 HOST_VISIBLE 内存 + CPU 侧时机选择（§3） |

对象表走了命令化更新那条路（写一次，稀疏，票据划算）；环数据每帧都动，命令化的开销（每帧 transfer 提交、票据生命周期管理）换不来任何东西——**宿主直写是"每帧重写"类数据的最低摩擦通道**，代价是把安全从 GPU 侧同步（barrier/信号量能管命令）换到 CPU 侧时机（fence）。

## §2 环防的是什么：物理重叠的时间线

宿主直写的那一刻，GPU 上可能有 0/1/2 个提交在飞（MAX_FRAMES_IN_FLIGHT=2 的语义就是"CPU 允许领先两帧"）。如果只有一个 buffer：

```
CPU:  提交帧N-2 ── 提交帧N-1 ────── [帧N: memcpy 写 buffer ── 录制提交帧N]
GPU:      (执行帧N-2) ─────────────── (还在执行...)    ↑
                            帧 N-2 的 draw 正在读这块 buffer ←—— 冲突
```

**GPU-bound 时这不是边界情况是稳态**：CPU 永远顶满 2 帧在飞，CPU 写的时刻稳定落在上一轮使用的执行窗口内。冲突形态比崩溃更阴险——64B 矩阵写不是原子的，GPU 读到半新半旧 = **撕裂矩阵**（物体几何直接扭曲）；不撕裂就是已定格帧的内容被篡改（瞬移）。而规范层面这是 UB，且**同步验证层对宿主写盲**（它只建模 GPU 侧操作）——零 VUID 判定线抓不到它，是最恶劣的"执法工具盲区内 UB"，所以防护必须结构性（写入点物理地放在 `wait_for_slot` 之后），不能靠验证层兜底。

环的解法是**空间换安全**：N 份副本按帧槽轮转，CPU 写 0 号环时 GPU 正在读的是 1 号环——重叠窗口里两者永不见面。

## §3 fence：时机证明的唯一信息通道

"轮到写 0 号环时，它上一轮的读者走完了吗？"——CPU 对 GPU 进度**一无所知**，除非问。fence 是唯一的信息通道：

```rust
// wait_for_slot（FramePool）：等本帧槽上一轮提交完成 + 重置命令缓冲
unsafe { device.wait_for_fences(&[frame.in_flight], true, u64::MAX)? };
// 之后的全部宿主写（帧 UBO / 模型环 / 材质环 / UI 顶点环）都以此为安全证据
```

时序账（×2 份，帧槽奇偶 0/1）：

```
帧 N   用 0 号环：帧首等 fence₀（帧 N-2 的提交完成）→ 写 0 号环安全
帧 N+1 用 1 号环：写 1 号环时 GPU 在执行帧 N（读 0 号环）→ 互不相见
帧 N+2 轮回 0 号环：帧首等 fence₂（= 帧 N 的提交完成）→ 0 号环上轮读者已退场 ✓
```

**为什么 barrier/信号量救不了单 buffer 方案**：barrier 只排序 GPU 命令（布局迁移、同提交写后读——这些岗位一直在用屏障），宿主映射写不是 queue 命令，没有命令侧执法点；规范对 mapped memory 的纪律是"宿主访问不得与在飞 GPU 访问并发"，唯一兑现方式 = CPU 侧等待 + 多份轮转。环不是 barrier 的穷版本，是**宿主写这条路上唯一合法的形状，fence 是它唯一的安全带**。

## §4 增量环：双奇偶脏集与"两帧写满两个环"

增量写有个双环特有的坑：帧 N 改了物体 A，写进"本帧奇偶"的环 F——但另一个环上还是上上帧写的旧值，下一帧读到的就是陈旧值，**两套环交替读 = 一帧新一帧旧地闪**。解法是账本里两套按帧槽奇偶的待写集：

```rust
// update_ledger（PostUpdate）：改动行进两套
pub(crate) fn mark_model_dirty(&mut self, entity: Entity) {
    self.model_dirty[0].insert(entity);
    self.model_dirty[1].insert(entity);
}
// draw_frame(frame)：只消费本帧奇偶集，写完清掉；另一套留给下帧
for entity in ledger.take_model_dirty(frame) { ...写 model_ring[frame]... }
```

时序效果：帧 N 的改动 → 帧 N 写环 N%2（本帧 draw 立即可见）→ 帧 N+1 补写另一环 → **两帧后两个环都新鲜**。期间每个环被读到的要么是新值、要么是"属于本帧合法状态"的值（读它的那个提交录制时改动力还没发生）——闪烁从结构上不可能。

三个配套细节：

- **新槽也进双套**：flush 分配新实例槽时 `mark_model_dirty`——新占用者的模型在两个帧槽各就位一次，之后与普通改动行同流。
- **行已清/槽未落 = 跳过**：待写标记引用实体，写入时现查行与槽——查无就跳（槽在停尸房途中或从未分配，那个位置的环内容无人读；复用后新标记会覆盖）。
- **泛化维度**：`MAX_FRAMES_IN_FLIGHT = K` 时，环 ×K 份、脏集 ×K 套、每改动行 K 帧写满 K 个环——**帧槽数是环和脏集的公共维度**。

## §5 全量环：材质环的"每帧重投影"语义

材质环每帧把**全部可绘材质**从资产容器现读现写（本帧奇偶的环）。它和模型环是同一个环结构、两种填充策略：

| | 模型环（增量） | 材质环（全量） |
|---|---|---|
| 填充策略 | 只写本帧奇偶集里的改动行 | 写全部可绘行的去重材质 |
| 内容来源 | 账本行 `row.model`（PostUpdate 终值） | 容器/驻留缓存现读（`Assets<StandardMaterial>` + `ImageCache`） |
| 为什么 | O(实例) 数据，全量 6.4MB/帧不划算 | O(唯一材质) 小到账本费 > 字节费；现读 = 容器变更自动次帧生效，零变更通道 |
| 陈旧性 | 靠双奇偶集在两帧内收敛 | 不存在——每帧都是容器现状的纯投影 |

全量环的本质：**它不是"存储"，是每帧把容器状态重新投影一遍到 GPU**——所以它没有"首写/补写/漏标"问题，也没有停尸房问题（记录不是按槽写一次的资产，是按帧重算的快照）。代价是投影成本随材质数线性——上千唯一材质时翻面成增量（照抄 §4 双奇偶），判据见设计决策篇 §5。

## §6 写下去之后：host write 的可见性纪律

环的安全有两半：**时机**（fence，§3）和**可见性**（写完的数据 GPU 读时必须看到）。后者是 `GpuBuffer::write` 的既有纪律（3.2 建）：

- 内存类型带 **HOST_COHERENT**：宿主写设备侧立即可见，不 flush（规范明言此时 flush 非必需且有性能代价）。
- 不带：写后按 `nonCoherentAtomSize` 对齐 flush（写区向两端舍入，只波及含写入字节的边界 atom）。

三张表所在 buffer 的内存类型由 `MemoryContract` 按角色选型（必需 HOST_VISIBLE + 优先 HOST_CACHED|COHERENT），选型结果落日志——环机制不关心落在哪个分支，`GpuBuffer::write` 内建统一处理。**可见性（flush）与并发（fence）是两件正交的事**：flush 保证"写完了能读到"，fence 保证"写的时候没人在读"——混为一谈是常见误区。

## §7 本仓库的环家谱（同一结构的不同实例）

| 环 | 内容 | 份/帧槽 | 填充 | 建于 |
|---|---|---|---|---|
| 帧 UBO | 相机 view_proj + 灯光 + 模式（128B） | ×2 | 全量 | 3.4 |
| UI 顶点/索引环 | egui 镶嵌产物 | ×2 | 每帧整换 | 3.7 |
| 模型环 | model 矩阵 ×实例槽 | ×2 | **增量**（双奇偶脏集） | 5.1 |
| 材质环 | base_color + 贴图/采样器槽 ×材质槽 | ×2 | **全量** | 5.1 |

四个环共享同一条 fence 纪律（写入点都在 `wait_for_slot` 之后）和同一份 GpuBuffer 写入纪律（§6）。新增一个环的三步定式：BufferRole::Storage 建份 ×帧槽数 → 描述符按帧槽绑本帧那份 → 写入点放 `wait_for_slot` 之后、按"量级×变更检测成本"选增量或全量。将来 5.2 的 compute 输入（若走 CPU 侧喂）或 6.x 的 LOD 决策数据，都是这个定式的潜在第四/五只环。

### 为什么没有抽成通用 Ring 类型（取舍声明）

环在代码里是**纪律 + 惯例**（`Vec<GpuBuffer>` + `current_index()` 轮转），不是类型——唯一以 Ring 命名的 `UiVertexRing`（顶点+索引成对才长成 struct）与 Uploader 内部私有的 staging `RingSlot`（按票据轮转，另一个体系）互不相干。不抽类型的理由有二：**抽象捕获不了关键不变式**——环的安全是"写点排在 `wait_for_slot` 之后"的时序事实，fence 在 FramePool、写点在调用方的调用序里，`Ring<T>` 类型装得下 buffer 装不下这条纪律，抽出来反而给"用了就安全"的虚假暗示；**四实例差异面宽于共性**（份内容/描述符形状/填充策略三维各不同，泛型参数面比四份手写实现还宽）。翻面条件：第五/六只环出现且形状收敛（K 副本 + 每帧描述符 + 双奇偶脏集同构），届时按上面定式收成 `FrameRing` 类型，`UiVertexRing`/frame_ubos 可迁入——先有稳定实例，再从实例收类型（与代码生成规范"重复模板必须下沉"的判据一致：现在的样板已经指得到 `GpuBuffer` 这个标准件，轮转只剩一行下标）。
